## 2.2 治疗 vs 训练的认知陷阱

**第一性追问**：

> 看到一个写作问题，正确做法是什么？

两个选项：

| 选项 | 做法 | 例子 |
|------|------|------|
| **方案 A：治疗** | 让作者**修改原文**，亲手把差的地方改好，在真实文本上建立控制感 | "你这段描写空洞，试着改一下" |
| **方案 B：训练** | 让作者去**做专门的练习**，然后回来继续写 | "你这个症候是 P001，去完成 T001 训练任务" |

**关键问题**：当前 P3 Training 链路默认走的是方案 B（训练/做作业）。但方案 A（治疗/修改原文）可能更有效——因为：

1. 作者关心的是自己的小说，不是抽象的训练任务
2. 在真实问题上练习比在孤立任务中练习更有效
3. 修改原文能产生即时成就感（"我把这段改好了"）
4. 训练任务容易被作者认为"浪费时间做作业"

**判定**：⚠️ P3 Training 链路的设计存在偏向**「训练任务」而非「治疗修改」**的风险。

**调整建议**：
- P3 的第一个功能应该是**"帮你改"而不是"让你练"**
- 诊断后优先让作者修改原文（方案 A），改完了再推荐训练任务（方案 B）
- 训练任务作为"假如你想练更多"的补充，不是默认路径
- P3.3 的 UI 设计：先展示"如何改写这段"的示范，再提供"你去练练别的"的入口

## 三、Evidence（证据）概念 — 更严厉的质疑

**第一性追问**：
> 作者知道"证据"这个词吗？
> 作者在乎"证据"这个词吗？
> 如果整个"证据"概念从前端消失，用户会发现吗？

### 三问测试

| 问 | 答案 | 判定 |
|----|------|------|
| **第一问**：证据解决了什么用户问题？ | 让作者"相信"诊断结果 | 间接有用 |
| **第二问**：删除证据，用户能否完成核心链路？ | **基本可以** — 只要诊断直接引用原文，用户就能相信 | ⚠️ 非核心 |
| **第三问**：证据是在帮助教学还是帮助系统？ | 帮助系统建立可信度，不是直接教学 | 🔴 风险 |

**核心矛盾**：

```
作者视角：
  "AI 说我这里写得太抽象了，它说得对，因为原文是'她很伤心'，确实抽象"
  → 不需要"证据"概念，原文引用就够了

系统视角：
  "需要 Level 1 文本证据 + Level 2 模式证据 + Level 3 统计证据 + Level 4 对比证据"
  → 概念太多，用户看不懂
```

**判定**：🔴 当前 Evidence 四级分层的设计是**系统视角优于用户视角**的典型案例。

**调整建议**：
- 前端展示**删除"证据"这个词**，改为"诊断依据"或"为什么这样判断"
- 后端保留 Evidence 数据结构（系统需要）
- 前端只展示 Level 1（原文引用），Level 2-4 不展示
- Level 4（对比）只在训练完成后展示，称为"训练效果对比"，不叫"Level 4 对比证据"
- 删除 3 个前端"证据"相关的 IPC 通道（evidence:getByDisease、evidence:getByAbility、evidence:getChain）
- 将前端证据查询全部合并为 "diagnosis:getDetail" 一个通道

**评分调整**：从 **75 → 45**（证据概念本身对用户无价值，扣 30 分）

## 四、能力评分系统 — 更严厉的质疑

**第一性追问**：
> 把作者的能力变成一个数字，真的在帮助他吗？

### 数字评分的副作用

| 副作用 | 表现 | 可能性 |
|--------|------|--------|
| **错误精确** | "你的 OBS 能力从 42 分涨到 45 分"——这种精度是假的 | 🔴 极高 |
| **焦虑来源** | 新手看到自己"30 分"可能放弃 | 🔴 高 |
| **目标扭曲** | 作者可能追求"刷分"而不是真的写好 | ⚠️ 中 |
| **可比性谬误** | 不同作者的能力评分没有对比意义 | 🔴 高 |
| **频率污染** | 练习越多不代表进步越快，但数字给人"练就涨分"的错觉 | 🔴 高 |

**第一性追问第二击**：

> 如果作者能力评分不是数字，而是文字，效果会更好吗？

**对比**：

| 方案 | 表达 | 效果 |
|------|------|------|
| 数字 | "你的世界观构建能力：72分" | 作者：72分是高还是低？怎么提到80分？ |
| 文本 | "你的世界观构建已经能自然融入剧情了，但细节密度还可以再提升" | 作者：我知道下一步做什么 |
| 分级 | "你的世界观构建能力：🟢 良好 — 已掌握基础，建议挑战复杂设定" | 作者：我知道自己在什么位置 |

**判定**：🔴 数字评分的问题是：**它满足了系统"量化追踪"的需求，但可能伤害了作者"继续学下去"的动力。**

**调整建议**：
- 前端默认不显示数字评分
- 改为文字描述 + 分级标记（🟢 良好 / 🟡 一般 / 🔴 薄弱）
- 后端保留数字评分（系统需要做趋势追踪）
- 雷达图改为"能力状态图"：用文字标签代替数字坐标
- 评分算法从精确数值改为区间判断（0-33=🔴 / 34-66=🟡 / 67-100=🟢）

**评分调整**：从 **65 → 40**（数字评分对新人作者有害，扣 25 分）

## 五、聚焦方向（Focus Area）— 质疑假设

**第一性追问**：
> 为什么要有聚焦方向？

**答案**：让作者选择"我这次想学什么"——worldbuilding / character / general。

**追问第二击**：
> 聚焦方向是在帮助作者，还是在帮助系统？

**系统视角**：聚焦方向限制诊断范围，减少 AI 需要处理的信息量，降低复杂度。
**用户视角**：作者可能不希望被限制。"我上传了小说，你直接告诉我所有问题，不要让我先选择方向。"

**追问第三击**：
> 如果一个新手作者选择了"character"聚焦方向，但他的核心问题是世界观设定（P001），系统怎么处理？

**答案**：当前设计是"不处理"——聚焦方向过滤后，不属于该方向的问题不被强调。

**这合理吗？**

**判定**：⚠️ 聚焦方向设计的默认假设是"用户知道自己的问题在哪"。但新手作者**不知道**。让不知道问题的人选择聚焦方向，这是一个设计悖论。

**调整建议**：
- 聚焦方向**不应在首次诊断前让用户选择**
- 默认：先无限制诊断，暴露所有问题
- 诊断后，如果问题集中在某个方向，**系统建议**聚焦方向，而不是让用户选择
- 聚焦方向改为**诊断后的引导工具**，不是诊断前的过滤器

**评分调整**：从 **88 → 70**（聚焦方向作为诊断前过滤器不合理，扣 18 分）

## 六、Training 链路（P3）— 质疑高评分

**第一次审计**给了 95。这是最高分，但也可能是我最保守的评分——因为我太想要 Training 了。

**第一性追问**：
> Training 链路真的会提高新人作者的成长速度吗？

### 条件分析

| 条件 | 是否满足 | 说明 |
|------|---------|------|
| 训练任务与用户问题直接相关 | ⚠️ 待验证 | 取决于 SPEC_Ability_Map 的 21 条映射是否准确 |
| 训练任务对新手友好 | ⚠️ 待验证 | T001-T021 的文字难度需要验证 |
| 用户有时间做训练 | ❌ 不确定 | 作者可能只想"诊断一下"，没准备好"做作业" |
| 训练后马上有效果 | ⚠️ 待验证 | 需要实际使用数据 |

**核心风险**：

```
训练任务不应该是"作业"。
训练任务应该是"手把手教你改好你现在这段"。
```

**当前的 P3 设计更接近"作业模式"（推送任务→用户完成→提交→评估），而不是"治疗模式"（你这里有问题，我教你改，你改给我看）。**

**判定**：⚠️ P3 的方向正确，但执行方案需要从"作业模式"调整为"治疗模式"。

**调整建议**：
- P3.3（训练任务 UI）的第一个视图改为**"修改建议 + 原文编辑"**
- 用户先看到"你可以这样改这段"，然后直接在界面上修改
- 修改完成后，AI 评估改得好不好
- 训练任务作为"还想练更多？这里还有类似的练习"的补充
- 删除"Level 4 对比 Evidence"的概念——直接展示"改前 vs 改后"

**评分调整**：从 **95 → 80**（方向正确但执行模式需要调整，扣 15 分）

## 八、本轮审计的额外发现

### 8.1 隐藏假设：用户愿意接受诊断

**第一性追问**：
> 作者为什么要接受诊断？

**当前假设**：作者希望被诊断。
**可能的事实**：作者可能只想"有人看我写的东西，告诉我写得怎么样"。诊断是系统强加的框架，不是作者主动寻求的。

**风险**：作者可能觉得"我只是想找人聊聊我的小说，结果你给我判了一堆病"。

**判定**：⚠️ 系统缺乏"非诊断模式"——作者可以只是聊聊，不会被自动诊断。

### 8.2 隐藏假设：用户有"被教练"的意愿

**第一性追问**：
> 作者为什么愿意花费额外时间做训练？

**当前假设**：作者愿意为了成长花时间。
**可能的事实**：大部分网文作者是兼职写作，时间和精力有限。

**风险**：训练任务可能被认为是"额外负担"，而不是"帮助"。

**判定**：⚠️ 训练链路的用户动机假设需要验证。

### 8.3 隐藏假设：P001-P010 的分类是准确的

**当前假设**：10 个症候是独立、互斥、完整的。
**可能的事实**：症候之间可能有重叠（P004 和 P008）、遗漏、或分类错误。

**风险**：基于错误分类的诊断和训练会积累错误数据。

**判定**：🔴 症候分类需要实证验证，否则整个系统的上层建筑（证据→画像→训练）都建立在沙子上。

## 十、最危险的问题：优先级反转

### 第一性原理最终追问

**第一问**：如果今天必须砍掉 50% 的功能才能上线 V1.0，砍什么？

```
保留：
✅ 对话（能聊就行）
✅ 诊断（发现问题 + 用原文解释为什么）
✅ 修改入口（"试试这样改" + 编辑功能）

❌ 聚焦方向过滤器（先全量诊断，再建议聚焦）
❌ 训练任务独立入口（诊断后直接改，改完再提"想练更多？"）
❌ 三标签面板（只保留一个视图）
❌ 雷达图/时间线/对比组件（用户没空看这些）
❌ 所有的 IPC 通道简化（合并重复通道）
❌ Pattern Detector（一个 if 语句）
❌ NovelProfile（不做）
❌ Agent 架构（不做）
```

**第二问**：这个版本叫 V1.0 吗？

**不叫。这个版本最多叫 V0.5。**

**V1.0 的交付标准应该是什么？**

```
V1.0 = 一个作者打开应用后：
  1️⃣ 上传小说 → 得到诊断（问题 + 原因 + 原文引用）
  2️⃣ 在诊断页直接修改原文
  3️⃣ 收到修改反馈（"这里改好了，那里还需要调整"）
  4️⃣ 关闭应用时比打开时写得更好
```

**当前离这个标准还有多远？**

| 步骤 | 状态 | 差距 |
|------|------|------|
| 1️⃣ 上传→诊断 | ✅ 基本完成 | 诊断内容需要验证症候准确性 |
| 2️⃣ 直接修改原文 | ❌ 缺失 | 当前没有"修改入口" |
| 3️⃣ 修改反馈 | ❌ 缺失 | 当前没有"评估修改"的功能 |
| 4️⃣ 写得更好 | ❌ 无法验证 | 没有闭环数据 |

## 十一、V2 审计总结

### 相比第一次审计，V2 发现了什么？

| 发现类型 | 发现 | 严重程度 |
|---------|------|---------|
| **症候基础不牢** | P001-P010 未经验证，P004/P008 重复 | 🔴 P0 |
| **Evidence 概念过度暴露** | 作者不需要"证据"，只需要原文引用 | 🔴 P0 |
| **数字评分有害** | 精确分数误导/打击作者，应改为文字描述 | 🔴 P0-1 |
| **聚焦方向设计悖论** | 让不知道问题的人选择聚焦方向，不合理 | 🟡 P1 |
| **Training 模式偏差** | "作业模式"应该改为"治疗模式" | 🟡 P1 |
| **症状 vs 治疗错位** | 诊断后没有"修改原文"的路径 | 🔴 P0 |
| **UI 优先级倒挂** | 能力画像/成长记录挤占了修改入口的空间 | 🟡 P1 |

### 最高优先级行动

```
1️⃣ 修正症候体系（技法蒸馏就是为了这个）
   → 新对话优先执行技法蒸馏
   → 用蒸馏结果验证/修正 P001-P010

2️⃣ 添加"修改原文"路径（这是 Training 的核心）
   → 诊断后展示修改建议
   → 提供内联编辑器
   → AI 评估修改效果

3️⃣ 前端删除"证据"和"数字评分"概念
   → 证据 → "诊断依据/原文引用"
   → 数字评分 → "文字描述/分级标记"
```

### 最终一句话

> **一个作者打开应用后，不需要知道"证据"是什么、"能力评分"是多少、"聚焦方向"怎么选。他只需要知道：我哪里写得不好 → 为什么不好 → 怎么改 → 改好了没有。**  
>  
> **当前系统做了前三步的前半段（诊断 + 解释），但最关键的是"怎么改"和"改好了没有"——这两步全缺。**
