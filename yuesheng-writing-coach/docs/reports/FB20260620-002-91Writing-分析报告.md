## 2. 91Writing Agentic 架构详解

### 2.1 架构决策背景

开发者对比了三种主流写作交互模式后做出选择：

| 模式 | 代表 | 优势 | 劣势 |
|:-----|:-----|:-----|:------|
| **传统写作平台** | 91Writing v0.7 / 蛙蛙 / 星月 | 高度可控，手动关联上下文 | 依赖提示词质量，学习成本高 |
| **全自动工作流** | 部分竞品 | 效率极高，一键生成 | 几乎不可控，修改崩溃 |
| **Agentic 写作** | 91Writing agentic 分支 | 对话驱动，可控且易用 | 暂无显著劣势 |

### 2.2 技术方案选择

**选择：ReAct（Reason + Act）模式**

对比 Multi-Agent 和 ReAct 后选择 ReAct，原因：
1. **简洁性** — 只需管理一个单 Agent 循环 + 多工具
2. **流行度** — Claude Code、Cursor、Trae 均采用此方案
3. **领域适配性** — 网文写作天然契合"脑洞→推理→延伸"的 ReAct 循环
4. **可扩展性** — ReAct 并非绝对单 Agent，可通过创建子代理实现多 Agent 交互

### 2.3 Agent 团队配置

```
┌─────────────────────────────────────────────────────────┐
│                    主专家                                 │
│          网文产品经理 / 任务分配 / 团队领导                  │
│          接收用户需求 -> 分析 -> 分配子专家 -> 汇总输出     │
└──────────────┬──────────────┬──────────────┬───────────┘
               │              │              │
     ┌─────────▼──┐   ┌──────▼──────┐   ┌───▼─────────┐
     │  脑洞大神   │   │ 人设规划专家 │   │ 世界观规划专家 │
     │  灵感生成   │   │ 角色设计     │   │ 世界设定      │
     └────────────┘   └─────────────┘   └──────────────┘
     ┌─────────┐       ┌────────────┐     ┌────────────┐
     │事件线策划│       │正文创作大神 │     │编辑润色大神 │
     │ 情节规划 │       │ 章节写作    │     │ 内容优化    │
     └─────────┘       └────────────┘     └────────────┘
     ┌────────────┐
     │阅读评价专家│
     │ 质量审计   │
     └────────────┘
```

### 2.4 技术栈（agentic 分支）

| 层 | 技术选择 |
|:----|:---------|
| 运行时 | Node.js + Express |
| Agent 框架 | LangChain |
| 前端 | Web 界面（与 main 分支共享） |
| 数据存储 | 本地文件系统（`novels/` 目录） |
| LLM 协议 | OpenAI 格式（兼容多模型） |

### 2.5 交互流程

```
用户输入写作需求
     │
     ▼
主专家分析需求
     │
     ├──→ 需要脑洞？ → 分配脑洞大神
     ├──→ 需要人设？ → 分配人设规划专家
     ├──→ 需要世界观？→ 分配世界观规划专家
     ├──→ 需要情节？ → 分配事件线策划专家
     ├──→ 需要正文？ → 分配正文创作大神
     ├──→ 需要润色？ → 分配编辑润色大神
     └──→ 需要评价？ → 分配阅读评价专家
     │
     ▼
子专家输出结果 → 主专家汇总 → 返回用户
     │
     ▼
用户反馈 → 主专家分析 → 重新分配 → 迭代优化
```

### 2.6 核心特点

- **文件即数据库**：每本小说对应 `novels/` 下的独立目录，包含章节、角色、世界观等文件，无加密
- **两级提示词入口**：项目级提示词（界定世界观/人物/风格）+ 系统级提示词（界定 Agent 推理逻辑）
- **弱提示词依赖**：通过自然对话即可驱动，不要求用户掌握提示词工程
- **开放式上下文**：Agent 主动读取文件自动选择上下文

## 3. 与 INKOS Agent 管线的异同分析

### 3.1 共同点

| 共同点 | 91Writing Agentic | INKOS |
|:-------|:-------------------|:------|
| **ReAct 模式** | 单 Agent 循环 + 多子专家 + 多工具 | 单 Agent 循环 + 10-Agent 链式流水线 |
| **本地文件存储** | `novels/` 目录，明文 JSON/MD | `books/<id>/story/` 目录，JSON + MD |
| **文件即真相** | 直接读写文件无需数据库 | Truth Files + SQLite 时间记忆 |
| **多模型兼容** | OpenAI 格式接口，主流模型均支持 | 30+ Provider Bank，Agent 级模型覆盖 |
| **内容审计** | 阅读评价专家负责质量 | ContinuityAuditor 37 维度审计 |
| **渐进式写作** | 通过对话迭代修改 | Plan → Compose → Write → Audit → Revise |

### 3.2 核心差异

| 维度 | 91Writing Agentic | INKOS |
|:-----|:-------------------|:------|
| **架构模式** | **主-从式**：1 个主专家 + N 个子专家，主专家负责任务分配和汇总 | **链式流水线**：10 个 Agent 按固定顺序串联执行，每个 Agent 专注单一职责 |
| **运行时** | Node.js + Express + LangChain | Node.js CLI（Commander）+ TUI（Blessed）+ Studio（Vite+React） |
| **Agent 框架** | LangChain | 自研（pi-ai + pi-agent-core） |
| **上下文管理** | Agent 主动读取文件，自动选择参考上下文 | **Governed Context**：protected/compressible 分层，Composer 精选组装 |
| **状态管理** | 较简单，直接读写文件 | **成熟**：RuntimeStateDelta（差分更新）、Zod 校验、快照回滚、文件锁 |
| **记忆系统** | 无显式记忆管理层 | 三层记忆：结构化 JSON + Markdown 投影 + SQLite 时间记忆 |
| **审计维度** | 1 个阅读评价专家（维度未公开） | 37 维度审计 + 钩子健康分析 + AI 痕迹检测 |
| **修订机制** | 对话迭代，用户描述问题 | 6 种修订模式（polish/spot-fix/rewrite/rework/anti-detect） |
| **批量写作** | 对话驱动，逐章/逐段 | `inkos write next --count N` 批量生成，自动锁定文件 |
| **成本控制** | Token 计费管理（前端层） | 多模型路由（昂贵模型用于写作，便宜模型用于审计） |
| **复杂交互** | 暂无 | Play 模式（开放世界/分支交互）+ World Contract |
| **许可协议** | MIT（宽松） | AGPL-3.0（强保护） |

### 3.3 差异的根因分析

| 差异 | 根因 |
|:-----|:------|
| **主-从 vs 链式** | 91Writing 面向"对话驱动"场景，用户与主专家对话即可完成全流程；INKOS 面向"专业化分工"，每个阶段由独立 Agent 完成，结果更稳定但灵活性略低 |
| **轻量 vs 重型** | 91Writing 为独立开发者作品，追求 MVP 和快速迭代；INKOS 为成熟项目（2.4.0），功能深度和工程化程度更高 |
| **弱提示词 vs 强治理** | 91Writing 强调"用户无需写 Prompt"；INKOS 强调"输入治理"，通过 Planned/Composed 控制上下文质量 |
| **无记忆 vs 三层记忆** | 差异源于项目复杂度：91Writing 单 Agent 循环上下文窗口充足；INKOS 需支持长篇小说（数百章）的一致性 |

### 3.4 对月笙的启示

| 启示 | 来源 | 建议 |
|:-----|:------|:------|
| 交互模式选择 | 91Writing 的"主-从式"更适合对话教学场景 | 教学 Agent 可采用主专家（教学规划）+ 子专家（诊断/纠错/练习）模式 |
| 上下文治理 | INKOS 的 Composer 设计 | 月笙教学 Agent 的上下文管理可参考 INKOS 的 governed context 思想 |
| 状态差分 | INKOS RuntimeStateDelta | 月笙的 TeachingDecisionLog 可借鉴差分模式，而非全量记录 |
| 审计维度 | INKOS 37 维度 | 月笙写作诊断的维度体系可参考 INKOS 的审计框架 |

## 4. 纯前端本地存储方案与月笙 Electron 架构的可比性

### 4.1 方案对比

| 维度 | 91Writing（纯前端） | 月笙（Electron） |
|:-----|:--------------------|:-----------------|
| **运行时** | 浏览器（Chrome/Firefox） | Electron（Chromium + Node.js） |
| **存储技术** | localStorage + IndexedDB | better-sqlite3（主进程） |
| **存储容量** | 受浏览器限制（通常 5MB~无上限取决于 API） | 受文件系统限制（通常无实际上限） |
| **存储安全** | 浏览器可被 DevTools 查看，无加密 | 主进程隔离，R-029 安全规范 |
| **数据导出** | JSON 文件下载 | SQLite 数据库文件 + 导出功能 |
| **离线能力** | 完全离线（纯前端） | 完全离线（Electron 本地） |
| **AI 请求** | 浏览器直接发请求（CORS） | 主进程代理，IPC 通道 |
| **多窗口** | 同标签页内 SPA | 多窗口/多进程 |
| **扩展性** | 依赖浏览器 API | Node.js 生态 + 系统级 API |
| **备份方案** | 导出 JSON + 手动恢复 | DB 文件复制 + 自动备份 |

### 4.2 关键差异分析

#### 4.2.1 数据持久化层

**91Writing**：Pinia store + 浏览器持久化。核心数据通过 Pinia 的 persist middleware 写入 localStorage 或 IndexedDB。优点是零配置、开箱即用；缺点是浏览器存储的容量上限不确定，且多标签页同步需要额外处理。

**月笙**：Electron 主进程中运行 better-sqlite3 + Knex migration。通过 typed IPC handlers 暴露数据操作接口给 renderer 进程。优点是有完整的关系型数据库能力（事务、索引、迁移）；缺点是架构更复杂，需要维护 IPC 通道和数据契约。

#### 4.2.2 AI 请求路径

**91Writing**：
```
浏览器 → fetch() → AI Provider API
```
优点：直连延迟低；缺点：API Key 暴露在前端（违反 R-029），需要用户自行管理。

**月笙**：
```
Renderer → IPC invoke → Main Process → fetch() → AI Provider API
```
优点：API Key 只在主进程存在（符合 R-029）；缺点：IPC 通信有额外延迟。

#### 4.2.3 编辑器集成

**91Writing**：WangEditor 5.1.23（Vue 组件封装），直接在浏览器中嵌入富文本编辑器。

**月笙**：当前使用 textarea/纯文本，计划升级。WangEditor 对 Vue 的深度绑定使其在 React 项目中不可直接复用。月笙可考虑 TipTap（ProseMirror 封装，React 生态兼容），这也是 OpenWrite 的选择。

### 4.3 可比性结论

| 结论 | 说明 |
|:-----|:------|
| **有参考价值** | 91Writing 的功能设计和交互逻辑对月笙有参考价值 |
| **架构不可直接复用** | 纯前端方案缺少 Electron 的进程隔离、IPC 通道、Node.js 生态等关键能力 |
| **存储层不可比** | SQLite 与浏览器存储的语义和性能差异巨大 |
| **AI 安全层不可比** | 91Writing 的直连模式不符合月笙的 R-029 安全规范 |
| **可借鉴点** | 前端 UI 交互设计、10 大工具的设计模式、世界观构建 UI |

## 5. 10 大智能工具的设计模式分析

### 5.1 工具全景

91Writing 提供 10 个独立智能工具，覆盖创作全链路：

| 序号 | 工具名称 | 输入 | 输出 | 创作阶段 |
|:----:|:---------|:-----|:-----|:---------|
| 1 | **细纲生成器** | 题材/类型/关键词 | 详细的章节大纲 | 规划 |
| 2 | **角色生成器** | 设定参数 | 1-15 个角色档案 | 设定 |
| 3 | **脑洞生成器** | 题材/元素 | 创意点子列表 | 灵感 |
| 4 | **书名生成器** | 类型/风格/关键词 | 爆款书名列表 | 包装 |
| 5 | **题材生成器** | 偏好/热门元素 | 题材推荐 | 定位 |
| 6 | **世界观生成器** | 类型/核心元素 | 完整世界观设定 | 设定 |
| 7 | **金手指生成器** | 题材/主角设定 | 金手指方案 | 设定 |
| 8 | **开篇生成器** | 题材/风格 | 黄金开篇方案 | 创作 |
| 9 | **简介生成器** | 小说内容/卖点 | 吸引人的简介 | 包装 |
| 10 | **冲突生成器** | 角色关系/世界观 | 冲突方案列表 | 规划 |

### 5.2 设计模式提炼

#### 模式一：输入驱动（Query-Driven）

所有工具采用统一的"输入 -> LLM 调用 -> 格式化输出"模式：

```
用户提供少数参数
    │
    ▼
工具组装提示词模板（+ 上下文变量替换）
    │
    ▼
调用 LLM（流式/非流式）
    │
    ▼
解析并格式化输出（列表/卡片/详细文本）
    │
    ▼
用户可以：复制/采纳/重新生成/微调
```

**特点**：
- 输入最少化 — 用户只需提供 2-5 个关键参数
- 输出多样化 — 每次生成多个方案供选择
- 非破坏性 — 生成结果不自动写入项目，用户决定是否采纳

#### 模式二：模板变量系统（Template Variable System）

每个工具背后是结构化提示词模板，支持变量注入：

```markdown
你是一个专业的小说{{类型}}{{工具}}专家。
请根据以下信息生成{{输出类型}}：

题材：{{题材}}
主要元素：{{元素}}

要求：
1. 生成至少 5 个方案
2. 每个方案包含标题和简要说明
3. 方案要新颖，避免套路
```

**变量系统支持**：
- 内置变量：类型、题材、角色名、世界观元素等
- 上下文变量：自动从当前项目提取（标题、已有设定等）
- 用户自定义变量：高级用户可创建

#### 模式三：上下文感知（Context-Aware）

工具在调用 LLM 时自动收集当前项目的上下文信息：

- 当前小说的类型、标题、简介
- 已创建的角色列表
- 已设定的世界观元素
- 最近的编辑内容

**上下文组装策略**：轻量级组装，只携带最相关的 3-5 条信息，避免上下文过载。

#### 模式四：工具自治（Tool Autonomy）

每个工具独立运行，不依赖其他工具的产出：
- 无状态设计 — 每次调用都是独立的
- 可组合使用 — 用户可任意顺序使用工具
- 结果不可变 — 生成结果用户自行决定是否使用

### 5.3 对月笙的借鉴价值

| 模式 | 月笙可借鉴点 |
|:-----|:-------------|
| **输入驱动** | 月笙的"写作训练工具集"可采用相同的参数最少化设计——用户提供作品片段和训练目标，AI 自动生成训练方案 |
| **模板变量** | 月笙的教学提示词模板可借鉴变量系统，实现"通用模板 + 项目特定变量" |
| **上下文感知** | 月笙的教学 Agent 需要感知当前学习项目、历史诊断结果、用户画像 |
| **工具自治** | 月笙的技能训练工具（如"人物描写练习""情节结构训练"）应保持独立，互不依赖 |

### 5.4 与月笙现有工具集的映射

| 91Writing 工具 | 月笙等价/可映射功能 | 差异 |
|:---------------|:--------------------|:------|
| 细纲生成器 | 写作规划工具 | 月笙侧重教学引导而非自动生成 |
| 角色生成器 | 人物塑造训练 | 月笙侧重分析而非生成 |
| 脑洞生成器 | 灵感发散训练 | 月笙暂无等价功能 |
| 书名生成器 | 暂不适用 | 月笙非出版工具 |
| 题材生成器 | 暂不适用 | 月笙不关注选题 |
| 世界观生成器 | 写作设定分析 | 月笙可借鉴其模板化设计 |
| 金手指生成器 | 暂不适用 | 月笙不关注网文金手指 |
| 开篇生成器 | 开篇分析工具 | 月笙侧重教学而非生成 |
| 简介生成器 | 暂不适用 | 月笙非出版工具 |
| 冲突生成器 | 情节设计训练 | 月笙可借鉴其冲突类型体系 |

## 6. 世界观构建的一致性检查方案

### 6.1 91Writing 的一致性检查设计

91Writing 的世界观构建模块设计为三层结构：

```
世界观构建
  ├── 模板层：预定义各类题材的世界观模板
  │   ├── 科幻类：技术水平、社会结构、星际关系
  │   ├── 修仙类：修炼体系、境界划分、门派势力
  │   ├── 赛博朋克：科技水平、社会阶级、黑市生态
  │   └── 奇幻类：魔法体系、种族设定、地理环境
  │
  ├── 编辑层：用户手动编辑和填充
  │   ├── 核心设定（技术水平、社会结构等固定字段）
  │   ├── 关键元素（物品、组织、环境等可扩展字段）
  │   └── 故事背景（历史事件、主要冲突等叙事字段）
  │
  └── 检查层：AI 驱动的一致性验证
      ├── 内部一致性：世界观元素之间是否逻辑自洽
      ├── 角色兼容性：角色能力/背景是否与世界设定冲突
      └── 叙事连贯性：故事发展是否违背世界观规则
```

### 6.2 一致性检查的技术实现

根据公开资料推断，91Writing 的一致性检查采用以下技术路径：

**检查方式**：AI 驱动的 Prompt-based 检查（非规则引擎）

**检查流程**：
1. 收集世界观设定内容（模板字段 + 自定义字段）
2. 组装检查提示词，包含当前世界观的全部要素
3. 调用 LLM 进行逻辑推理检查
4. 输出检查结果（一致/不一致 + 不一致的具体问题）

**检查维度**：

```
一致性检查清单（推断）：
┌─────────────────────────────────────────────┐
│  1. 技术层面                                  │
│     ├── 科技水平是否与时代设定一致              │
│     └── 不同地区的科技差异是否合理              │
│                                              │
│  2. 社会层面                                  │
│     ├── 社会结构是否与故事主题匹配              │
│     ├── 权力关系是否逻辑自洽                    │
│     └── 经济体系是否支持故事设定                │
│                                              │
│  3. 元素层面                                  │
│     ├── 物品的能力是否在设定范围内              │
│     ├── 组织的动机和行为是否一致                │
│     └── 环境规则是否被遵守或合理解释             │
│                                              │
│  4. 叙事层面                                  │
│     ├── 历史事件是否因果合理                    │
│     ├── 主要冲突是否与世界设定兼容              │
│     └── 故事发展是否受世界观规则约束            │
└─────────────────────────────────────────────┘
```

### 6.3 与 INKOS Truth Files 的对比

| 维度 | 91Writing 世界观 | INKOS Truth Files |
|:-----|:-----------------|:------------------|
| **存储格式** | 模板化字段 + 自由文本 | 结构化 JSON（Zod 校验）+ Markdown 投影 |
| **状态管理** | 静态设定（创建后少修改） | 动态状态（RuntimeStateDelta 持续更新） |
| **一致性检查** | Prompt 驱动，按需触发 | ContinuityAuditor 37 维度，每章自动审计 |
| **关联性检查** | 世界观元素之间的逻辑自洽 | 角色/物品/地点/钩子的交叉引用验证 |
| **权威层级** | 未明确 | `direction > foundation > rules > runtime-truth > memory` |
| **版本管理** | 无 | 快照回滚 + 文件锁 |
| **自动化程度** | 用户手动触发检查 | 每次写作后自动审计 |

### 6.4 对月笙的启发

月笙项目中，"世界观构建"本身不是核心教学目标（月笙是写作教练而非创作工具），但一致性检查的思想可以迁移到**教学一致性检查**：

| 月笙教学场景 | 借鉴思想 | 说明 |
|:-------------|:---------|:------|
| 学生作品诊断 | 多维度检查 | 像 91Writing 检查世界观那样，按维度检查学生写作的问题 |
| 教学建议一致性 | 规则引擎 vs AI 驱动 | 月笙当前的诊断引擎采用规则驱动，可结合 AI 驱动的一致性检查作为补充 |
| 学习路径连贯性 | 关联性检查 | 检查当前训练目标与学生历史诊断结果的一致性 |
| 反馈一致性 | 模板化管理 | 将教学反馈模板化，确保不同场景下的反馈逻辑自洽 |

### 6.5 方案优劣评估

| 方案 | 优势 | 劣势 | 适用场景 |
|:-----|:------|:------|:---------|
| **规则引擎检查**（月笙诊断引擎） | 确定性强、可测试、零 Token 成本 | 覆盖维度有限、难以处理模糊逻辑 | 已知问题模式匹配 |
| **AI Prompt 检查**（91Writing 方式） | 灵活、覆盖维度广、可处理模糊逻辑 | Token 成本高、结果不确定性、不可测试 | 开放式语义一致性检查 |
| **混合方案**（INKOS 方式） | 规则 + AI 互补、分级处理 | 架构复杂、维护成本高 | 大规模生产系统 |

**推荐**：月笙可采用**规则引擎为主、AI 检查为辅**的混合方案。明确可定义的问题（如标点错误、字数不足、段落过长）用规则引擎；需要语义理解的开放问题（如人物塑造是否一致、情节逻辑是否合理）用 AI 补充检查。

## 7. 对月笙项目的可借鉴设计

### 7.1 高价值借鉴项

| 借鉴项 | 来源 | 优先级 | 说明 |
|:-------|:------|:------:|:------|
| 工具自治模式 | 91Writing 10 大工具 | 高 | 月笙的技能训练工具可参考"输入驱动 + 模板变量 + 上下文感知"设计模式 |
| 两级提示词入口 | 91Writing agentic 分支 | 高 | 月笙教学 Agent 可设置"项目级提示词（学生画像/目标）+ 系统级提示词（教学策略）" |
| 主-从 Agent 模式 | 91Writing agentic 分支 | 中 | 月笙教学 Agent 可采用主专家（教学规划）+ 子专家（诊断/纠错/练习）模式 |
| 多维度检查清单 | 91Writing 世界观一致性 | 中 | 月笙诊断引擎的维度体系可参考一致性检查的维度设计 |
| 模板变量系统 | 91Writing 提示词库 | 中 | 月笙教学提示词模板的变量替换机制 |
| 交互式工具 UI | 91Writing 工具界面 | 低 | 工具的一键调用 + 流式输出 + 结果预览的交互模式 |

### 7.2 不适用项

| 项 | 原因 |
|:---|:------|
| 纯前端存储架构 | 月笙需要 SQLite 跨进程能力和 Node.js 生态 |
| WangEditor 编辑器 | 对 Vue 深度绑定，月笙基于 React |
| 前端直连 AI API | 违反 R-029 安全规范 |
| 无版本管理的文件存储 | 月笙需要完整的迁移和变更溯源 |
| 字数目标和成就系统 | 月笙是教学工具而非写作工具 |

### 7.3 已覆盖项

以下 91Writing 的设计点已在 INKOS 研究（FB20260620-001）中被覆盖或优于 91Writing：

| 设计点 | INKOS 方案 | 对比 |
|:-------|:-----------|:------|
| Truth Files | INKOS 的真相文件机制更成熟 | INKOS 更优 |
| Agent 管线 | INKOS 10-Agent 链式更专业 | INKOS 更优 |
| 上下文治理 | INKOS Composser + RuleStack | INKOS 更优 |
| 记忆系统 | INKOS 三层记忆（JSON + MD + SQLite） | INKOS 更优 |
| 多模型路由 | INKOS 30+ Provider + Agent 级覆盖 | INKOS 更优 |
| 审计维度 | INKOS 37 维度 | INKOS 更优 |
