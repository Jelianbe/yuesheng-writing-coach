### 2.2 10-Agent 流水线

INKOS 的核心是 10 个专业化 Agent 形成的链式流水线：

| 序号 | Agent | 职责 | 对月笙的启发 |
|:----:|-------|------|-------------|
| 1 | **RadarAgent** | 市场扫描（番茄/七猫趋势分析） | 可对应"学生常见错误模式检测" |
| 2 | **ArchitectAgent** | 书籍架构设计（story_bible, book_rules） | 可对应"学生写作计划定制" |
| 3 | **PlannerAgent** | 章节意图生成（ChapterIntent + ChapterMemo） | 可对应"教学步骤规划" |
| 4 | **ComposerAgent** | 上下文精选组装（ContextPackage + RuleStack） | 可对应"教学上下文组装" |
| 5 | **WriterAgent** | 章节正文生成 | 可对应"教学内容生成" |
| 6 | **SettlerAgent** | 状态结算（解析 RuntimeStateDelta） | 可对应"教学进度更新" |
| 7 | **ContinuityAuditor** | 连续性审计（37 维度） | **可对应"教学质量审计"** |
| 8 | **ReviserAgent** | 章节修订（6 种模式） | 可对应"教学策略调整" |
| 9 | **PolisherAgent** | 语言润色 | 可对应"教学表达优化" |
| 10 | **ConsolidatorAgent** | 卷摘要合并 | 可对应"学习阶段总结" |

### 2.3 真相文件（Truth Files）机制

**最重要**的架构设计。INKOS 不依赖向量数据库，而是用结构化文本文件维护"当前真相"：

```
TruthFiles
  ├── currentState:       当前状态快照（角色位置/目标/冲突）
  ├── particleLedger:     细粒度状态事实记录（"粒子账本"）
  ├── pendingHooks:       待处理钩子（伏笔管理）
  ├── storyBible:         故事圣经（世界观设定）
  ├── volumeOutline:      卷纲
  └── bookRules:          本书规则（写作规范）
```

**分级权威控制**：`direction > foundation > rules > runtime-truth > memory`

**运行时状态差分**：每次写操作产生 `RuntimeStateDelta`（补丁），而非全量重写。

> **对月笙的启发**：月笙的 `TeachingDecisionLog` + `TeachingOutcomeLog` 可以借鉴"真相文件"的设计思想——将教学状态持久化为结构化文本文件，而非仅依赖数据库。Composer 的概念（精选上下文 + 规则栈组装）可直接对应教学 Agent 的上下文管理。

### 2.4 多模型路由

INKOS 构建了松耦合的 LLM 抽象层，支持 30+ 服务提供商：

- **Provider Bank**：内置 Google Gemini、Moonshot、MiniMax、智谱、百炼、DeepSeek、硅基流动等
- **Service Preset**：每个 service 定义 providerFamily、baseUrl、knownModels
- **Agent 级模型覆盖**：`modelOverrides: Record<string, AgentLLMOverride>`
- **三层 env 叠加**：studio → global env → project env → CLI 参数

### 2.5 交互层设计

- **三层输入源**：TUI (Blessed Terminal) / Studio Chat (Web UI) / CLI (Commander)
- **6 种 SessionKind**：chat, book-create, book, short, play, edit
- **22 种 InteractionIntent**：覆盖全部操作
- **Execution State Machine**：`idle → planning → composing → writing → assessing → repairing → persisting → waiting_human → blocked → completed/failed`

### 2.6 INKOS Play 开放世界

INKOS Play 的"事件溯源式"图存储设计：

- **Entities**：actor, location, item, evidence, clue, claim 等
- **Edges**：关系图（from→to，带 validFrom/UntilEventId）
- **StateSlots**：resource, relation, pressure, clue, evidence, flag, timer
- **EvidenceTransitions**：unknown → hinted → seen → collected → verified → weaponized → exposed → exhausted
- **快照/检查点**：captureRunSnapshot + saveCheckpoint / loadCheckpoint

### 3.3 核心功能模块

#### 3.3.1 Codex 系统（世界观百科）

OpenWrite 的 Codex 是最值得借鉴的功能：

- **角色管理**：完整 CRUD，每项目独立空间
- **地点管理**：与角色关联
- **传说/设定管理**（Lore）：类型化分类
- **情节点管理**：6 种情节类型（inciting_incident, plot_point_1, midpoint 等）

前端组件（`codex-modal.tsx`, `dynamic-codex-form.tsx`）采用"Modal + 分类 Tab + 详情编辑"布局，左侧列表+右侧详情。

> **对月笙的启发**：月笙的 `ProjectSettingTree` 教学笔记树可以参考 Codex 的 UI 布局和 CRUD 模式。

#### 3.3.2 AI 助手

**BYOK（Bring Your Own Key）设计**：

- 支持的提供商：OpenRouter, OpenAI, Anthropic, Groq, Gemini, Cohere, Ollama
- API Key 在服务端加密存储（AES-GCM）
- AI 上下文感知：知晓当前项目的 title, genre, characters
- 侧边栏 Chat + "Insert into editor" 按钮

服务器路由（`POST /api/ai/chat`）：
1. 解密用户存储的 provider key
2. 根据提供商选择不同的 API 调用方式
3. 组装 System Prompt（项目上下文 + 角色信息）
4. 流式返回 AI 回复
5. 追踪每次请求的使用量

#### 3.3.3 编辑器

基于 Tiptap（ProseMirror 封装）：

- **自动保存**：1.5s debounce，切换章节时 flush
- **字数统计**：按项目/章节追踪
- **富文本工具栏**：shadcn-ui 重写，删除了 16k 行冗余样式
- **右键菜单**：浮动工具栏

#### 3.3.4 故事画布（Story Canvas）

基于 React Flow 的节点编辑器（`node-writing-panel.tsx`）：

- **节点类型**：story_flow, character_arc, setting, thematic
- **AI 生成**：选中节点可调用 AI 生成草稿
- **上下文组装**：自动收集关联节点的 prose + 元数据

### 3.4 数据库设计

使用 Drizzle ORM + D1 SQLite，核心表包括：

- **users**（Better Auth 管理）
- **projects**（作品容器，含 type/status/wordCount）
- **works**（作品，关联 project）
- **chapters**（章节，关联 work）
- **characters, locations, lore, plot_points**（Codex 系统）
- **api_keys**（加密存储的 AI 提供商密钥）

## 3.5 BYOK AI 助手源码精读（WebFetch 获取）

通过 WebFetch 读取了 [`apps/server/src/routers/ai.ts`](https://github.com/ilrein/openwrite/blob/main/apps/server/src/routers/ai.ts)（~230 行），这是 OpenWrite 的 BYOK AI 路由实现。

### 3.5.1 提供商支持

OpenWrite 支持 7 种 AI 提供商：

| 提供商 | API 类型 | 默认模型 | 密钥要求 |
|:-------|:---------|:---------|:---------|
| **OpenRouter** | OpenAI-compatible | openrouter/auto | API Key |
| **OpenAI** | OpenAI-compatible | gpt-4o-mini | API Key |
| **Anthropic** | Native Messages | claude-haiku-4-5 | API Key |
| **Groq** | OpenAI-compatible | llama-3.3-70b-versatile | API Key |
| **Gemini** | OpenAI-compatible | gemini-2.0-flash | API Key |
| **Cohere** | OpenAI-compatible | command-r-08-2024 | API Key |
| **Ollama** | OpenAI-compatible (local) | llama3.2 | 不需要 |

### 3.5.2 AI 请求处理流程

```
POST /api/ai/chat
  │
  ├─ 1. requireAuth 中间件验证会话
  ├─ 2. validateMessages() 验证消息
  │     ├─ 最多 40 条消息
  │     ├─ 最多 32,000 字符
  │     └─ 最后一条必须是 user 角色
  ├─ 3. buildSystemPrompt() 组装 System Prompt
  │     ├─ BASE_SYSTEM_PROMPT（固定写作助手角色）
  │     ├─ 项目信息（title, type, genre, description）
  │     └─ 角色数据（最多 20 个角色 + 描述）
  ├─ 4. runCompletionForUser() 执行
  │     ├─ 查询用户激活的 AI Provider
  │     ├─ AES-GCM 解密 API Key
  │     ├─ dispatchToProvider() 路由到具体 API
  │     │   ├─ OpenAI-compatible: callOpenAiCompatible()
  │     │   └─ Anthropic: callAnthropic()
  │     └─ 更新 usage 计数
  └─ 5. 返回 { message, provider, model }
```

### 3.5.3 密钥管理

- **存储**：数据库 `ai_provider` 表，`apiKey` 字段 AES-GCM 加密
- **解密**：`decryptApiKey()` 使用 Cloudflare Workers 环境变量 `ENCRYPTION_KEY`
- **Bug 修复经验**：早期版本用 `btoa()` + `TextDecoder("latin1")` 处理二进制，但在约一半密文上会随机失败。修复为 chunked bytes→base64 方式。
- **分层配置**：用户可在 UI 配置多个 provider，其中一个是默认

### 3.5.4 系统 Prompt 组装

```typescript
// 从 routers/ai.ts 提取的 prompt 结构
const BASE_SYSTEM_PROMPT = "You are a thoughtful writing assistant for fiction writers...";

async function buildSystemPrompt(projectId, organizationId) {
  const projectData = await db.select(...).from(project).where(...).get();
  const characters = await db.select(...).from(character).where(...).limit(20);

  return [
    BASE_SYSTEM_PROMPT,
    "",
    "The writer is working on this project:",
    `- Title: ${projectData.title} (${projectData.type})`,
    `- Genre: ${projectData.genre}`,
    `- Description: ${projectData.description}`,
    "- Characters:",
    ...characters.map(c => `  - ${c.name} — ${c.description}`),
  ].join("\n");
}
```

> **对月笙的启发**：这种"固定角色 Prompt + 动态项目上下文"的模式可以直接应用。月笙可以将 `CoachChat` 的 system prompt 改为：BASE_TEACHING_PROMPT + 学生当前发音问题 + 练习历史。

## 3.8 SoloEnt—AI-native 桌面写作工作空间

通过 WebFetch 获取了 [SoloEnt 官网](https://soloent.ai/) 和 [AnyFP 评测页面](https://anyfp.com/soloent-ai/) 的产品描述。SoloEnt 是商业产品（非开源），免费版可用，Pro/Max 从 $9.9/月起。

### 3.8.1 SoloEnt.md — 故事宪法

**核心创新**：每个项目的 `SoloEnt.md` 文件是"故事宪法"（Story Constitution），扮演 AI 的**长期记忆**。

| 维度 | SoloEnt.md | INKOS Truth Files | 月笙 TeachingDecisionLog |
|:-----|:-----------|:------------------|:------------------------|
| **模型** | 宪法模型——定规则、人主导 | 真相模型——存事实、机器主导 | 纯记录器（写不读） |
| **格式** | 单文件 Markdown | 7 个结构化 JSON + Zod | SQLite 表 |
| **可读性** | 创作者可读可写 | 开发者可读、机器主导 | 仅机器可读 |
| **类比** | 美国宪法（原则性、可解释） | 数据库 Schema（精确性、不可篡改） | 日志文件（追加写入） |

### 3.8.2 Rules, Workflows, Skills 系统

- **Rules**：写作铁律（如"不可以用同一种修辞超过三次"）
- **Workflows**：自定义写作管线（如一键审阅 + 反 AI 味过滤 + 字数统计）
- **Skills**：AI 智能体技能包（BYOK 或本地 LLM）
- **Plugin Marketplace (v0.3.0)**：插件商店

### 3.8.3 三阶段创作流程

```
规划 → 完善 → 改编
  │      │       └─ 书籍封面 / 配音片段 / 短视频
  │      └─ 细化结构 + AI 审阅
  └─ AI 智能体规划世界观/角色/情节
```

### 3.8.4 对月笙的启发

1. **"教学宪法"(Teaching Constitution) 概念**：将 `teaching_decision_log` 从纯记录器升级为可注入、人机可读的活文档。宪法（运行时）与日志（审计层）分离。
2. **Plugin Marketplace 模式**：Anti-AI-Tone 过滤器体现了反脆弱设计——引擎层承认自身局限，让生态补充。
3. **本地优先 + BYOK**：与月笙 R-029 安全规范一致，数据不出设备。

## 3.9 91Writing—纯前端 AI 小说创作工具

通过 WebFetch 获取了 [GitHub README](https://github.com/ponysb/91Writing) 和 [开发者掘金文章](https://juejin.cn/post/7559124639323979786)。Vue 3 + Element Plus + Pinia + Vite，MIT 开源，在线演示 https://xiezuo.91hub.vip。

### 3.9.1 架构演进：传统 → Agentic

开发者从 3,000 用户和 600 份反馈中总结：

| 模式 | 典型代表 | 优点 | 缺点 |
|:-----|:---------|:-----|:-----|
| **传统** | 91Writing v0.x、蛙蛙、星月 | 完全可控 | 依赖高质量提示词，操作复杂 |
| **工作流** | 全自动写作平台 | 效率高 | 零可控性，修改困难 |
| **Agentic (ReAct)** | 91Writing agentic 分支 | 对话驱动，最短路径 | 暂无 |

### 3.9.2 Agentic 架构（"就要创作"）

```
主专家（网文产品经理/任务分配）
  ├── 脑洞大神（创意点子）
  ├── 人设规划专家（角色卡生成）
  ├── 世界观规划专家（世界设定）
  ├── 事件线策划专家（情节线）
  ├── 正文创作大神（章节撰写）
  ├── 编辑润色大神（质量优化）
  └── 阅读评价专家（质量反馈）
```

- **模式**：ReAct（单 Agent 循环 + 多工具 + 子专家）
- **技术栈**：Node.js + Express + LangChain
- **特点**：通过对话即可创作，自动分配子专家

### 3.9.3 10 大智能工具

工具自治设计模式：
- **输入驱动**：参数最少化，输出多样化
- **模板变量系统**：结构化提示词 + 三层变量（内置/上下文/自定义）
- **上下文感知**：自动关联前 2 章内容
- **无状态、可组合、结果不可变**

### 3.9.4 对月笙的启发

1. **工具自治模式**：月笙的诊断工具也可以设计为"输入最小参数 + AI 自动分析"，降低使用门槛
2. **两级提示词入口**：项目级（全局）和系统级（预设）
3. **Agentic 交互**：对话驱动创作的理念可以借鉴到教学场景（学生用自然语言描述问题→系统自动路由）

```
  ├── nwProject.nwx     ← XML：项目结构 + 元数据
```


### 3.10.3 "100% free of AI slop"

核心原因：
1. **创作本质是个人表达**，AI 生成是"平均语言"——抹平个体差异
2. **辅助 vs 替代**：novelWriter 帮助组织写作，而非帮人写
3. **版权与伦理**：AI 训练数据使用未授权作品的担忧
4. **市场定位**：细分用户群体明确排斥 AI

### 3.10.4 对月笙的启示

1. **文件句柄机制**：月笙 `novel-chapters/` 下 `ch0001.txt` 应改为 UUID 命名，避免命名冲突
2. **延迟加载+LRU缓存**：`chapter.store.ts` 的 `contentCache` 应加容量上限
3. **内容与元数据分离**：正文纯文本存储，元数据 SQLite 存储
4. **增量索引引擎**：客户端标签提取（`@tag:`）可减少 AI 调用开销
5. **"不替写"是共同底线**：novelWriter 通过排除 AI 守住，月笙通过"诊断+教学"守住

### 3.11.1 CoachGPT—脚手架式学术写作助手

来源：arXiv:2506.18149v1，University of Delaware，SIGIR '25

#### 架构核心：11 阶段脚手架

```
预写作 → 资源识别 → 论题陈述 → 大纲构建 → 引言段 → 主体段 → 主体段收尾 → 结论段 → 通用修订 → 词汇评估 → 语法检查
```

每个阶段设计模式：用户输入 → AI 评估 → 反馈 → 用户修订 → AI 再评估（无限循环，用户不点击下一步则系统等待）

#### Prompt 工程策略

| 策略 | 示例 | 与月笙对比 |
|:-----|:------|:-----------|
| Persona Prompting | "Act as a writing coach" | 月笙三档态度（豆包/月笙如歌/sensei）更细粒度 |
| Limiters/Constraints | "You must not suggest any ideas or examples" | 月笙在 core-principles.md 有 7 条禁忌，但未在代码层硬约束 |
| Criteria-Based Feedback | off-topic / logical / strong 三级 | 月笙症候手册 P001-P010 更结构化 |
| Output Presentation | 降低认知负荷的分块输出 | 月笙 `---DIAGNOSIS_START---` 标记类似 |

#### 对月笙的启示

1. **脚手架结构同构性**：CoachGPT 的 11 阶段对应月笙的 5 阶段，本质都是将复杂任务拆为可控步骤
2. **三级评估 Prompt 模式**：可作为月笙诊断输出的简化参考
3. **"微小胜利"设计**：每个阶段完成后给正反馈——月笙可在每个教学子阶段结束时借鉴
4. **学术支撑**：论文引用的 Vygotsky (1978)、Schulhoff et al. (2024, The Prompt Report) 可作为月笙设计决策的学术引用

### 3.11.2 Khanmigo—苏格拉底式 AI 导师

Khan Academy 基于 GPT-4，服务 200M+ 学习者。

#### 核心架构：不给答案的三层工程化约束

| 层级 | 机制 | 具体实现 |
|:-----|:------|:---------|
| **系统 Prompt** | 硬编码约束 | "Never provide the answer. Never solve the problem. Ask guiding questions." |
| **请求过滤** | 脱敏与隔离 | 仅传 session-scoped 上下文 |
| **响应验证** | 安全分类器 | LLM 返回后用独立分类器检查是否违反苏格拉底约束 |
| **日志审计** | 行为追溯 | 所有交互留本地，不入第三方训练数据 |

直接答案损害 **40-60%** 学习保留率（Sweller et al., Cognitive Load Theory）。

#### 六层架构与对比

| 层 | Khanmigo | 月笙对应 |
|:---|:---------|:---------|
| 交互层 | 现有平台 UI | React + Zustand |
| 解析层 | 教育 NLP 微调 | 诊断解析器 |
| 生成层 | GPT-4 Omni | 任意 LLM（IPC 安全调用） |
| 知识检索 | RAG + 课程库 | 症候手册 + 动作库 |
| 安全过滤 | 规则+AI 语义分析 | （月笙缺少） |
| 对话管理 | DST 跟踪 | 状态机 + 症候锁定 |

#### 对月笙的启示

1. **响应后安全验证层**：月笙目前只在解析阶段做格式校验，缺少对"AI 是否违反教学原则"的二次验证。建议在 `diagnosis-parser.ts` 输出后增加规则验证
2. **量化评估指标**：引入诊断准确率、用户独立完成率、症候解决持久度等系统化指标
3. **关键参数外置**：症候权重、严重度降级阈值等外置为可配置项

### 3.11.3 Class Companion—AI 作业反馈平台

68,000+ 教师，170 万学生，2025 年 4 月被 Panorama Education 收购。

#### 六步工作流

```
教师创建作业+rubric → 发布 → 学生提交 → GPT-4 评估(秒级) → 学生修订 → 申诉/教师最终裁决
```

关键设计：**教师至上**（教师设置所有参数、覆盖所有 AI 评分），**Ditto AI 导师**（不给答案），**无限修订**，**申诉机制**。

#### 对月笙的启示

1. **"教师至上"角色模型**：教师设定参数、AI 执行、教师复审——直接适用于月笙的教师/学生/系统角色设计
2. **无限修订 + 即时反馈**：与月笙"多轮诊断→教学"循环天然匹配
3. **申诉机制**：学生对诊断结果提出异议→教师介入
4. **反作弊检测**：复制粘贴、标签离开、输入异常检测——月笙可参考

### 3.11.4 横向对比

| 维度 | CoachGPT | Khanmigo | Class Companion | 月笙写作教练 |
|:-----|:---------|:---------|:---------------|:-------------|
| **教学哲学** | 脚手架引导 | 苏格拉底式 | 教师主导 | 诊断→教学循环 |
| **AI 角色** | 写作教练 | AI 导师 | AI 批改助手 | 写作教练 |
| **阶段管理** | 11 阶段线性 | 自由对话 | 作业周期 | 5 阶段状态机 |
| **确定性** | 低（依赖 LLM） | 中（对话跟踪） | 中（rubric 约束） | **高**（状态机+锁定） |
| **隐私架构** | 云端 | 云端 FERPA | 云端 FERPA | **本地桌面** |
| **评估方式** | 人工评分 | 下题正确率 | AI 评分+教师覆盖 | 症候+训练评分 |

**核心定位差异**：月笙是唯一将"诊断→教学"作为核心循环而非辅助功能的平台。Khanmigo 和 Class Companion 都是"检测→反馈"的单向模式；CoachGPT 是线性脚手架。月笙的**循环迭代**（诊断→锁定→教学→再诊断）是区别所有三者的核心设计。
