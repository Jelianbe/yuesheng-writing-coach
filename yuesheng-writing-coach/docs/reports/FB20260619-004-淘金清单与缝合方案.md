## 五、最小可运行版本(MVP)缝合方案

### 5.1 目标

**跑起来一个能接后端、能走通教学对话的应用。** 不是完美版,是"能看到真数据、能发消息收回复、能走一次诊断"的版本。

### 5.2 缝合策略:archived 业务逻辑 + V6.2 视觉皮肤

核心思路:
1. **业务逻辑层**:全部用 archived 的(store 已就绪,组件逻辑已写完)
2. **视觉皮肤**:V6.2 的 CSS Module + 设计 token
3. **入口**:用 archived/layout/AppShell 替换当前空壳 AppShell

### 5.3 具体步骤(按依赖顺序)

#### Step 1:清理(15 分钟)
- 删除 `components_archived/v1/`(真死代码)
- 删除当前 `components/AppShell` + `left/center/right` 骨架(被 archived 替代)

#### Step 2:复活 layout(30 分钟)
- `components_archived/layout/` → `components/layout/`
- 修复 import 路径(批量替换 `components_archived/layout` → `components/layout`)
- 替换 AppShell 的 CSS 为 V6.2 视觉(沿用 variables.css token)

#### Step 3:复活 chat(1 小时)
- `components_archived/chat/` → `components/chat/`
- ChatView 采用**方案 A**:注释 EditPanel/EvaluationCard 渲染
- 修复 import 路径

#### Step 4:复活 training(30 分钟)
- `components_archived/training/` → `components/training/`
- 纯展示组件,修路径即可

#### Step 5:接 App.tsx(1 小时)
- 把 App.tsx 的 `void handleSendMessage` 真正接到 ChatView
- 让 archived/layout/AppShell 成为入口

#### Step 6:门禁验证(30 分钟)
- `npm run typecheck` — 修编译错误(主要是路径)
- `npm run test` — 确认 store 测试还绿

**预估总工作量:3-4 小时**(单人专注)

## 七、风险与注意事项

### 7.1 archived 组件的视觉是旧版

archived/layout 的 CSS 是 V6.2 之前的样式。复活后**视觉不会立刻是样板那样**,需要逐步换 CSS Module。但**功能会全部可用**。

**建议**:先接受"功能可用但视觉旧",跑起来后再逐步美化。不要追求"复活同时还要视觉完美",那会重新陷入泥潭。

### 7.2 一个隐藏的依赖陷阱

`stores/right-panel.store.ts`(当前在用)**反向依赖** `components_archived/layout/drawer-constants.ts`。如果删 archived 时不小心,会把这个 store 搞坏。

**处置**:淘金时先把这个 constants 文件移到 `stores/` 或 `shared/`,断开对 archived 的依赖。

### 7.3 几个 orphan store 可清理

`right-tools.store.ts`(无任何引用)、`paradigm.store.ts`(只被 archived v1 用)、`hint-store.ts`(只被 archived HintPanel 用)—— 复活后可评估是否清理。不是 MVP 阻塞项。
