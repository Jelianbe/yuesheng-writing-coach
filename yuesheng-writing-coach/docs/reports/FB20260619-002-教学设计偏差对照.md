## 一、核心判断(先说结论)

**当前样板没有覆盖 spec §4 的核心教学需要,而且偏差是结构性的,不是细节微调能解决的。**

具体说:

| 评估维度 | 结论 |
|:---|:---|
| **视觉皮肤**(配色、字体、间距、微交互) | ✅ 优秀,值得保留 |
| **布局骨架**(三栏 + 拖拽 resize) | ✅ 符合 spec §2.1 |
| **教学信息架构**(教学状态、进度、训练入口的主舞台位置) | ❌ **结构性偏差** |
| **教学核心交互**(训练发起、教学笔记、精通反馈) | ❌ **6 处缺失或走样** |

**我的建议:需要重新设计一版,但不是从零开始** —— 保留视觉皮肤和布局骨架,重做信息架构。具体走 A/B/C 哪条路,在第六部分给选项。

## 二、偏差逐条对照(共 6 条)

### 🔴 偏差 1:教学的"主舞台"错位 —— 进度数字被藏起来了

**spec §4.2 原文(教学进度条)**:
> 核心规则:数字位置 —— 每个阶段在诊断和教学之间,"3/7" = "诊断出的 7 个问题中已完成 3 个"
> 点击数字 → 展开详细教学概览
> 可展开状态指示器 —— 中间栏 header 左上角项目选择器旁,小标签显示当前系统状态

**spec §十五 验收标准**:
> 教学进度一致性 — 精通确认后 progressMap.resolvedIssues 正确 +1
> 进度跳动 — 手动测试:解决一个问题后 0/N 分子 +1

**当前 HTML 样板**:
- 中间栏 header 第 98-101 行:只有一个静态 badge,显示固定文字"教学中"
- **没有 0/N 数字**,**没有阶段显示**,**没有点击展开**
- 进度数字(如 "3/7")只在右栏"教学进度"工具里(HTML 第 944-950 行),用户必须主动点开工具才看得到

**影响等级**:🔴 **高** — 这是 spec 反复强调的"教学感"核心。spec §一明确写"用户感知不到教学感"是要解决的头号问题,而进度数字是最直接的"教学感"信号。当前样板把它藏起来,**spec 要解决的头号问题在样板里依然没解决**。

**为什么是结构性的**:这不是"加个 badge"的事 —— spec §4.2 要求进度数字**驱动中间栏 header 的视觉**,还要"点击展开教学概览",这是组件层级的事,改 mock 数据解决不了。

### 🔴 偏差 2:训练的发起路径完全错了 —— 从"主动作"降级成"被动筛选"

**spec §6.1 + §6.3 原文(左侧栏结构 + 训练交互流)**:
```
┌── 左侧栏 ──┐
│ 月笙[☰] [⚙]│  ← header
├─────────────┤
│ [训练]      │  ← 独立行,点击右侧栏展开技法列表
│ [对话] [项目]│  ← 并列行,切换左下列表
```
> §6.3 步骤 1:用户点击 `[训练]` → 右侧栏展开技法分类按钮
> §6.3 步骤 4:用户选中技法 → 系统创建新聊天会话,调用 IPC `training:createSession`
> 会话命名:"训练:{技法名}",**会话标记 `type: 'training'`**

**spec 附录决策记录**:
> 2026-06-16:左侧栏垂直分割为 [对话][项目][训练] 三标签 —— 讨论结论
> 2026-06-16:训练入口统一到聊天,面板不主动弹出 —— 教学案例 + 讨论

**当前 HTML 样板**:
- 左栏第 69-72 行:**只有 `[对话] [项目]` 两个 tab**,**没有独立的 `[训练]` 行**
- 训练会话靠 `title.includes('训练')` 字符串筛选(HTML 第 642、647、986、1033 行)
- `createTraining()`(第 687 行)是前端硬编码 push 到 SESSIONS 数组,**没调用任何 IPC**
- 会话**没有** `type: 'training'` 标记字段(SessionInfo 合约里也没有这个字段 —— 见 FB20260619-001 的 G-08)

**影响等级**:🔴 **高** — 这是**主操作路径的根本性错误**。spec 把训练设计成主动作(用户从 `[训练]` 发起 → 进技法目录 → 创建训练会话),样板做成了被动筛选(训练会话和普通会话混在一个列表里靠颜色区分)。

**为什么是结构性的**:
1. 左栏组件树不一样(2 tab vs 3 tab + 独立行)
2. 数据模型不一样(需要 SessionInfo.kind 字段)
3. 训练创建链路不一样(需要 training:createSession IPC,后端没有)
4. 这一条直接关联 FB20260619-001 的 G-04 + G-08 + G-10,三个缺口叠加

### 🔴 偏差 3:右栏的"查阅 vs 操作"定位被破坏

**spec §4.8 原文(右侧栏"不主动打开")**:
> 右侧栏是**查阅区,不是操作区**。三条硬规则:
> - 从不主动打开 — 右侧栏的打开/关闭完全由用户控制
> - AI 在聊天中"邀请" — AI 说"我准备了练习,去右侧看看?" → 用户说"好" → 用户手动打开
> - 已打开时自动切内容

**spec §4.7 原文(训练反馈回路)**:
> 如果右侧栏已打开 → 切换到进步摘要卡片
> 如果右侧栏未打开 → 不主动打开,AI 在聊天中告知

**当前 HTML 样板**:
- 右栏默认就是工具网格(HTML 第 921-927 行),**所有教学信息都封装在"工具"概念里**
- 用户必须主动点开"教学进度""学习日志""教学笔记""技法目录"四个独立工具,才能看到任何教学信息
- 没有任何"AI 邀请 → 用户确认 → 切换内容"的逻辑

**影响等级**:🟠 **中** — 样板的做法不算"错",但**偏离了 spec 的核心定位**。spec 把右栏设计成"信息陈列区"(像书架),样板做成了"工具集合"(像 IDE 的面板系统)。两者哲学不同:
- spec 哲学:教学信息是**被动的、查阅式的**,不强迫用户操作
- 样板哲学:教学信息是**主动的、工具化的**,用户需要"打开工具"才能获取

**关键问题**:这个偏差是**故意的还是无意的**?如果是故意的(你觉得工具化更符合实际),那应该**改 spec §4.8**;如果是无意的,那应该**改样板**。这需要你拍板。

### 🔴 偏差 4:教学笔记系统(`[模板]` 按钮)整个缺失

**spec §4.11 原文(教学笔记系统)**:这是一整节,核心设计:
```
聊天中 AI 判断某个教学话题已充分展开(3-5 轮无新信息)
  ↓
AI 在回复末尾以自然语言汇总讨论要点(预览),例如:
"主角的背景我们聊得差不多了:
 ↘ 主线:成为剑仙
 ↘ 出身:普通山村少年
 ↘ 奇遇:遇到隐居剑仙"
  ↓
回复末尾附带非侵入式按钮:[记录到教学笔记]
  ↓
用户点击 → 右侧栏展开"教学笔记"标签
          → 预览内容写入树状结构
          → 后续聊天中 AI 继续更新同一棵树
```

**spec 定义的数据结构**:
```typescript
interface ProjectSettingTree {
  projectId: string;
  treeGroup: string;       // 默认 'main',支持多树
  nodes: TreeNode[];
}
interface TreeNode {
  id: string;
  label: string;
  content: string;
  parentId: string | null;
  order: number;
  sourceSessionId: string; // 可追踪到聊天记录
  sourceMessageId: string;
}
```

**spec §2.4 按钮功能表**:
> `[模板]` | 输入框上方工具栏左侧 | 教学中AI自动汇总讨论要点,在对话末尾以预览形式展示,下方附带[记录到教学笔记]按钮

**当前 HTML 样板**:
- 第 114 行:只有一个静态 `<button>[模板]</button>`,**无 onclick,无任何交互**
- **没有预览-确认流程**
- **没有树状结构渲染**(spec 附录C 推荐用 react-arborist,样板里完全没有)
- **没有 ProjectSettingTree / TreeNode 数据**

**影响等级**:🔴 **高** — 这是 spec §4 里**最重要的教学产出物可视化机制**。它的设计意图是:**让对话中的知识沉淀成可查阅的资产**。没有它,月笙就只是一个聊天工具,每次对话结束知识就散落在聊天记录里,用户无法回看"我和教练讨论出了什么"。

**为什么是结构性的**:
1. 需要新的数据模型(ProjectSettingTree / TreeNode)
2. 需要新的 IPC(projectSetting:* 或在 project:* 扩展)
3. 需要树组件(react-arborist)
4. 需要 AI prompt 配合(在合适时机生成预览)
5. 这是一整个子系统,不是补一个按钮的事

**spec §9.1 原文(progress.store)**:
```typescript
displayStatus: 'idle' | 'diagnosing' | 'teaching' | 'reflecting' | 'completed';
```

**spec §4.12 原文**:
> 现有的 `displayStatus: idle | diagnosing | teaching | reflecting | completed` 能够表达所有有效状态

**当前 HTML 样板**:

## 四、为什么这些偏差是"系统性"的,不是"遗漏"

我想诚实地指出一个模式:**这 6 处偏差不是零散的疏忽,它们有一个共同的根源**。

**根源:样板把月笙做成了"带教学工具的聊天应用",而 spec 要的是"以聊天为界面的教学应用"。**

这两个定位的差异:

| 维度 | 样板实际定位 | spec 目标定位 |
|:---|:---|:---|
| 中间栏 | 聊天主舞台,教学是附属 | **教学主舞台,聊天是教学媒介** |
| 右栏 | 工具集合,用户主动取用 | 信息陈列区,AI 邀请后查阅 |
| 训练 | 已有会话的分类筛选 | **独立的教学主动作入口** |
| 进度 | 藏在工具里的数据 | **中间栏可见的核心反馈** |
| 知识沉淀 | 没有 | 教学笔记树(对话产出物) |

这个根源差异导致:**不管你怎么微调样板,只要不重做信息架构,spec §4 的教学闭环就建立不起来**。这就是为什么你"头疼" —— 不是因为哪一处没改好,而是因为整体的"教学感"出不来,而你又说不清具体哪里不对。

## 五、spec 自身的内部矛盾(必须先解决)

在出新稿之前,我必须指出 **spec 自己也有 3 处内部矛盾**,这些矛盾是导致样板走样的部分原因(样板作者复制 spec 时,每个矛盾点都只能选一边):

### 矛盾 1:态度档位用词不一致

| spec 位置 | 用词 |
|:---|:---|
| §4.4(画像 attitudeLevel) | `'gentle' \| 'balanced' \| 'direct'` |
| §8.2(决策日志) | `'gentle' \| 'balanced' \| 'direct'` |
| §5.2(态度灯表格 UI) | `🟢豆包 / 🟡月笙如歌 / 🔴sensei` |

**数据层用 direct,UI 层用 sensei**。这就是 FB20260619-001 缺口 G-05 三处打架的根源。

### 矛盾 2:training:createSession 在 IPC 清单里缺失

- §6.3 步骤 4 明确写"调用 IPC `training:createSession`"
- 但 §10.1(需新增 IPC)清单里**没有 training:createSession**
- 现有 training.contract.ts 里**也没有**这个通道

spec 自己引用了一个不存在的 IPC。这就是 G-04 的根源。

### 矛盾 3:项目层级 spec 内部没说清

- §3.1 数据模型:用户 → 项目 → 章节 / 会话 / 诊断表(三层:project → manuscript → chapter 隐含)
- §6.4:点击章节 → 右栏展开作品编辑器(暗示 manuscript 层存在)
- 但 spec 全文**从未明确 manuscript 这一层是否保留**

这就是 G-09 的根源。

**这三个矛盾必须在新稿之前解决**,否则新稿一样会走样。

## 六、三条出路(A / B / C)

基于以上分析,我给你三个方向选择:

### 方向 A:回归 spec(推荐) — 重做信息架构,保留视觉皮肤

**做法**:
- 视觉皮肤(配色/token/微交互)完全沿用当前样板
- **重做信息架构**:中间栏成为教学主舞台(进度数字、状态机、教学笔记预览都进中间栏)
- 左栏加回 [训练] 独立行
- 右栏从"工具集合"改回"查阅区"
- 补齐教学笔记树系统
- 先解决 spec 的 3 处内部矛盾

**工作量**:中等偏大。需要新出一版 HTML 设计稿(v7),但视觉工作量小(复用 skin),主要是信息架构重排。

**风险**:如果 spec 某些设计(如训练独立行)你觉得过重,会返工。

### 方向 B:修订 spec — 承认样板的工具化定位,反向改 spec

**做法**:
- 保留当前样板的信息架构(右栏工具集合、训练被动筛选)
- **修改 spec §4.8 / §6.1 / §6.3**,把"查阅区"改成"工具区",把训练从主动作改成筛选
- 接受"教学感"靠右栏工具体现,不靠中间栏

**工作量**:小。改 spec 文字 + 微调样板。

**风险**:**你最初说的"不满足设想"恰恰就是这个方向** —— 如果走 B,你还是会觉得教学感不够。这条路是放弃 spec 的核心教学理念换工作量。

### 方向 C:折中 — spec 核心闭环必须实现,布局沿用样板

**做法**:
- 保留三栏布局和视觉皮肤
- **必须实现**:偏差 1(进度进中间栏)、偏差 2(训练主动作)、偏差 4(教学笔记)
- **可以妥协**:偏差 3(右栏保留工具化)、偏差 5(状态机进 badge)、偏差 6(文件上传延后)
- 先解决 spec 3 处内部矛盾

**工作量**:中等。需要新出一版 HTML,但范围比 A 小。

**风险**:需要你明确"哪些 spec 条款是不可妥协的红线"。

## 七、我的推荐

**推荐方向 A**,理由:

1. **方向 B 会让你继续头疼** —— 你说"不满足设想",B 就是延续现状
2. **方向 C 需要你做大量取舍决策**,在你还没看到完整新稿之前,取舍很容易做错
3. **方向 A 工作量看似最大,但最彻底** —— 而且视觉皮肤复用,实际主要工作是信息架构重排
