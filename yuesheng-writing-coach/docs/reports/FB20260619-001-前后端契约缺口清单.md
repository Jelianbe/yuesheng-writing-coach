### 🔴 G-01 学习日志数据源完全虚构

**前端假设**(HTML 第 345 行):
```js

  { date:'2026-06-17', entries:[
```

**处置建议**:**改前端**。学习日志工具(H-03)的整个数据模型必须从"日志条目"重写为"症候趋势折线"。如果一定要保留"日志"语义(有时间、有 note),则**需决策是否新增 `learningLog:list` 通道** —— 这会是后端工作。

### 🔴 G-04 训练会话创建链路后端未建模

**前端假设**(HTML 第 687 行 `createTraining(techName)`):
```js
// 选技法 → 直接 push 一个新 session,title = '训练: ' + techName
SESSIONS.push({ id:newId, title, createdAt, updatedAt, messageCount });
SESSION_MESSAGES[newId] = mockMessages;  // 训练对话内容直接塞进 session 消息

```

**后端真相**:
- `TrainingRecord`(`types-training.ts`)和 `SessionInfo`(`session.contract.ts`)是**两个独立对象**,合约层**没有定义它们的关联字段**。
- 真实训练链路是:
  ```
  training:recommend → training:assign(challengeId) → TrainingRecord
                                                        ↓
                              ??? ← 这一步合约里没有
                                                        ↓
                              session:id(训练对话归属哪个 session?)
  ```
- `training:submit` / `training:evaluate` 入参都带 `sessionId` + `recordId`,但**没有任何合约规定"创建训练时新建 session"还是"复用当前 session"**。

**处置建议**:**需决策**(Phase I)。三个可选方案:
1. 训练 = 新建 session,前端 `session:create` 后 `training:assign`,session id 挂到 record 元数据
2. 训练 = 复用当前 session,TrainingRecord 是 session 内的"训练子流"
3. 新增 `training:create` 端点原子化封装"建 session + 建 record"

HTML 假设的是方案 1,但**这是前端拍的板,后端没认**。必须先和后端 owner 对齐。

**这是整个清单里最危险的一条**,因为三个地方各自为政,运行时不会报错但行为完全错乱。

**三处定义对比**:

| 位置 | 定义 | 来源 |
|:----:|:----:|:----:|
| `src/shared/types/types-config.ts:4` | `'doubao' \| 'yuesheng' \| 'direct'` | **权威后端契约** |
| `src/renderer/stores/ui.store.ts:24` | `'doubao' \| 'yuesheng' \| 'sensei'` | V6.2 新建 store |
| `dev-docs/previews/...v6.2.html` `data-lv` 属性 | `'doubao' \| 'yuesheng' \| 'direct'` | HTML 样板 |

### 🟠 G-07 "当前诊断"缺少直接获取入口

**前端假设**(HTML 第 318-328 行 `CURRENT_DIAGNOSIS`):
- 注释写 `// DiagnosisEntry (diagnosis.contract.ts)`
- 用法:教学笔记工具直接读 `CURRENT_DIAGNOSIS.syndromes` 展示"最新诊断"

**后端真相**:
- `DiagnosisEntry` 类型 ✅ 存在且结构对得上
- **但没有任何"获取当前会话最新一条诊断"的语义入口**
- 只有 `diagnosis:query`({sessionId, limit, offset})分页历史 —— 前端要"最新"必须 `limit:1, offset:0` 自己取
- 另有 `diagnosis:update` **事件**(主进程推送),前端可订阅实时更新

**处置建议**:**改前端**。前端"教学笔记"工具应该:
1. 初始挂载时 `diagnosis:query({sessionId, limit:1})` 拉最新
2. 同时订阅 `diagnosis:update` 事件,收到推送就刷新
3. 不要假设有 `diagnosis:getCurrent` 这种入口

这是 spec §13.5 事件驱动架构的正确用法。

### 🟠 G-08 训练会话筛选靠 `title.includes('训练')` 字符串匹配

**前端假设**(HTML 多处,例如 642、647、986、1033 行):
```js
const isTrain = session.title.includes('训练');
SESSIONS.filter(s => s.title.includes('训练'))
```

**后端真相**:

### 🟡 G-10 [训练] Tab 的归属与 spec 冲突

**前端假设**(HTML 第 70-72 行):只有 `[对话] [项目]` 两个 tab,训练会话混在对话列表里靠颜色区分。

**后端真相**:不涉及后端,纯设计层冲突。

**spec §2.4 明确规定**:
> `[训练]` | 左侧栏标签区上方独立行 | 点击后右侧栏展开技法分类列表,用户选技法后新建训练会话

**矛盾**:HTML 把 [训练] 从"上方独立行入口"降级成了"对话列表里的颜色筛选"。spec 的意图是训练是**主动作**(从技法目录发起),HTML 的实现是**被动筛选**(从已有会话里挑)。

**处置建议**:**需决策**(设计级)。两种方向:
1. 回归 spec:加独立的 [训练] 入口 → 点开右栏技法目录 → 选技法 → 建训练
2. 维持 HTML 现状:修改 spec §2.4,承认训练是对话的子类型

我个人倾向方向 1,因为 spec §一的核心理念是"教学优先",训练作为教学的核心动作应该有独立入口,不该藏在对话里。但这是设计决策。

## 第二部分:架构层缺口(交互模式 vs 事件流)

### 🟠 G-11 中间栏消息渲染假设静态拉取,后端是事件流

**前端假设**(HTML `renderCenter` 第 829 行):
```js
const msgs = SESSION_MESSAGES[chatSessionId] || [];
// 点开会话 → 全量渲染静态数组
```

**后端真相**(`chat.contract.ts` + `event-map.ts`):
- `chat:send` 只返回 `{acknowledged, messageId}` —— **不是消息内容**
- 真正的 AI 回复通过 `chat:stream:data` 事件**流式推送**:`{sessionId, chunk: string}`
- 推送结束发 `chat:stream:end`:`{sessionId, fullResponse, messageId}`
- 用户发消息后,**前端必须订阅事件拼接 chunk**,不能等 invoke 返回

**影响**:迁移到 React 时,中间栏组件**不能**是"props 传 messages 数组就完事",必须是:
1. 挂载时 `session:getMessages` 拉历史
2. 用户发送时订阅 `chat:stream:data` 流式追加
3. 收到 `chat:stream:end` 落库
4. 订阅 `diagnosis:update` / `teachingState:updated` 触发右栏刷新

这是**架构级差异**,不是细节。Phase J React 迁移时这是核心难点。

**处置建议**:**改前端**(Phase J-04)。`useIpc` hook 必须区分 invoke 和 event 两类 API,中间栏 store 必须支持流式 append。

### 🟠 G-12 `teachingState:mastery` 事件后端自己有 bug

**前端假设**:训练达成精通后,UI 收到事件刷新"已攻克"标记。

**后端真相**(Agent 报告确认):
- `TeachingStateApi.mastery` 合约 ✅ 定义了
- `IPC_CHANNELS.TEACHING_STATE_MASTERY` ✅ 定义了
- 但 `ALLOWED_EVENT_CHANNELS` 白名单 ❌ **没有它**
- `EventChannelMap` ❌ **也没有它**

**后果**:即使前端正确订阅,preload 白名单会把 `teachingState:mastery` 事件**直接丢弃**,前端永远收不到。这是后端 SEC-DEBT-3(三份白名单不一致)的具体表现之一。

**处置建议**:**改后端**(Phase I,并入 SEC-DEBT-3 修复)。在 `constants.ts` 的 `ALLOWED_EVENT_CHANNELS` 和 `event-map.ts` 的 `EventChannelMap` 同步补上 `teachingState:mastery`。前端无责。

### 🟡 G-13 `diagnosis:update` 同名既是 invoke 又是 event

**前端假设**:可能分不清该 invoke 还是订阅。

**后端真相**(`diagnosis.contract.ts`):
- invoke 通道 `diagnosis:update`(DiagnosisApi.update):renderer 主动写诊断
- event 通道 `diagnosis:update`(DiagnosisApi.updated):main 推送诊断更新
- **字面量完全一样**,都是 `'diagnosis:update'`

**风险**:前端代码 `ipcRenderer.on('diagnosis:update')` 会同时收到自己 invoke 的回声 + 主进程主动推送,容易重复处理。

**处置建议**:**需决策**。两种方向:
1. 改后端:event 通道改名 `diagnosis:updated`(过去式),和 invoke `diagnosis:update` 区分 —— 推荐,语义更清晰
2. 改前端: invoke 后忽略同 sessionId 的下一拍事件(脆弱)

涉及契约改动,建议走 ADR。

回到你最初的问题 —— "前端的事情卡住很久""设计方面和后端契合度都让我头疼"。
