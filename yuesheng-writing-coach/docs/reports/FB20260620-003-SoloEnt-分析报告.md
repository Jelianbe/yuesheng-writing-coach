## 1. 产品全景画像

### 1.1 产品定位

SoloEnt 定位为 **"AI-native 桌面写作工作空间"**，面向严肃故事创作者（小说家、剧本作者、游戏叙事设计师）。其核心差异化在于：

- **Local-first（本地优先）**：所有数据在设备端运行，不上传云端
- **免费可用**：免费版开放核心功能，付费 Plans 从 $9.9/月起
- **一人工作室**：品牌口号 "Start a Solo Entertainment Studio from Your Story"

### 1.2 产品架构全景

### 1.3 核心理念三支柱

| 理念 | 含义 | 表现 |
|:----|:-----|:-----|
| **以人为本** | AI 是增强创造力的助手，不是替代品 | 不替写、不替决定 |

## 2. 核心机制对比

### 2.1 SoloEnt.md "故事宪法" vs INKOS "真相文件"

两者都是 **AI 系统外置状态管理** 的工程方案，核心目标一致：**解决长文本创作中的 AI 遗忘和逻辑不一致问题**。但在实现哲学上有根本差异。

#### 对比总表

| 维度 | SoloEnt "故事宪法" | INKOS "真相文件" |
|:----|:-------------------|:------------------|
| **文件形式** | 单一 Markdown 文件 (`SoloEnt.md`) | 7 个结构化 JSON 文件 (`story/state/*.json`) + SQLite 记忆库 |
| **数据模型** | 松散、叙事驱动的文本描述 | 严格模式——Zod schema 校验、不可变状态更新 |
| **更新方式** | "活文档"（living document），人机协作维护 | 自动管线——Observer 提取 + Reflector 生成 JSON delta |
| **目标用户** | **人**——创作者可读可写 | **机器**——AI Agent 优先，Markdown 投影仅供人类审阅 |
| **哲学定位** | 宪法（Constitution）——根本大法，定方向 | 真相（Truth）——事实源，防幻觉 |
| **粒度** | 粗粒度——世界观、角色、叙事一致性 | 细粒度——7 类：世界状态/角色矩阵/资源账本/未闭合伏笔/章节摘要/支线进度/情感弧线 |
| **校验机制** | 隐式——依赖创作者自行维护 | 显式——33 维审计检查，不通过则打回修订 |
| **上下文管理** | 注入 AI prompt 作为长期记忆 | 每章生成前按需注入相关切片，写入后回写更新 |
| **逆向工程** | 不支持 | 支持——导入已有小说文本，自动解析重构世界观 |
| **开源** | 未开源（商业产品） | 开源（AGPL，npm `@actalk/inkos`） |

#### 核心差异分析

**1. 设计哲学差异**

```
SoloEnt:     宪法模型 ── 定规则、管方向、人主导
               │
               └── 类比：美国宪法（原则性、可解释）
               
INKOS:       真相模型 ── 存事实、防幻觉、机器主导
               │
               └── 类比：数据库 Schema（精确性、不可篡改）
```

SoloEnt 的 "故事宪法" 更像是一份 **创作者的意图宣言**——它规定"这个世界的规则是什么"，而非"这个世界当前的状态是什么"。它服务于 **人的创作过程**，帮助创作者保持自我一致性。

INKOS 的 "真相文件" 则是一套 **工程化的状态管理系统**——它将"故事事实"完全外置为结构化数据，AI 不依赖自身的上下文窗口，而是从真相文件中读取事实。它服务于 **AI 的自动化生产**，目标是让机器生成的长篇内容不自相矛盾。

**2. 工程复杂度差异**

INKOS 的工程复杂度远高于 SoloEnt：
- 7 类分离文件 + Zod Schema 校验 + 不可变更新
- 33 维审计管线 + 自动修订循环
- multi-agent 管线（Radar → Planner → Composer → Architect → Writer → Observer → Reflector → Normalizer → Auditor → Reviser）

SoloEnt 则更轻量：
- 单文件 Markdown
- Rules/Workflows/Skills 作为自定义层
- 强调创作者控制，而非自动化

**3. 适用场景差异**

| 场景 | SoloEnt 更优 | INKOS 更优 |
|:----|:------------:|:----------:|
| 严肃文学创作（人主导） | V | |
| 网络小说批量生产（机器主导） | | V |
| 创作者需要灵活调整设定 | V | |
| 需要严格逻辑一致性的长篇 | | V |
| 创作新手 | V | |
| 技术型创作者/工程师 | | V |

## 3. Plugin Marketplace 设计价值分析

### 3.1 功能概述

SoloEnt v0.3.0 引入的 Plugin Marketplace 支持"一键安装"插件，提供：
- **章节审阅工具**（Chapter Review Tools）
- **Anti-AI-Tone 过滤器**（消除 AI 味）
- 插件生态持续扩展中

### 3.2 设计价值五维分析

#### 维度一：能力边界扩展（Capability Extension）

Plugin Marketplace 使 SoloEnt 从"封闭功能集"进化为"开放平台"。核心意义在于：

```
Before:  ┌──────────────────────────┐
         │  SoloEnt 内置功能集       │
         │  (有限、固定、供应商定义)  │
         └──────────────────────────┘

After:   ┌──────────────────────────┐
         │  SoloEnt 核心引擎         │
         ├──────────────────────────┤
         │  Plugin A │ Plugin B │ … │  ← 社区贡献
         ├──────────────────────────┤
         │  Plugin C │ Plugin D │ … │  ← 第三方开发者
         └──────────────────────────┘
```

**类比**：类似 VS Code 的 Extension Marketplace——核心 IDE 提供基建，生态提供功能。

#### 维度二：垂直场景覆盖（Vertical Coverage）

故事创作是高度异质化的领域：

| 创作类型 | 需要的工具 | 通用编辑器能否满足 |
|:---------|:-----------|:-----------------:|
| 奇幻世界观 | 地图生成、种族/魔法系统追踪 | 部分 |
| 悬疑推理 | 线索板、时间线管理、红鲱鱼追踪 | 否 |
| 爱情小说 | 情感弧线追踪、关系图谱 | 否 |
| 科幻 | 科技树、物理规则一致性检查 | 否 |
| 历史小说 | 年表管理、史实校验 | 否 |

Plugin Marketplace 让 SoloEnt 可以 **不自己造所有垂直工具**，而是通过生态覆盖长尾需求。

#### 维度三：社区网络效应（Network Effect）

```
用户数增长  ──→  插件需求多样化
                     │
                     ↓
             更多开发者加入
                     │
                     ↓
             插件数量/质量提升
                     │
                     ↓
             用户留存率上升  ──→  用户数增长（闭环）
```

#### 维度四：反脆弱性设计（Anti-Fragile）

"A nti-AI-Tone 过滤器" 这类插件体现了深度思考：

- AI 写作助手面临的终极矛盾是 **"AI 本身的味道"**
- SoloEnt 选择 **不试图在引擎层消除 AI 味**
- 而是通过插件机制让社区来 **解决这个引擎层不想/不能解决的问题**

这是一种 **反脆弱的设计**——承认核心引擎的局限，用生态弥补。

#### 维度五：与月笙项目的差异化对比

| 维度 | SoloEnt Plugin Marketplace | 月笙写作教练 |
|:-----|:--------------------------|:-------------|
| 插件接口 | 公开 API，第三方可开发 | 暂无插件体系 |
| 核心诉求 | 扩展创作功能 | 扩展教学策略 |
| 可借鉴点 | 插件作为"教学策略包"分发 | Rules/Workflows 概念可用于定义教学流程 |
| 风险 | 碎片化体验 | 当前不需要——MVP 阶段聚焦核心 |

### 3.3 关键设计决策评估

**好的决策**：
- 使用 `Rules / Workflows / Skills` 作为底层抽象——这三者分别对应 **规则定义 / 流程编排 / 能力封装**，比单纯的"插件"更灵活
- 一键安装——降低使用门槛

**风险/不足**：
- 插件质量管控机制未公开（如何防止低质量插件破坏创作体验？）
- 早期阶段（v0.3.0）就引入 Marketplace 是否会分散核心体验打磨的精力？

## 4. "故事宪法"对月笙教学决策日志的启发

### 4.1 月笙当前的教学决策日志设计

从代码和数据库 Schema 看，月笙的 **teaching_decision_log** 当前设计为：

```
teaching_decision_log
├── decision_id      (PK, UUID)
├── session_id       (FK → sessions)
├── syndrome_id      (关联诊断症候)
├── strategy_chosen  (教学策略选择)
├── reason           (决策理由)
├── student_state_json (学生状态快照)
├── decided_at       (决策时间)
├── outcome          (预留——效果评估)
├── outcome_at       (预留)
└── notes            (预留)
```

当前阶段（Phase 1）的设计哲学是 **"写不读"**——只积累数据，不开放读取通道。这相当于一个 **纯记录器**，尚未形成闭环。

### 4.2 故事宪法 vs 教学决策日志

| SoloEnt 故事宪法 | 月笙教学决策日志 | 差异本质 |
|:-----------------|:----------------|:---------|
| 活文档，持续更新 | 静态记录，追加写入 | 前者是 **主动维护的状态**，后者是 **被动积累的日志** |
| 创作者可读可写 | 系统内部只写 | 前者是 **协作工具**，后者是 **审计痕迹** |
| 决定"故事世界的规则" | 记录"教学的决策" | 前者是 **规范**，后者是 **轨迹** |
| 作为 AI 长期记忆注入 | 作为统计分析的原始数据 | 前者是 **运行时依赖**，后者是 **离线分析源** |

### 4.3 核心启发：从"决策日志"走向"教学宪法"

**启发点 1：引入"教学宪法"概念**

月笙的 `teaching_decision_log` 可以演进为 **"教学宪法"**——不仅记录决策本身，还维护一个 **结构化、可读、可注入到 AI Prompt 的教学规则文件**。

```
┌───────────────────────────────────────────────────────┐
│              月笙 "教学宪法" 设计建议                      │
├───────────────────────────────────────────────────────┤
│                                                        │
│  teaching_constitution.md（教学宪法）                    │
│  ├── 当前学生画像（student profile snapshot）             │
│  ├── 活跃症候列表（active syndromes with status）          │
│  ├── 已用策略及效果（strategy effectiveness history）      │
│  ├── 教学规则（pedagogical rules）                       │
│  └── 禁忌事项（anti-patterns / past failures）            │
│                                                        │
│  ↑ 运行时写入（诊断流水线更新）                              │
│  ↓ 运行时读取（注入 AI System Prompt）                     │
│                                                        │
├───────────────────────────────────────────────────────┤
│  teaching_decision_log（决策日志 — 审计层）               │
│  └── Phase 1 写不读 → Phase 4+ 回流优化                 │
└───────────────────────────────────────────────────────┘
```

**设计原则**：
- **宪法（constitution）** 负责"当前应该怎么做"——运行时、可读、可注入
- **日志（log）** 负责"过去做了什么"——审计、离线分析、回流优化

**启发点 2：结构化学生状态快照**

月笙当前的 `student_state_json` 是一个 JSON 字段，但缺乏标准化 Schema。

借鉴 SoloEnt.md 的"活文档"思路，可以将学生状态结构化为：

```typescript
// 建议：教学宪法数据结构
interface TeachingConstitution {
  // 版本控制
  version: string;
  updatedAt: number;

  // 当前学生画像
  studentProfile: {
    confidence: 'low' | 'neutral' | 'high';
    frustrationCount: number;
    relapseSyndromes: string[];  // 反复出现的症候
    currentStage: string;
    effectiveStrategies: Record<string, number>;  // 策略→效果评分
  };

  // 活跃教学规则
  activeRules: Array<{
    condition: string;    // 触发条件
    strategy: string;     // 建议策略
    priority: number;     // 优先级
    lastApplied: number;  // 最后应用时间
  }>;

  // 禁忌事项
  antiPatterns: Array<{
    syndromeId: string;
    failedStrategy: string;
    failureReason: string;
    recordedAt: number;
  }>;
}
```

**启发点 3：AI Prompt 注入策略**

SoloEnt 将 SoloEnt.md 作为 AI 的长期记忆注入 prompt。月笙可以采用类似策略：

```
## 当前教学宪法（Teaching Constitution）

### 学生画像
- 信心水平: neutral
- 当前阶段: P3_GUIDED_PRACTICE
- 反复症候: 细节冗余 (复发 3 次), 对话标签单一 (复发 2 次)

### 已生效教学策略
| 症候 | 当前策略 | 效果 | 应用次数 |
|------|---------|------|---------|
| 细节冗余 | 对比示范法 | 有效 (评分 4/5) | 3 次 |

### 规则
- 如果用户信心 < low，优先使用鼓励策略
- 如果某症候复发 > 2 次，切换教学策略
```

**启发点 4：区别"宪法"与"日志"的生命周期**

| | 教学宪法 (Constitution) | 决策日志 (Decision Log) |
|:--|:------------------------|:----------------------|
| 更新方式 | 原地更新（upsert） | 追加写入（append-only） |
| 读取频率 | 每次 AI 调用前读取 | 离线分析时查询 |
| 可读性 | 人机都可读 | 人类需工具辅助 |
| 数据量 | O(1) — 固定大小 | O(n) — 随使用增长 |
| 容错 | 允许近似值 | 要求精确记录 |

### 4.4 与现有代码的兼容性

这项演进 **不破坏现有 Phase 1 设计**：

- `teaching_decision_log` 表继续作为审计层存在
- 新增的"教学宪法"作为 **运行时缓存文件**（可存为 SQLite 的单独表或 JSON 文件）
- 现有 `decision.service.ts` 的 record 方法保持不变
- 新增一个 `TeachingConstitutionService` 负责宪法的读取/更新/注入

## 5. 三阶段创作流程对应的工程架构分析

### 5.1 流程概述

SoloEnt 定义了三个创作阶段：

```
阶段 1: 规划故事 ──→ 阶段 2: 完善结构 ──→ 阶段 3: 改编格式
  │                    │                     │
  ▼                    ▼                     ▼
AI 智能体辅助        AI 审阅              多格式输出
世界观/角色/情节    细化/审阅/迭代        书籍封面/配音/短视频
```

```
│                    │ Generator  │  │ Generator        │         │
│                    └────────────┘  └──────────────────┘         │
└──────────────────────────────────────────────────────────────────┘
```

### 5.3 工程架构核心模式

从架构角度分析，SoloEnt 采用了三个关键模式：

#### 模式 1：Pipeline + State Store（管线 + 状态仓库）

```
Input → [Stage 1 Pipeline] → Update State → [Stage 2 Pipeline] → ...
                                  ↑
                          SoloEnt.md (State Store)
```

这与 INKOS 的 **"真相文件 + 多 Agent 管线"** 模式同构。核心洞见是：
- **创作是一个状态转换过程**，不是一次性生成
- **状态必须在外部维护**，不能依赖模型上下文窗口
- **每个阶段都是对状态的转换/增强**

#### 模式 2：Adapter Pattern（适配器模式）用于输出

阶段 3 的本质是适配器模式：

```
                  ┌─────────────┐
                  │  Book Cover  │ ← 封面适配器
                  │  Adapter    │
                  ├─────────────┤
Story Canonical ──┤  Audio      │ ← 音频适配器
(标准文本格式)      │  Adapter    │
                  ├─────────────┤
                  │  Video      │ ← 视频适配器
                  │  Adapter    │
                  └─────────────┘
```

关键设计决策：**统一中间表示（Canonical Format）**。所有输出格式都从一个标准文本格式转换而来，而非各自为政。

#### 模式 3：Agent-as-a-Service（智能体即服务）

AI 智能体不是嵌入在流程中的"魔法按钮"，而是：
- 作为 **独立服务** 存在
- 通过 Rules/Workflows/Skills 配置行为
- 可以被用户自由编排

### 5.4 与月笙工程架构的对照

| 架构层 | SoloEnt | 月笙写作教练 | 可借鉴程度 |
|:-------|:--------|:------------|:----------|
| **状态管理** | SoloEnt.md（文件级） | Zustand store + SQLite | 高——月笙可考虑"教学宪法"文件 |
| **流程管线** | Rules/Workflows/Skills | Teaching State Machine | 中——月笙状态机已是管线模式 |
| **AI 集成** | BYOK + 本地 LLM + 内置模型 | DeepSeek API 调用 | 低——SoloEnt 的 local-first 是差异化 |
| **插件系统** | Plugin Marketplace | 无 | 中——未来月笙可支持"策略包" |
| **输出适配** | 多格式输出管线 | 无输出层 | 低——月笙是教学工具，不是创作工具 |
| **用户控制** | 完整的自定义管线 | 态度档位+安全词 | 高——月笙可引入"教学规则"自定义 |

## 6. 综合评估与策略建议

### 6.1 SoloEnt 的优势

1. **本地优先**：隐私是强卖点，尤其对专业创作者
2. **故事宪法**：轻量级状态管理，比 INKOS 更贴近创作者的思维模式
3. **Plugin Marketplace**：平台化思维，借力社区
4. **BYOK 支持**：用户自带 Key，降低运营成本，避免供应商锁定
5. **三阶段覆盖**：从构思到改编的全流程闭环

### 6.2 SoloEnt 的风险

1. **新人用户门槛**：Rules/Workflows/Skills 的概念对非技术用户可能较陡峭
2. **生态冷启动**：Plugin Marketplace 在早期阶段面临鸡和蛋问题
3. **本地 LLM 性能**：依赖用户本地硬件，体验参差不齐
4. **竞品挤压**：Sudowrite 等成熟产品已有社区基础和品牌认知

### 6.3 对月笙写作教练的具体建议

**优先级 P0（立即采纳）**：

1. **引入"教学宪法"概念**，与"决策日志"分离：
   - 教学宪法 = 运行时/可注入/人机可读
   - 决策日志 = 审计层/追加写入/离线分析

2. **结构化学生状态**：当前 `student_state_json` 过于随意，应定义 TypeScript Schema

3. **AI Prompt 注入优化**：将教学宪法结构化注入 System Prompt，替代当前的简单历史诊断注入

**优先级 P1（未来 1-2 个月）**：

4. **能力容器化**：借鉴 SoloEnt 的 Skills 概念，将教学能力封装为独立模块

5. **教学流可视化**：借鉴三阶段流程，将教学状态机可视化呈现给用户

**优先级 P2（长期规划）**：

6. **策略插件化**：借鉴 Plugin Marketplace，设计"教学策略包"分发机制

7. **跨会话记忆增强**：借鉴 SoloEnt.md 的"活文档"思路，实现跨会话的学生模型持久化

### 6.4 核心认知总结

```
AI 写作工具的核心矛盾：
  "模型上下文窗口装不下长篇"
  解决：外置状态（SoloEnt.md / Truth Files）

AI 教学工具的核心矛盾：
  "模型记不住学生的历史"
  解决：外置教学宪法（Teaching Constitution）

本质相同的问题，可以借鉴相同的解法：
  ┌─────────────────────────────────┐
  │  Long-term Memory Externalization │
  │  （长期记忆外置化）               │
  │                                  │
  │  写作领域 → SoloEnt.md           │
  │  写作领域 → INKOS Truth Files    │
  │  教学领域 → 教学宪法（建议）      │
  └─────────────────────────────────┘
```
