## 一、核心原则

1. **单一正本** — `TASK-CHAIN.md` 是唯一任务注册中心，所有任务必须在其中登记
2. **顺序依赖** — 每个任务必须是前一个任务的延续/总结，或者是后一个任务的基础/前置条件
3. **状态可追踪** — 每个任务必须在自身文件头和 TASK-CHAIN.md 中包含明确状态，变更时同步更新
4. **审计驱动** — 任务状态基于代码实际完成度，而非文档声明
5. **前后端显式标注** — 每个任务必须明确列出前端组件/后端服务的分工，不得隐含 UI 工作
6. **格式统一** — 所有任务文件（无论已完成或待执行）遵循同一模板结构

## 四、任务状态定义

### 状态流转图

```
                    ┌───────────────────────────────────┐
                    │                                   │
                    ↓                                   │
draft ──→ ready ──→ in_progress ──→ review ──→ done ───┤
                    ↑                    │              │
                    │                    ↓              │
                    └───────── rework ←──┘              │
                                                        │
                    ┌────────────────────────────────────┘
                    ↓
               archived（已完成且不再活跃）
```

### 状态含义与判定标准

| 状态 | 含义 | 判定标准 |
|------|------|---------|
| **draft** | 任务已创建但未就绪 | 文档框架完成，但：依赖未满足 / 设计文档未完成 / DoD 不完整 |
| **ready** | 可开始执行 | 前置条件满足、设计文档完整、DoD 至少有 3 条、涉及文件明确 |
| **in_progress** | 正在执行中 | 代码正在编写，至少有一个文件被修改 |
| **review** | 等待审查 | 代码完成，DoD 全部实现，等待测试验证或人工确认 |
| **done** | 已完成 | DoD 全部满足、类型检查通过、测试通过、TypeScript 编译无错误 |
| **rework** | 需返工 | 审查未通过或测试失败，需修正后重新 review |
| **archived** | 已归档 | done 后保持不动，或废弃后将状态改为 archived 并移入 `archive/` |

### 状态强制规则

1. **不能跳转**：不能从 draft 直接到 done，必须经过 ready → in_progress → review → done
2. **每天结束时更新**：如果当天有代码改动，状态必须反映实际进度
3. **同步更新**：任务文件自身的状态字段和 TASK-CHAIN.md 的表格必须一致

## 五、优先级定义与规则

### 优先级分级

| 级别 | 含义 | 标准 | 示例 |
|------|------|------|------|
| **P0** | 阻塞链 | 不做此任务，后续所有任务无法推进 | 动态上下文装载（不改 PromptBuilder，后续翻译层/反思门控可能冲突）|
| **P1** | 核心交付 | 直接影响用户体验或架构完整性 | 辩驳追踪+强度升级 |
| **P2** | 体验增强 | 有价值的改进，但不阻塞核心链 | 从零构建引导流程 |
| **P3** | 条件触发 | 需要外部条件（数据/反馈）才能启动 | BKT 知识追踪（需足够训练数据）|

### 优先级调整规则

1. **P0 优先原则**：P0 任务必须是当前唯一正在推进的任务（完成后再启动其他 P0）
2. **P0→P1 串行**：P0 和 P1 之间不允许并行（先完成 P0 再推进 P1）
3. **自动升级**：如果发现某个 P2 任务实际阻塞了后续工作，自动升级为 P1
4. **审计优先**：依赖 TASK-CHAIN.md 的状态一览表做优先级判定，不在任务文件中单独声明

## 七、任务链序列化规则

### 核心约束

链中的每个任务必须满足以下**至少一条**：

1. **延续关系** — 是前一个任务的直接延续（在前一个任务的输出基础上深化）
2. **总结关系** — 将前一个任务的成果整合到系统中（前一个任务产出材料，本任务使用）
3. **基础关系** — 产出物被后一个任务消费（本任务新增的服务/接口被后一个任务使用）

### 序列化判定流程

```
检查任务 A 和任务 B 的关系：
├── A 产出的服务/接口是否被 B 使用？       → 基础关系 ✓
├── B 是否在 A 的改动基础上深化？           → 延续关系 ✓
├── B 是否使用了 A 产出的数据/配置？        → 总结关系 ✓
└── 以上都否                                → 不构成序列，需要调整
```

### 当前任务链序列

```
T-014 动态上下文装载 [P0]         ← 架构基础：改造 PromptLoader
  → T-020 状态锁定机制 [P2]       ← 延续：状态机扩展（需 Prompt 架构稳定）
  → T-013 能力成长可视化 [P1]     ← 延续：右侧栏使用 T-014 后的 Prompt 数据
  → T-016 辩驳追踪+强度升级 [P1]  ← 延续：chat.handler 集成辩驳检测
  → T-017 态度系统统一 [P1]       ← 总结：整合 T-016 的升级逻辑
  → T-018 反思门控 [P1]           ← 延续：复用 T-017 的态度系统
  → T-015 翻译层 [P1]             ← 延续：诊断展示使用 T-018 后的数据流
  → T-019 从零构建引导 [P2]       ← 总结：全部核心功能稳定后做
```

### 链的更新机制

1. 任务完成 → 更新自身文件头状态为 `done`
2. 同步更新 TASK-CHAIN.md 的"状态一览"表格
3. AI 在完成时填写"下个任务建议"
4. 链可以分叉（一个前置触发多个后续），但不能有循环依赖
5. 已完成任务从"待执行"移入"已完成"表格，保留编号
