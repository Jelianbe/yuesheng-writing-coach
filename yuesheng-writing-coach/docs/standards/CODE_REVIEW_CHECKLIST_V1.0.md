# 代码审查清单 V1.0

> 用于 R-030 Step 4.5 的增量 diff 审查
> 版本: V1.0 | 日期: 2026-06-11

---

## 使用说明

本清单用于代码变更后的增量审查（Step 4.5），与每日定时全量扫描（SYSTEM_HEALTH_CHECK_PROMPT / AI_DAILY_REVIEW_PROMPT）不同：
- **本清单**：审查本次 diff 的代码质量，逐项检查变更文件
- **全量扫描**：每日定时扫描整个代码库的静态指标

---

## 第一层：P0 致命（必须修复，否则阻塞 Step 5）

### P0.1 Import 正确性
- [ ] 新增/修改的 import 路径目标文件是否存在
- [ ] 被删除/重命名的组件/模块的 import 是否已同步更新

### P0.2 IPC 通道完整性（涉及 IPC 变更时必检）
- [ ] 新增通道是否在 `IPC_CHANNELS` 常量中定义
- [ ] 新增通道是否加入 `ALLOWED_INVOKE_CHANNELS` 白名单
- [ ] renderer invoke 的通道名与 main handle 的通道名一致

### P0.3 数据流断裂
- [ ] Zustand store 新增的 `fetch*` action 是否被对应组件调用
- [ ] IPC `{ success: false }` 返回在 renderer 侧是否被处理

### P0.4 类型安全
- [ ] 无 `any` 类型新增（或已标注可接受理由）
- [ ] 无新的 `@ts-ignore` / `// @ts-nocheck`

---

## 第二层：P1 架构（建议修复，可在本步骤修复或标记为已知债务）

### P1.1 函数签名一致性
- [ ] 新增/修改的函数签名与调用处匹配
- [ ] IPC handler 签名符合 `(event, args) => result` 约束

### P1.2 防御性编码（R-028）
- [ ] IPC handler 输入是否经过 `validatePayload<T>()` 校验
- [ ] 外部数据源的处理是否有 try/catch

### P1.3 状态变更原子性
- [ ] Zustand 状态更新使用了 `immer` 或不可变模式
- [ ] 批量状态变更合并为单次 `set()` 调用

---

## 第三层：P2 质量（可选修复，记录到审查报告）

### P2.1 文件大小
- [ ] 新增文件 ≤300 行（R-019）
- [ ] 修改后的文件是否接近 300 行红线

### P2.2 代码风格
- [ ] 使用具名导出（非 `export default`）
- [ ] 变量/函数 `camelCase`，常量 `UPPER_SNAKE_CASE`
- [ ] 无内联样式（使用 CSS 变量 / CSS Modules / Tailwind）

### P2.3 调试残留
- [ ] 无新增 `console.log` 应在生产环境移除
- [ ] 无新增 `TODO` / `FIXME` 未被处理

---
