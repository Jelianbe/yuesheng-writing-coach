# 月笙写作教练项目开发框架文档

## 1. 项目概述

### 1.1 项目背景
月笙写作教练系统是基于大语言模型的 AI 写作教练，定位为"教练"而非"助手"：
- 不替用户写
- 不替用户决定  
- 帮用户看清问题，让用户自己解决

### 1.2 项目目标
- 实现结构化的写作诊断系统
- 提供个性化的训练任务推荐
- 建立用户成长轨迹记录
- 构建长期有效的用户诊断记忆库

## 2. 开发规则规范

### 2.1 核心规则（L1层 - alwaysApply: true）

#### R-004: 准出标准（DoD）
**规则内容**：每个阶段开始前都必须定义完成标准。没有标准，不得开发。每个阶段的 DoD 必须包含至少 3 条可验证标准。

**DoD 质量标准**（SMART原则）：
- **S**pecific（具体的）
- **M**easurable（可测量的）
- **A**chievable（可实现的）
- **R**elevant（相关的）
- **T**ime-bound（有时限的）

**DoD 示例（MVP阶段）**：
1. 用户能成功配置 API Key 并测试连接
2. 聊天界面能正常发送和接收消息
3. 诊断面板能显示识别到的病症和建议动作
4. 会话历史能正确保存和加载

#### R-007: 双向绑定
**规则内容**：所有数据变更必须保持一致性，前端显示与后端存储保持同步。

**实现要求**：
- 使用状态管理库（Zustand）确保数据一致性
- IPC 通信确保主进程与渲染进程数据同步
- 数据库事务确保数据完整性

#### R-011: 用户主权
**规则内容**：用户拥有所有决策的最终否决权。一旦用户表达否定意图，必须立即停止当前自动化流程。

**触发关键词**：
- "停止"、"错了"、"换方法"、"不对"、"不是这样"等

### 2.2 关键节点规则（L2层 - 任务启动时触发）

#### R-002: 依赖锁定机制
**规则内容**：启动任务时，若上游任务状态非 [已审核]，必须停止并报警。

**检查流程**：
1. 扫描 Depends On 字段
2. 检查上游任务状态
3. 若任一 ≠ [已审核]，阻止启动

#### R-003: 里程碑节点管理
**规则内容**：阶段结束时必须设置里程碑，只有达成才能开启下一阶段。

**检查清单**：
- 核心任务是否都已审核？
- 是否生成了阶段小结？

#### R-013: 记忆强化
**规则内容**：关键决策和状态变更必须持久化记录。

**实现方式**：
- 诊断历史记录到 SQLite
- 用户画像定期更新
- 会话状态持久化

### 2.3 智能触发规则（L3层 - 特定场景触发）

#### R-014: 假设驱动开发
**规则内容**：算法改动前填写假设模板，改动后验证并记录结果。

**四步循环**：
明确目标 → 提出假设 → 设计实验 → 接受/拒绝

**决策矩阵**：
| 情况 | 决策 |
|------|------|
| 目标达成，基线不降 | ✅ 接受 |
| 目标达成，但某基线降了 | ⚠️ 拒绝，分析降分原因 |
| 目标未达成，基线不降 | ⚠️ 拒绝，记录教训 |
| 目标未达成，基线也降了 | ❌ 立即回退 |

#### R-012: 最小化范围
**规则内容**：改动范围最小化，避免不必要的影响。

**实现原则**：
- 每次提交只解决一个问题
- 功能模块边界清晰
- 依赖关系最小化

### 5.3 标准化接口规范

#### IPC 通信接口规范
```typescript
// 通用 IPC 消息格式
interface IpcMessage {
  channel: string;
  payload: any;
  requestId?: string;
  timestamp: number;
}

// 响应格式
interface IpcResponse {
  success: boolean;
  data?: any;
  error?: string;
  requestId: string;
}
```

#### 诊断引擎接口规范
```typescript
// 诊断输入
interface DiagnosisInput {

interface DiagnosisOutput {
```

### 5.4 模块化构建方案

#### 构建流程
```
1. 依赖分析  →  识别模块间依赖关系
2. 模块编译  →  按模块分别编译
3. 依赖注入  →  通过 DI 容器注入依赖
4. 代码分割  →  按功能模块分割代码
5. 优化打包  →  Tree-shaking, 压缩优化
```

#### 模块化原则
- **单一职责**：每个模块只负责一个功能
- **依赖倒置**：高层模块不依赖低层模块
- **接口隔离**：模块间通过接口通信
- **开闭原则**：对扩展开放，对修改封闭
