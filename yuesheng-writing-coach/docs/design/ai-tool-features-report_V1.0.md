## 逐项评估

### F-01：写作前七问引导

**来源**：InkoS TP-014（写作前七问规划法）

---

#### Step 1：功能定位

| 维度 | 回答 |
|:----|:----|
| **解决什么问题** | 用户写到哪算哪，缺乏章节规划导致节奏停滞(P006)和结构单一(P007) |
| **属于哪一层** | 训练层(Layer 4) — 预防性训练，在用户动笔前介入 |
| **与现有功能是否重叠** | 无重叠。现有系统只覆盖写作后诊断+训练，F-01填补了"写作前"环节的教学空白 |

#### Step 2：接受/拒绝决策

**决策**：✅ 接受

**支撑理由**：
1. **填补"写作前"教学空白**：现有系统的教学闭环是"写→诊断→训练→再写"，缺少"规划怎么写"。F-01在"写"之前加了一层规划引导，使教学链路更完整
2. **纯认知引导，无代写风险**（P2=5）：七问全是提问/引导，不替用户生成内容
3. **与T-024训练效果评分互补**：F-01管"写之前"，T-024管"写之后"，形成规划→写作→评估的闭环

#### Step 3：模块规格

| 字段 | 内容 |
|:----|:------|
| **功能名称** | 写作前七问规划工具 |
| **所属模块** | 新建 — 训练模块的子功能 |
| **核心交互** | 用户在训练面板选"写前规划" → 系统展示七问（按优先级排序） → 用户逐题回答 → AI对回答做引导性反馈（"你写读者期待是XX，非常好。章尾改变想好了吗？"） |
| **前端表现** | 训练侧栏内的内联表单面板（非独立页面）。问题逐个展示，答完一题再展示下一题 |
| **数据需求** | 七问内容存为 config JSON（`writing-prompt-questions.json`） |
| **AI调用** | 无新 Prompt。复用现有教练 Prompt 中的提问引导能力 |
| **MVP 范围** | 只做3个核心问题：① 这章的核心任务是什么？② 读者此刻在等什么？③ 章尾必须发生什么改变？后续4个问题为"进阶模式" |
| **影响范围** | 新建：`src/renderer/components/Training/PreWritingPlanner.tsx`；修改：`src/renderer/components/Training/ActiveTrainingView.tsx`（新增起点） |
| **风险与限制** | 用户可能觉得"太麻烦"跳过。解决：默认展开但保留关闭选项，使用率<20%则降级为仅提示 |

#### Step 4：优先级

**P1** — 应该在当前 Phase 中实现（写前规划是教学链路的重要补充，但不如 P0 改进现有面板紧迫）

### F-02：AI味四维自查工具

**来源**：InkoS TP-016（AI味四维识别法）

---

#### Step 1：功能定位

| 维度 | 回答 |
|:----|:----|
| **解决什么问题** | 用户的写作有公式化/AI味（段落等长、套话密集、转折重复），自己难以察觉 |
| **属于哪一层** | 训练层(Layer 4) — 用户主动发起的自检工具 |
| **与现有功能是否重叠** | 与P007(阅读结构单一)相关但不重叠。P007关注的是"读者的阅读体验"，AI味关注的是"写作风格特征" |

#### Step 2：接受/拒绝决策

**决策**：✅ 接受

**支撑理由**：
1. **教"识别能力"而非"生成能力"**（P1=5，P2=5）：用户学会识别AI味本身就是写作素养提升，符合"教可教的认知能力"
2. **纯规则检测，零资源消耗**：无需AI调用，纯正则匹配+统计计算
3. **审查直接标记为"适合优先实现"**：审查报告明确标注"AI味自查工具适合优先实现"

#### Step 3：模块规格

| 字段 | 内容 |
|:----|:------|
| **功能名称** | AI味四维自查 |
| **所属模块** | 新建 — 训练模块的独立自检工具 |
| **核心交互** | 用户粘贴或选中文本 → 系统执行四维检测 → 在原文上标注问题区域 → 给出修改方向提示（非改写） |
| **前端表现** | 训练面板内的文本分析展示。原文中标注段落等长/套话密度，下方显示统计数据和修改方向 |
| **数据需求** | 无新表。检测算法在训练推荐服务中实现 |
| **AI调用** | 纯规则，无需AI。规则引擎：段落长度变异系数<0.15、套话密度>3/千字、重复转折词>3次、连续相同前缀句式>3句 |
| **MVP 范围** | 只做2个维度：段落等长检测 + 套话密度检测。公式化转折和列表式结构暂缓 |
| **影响范围** | 新建：`src/main/services/ai-taste-detector.service.ts` + 对应IPC + 前端组件 |
| **风险与限制** | 中文网文的特殊性可能导致误判（故意重复句式可能是风格）。解决：标注"仅供参考"而非"绝对错误" |

#### Step 4：优先级

**P1** — 快速见效的工具型功能。MVP（2维度）工作量约2天

### F-03：角色行为推导模板

**来源**：InkoS TP-019（角色行为推导法）

---

#### Step 1：功能定位

| 维度 | 回答 |
|:----|:----|
| **解决什么问题** | 角色行为由"剧情需要"驱动而非"角色内在逻辑"驱动，导致OOC/工具人化(P002/P009/P010) |
| **属于哪一层** | 训练层(Layer 4) — 角色构建训练工具 |
| **与现有功能是否重叠** | 与技法库TQ-037(矛盾动机法)、TQ-045(动机可视化法)互补——技法教"怎么写"，模板教"怎么想" |

#### Step 2：接受/拒绝决策

**决策**：✅ 接受

**支撑理由**：
1. **经典"推理能力"教学**（P1=5，P2=5）：三问推导要求用户思考角色的内在动机，而非接受外部设定
2. **填补P009/P010的弱覆盖区域**：蒸馏覆盖率统计显示P009(角色动机缺失)和P010(OC平面化)各只有1-2条覆盖，F-03直接覆盖2个症候
3. **与现有技法库形成认知互补**：技法库教"写出来"，F-03教"想清楚"。想清楚后写出来自然更自然

#### Step 3：模块规格

| 字段 | 内容 |
|:----|:------|
| **功能名称** | 角色行为推导模板 |
| **所属模块** | 新建 — 训练模块的子工具 |
| **核心交互** | 用户选择角色 → 回答三问：① 他的过往经历让他怎么看待这件事？② 他当前的利益诉求是什么？③ 他的性格底色驱使他怎么做？ → AI根据三问推演"行为预期" → 用户对比"自己写的行为"和"推导出的行为"是否一致 |
| **前端表现** | 训练侧栏内的三问表单。AI推演结果以"如果按照三问推导，这个角色应该会[行为描述]"展示。不一致时高亮提示 |
| **数据需求** | 无新表。AI推演Prompt在训练服务中实现 |
| **AI调用** | 新Prompt模块（约10行）：角色行为推导引导——"根据用户填写的三问，推演角色在给定场景中的合理行为" |
| **MVP 范围** | 只做三问表单 + AI推演，不做"行为矛盾标注"。用户自行判断 |
| **影响范围** | 新建：`src/renderer/components/Training/BehaviorDerivationTemplate.tsx`；修改：训练推荐服务新增推导逻辑 |
| **风险与限制** | 用户可能觉得推导结果和自己想的一致就不用了。解决：加入提示"如果你写的和三问推导一致，很好；如果不一致，说明这个行为可能是'剧情需要'而非'角色需要'" |

#### Step 4：优先级

**P1** — 覆盖P009/P010弱区，但需要新Prompt，工作量约3天

### F-04：分层反馈策略

**来源**：InkoS 审计员"只审结构不审文笔"的分层思路

---

#### Step 1：功能定位

| 维度 | 回答 |
|:----|:----|
| **解决什么问题** | 诊断反馈把所有问题混在一起，用户分不清"必须改"和"建议改"，认知负荷过高 |
| **属于哪一层** | 教练层(Layer 3，呈现方式) + 反馈层(Layer 2，分级逻辑) |
| **与现有功能是否重叠** | 不重叠。这是"反馈呈现方式的改进"而非新功能。现有诊断面板把所有症候平铺展示 |

#### Step 2：接受/拒绝决策

**决策**：✅ 接受

**支撑理由**：
1. **直接提升现有诊断面板的可用性**：不新增任何模块，只改造前端呈现，投入产出比极高
2. **降低用户认知负荷**（Sweller认知负荷理论依据）：用户一次性看到5个症候可能不知所措，分层后先看到"必须处理的"再看到"建议了解的"
3. **审查判定为通过**（P1/P2都≥4）

#### Step 3：模块规格

| 字段 | 内容 |
|:----|:------|
| **功能名称** | 分层反馈（诊断面板升级） |
| **所属模块** | 修改 — 右侧诊断面板UI改造 |
| **核心交互** | 诊断结果分两区：上方"需要处理"（L2+症候、critical问题）和下方"仅供参考"（L1症候、info问题）。默认展开"需要处理"区，折叠"仅供参考"区 |
| **前端表现** | 诊断面板症候列表增加折叠逻辑。每个症候增加严重度标签(critical/warning/info) |
| **数据需求** | 诊断结果中增加 `severity` 字段（`critical | warning | info`），从症候级别映射（L2+→critical，L1→warning，训练评分≥7→info） |
| **AI调用** | 现有诊断Prompt增加"严重度标注"指令（约5行）："标注每个症候的严重度；L2+症候标critical，触发性信号标warning，轻微信号标info" |
| **MVP 范围** | 先做两区（需要处理/仅供参考），不做三级（critical/warning/info）。L2+症候自动归类"需要处理"，L1症候归类"仅供参考" |
| **影响范围** | 修改：`src/renderer/components/Diagnosis/DiagnosisPanel.tsx`（折叠逻辑）；修改：诊断结果类型定义（加severity） |
| **风险与限制** | 分层可能让用户忽略"仅供参考"区的症候。解决：在折叠区顶部标注"还有N个轻微问题，点击展开查看" |

#### Step 4：优先级

**P0** — 必须做。这是对现有诊断面板的直接优化，无需新模块，投入产出比最高。

### F-05：看点密度反馈

**来源**：InkoS 看点密集度硬尺（TP-018）

---

#### Step 1：功能定位

| 维度 | 回答 |
|:----|:----|
| **解决什么问题** | 用户的大段文字缺乏节奏/看点，读者容易流失（P006节奏停滞） |
| **属于哪一层** | 混合层 — 诊断层(Layer 1，规则检测) + 反馈层(Layer 2，可视化展示) |
| **与现有功能是否重叠** | 与P006诊断部分重叠，但现有诊断只输出"是否识别为P006"，不输出具体的密度曲线数据 |

#### Step 2：接受/拒绝决策

**决策**：✅ 接受

**支撑理由**：
1. **提供量化数据补充现有定性诊断**：现有诊断给出"你有节奏停滞问题"，密度曲线展示"你在这里节奏掉下去了"
2. **让"节奏停滞"变得可视化、可感知**：用户能直观看到"这段6行没有钩子"——看到比听到更容易接受
3. **纯规则计算，零AI调用成本**

#### Step 3：模块规格

| 字段 | 内容 |
|:----|:------|
| **功能名称** | 看点密度可视化 |
| **所属模块** | 新建 — 诊断报告的子微件 |
| **核心交互** | 用户选中文本段 → 系统计算"钩子密度"（每500字钩子数） → 以迷你折线图展示密度变化 → 低于阈值（钩子间距>500字）时高亮标注 |
| **前端表现** | 诊断面板中的迷你折线图微件（约120px高）。x轴=字数轴，y轴=密度轴。低于阈值的区段用红色背景标注 |
| **数据需求** | 无新表。规则引擎钩子识别规则：问号结尾句、"他发现了"类揭示句、决定/行动预告句 |
| **AI调用** | 纯规则，无需AI |
| **MVP 范围** | 只做"钩子密度"一种曲线，不做"爽点密度"。只展示最近5000字的统计 |
| **影响范围** | 新建：`src/main/services/density-detector.service.ts`（规则引擎）；修改：诊断面板（集成迷你图表） |
| **风险与限制** | 规则匹配准确率可能不高。解决：MVP先用窄规则（仅问句+"发现/想到/决定"类句式），后续扩展 |

#### Step 4：优先级

**P1** — 对诊断系统有价值的补充

### F-06：伏笔生命周期追踪

**来源**：InkoS Hook-debt（TP-021伏笔生命周期管理）

---

#### Step 1：功能定位

| 维度 | 回答 |
|:----|:----|
| **解决什么问题** | 用户埋了伏笔但忘了推进/回收，导致读者追读动力下降（P006/P007） |
| **属于哪一层** | 数据管理 + 训练层(Layer 4) |
| **与现有功能是否重叠** | 与技法库TP-012(伏笔管理三问)和TP-021(伏笔生命周期管理)的教学内容重叠——但技术实现（自动追踪+提醒）是现有训练未覆盖的 |

#### Step 2：接受/拒绝决策

**决策**：✅ 接受

**支撑理由**：
1. **将"手动管理"升级为"系统辅助追踪"**：现有训练教用户"手动维护伏笔表"，追踪器降低元认知负担
2. **提供"半衰期"的量化视角**：让用户直观理解伏笔的时间维度——"这个伏笔已经超过半衰期了"
3. **审查判定为通过**

#### Step 3：模块规格

| 字段 | 内容 |
|:----|:------|
| **功能名称** | 伏笔生命周期追踪器 |
| **所属模块** | 新建 — 训练模块的辅助追踪工具 |
| **核心交互** | 用户在训练中创建伏笔条目 → 系统记录埋设章节 → 每5章自动检查各伏笔的上次推进章节 → 超期伏笔在训练面板显示提醒 → 用户可点击"已推进"更新状态 |
| **前端表现** | 训练侧栏中的列表式追踪面板。每项显示：伏笔名称、状态(活跃/搁置/已收)、上次推进章节、半衰期进度条 |
| **数据需求** | 新表 `foreshadowing_tracker`（id, sessionId, techniqueId, content, status, setChapter, lastAdvanceChapter, halfLife, expectedRecoveryChapter, createdAt, updatedAt） |
| **AI调用** | 无需AI调用 |
| **MVP 范围** | 只做"伏笔列表+状态标记"的纯手动版本（用户自己创建和管理），不做自动半衰期检测。用户手动标记"活跃/搁置/已收" |
| **影响范围** | 新表迁移脚本；新建IPC通道；新建前端组件 |
| **风险与限制** | 用户不愿意手动维护表格。解决：MVP手动版验证用户需求，如果使用率<10%则暂缓自动版开发 |

#### Step 4：优先级

**P2** — 先MVP手动版验证需求，不急于正式开发

### F-07：迷你维度反馈（37维度缩减版）

**来源**：InkoS TP-013（37维度结构化反馈框架）

---

#### Step 1：功能定位

| 维度 | 回答 |
|:----|:----|
| **解决什么问题** | 现有诊断系统的维度不够结构化，用户知道"有P006"但不知道"具体哪里节奏出问题了" |
| **属于哪一层** | 诊断层(Layer 1，检测) + 反馈层(Layer 2，呈现) |
| **与现有功能是否重叠** | 与症候系统互补而非重叠。症候是"问题类型"（你的问题是P006节奏停滞），维度是"具体检查项"（你的节奏在第3段和第7段出现了停顿） |

#### Step 2：接受/拒绝决策

**决策**：⚠️ 条件接受

**条件**：按照审查报告要求，必须缩减到3-5维度迷你版。不得一次性引入全部37维度。

**支撑理由**：
1. 补充症候诊断的"具体性"不足——用户的反馈需求不是"我有P006"而是"我的第三段有问题"
2. 迷你版（3维度）不会造成认知负荷过载
3. 审查明确标记"条件通过"并指明了处理方式

#### Step 3：模块规格

| 字段 | 内容 |
|:----|:------|
| **功能名称** | 迷你维度反馈 |
| **所属模块** | 修改 — 现有诊断面板扩展 |
| **核心交互** | 在现有症候诊断下方，新增3个具体维度的检查结果（默认折叠）。每个维度1句话结论 + 问题段落引用 |
| **前端表现** | 诊断面板中症候下方的可折叠扩展区。每项显示：维度名、结论（通过/不通过）、问题段落（如适用） |
| **数据需求** | 维度定义存为JSON配置（`dimension-checks.json`） |
| **AI调用** | 现有诊断Prompt增加"维度检查指令"（约15行）："对P006症候激活维度检查：dim7节奏检查——分析段落节奏是否有超过500字无钩子的区域" |
| **MVP 范围** | 只做3个维度：dim1(OOC检查)、dim6(伏笔检查)、dim7(节奏检查)。关联P002/P005/P006症候时激活 |
| **影响范围** | 修改：诊断Prompt（维度检查指令）；修改：诊断面板UI（折叠扩展区）；新建：维度定义JSON |
| **风险与限制** | 3个维度也可能给用户负担。解决：仅在关注度≥3的症候上展示维度详情，其余默认折叠 |

#### Step 4：优先级

**P2** — 等现有诊断系统稳定后再扩展

### F-08：叙事漏洞审计

**来源**：InkoS TP-020（明线暗线设计法/叙事一致性审计）

---

#### Step 1：功能定位

| 维度 | 回答 |
|:----|:----|
| **解决什么问题** | 故事存在逻辑漏洞/设定矛盾/时间线错误等叙事一致性问题 |
| **属于哪一层** | 诊断层(Layer 1) |
| **与现有功能是否重叠** | **严重重叠**。现有P004(信息硬塞)覆盖"设定一致性"、P005(视角漂移)覆盖"视角一致性"、P006(节奏停滞)覆盖"叙事连贯性"。三个症候合起来已经覆盖了"叙事一致性审计"的核心里程功能 |

#### Step 2：接受/拒绝决策

**决策**：❌ 拒绝

**一票否决理由**：与现有诊断系统功能性重叠。现有P004+P005+P006三个症候从三个维度覆盖了"叙事一致性"检查。新加一个"叙事漏洞审计"不会新增诊断能力——更精确地说，它能做到的检查（OOC检查 → P002已覆盖；时间线错误 → P006已覆盖；设定矛盾 → P004已覆盖），现有症候系统都能做到。引入只会增加系统复杂度和AI调用成本，无新增用户价值。

## 关键决策记录

| 决策 | 理由 |
|:----|:------|
| F-04 定为唯一的 P0 | 不是因为这个功能"最重要"，而是因为没有比它投入产出比更高的：0.5天改造现有面板，让所有用户每次使用都受益 |
| F-01~F-05 全部接受（P0/P1） | 这些设计都满足"填补现有系统空白"或"增强现有系统能力"，且审查全部通过 |
| F-06 定为 P2 | 纯手动版的伏笔追踪需要用户主动维护，存在用户不愿意维护的风险。先手动版验证需求 |
| F-07 条件接受 | 审查报告明确要求缩减到3-5维度迷你版。直接引入37维度违反设计哲学§9"小规模验证"原则 |
| F-08 拒绝 | 与现有诊断系统功能重叠，两个不同的诊断路径（症候 vs 维度）可能互相矛盾，增加用户困惑 |
| 37维度不拒绝而接受迷你版 | 37维度的问题不是"功能有问题"而是"尺度过大"。3维度的迷你版在已有的症候诊断下增加具体性，有价值 |
