## 评估流程

对每个候选设计执行以下评估：

### Step 1：功能定位
回答：
- 这个功能解决用户的什么问题？
- 它属于月笙现有四层架构的哪一层？（诊断/反馈/教练/训练）
- 与现有功能是否重叠？

### Step 2：拒绝/接受决策
回答：
- 是否应该实现？给出 3 个支撑理由或 1 个一票否决理由
- 如果拒绝，明确理由（功能重叠/设计哲学冲突/技术不可行/回报低）

### Step 3：接受后的模块规格
如果接受，提供以下内容：

```
功能名称：
所属模块（新建/扩展现有组件）：
核心交互（用户做什么 → 系统做什么 → AI做什么）：
前端表现（新建UI/面板/弹窗/侧栏/内联提示）：
数据需求（新表/新字段/新配置JSON）：
AI调用（新prompt/新Agent/新诊断维度）：
影响范围（哪些现有文件需要修改）：
最小可行版本（MVP 范围，不超过3天工作量）：
风险与限制：
```

### Step 4：优先级评定
- P0（必须做，当前Phase）
- P1（应该做，下个Phase）
- P2（可以考虑，长期计划）
- P3（已排除，不实现）

## 特别注意

### F-07（37维度反馈框架）的条件约束

现有诊断系统已覆盖"逻辑自洽性检查"。请确认：

- 如果是重复功能，标记为"不实现"
- 如果存在差异点，标注差异
