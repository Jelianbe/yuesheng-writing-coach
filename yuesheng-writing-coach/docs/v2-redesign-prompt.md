## ════════════════════════════════════════════════════════
##  一、项目核心哲学（必读）
## ════════════════════════════════════════════════════════

月笙写作教练不是一个"AI 代笔工具"。它的核心哲学是：

> **保护人的创作主体性** — 让 AI 退到"教练"的位置，不上场替学员打球。

这体现在现有的五个教学机制中：
- **反思门控（T-018）** — 不让 AI 每次都直接给答案，先让学员自己反思
- **辩驳追踪（T-016）** — 学员说"不"的时候强度升级，保护学员的判断权
- **锁定症候（T-020）** — 不让 AI 跟着学员的话题跑，聚焦薄弱环节
- **训练评分（T-024）** — 量化能力，让学员看到自己哪里进步
- **证据展示（T-025）** — 让学员看到"具体哪段写得如何"，反馈挂在原文上

**每一次代码变更都必须问自己：这个改动是在帮学员"学会写"，还是在替学员"写完"？**
如果答案是后者——即使技术再优雅、UI 再漂亮——也是方向性错误。

##  一·五、设计边界声明（重要 ⚠️）
## ════════════════════════════════════════════════════════

### 核心原则：一套界面，逐步改造

**我们只有一套主界面。没有两套界面。** V2 改造的全部工作是对**当前正在运行的这个主界面**进行渐进式重构，不是新建一个"新界面"然后把旧界面留在旁边。

### SOLO / IDE 是什么关系

| 模式 | 状态 | 说明 |
|:----:|:----:|------|
| **SOLO 模式** | **正在改造 ← 当前焦点** | 这是 V2 改造的目标——去掉 Header，三栏布局，对话区 ≥60%，右侧面板双态。改造后的界面就是 SOLO 模式本身。 |
| **IDE 模式** | **尚未设计，不在此次范围内** | 是一个未来概念（编辑器集成、多文件标签页等），本次 V2 的 Phase 0-2 **全部不涉及 IDE 模式的实现**。 |

### V2-014 ModeSwitch 的真实含义

V2-014 实现的只是一个**胶囊切换器 UI 元素**——它在侧栏顶部显示当前模式，允许用户点击切换。但：

- **SOLO 侧** → 正常工作，就是当前改造后的界面
- **IDE 侧** → **只显示一个"开发中"占位提示**，不做任何 IDE 界面

**不得做以下事情：**
- ❌ 不得创建一个独立的 IDE 页面/路由/组件树
- ❌ 不得为 IDE 模式编写任何业务逻辑
- ❌ 不得在文件系统中新增 IDE 相关目录或文件
- ❌ 不得设计或实现多文件标签页系统（那是 Phase 3 以后的事）
- ❌ 不得实现编辑器集成

**任何时候如果觉得"这个功能好像属于 IDE 模式"——把它放到 Phase 3，不要碰。**

### 为什么不能现在做 IDE

不是技术原因——是为了保护项目的聚焦能力。V2 改造已经涉及 28 项任务、~33 人天的工作量。如果再塞入 IDE 模式的任何部分，会导致：
1. 范围爆炸，Phase 0-2 永远做不完
2. 两套界面相互牵制，测试和维护成本翻倍
3. 核心教学体验（对话 + 诊断 + 训练）被稀释

**先让 SOLO 模式站稳，再谈 IDE。**

##  二、任务背景说明
## ════════════════════════════════════════════════════════

月笙写作教练是一个基于 Electron + React + TypeScript 的 AI 写作教练桌面应用。项目代码位于 `D:\ai-teacher\yuesheng-writing-coach`。

经过全面的系统扫描（覆盖 `src/` 全目录的 47 个代码分析维度），当前项目存在以下核心问题需要解决：

### 核心问题

1. **UI/UX 缺陷**：当前 AppShell 强制包含 40px Header，对话区仅占 ~45% 屏幕宽度。左侧栏在 240px 内混合了 6 个功能模块，认知负载过高。缺少 Status Bar 全局上下文感知和对话历史管理。

2. **数据模型缺失**：manuscripts / chapters 两张核心表完全不存在，导致内容查看器、作品管理等功能无法落地。sessions 表缺少 title / preview 字段，对话历史列表功能无法实现。

3. **架构债务**：App.tsx (455 行) 和 AppSidebar.tsx (828 行) 是 God Component。推荐引擎 recommendation-engine.ts 的 recommendTasks() 方法体为空，核心训练链路断裂。saveMessage() 缺少事务保护。

4. **技法按需装载断裂**：technique-library.json 的 100 条技法已在数据层标注了 coreId/coreName/difficultyOrder/genreScope（核心+变种结构），但消费层未落地——`injectTechniquePool()` 仍全量 100 条注入诊断 Agent Prompt，不做预过滤；`matchTechniques()` 扁平匹配不使用 coreId。过滤完全依赖 LLM，存在 token 浪费 + 噪声风险。

5. **代码质量**：68 处 console 残留，8 处 @ts-ignore，约 40 处 any 类型，7 个空壳服务/函数，23 处 TODO/FIXME 标记。

### 已有设计参考

高保真交互原型文件位于 `prototype-v2-workspace.html`（3144 行），包含了完整的 SOLO 模式 UI 设计、CSS Design Token 体系、交互逻辑。该原型已通过 3 轮独立的工具审查（TRAE Code Review、TRAE Security Review、Impeccable Audit），所有 P0/P1 审查问题均已修复。

### 任务链正本

所有任务的完整依赖关系和状态见 `docs/tasks/TASK-CHAIN.md` V12.1。

##  四、技术约束与规范
## ════════════════════════════════════════════════════════

### 技术栈约束
- **前端框架**: React 18 + TypeScript（strict 模式）
- **状态管理**: Zustand 4（必须遵循 R-007 双向绑定规则）
- **后端框架**: Electron 30 + better-sqlite3
- **IPC 通信**: 主进程 ipcMain.handle + ipcMain.on / 渲染进程 ipcRenderer.invoke + ipcRenderer.on
- **样式**: CSS Modules 或 CSS-in-JS（不允许使用 Tailwind 等与现有架构不一致的方案）
- **构建**: Vite（渲染进程）

### 架构约束
- 所有 IPC 通道必须统一使用 `{ success: boolean, data?: T, error?: string }` 响应格式
- 所有有写操作的数据库操作必须放在事务中
- 不允许使用 `innerHTML`、`dangerouslySetInnerHTML` 或字符串拼接创建 DOM
- 不允许引入新的 npm 包增加包体积（除非确实必要且经过评估）
- Store 与 UI 组件必须保持解耦——Store 不引用任何 React 或组件类型
- 新增文件必须遵循现有目录结构和命名约定

### 代码规范（基于 R-019 和 CODE_STANDARDS_V1.0）
- 不允许出现 `console.log` / `any` 类型 / `@ts-ignore`
- 所有 React 组件使用函数组件 + hooks，不使用 class component
- 所有公共函数必须有 JSDoc 注释
- 硬编码值必须提取为命名常量或配置项
- CSS 类名命名统一（英文 kebab-case）
- 每个文件不超过 300 行（超过必须拆分子组件/函数）

### 交互规范
- 必须保持 SOLO 模式的「无 Header」沉浸式设计
- 动画使用缓动曲线（ease-out / spring），时长不超过 250ms
- 所有触控目标 ≥ 44px（无障碍 WCAG 2.1）
- 所有交互元素必须有 aria-label 或 label 关联（无障碍）
- 键盘快捷键：ESC 关闭面板、Enter 发送消息、Shift+Enter 换行
- 新 UI 覆盖遮罩层必须使用 `<button>`（可键盘焦点），不得使用 `<div onclick>`

### 技法按需装载规范
- `injectTechniquePool()` 必须按活跃症候 ID + coreId 预过滤技法，不得全量 100 条注入
- `matchTechniques()` 必须使用 coreId 做"先选核心模式，再按 difficultyOrder 推荐变种"的分组推荐
- 诊断 Agent Prompt 中技法匹配的 token 配额应当缩小（100 条全量 → 按需子集）
