# 月笙写作教练 — 项目规则

> 以下规则在编码、审查和验收时必须遵守。

## 1. 编码前必须回答（推理闸）

开始实现前，必须回答以下问题，并将结论记录到 `dev-docs/decisions/`：

1. 实际要解决的问题是什么？
2. 当前真源在哪里？是否已有同职责模块、合同或状态机？
3. 唯一 owner 是哪一层？
4. 更简单、更保守的设计是什么？
5. 最大回归风险是什么？用什么验证？

未闭合推理闸，不开始实现。

## 2. 必须停止并询问的情况

遇到以下情况必须停止并等待确认：

- **需求冲突**：用户需求与当前架构、规则、文档或已否定方向冲突
- **无意义兼容**：需要保留旧产品残影、已否定方向或同时支持互斥路线
- **核心变更**：需要创建/改写/废弃核心 API、schema、权限模型或部署流程
- **架构损害**：当前证据表明目标会损害数据完整性、安全性、UX 或长期可维护性
- **owner 边界不清**：不确定哪个模块应拥有某概念，且错误判断会造成不可逆影响

停止时不要只说「无法继续」。必须给出冲突证据、可选方向、推荐方向、需要确认的问题。

## 3. 验收门禁（四道，对应 R-027）

声称「完成」前必须逐条检查四项门禁：

### 门禁 1：规格校验（Spec Check）
- [ ] 改动是否符合任务描述/需求文档/Issue 说明？
- [ ] 是否有超范围的改动？（对照 R-010 最小化范围）
- [ ] 是否引入了任务不需要的新依赖或新文件？

**通过标准**：所有改动可追溯到明确的需求来源。

### 门禁 2：Diff 审查（Diff Review）
- [ ] `git diff` 是否只包含预期内的文件？
- [ ] 每个文件的改动量是否合理？（单文件 >100 行需特别关注）
- [ ] 是否有"顺手"删除/添加的无关代码？

**通过标准**：diff 清洁，无意外改动。

### 门禁 3：测试证据（Test Evidence）
运行：
```bash
npm run gate
# tsc --noEmit && vitest run && eslint --max-warnings 300 && a11y scan
```
- [ ] tsc 零错误
- [ ] 测试全绿
- [ ] lint zero errors（warnings ≤ 300）
- [ ] UI 改动检查真实渲染、交互、加载态、错误态
- [ ] 不能运行时，说明原因和替代证据

### 门禁 4：人工签字（Human Sign-off）
以下变更需记录 "✅ 已由 [谁] 在 [时间] 人工审查通过"：
- 诊断引擎代码变更
- 教学 Agent / Prompt 变更
- 数据库 schema 变更
- IPC 通道定义变更
- 涉及安全配置的变更

### 分级执行

| 风险等级 | 需通过的门禁 | 典型场景 |
|---------|:----------:|---------|
| 低（单文件 bug 修） | 1 + 2 + 3 | 修 typo、调样式 |
| 中（多文件联动） | 1 + 2 + 3 | 功能增强、重构组件 |
| **高（核心模块变更）** | **1 + 2 + 3 + 4** | 诊断/Agent/DB/IPC |

## 4. 实现纪律

- **禁止补丁式开发**：不得用散落 `if`、临时兼容分支、硬编码绕过架构问题
- **禁止无意义向后兼容**：旧字段若污染当前合同，必须先说明取舍
- **UI 不私造业务语义**：组件只消费 store 提供的结构化状态，禁止直接 `getState()` 操作业务逻辑
- **禁止 `git add .`**：只 stage 与本任务相关的文件
- **dirty worktree 中不得回滚或覆盖未授权改动**

## 5. 文档纪律

- 重大决策写入 `dev-docs/decisions/ADR-NNN-title.md`
- 修改核心类型、API 或架构后必须同步 `dev-docs/README.md`（真源索引）
- 不再有效的文档必须标注「非当前」或移入 `dev-docs/archive/`
