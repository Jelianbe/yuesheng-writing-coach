## 0. 核心哲学转变

### 从功能中心 → 意图中心

```
过去（写作中心）：                         现在（教学中心）：
┌──────────────────────┐                ┌──────────────────────┐
│  诊断  │  训练  │  技法  │            │                      │
│────────┼────────┼───────│            │    对话（主入口）     │
│  成长  │  画像  │  世界观│            │   ↓ AI 判断意图      │
│────────┼────────┼───────│            │  诊断/教学/训练/...   │
│  项目  │  设定  │  资料  │            │                      │
└──────────────────────┘                │  成长（结果展示）    │
                                         │  项目（教学载体）    │
                                         └──────────────────────┘
```

**核心变化**：
1. 不再让用户选择模式，而是由 AI 判断用户意图
2. 前端从"功能操作台"变成"教学对话界面"
3. 后端已有的教学系统（诊断引擎、状态机、训练流）终于有匹配的前端形态

### 教育学的根因

**"学生不知道自己不知道什么"**——这是整个设计的锚点。

- 用户问「帮我看看这段」，AI 可以分析
- 但系统可能知道：冲突设计 35 分
- 如果完全隐藏，用户永远不会知道自己最大的短板是什么
- 所以能力画像、症候历史、成长记录**不能只活在 AI 的上下文里**
- 它们需要以"可见的认知缺口"形态存在

## 2. 三层详细说明

### 第一层：对话（主入口）

**定位**：用户进入月笙的第一界面，90% 的时间停留在这里。

**核心交互**：

| 交互 | 说明 | AI 角色 |
|:-----|:------|:---------|
| 提问 | 「老师，我写不出来」 | 判断意图 → 诊断/教学/训练 |
| 上传 | 小说/图片/TXT/设定/大纲 | 分析内容 → 主动给出建议 |
| 写作 | 在对话中写/改 | 实时反馈 |
| 练习 | AI 出题 → 用户答 → AI 评 | 训练模式 |

**关键设计原则**：
- 用户**不需要选择模式**——AI 根据上下文自动判断该诊断还是教学还是训练
- 所有上传操作在对话中完成，不需要切换到其他界面
- 对话上下文包含用户的成长历史和项目数据，AI 可以主动提及「你的冲突设计最近有提升」

**意图路由（隐性）**：

| 用户行为 | AI 判断 | 后端调用 |
|:---------|:---------|:----------|
| 「帮我看看这段写得怎么样」 | 诊断 | 诊断引擎 |
| 「人物对话怎么写更自然」 | 教学 | 教学状态机 |
| 「来练练描写」 | 训练 | 训练流 |
| 「今天心情不好」 | 闲聊 | 普通对话 |

### 第二层：成长（结果展示）

**定位**：独立页面，从主界面可通过按钮进入。不是教学入口，是**教学结果的展示**。

**解决的问题**：「学生不知道自己不知道什么」

**展示内容**：

| 模块 | 数据来源 | 说明 |
|:-----|:---------|:------|
| 本周提升 | 能力画像增量 | 相比上周哪些能力进步了 |
| 能力雷达图 | 能力画像 | 各维度评分，直观显示短板 |
| 最近症候 | 症候历史 | 最近诊断出的写作症候 |
| 训练记录 | 训练记录 | 已完成和进行中的训练 |
| 学习路径 | 教学状态机 | 当前所处的教学阶段 |
| 成长轨迹 | 历史数据 | 长期趋势图 |

**交互规则**：
- 点击能力项 → 展开详情 + 对应的历史诊断
- 点击症候 → 跳转到相关对话/训练
- 纯浏览、不引导操作（不是功能入口）

### 第三层：项目空间（教学载体）

**定位**：书架/项目管理，属于辅助页面。

**解决的问题**：教学不能脱离作品空转。

**结构**：

```
书架
 └── 项目 A（一本小说）
      ├── 章节列表
      ├── 素材库
      ├── 世界观设定
      ├── 角色卡片
      ├── 历史对话（按章节/时间归档）
      ├── 诊断记录
      └── 训练记录
 └── 项目 B（另一本小说）
      └── ...
```

**关键规则**：
- 对话始终关联当前项目（用户在写哪本书）
- 教学产出（诊断结果、训练记录）自动归入项目
- 项目间的知识不混用

|:-----|:-----------------|:-----------------|

| 用户路径 | 选模块 → 操作 | 问 → AI 判断 → 回应 |

## 4. 关键约束与陷阱

### 4.1 前端极简 ≠ 产品极简

对话入口是"交互极简"，但后端能力不能精简。诊断引擎、教学状态机、训练流、能力画像——这些必须都在，且持续增强。

### 4.2 对话入口 ≠ 只有对话

**最危险的陷阱**——把所有东西塞给 AI，导致能力画像、成长记录、症候历史、训练计划等失去存在感。

教育学经典问题「学生不知道自己不知道什么」要求系统必须**主动呈现**认知缺口，不能等用户问。

### 4.3 成长页面不能变成功能入口

成长页面是"结果展示"，不是"教学入口"。用户不应该从成长页面进入训练——训练应该由 AI 在对话中触发。

### 4.4 项目空间要有存在感但不要喧宾夺主

项目空间是教学的载体，不是编辑器。用户来月笙不是为了「打开项目写章节」，而是为了「在项目中接受教学」。

## 6. 未决问题（已决策）

| # | 问题 | 决策 | 影响 |
|:-:|:-----|:-----|:-----|
| 1 | 第一版是否做手机端？ | **是，第一版改作手机版** | 前端架构从 Electron 优先 → 移动端优先（H5/小程序），Electron 版本后移 |
| 2 | 意图路由的触发机制 | **AI 自动判断**，用户不手动选择模式 | 对话层需要强意图识别模块，路由结果对用户透明 |
| 3 | 成长页面是否做历史对比？ | **做对比**（本周 vs 上周） | 能力画像需要存储时间序列数据，查询需支持增量计算 |
| 4 | 项目空间是否支持"空白项目"？ | **支持，但创建入口在对话中** | 用户说「我想开始学写作」→ AI 在对话中新建项目，不需要独立的新建项目页面 |
| 5 | 对话上下文长度如何控制？ | **设长度上限 + 对话压缩机制** | 需要上下文压缩策略（摘要/截断/滑动窗口），超出上限时自动压缩历史 |
