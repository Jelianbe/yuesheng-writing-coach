# 后端框架搭建规则与流程

> 后端骨架不是一上来就写登录、订单、支付，而是先把业务边界与工程规则写入架构设计文档，再基于文档搭建一个最小可运行的基础骨架。这套规则与流程专为 AI 辅助编程设计，目标是让后续每一个功能都长在同一套规则上，可维护、可迭代。

---

## 一、核心原则

- **规则先行**：不写业务代码，先定义业务边界和工程规则，形成项目架构设计文档。
- **框架最大化利用**：能用框架自带能力（路由、校验、错误处理、日志等）就绝不手写替代方案。
- **最小可运行**：骨架只包含启动、接口、分层、运维四条基础线，不包含任何完整业务功能。
- **统一规范**：接口响应格式、错误码、日志、目录结构等必须在骨架阶段固化。
- **分层清晰**：请求接入、业务逻辑、数据访问各层分离，即使框架叫法不同也要概念明确。
- **文档驱动**：所有后续开发必须基于架构设计文档，任何偏离需先更新文档。

---

## 二、搭建流程（5 步）

### 第 1 步：复核语言与框架，防止过度选型
**目标**：确认当前技术路线是基于真实项目需求，而非追求“高级感”。

**操作**：
1. 如果已选定语言和框架，请 AI 复核：
   > “请根据立项文档判断当前后端语言和框架是否适合本项目。只判断是否存在为追求高级/性能/安全而过度选型的问题。若较重，说明项目为什么真的需要它，以及后续必须遵守哪些框架规范。”
2. 如果尚未选定，让 AI 基于项目类型（后台、SaaS、API 服务等）**只给一个唯一推荐**，并说明理由。
3. 优先选择轻量且 AI 熟悉度高的方案。常见业务系统（内容平台、后台管理、普通 API）大多不需要 Java/C++ 级别的重语言，Python、Node.js、Go 等配合成熟框架通常更合适。

**产出**：一句明确的技术路线声明（如：Node.js + Express，或 Python + FastAPI），并记录选型理由。

---

### 第 2 步：编写《项目架构设计文档》
**目标**：融合业务边界与工程规则，形成一份约束 AI 后续行为的权威文档。

**文档必须包含**：
- **语言与框架**：选型理由，明确排除的其他方案。
- **语言工程规范**：依赖管理、配置读取、日志、异常处理、测试等通用约定。
- **框架最佳实践**：官方推荐的目录结构、路由组织、中间件机制、错误处理模式等。
- **框架最大化利用原则**：声明“优先复用框架内置能力，禁止在框架外手写一套”。
- **项目自定义部分**：哪些目录/模块是项目特有的，为什么偏离框架常规（若有）。
- **目录结构**：每层目录的用途，指明请求入口、业务逻辑、数据访问、公共工具等分别放在哪里。框架的叫法可能不同（controller/service/repository 或 handler/usecase/model），需明确映射。
- **接口规范**：统一成功响应格式（列表要含数组、分页、总数；对象要含详情数据），统一失败响应格式（参数错误、未登录、无权限、系统异常等），HTTP 状态码使用规则。
- **错误处理规则**：全局异常捕获、业务错误码定义原则。
- **日志规则**：日志级别、格式、输出目标。
- **数据库连接方式**：连接配置、连接池、迁移策略。
- **权限校验入口**：中间件/守卫的占位方式。
- **模块扩展规则**：以后新增模块时文件该怎么放、命名规则。

**生成指令示例**：
> “请根据立项文档和已确定的后端语言/框架，整理项目架构设计文档。不要写业务代码。文档必须写清：选型理由、语言规范、框架实践、目录约束、接口响应格式、错误处理、日志、数据库连接、权限占位，以及新模块的存放规则。”

**产出**：`docs/backend-architecture.md`，作为后续所有后端开发的“技术宪法”。

---

### 第 3 步：基于文档搭建最小可运行骨架
**目标**：生成一个能启动、有分层、规范统一的空骨架，不含任何完整业务功能。

**前置条件**：架构设计文档已经确认，并与 AI 约定：“后续搭建必须严格依据此文档，不得自由发挥。”

**搭建指令约束**：
- 必须基于选定语言和框架。
- 必须遵守语言规范与框架最佳实践。
- 必须按照架构设计文档的目录结构。
- 必须先解释目录结构（来源、作用），再写代码。
- 只搭骨架，不写登录、订单等完整业务。

**骨架必须包含的四条线**：

| 基础线 | 必须实现的内容 | 验证目标 |
|--------|----------------|----------|
| **启动线** | 项目可启动；环境变量/配置文件（有 sample）；健康检查接口 `/health`；密钥不硬编码 | 后端能正常跑起来 |
| **接口线** | 路由分组；统一成功响应（列表含分页，对象含数据）；统一失败响应（参数错误、未登录、无权限、系统异常）；HTTP 状态码规范 | 以后前端和 AI 都能按同一套规则对接 |
| **业务线** | 分层结构：请求入口 → 业务逻辑 → 数据访问；参数校验占位；权限校验占位 | 未来新增功能不会把逻辑全堆在一起 |
| **运维线** | 统一日志输出；全局异常处理；数据库连接验证；README 写清启动、配置、测试方式 | 出问题时能排查，能交接 |

**产出**：一个可启动的后端项目骨架，提交 Git。

---

### 第 4 步：骨架验证与修复
**目标**：对骨架进行基础验证，确保四条线都真正跑通，而不是只看 AI 说“完成”。

**验证清单**：
- [ ] 执行启动命令，无报错，`/health` 返回成功。
- [ ] 修改配置文件后重启，配置项生效。
- [ ] 调用一个不存在的路由，返回统一格式的 404。
- [ ] 模拟参数错误的请求，返回统一错误格式。
- [ ] 检查分层：新建一个测试模块，能否在不修改已有框架代码的情况下完成接入。
- [ ] 日志正常输出到控制台或文件。
- [ ] README 按步骤操作可独立复现启动流程。

**问题修复**：任何一项不通过，都先要求 AI 解释原因，再修正，直至全部通过。

---

### 第 5 步：归档并锁定规则
1. 将架构设计文档、骨架代码一并提交 Git，标注为 `chore: init backend scaffold`。
2. 将以下核心规则写入 Agent 宪法：
   - 后端开发必须遵守架构设计文档。
   - 新增接口必须沿用统一响应格式和错误码规范。
   - 新增依赖、调整目录、更换框架组件必须先更新架构设计文档并说明原因。
3. 后续业务开发时，每个模块严格按骨架的分层和规范进行，每完成一个稳定功能就提交一次。

---

## 三、检查清单

- [ ] 语言与框架选型已复核，无过度设计
- [ ] 架构设计文档已生成，涵盖选型理由、规范、目录、接口、错误、日志等
- [ ] 目录结构已解释清楚，框架推荐与项目自定义部分已区分
- [ ] 骨架已包含启动线、接口线、业务线、运维线，且无完整业务功能
- [ ] 健康检查接口可正常访问
- [ ] 统一成功/失败响应格式已验证
- [ ] 请求 → 业务 → 数据访问分层清晰
- [ ] 日志与异常处理可正常工作
- [ ] README 中启动步骤可独立复现
- [ ] 代码已提交 Git，规则已加入宪法

---

> 后端骨架搭建的本质，是让项目从一开始就拥有一套可执行的工程纪律。先定规则，再跑通骨架，最后在规则里生长出业务功能——这才是非技术用户驾驭 AI 后端开发的正确路径。
