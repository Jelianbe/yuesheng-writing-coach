# 验收规则与标准及流程

> 适用于 AI 辅助编程中后端架构的验收。核心原则：不看 AI 说“完成”，只看它拿什么证明完成。以下流程将后端架构验收拆解为七个步骤，每一步都要求 AI 提供可核查的证据，确保架构能够支撑后续业务开发。

---

## 一、核心原则

- **证据驱动**：每一项验收必须伴随可查的文件、命令、返回示例、日志结果，模糊描述视为未通过。
- **规则优先**：验收的重点是“后续开发能否按统一规则生长”，而非当前功能是否可用。
- **分层核验**：从规则审计、目录责任、请求链路、接口规范、框架复用、运行验证六个维度逐项确认。
- **拒绝糊弄**：“已完成”“已优化”“基本完成”等无证据表述一律视为未验证，必须诚实标记。
- **收口存档**：验收结果汇总成《后端架构实施真源文档》，作为后续开发的绝对依据，并在 Agent 宪法中引用。

---

## 二、验收流程

### 第一步：规则审计——要求 AI 出具带证据的验收报告
**目的**：让 AI 对照架构设计文档，逐一证明每条规则已落地。

**验收指令模板**：
> “请根据项目实际业务文档和项目架构设计文档，对后端架构层代码做详细审计和验收。每一项必须说明：规则来源、对应文件、验证方式、实际结果，没有证据的项目标记为未验收，不允许写‘通过’。”

**验收标准与检查点**：
- [ ] 每一项验收结论都有具体的文件路径、命令或截图作为证据。
- [ ] 未验证的项目已明确标出，而非被“基本完成”掩盖。
- [ ] 不存在与后续业务逻辑明显冲突的设计。
- [ ] AI 的解释通俗易懂，无大量无意义技术名词堆砌。

---

### 第二步：目录责任验收——输出目录责任表
**目的**：确认每个目录的职责边界清晰，符合框架惯例和项目自定义需求。

**验收指令模板**：
> “请根据当前后端架构输出目录责任表。每一行包含：目录、主要职责、以后应该放什么、禁止放什么、对应的框架机制、示例文件。标注哪些目录来自框架推荐，哪些是项目自定义。同时说明请求入口、业务规则、数据库访问、参数校验、错误处理、权限校验入口分别在哪个目录或机制。”

**验收标准与检查点**：
- [ ] 每个目录有且仅有一个清晰的主要职责。
- [ ] 明确规定了该目录“应该放什么”和“禁止放什么”。
- [ ] 框架推荐目录与项目自定义目录已区分，自定义目录有正当理由。
- [ ] 请求入口、业务逻辑、数据访问、校验、错误处理等职责在目录层面被明确分离，没有含糊表述（如多个目录都写“处理业务逻辑”）。

---

### 第三步：最小模块演练——验证分层能否落地
**目的**：通过一个极简的模拟模块，检验架构的分层规则能否被实际执行，而不依赖于业务复杂度。

**验收指令模板**：
> “请做一次最小模块演练，不写完整业务代码，只输出文件清单和调用路径。说明：需要新增或修改哪些文件，每个文件放哪个目录、负责什么；请求从哪里进入，参数在哪里校验，业务规则放在哪里，数据访问放在哪里，统一响应和错误处理在哪里完成。这些安排是否符合项目架构设计文档。”

**验收标准与检查点**：
- [ ] 文件放置完全符合第二步产出的目录责任表。
- [ ] 请求入口、参数校验、业务规则、数据访问、统一响应、错误处理在文件层面被清晰分离。
- [ ] 不存在“所有逻辑写在一个接口/函数里”的现象。
- [ ] 演练结果稳定，不应出现每次回答文件都不一样的情况。

---

### 第四步：接口返回示例验收——提供具体场景 JSON 示例
**目的**：确认统一响应格式已真正实现，覆盖成功与失败的各类典型场景。

**验收指令模板**：
> “请输出当前后端架构的接口响应样例。至少包含：列表成功、详情对象成功、创建成功、更新成功、删除成功、空列表、参数错误、未登录、无权限、资源不存在、系统异常。每个场景给出 HTTP 状态码、响应 JSON 示例，并说明由哪个文件或框架机制统一处理。”

**验收标准与检查点**：
- [ ] 列表场景示例中包含数组、分页信息、总数等字段。
- [ ] 对象场景示例中包含完整的详情数据或操作后的最新数据。
- [ ] 每个错误场景有明确的 HTTP 状态码（优先使用标准状态码，如 400/401/403/404/500），且有统一的响应体结构。
- [ ] 存在明确的“统一处理机制”（如中间件、响应封装函数），并在示例中指向具体文件。
- [ ] 若使用自定义业务错误码，必须已在架构设计文档中定义格式和规则。

---

### 第五步：框架复用与封装边界验收
**目的**：确保充分复用框架内置能力，自定义封装有充分且必要的理由，杜绝过度设计。

**验收指令模板**：
> “请审查当前后端架构的框架复用和封装边界。哪些能力直接复用了框架，哪些是项目自定义封装？每个自定义封装解决什么问题，如果去掉会有什么影响？是否存在为了显得专业而提前封装的内容？”

**验收标准与检查点**：
- [ ] 参数校验、异常处理、HTTP 状态码、路由分组、中间件、日志等能力优先使用框架原生机制。
- [ ] 每个自定义封装都有明确的解决问题，且当前已被使用（而非“以后可能用”）。
- [ ] 不存在可以被框架能力替代的重复封装。
- [ ] 自定义封装的相关规则已记录在架构设计文档中。

---

### 第六步：运行证据包验收——固定启动、配置、数据库和日志
**目的**：将项目的运行方式固定下来，避免后续开发中依赖重新猜测启动方式。

**验收指令模板**：
> “请输出后端架构运行证据包。包含：依赖安装命令、启动命令、服务监听端口、健康检查命令和结果、配置读取位置、`.env.example` 内容检查、数据库连接验证方式和结果、请求日志示例、错误日志示例。每一项都要写明实际执行结果，没有执行的项目标记为‘未验证’。”

**验收标准与检查点**：
- [ ] 启动命令明确，且经实际执行验证可成功启动。
- [ ] 配置文件位置和示例文件（`.env.example`）已给出，敏感信息无硬编码。
- [ ] 健康检查接口可访问，并返回成功响应。
- [ ] 数据库连接已验证，并提供验证方式和成功结果。
- [ ] 请求日志和错误日志均有实际输出示例，日志入口固定。
- [ ] 不存在“理论上可以启动”等未经证实的表述。

---

### 第七步：收口成《后端架构实施真源文档》并提交存档
**目的**：汇总所有验收结论，形成后续开发的绝对规则依据，并与 Agent 宪法联动。

**验收指令模板**：
> “请汇总本次后端架构验收结果。不要重新发散或重复解释。每项列出：验收项、是否通过、证据位置、未通过原因、下一步处理、是否影响进入业务开发。最后给出明确结论：当前后端架构是否可以开始写业务功能。没有证据的项目必须标记为未验证。”

**验收标准与检查点**：
- [ ] 汇总报告中每一项的通过/未验证状态明确。
- [ ] 未通过项指出了具体的阻塞原因和处理建议。
- [ ] 给出明确的“是否可以进入业务开发”的最终结论。
- [ ] 所有关键项（目录责任、接口示例、错误处理、启动证据）均已通过，方可进入业务开发。
- [ ] 若通过，AI 已基于验收结果生成《后端架构实施真源文档》，内容完整（语言框架、规则来源、目录责任、模块组织、接口规范、错误处理、启动配置证据、框架复用边界等）。
- [ ] Agent 宪法中已添加引用条款（例如：“后端开发必须先读取并遵守《后端架构实施真源文档》”），详细规则不塞入宪法。
- [ ] 最终架构代码连同真源文档一并提交 Git，形成稳定版本。

---

## 三、验收通过后的标准动作

- [ ] **Git 存档**：将当前通过验收的后端架构作为第一个稳定版本提交，标注为 `chore: backend scaffold verified`。
- [ ] **真源文档入库**：确保《后端架构实施真源文档》放置在项目 `docs/` 目录下，并纳入版本管理。
- [ ] **宪法引用**：在 Agent 宪法中添加后端开发最高约束条款，指向真源文档。
- [ ] **未验证项闭环**：任何未验证项都必须在进入业务开发前排定处理计划，不得以“基本完成”掩盖。

---

> **记住**：验收不是走形式，而是给后续开发铺设安全轨道。你没有技术背景，但你有权利要求 AI 留下每一条规则对应的证据。不看代码，看证据；不听“完成”，看证明。
