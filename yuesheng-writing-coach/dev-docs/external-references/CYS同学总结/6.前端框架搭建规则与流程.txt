# 前端框架的搭建规则与流程

> 用 AI 做前端项目，第一步不是写页面，而是搭骨架。骨架定好了，后面所有页面都长在同一套规则上；没有骨架，页面越多越乱。以下是一套适用于 AI 辅助编程的前端框架搭建标准流程。

---

## 一、核心原则

- **规则优先于页面**：先确定设计风格、技术方案、目录规范、组件复用规则，再动手写页面。
- **成熟框架/组件库优先**：不使用 AI 从零发明项目结构和 UI 组件，必须基于成熟方案并遵守其官方规范。
- **样式统一靠系统**：颜色、字号、间距等通过设计 Token 统一管理，不允许硬编码。
- **组件复用强制化**：同类 UI 结构出现超过两次，必须封装为可复用组件。
- **分步实施，阶段提交**：先让基础骨架跑通并 Git 存档，再按模块逐个添加功能。

---

## 二、前端骨架搭建流程（6 步）

### 第 1 步：确定整体设计风格
**目标**：为项目选定一套统一的视觉语言，让 AI 有明确的风格参照。

**操作**：
1. 如果你有明确偏好，直接描述风格方向（极简、科技感、管理后台等）。
2. 如果不确定，找 2-3 个你喜欢的网站或 App 截图，把链接或图片发给 AI。
3. 让 AI 完成以下分析：
   > “请分析这些界面的视觉风格、配色方案、字体层级、间距规律、组件形态，总结出一套设计风格关键词和要点，并判断是否适合我的项目（项目类型：XXX）。”
4. 与 AI 讨论后，锁定一个风格方向，并用简短关键词固定，例如：“现代极简 SaaS 风格，卡片式布局，蓝色主色调，Inter 字体，大留白”。

**产出**：一段风格定义描述，作为后续所有页面设计的依据。

---

### 第 2 步：选定前端技术方案与 UI 组件库
**目标**：确定项目组织方式（框架）和界面元素来源（组件库），并明确两者边界。

**操作**：
1. 将产品形态、项目复杂度、你的部署需求告诉 AI，要求给出唯一推荐。
   > “根据我的项目（Web 应用，中等复杂度，后期可能扩展移动端），推荐一套前端技术方案 + UI 组件库组合。只推荐一个主线方案，说明为什么选它，为什么不选其他常见方案。”
2. 让 AI 对推荐的组件库进行可靠性审查：维护状态、GitHub star、文档完整度、许可证。
3. 锁定后，对 AI 施加硬性约束：
   > “本项目必须严格遵循 [框架名] 的官方目录结构和最佳实践，UI 元素必须优先使用 [组件库名] 提供的组件，禁止绕开框架设计或手写重复组件。”

**产出**：确定的前端框架名（如 Next.js）、UI 组件库名（如 Ant Design），以及一份可靠性审查结论。

---

### 第 3 步：制定目录结构、模块边界与组件复用规则
**目标**：让 AI 知道文件往哪放、模块怎么隔离、什么情况必须封装组件。

**操作**：
1. 让 AI 根据选定的框架和组件库，生成一份标准目录结构。
   > “根据 Next.js 官方规范和 Ant Design，生成一个本项目的基础目录结构。说明每个目录的用途，页面放哪里、公共组件放哪里、请求模块放哪里、工具函数放哪里。”
2. 与 AI 一起划分模块边界：登录、用户、订单、内容、设置等功能区域分别放在哪些目录下。
3. 明确组件复用规则，并将其写入项目规范：
   > “同类 UI 结构在项目中出现的次数超过 2 次时，必须抽象为可复用组件，放置在 `components/common/` 下。不允许在页面中复制粘贴重复的 UI 代码。”

**产出**：一份含模块说明的目录结构图，以及一条可写入 Agent 宪法的组件复用规则。

---

### 第 4 步：建立样式系统（设计 Token、多语言、主题）
**目标**：用变量统一所有视觉属性，杜绝硬编码样式。

**操作**：
1. 让 AI 根据第 1 步确定的风格，生成一套设计 Token。
   > “请基于‘现代极简蓝白风格’生成一套前端设计 Token，包括：主色/辅色/中性色色板、字号层级（标题/正文/辅助）、间距梯度（xs/sm/md/lg/xl）、圆角值、阴影层级。输出为 CSS 变量或 JS 对象均可。”
2. 如果项目未来可能支持多语言，要求文案统一管理。
   > “项目中所有面向用户的文案（按钮文字、标题、提示信息）必须提取为文本常量，存放在独立的文案文件中，不允许在页面中硬编码。”
3. 确定主题扩展规则：主色调可以通过修改少量变量全局切换，不允许在各处单独指定颜色。

**产出**：一套设计 Token 文件（或变量清单）、文案管理方案、主题规则约束。

---

### 第 5 步：编写前端实施计划并归档
**目标**：将以上所有决策形成书面计划，作为后续开发的指令和验收依据。

**操作**：
让 AI 生成一份 `docs/frontend-plan.md`，至少包含：
- 设计风格描述
- 前端技术方案（框架 + 组件库 + 关键依赖）
- 目录结构说明
- 模块边界划分
- 组件复用规则
- 设计 Token 概览
- 多语言/主题预留方案
- 第一阶段实施范围（只搭骨架，包含哪些页面和基础组件）
- 验收标准（项目能启动、路由正确、组件库正常加载、基础布局无异常等）

**产出**：`docs/frontend-plan.md` 文档，并与 AI 确认：“后续所有前端开发必须以此文档为基准。”

---

### 第 6 步：搭建基础骨架并提交 Git
**目标**：让项目跑起来，得到一个结构正确、可扩展的起点，然后存档。

**操作**：
1. 指示 AI 按实施计划搭建骨架，严格限制范围。
   > “请严格按照《前端实施计划》创建项目骨架。现阶段只做：项目初始化、路由骨架（首页+占位页）、全局布局组件、组件库接入、设计 Token 配置。不要添加具体业务功能，确保项目能启动、首页能打开即可。”
2. 骨架跑通后，让 AI 总结变更并提交。
   > “请总结本次搭建的内容，以 `chore: 初始化前端项目骨架` 格式提交一次 Git。”
3. 之后按模块逐个开发，每完成一个模块稳定后提交一次。

**产出**：一个可运行的、结构规范的前端项目基础，以及一次 Git 存档。

---

## 三、前端开发关键规则（建议写入 Agent 宪法）

在项目宪法中补充以下条款，约束 AI 的日常行为：

```markdown
## 前端开发规则
1. **框架规范优先**：所有代码必须遵循已选定前端框架的官方目录结构和最佳实践。
2. **组件库复用**：UI 组件优先使用选定组件库，禁止手写已有官方组件的替代实现。
3. **组件抽象规则**：同类 UI 结构出现超过 2 次，必须封装为通用组件，禁止复制粘贴。
4. **样式 Token 强制**：颜色、字号、间距、圆角、阴影必须从设计 Token 中引用，严禁硬编码。
5. **文案统一管理**：所有用户可见文案存放在指定文案文件中，不在组件内直接写死文本。
6. **模块边界不可跨**：修改一个功能模块时，不得随意改动其他模块的内部文件。
```

---

## 四、验收标准与检查清单

骨架阶段完成时逐项检查：

- [ ] 项目能无错误启动，首页可正常打开
- [ ] 路由结构正确，页面层级关系符合预期
- [ ] 目录结构符合框架规范，模块边界清晰
- [ ] UI 组件库已正确接入，测试组件可正常渲染
- [ ] 设计 Token 已定义且全局可用，颜色/字号等通过变量引用
- [ ] 存在全局布局组件（Header/Footer/Sidebar 等占位即可）
- [ ] 文案管理文件已创建，至少有一处示例使用
- [ ] 组件复用规则已文档化，并已告知 AI 必须遵守
- [ ] Git 已完成首次存档，提交信息规范
- [ ] 前端实施计划文档已生成并放置在项目目录中

## 五、常见问题

**Q: 我是新手，不知道选什么框架和组件库怎么办？**
A: 把项目类型（官网/后台/SaaS/小程序）告诉 AI，让它只推荐一套最主流的组合。比如：后台管理 → React + Ant Design；内容网站 → Next.js + Tailwind CSS。不用纠结，先用起来。

**Q: 设计 Token 听起来很专业，不会写怎么办？**
A: 直接让 AI 生成。你只需描述“我想要一套简洁的蓝色系设计变量”，AI 会输出完整的 CSS 变量或 JS 配置文件。

**Q: 组件复用规则怎么才算“相似度高”？**
A: 一个简单判断：如果两个地方的按钮、卡片、列表项只在文字内容上不同，但结构和样式几乎一样，就算同类。你可以让 AI 在写代码时主动提醒：“这个结构和之前 XX 组件重复了，建议复用。”

**Q: 骨架搭完后能不能让 AI 一口气把所有页面做了？**
A: 坚决不要。骨架之后应该按模块（登录、用户中心、核心功能页等）逐个开发、逐个验收、逐个提交。一次性铺开十几个页面，出了问题你都不知道 AI 改乱了哪里。

---

> 记住：**前端骨架的本质不是做页面，而是立规矩。** 规矩立好了，AI 写的每一行代码都会长在同一棵树上，项目才能持续生长而不腐烂。
