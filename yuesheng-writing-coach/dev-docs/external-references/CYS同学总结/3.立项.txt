# 项目立项流程与标准

> 立项是 Vibe Coding 的第一步：不写代码，先与 AI 讨论产品方向，并把结论沉淀为可回溯的文档。  
> 本流程与标准适用于使用 AI IDE 从零开始的项目，需配合《Agent 宪法》和《Skill 选择纲要》共同使用。

---

## 一、核心原则
- **代码之前，先有共识**：AI 不知道你真正想要什么，讨论清楚才能避免方向错误。
- **方向错误是最大的成本**：数据结构、功能边界、页面流程一旦跑偏，往往不是修几行代码，而是整个地基重来。
- **文档是防漂移锚点**：所有后续开发、任务拆解、技术选型，都必须回到立项文档找依据。

---

## 二、立项流程（五步走）

### 第一步：创建项目空间
- 新建一个**空文件夹**，用 AI IDE 打开。
- 命名规范：英文 + 中划线/下划线（如 `task-manager`、`resume_assistant`）。
- 此文件夹暂不包含代码，用于存放立项文档、宪法、开发计划等一切项目资产。

### 第二步：发起立项讨论
- **直接告诉 AI**：  
  > “我准备做一个 XX 类型的产品，大致功能是 XX。你先帮我梳理这个项目的核心设计，追问我不清楚的地方，我们先把产品搞清楚，暂时不写代码。”
- 如果只有模糊方向：  
  > “我只有一个大概想法，帮我一起梳理这个项目应该怎么做。”
- **禁止 AI 写代码**：必须明确拦住，让 AI 进入“产品合伙人 + 架构顾问”角色。

### 第三步：结构化讨论（至少覆盖以下主题）
| 讨论维度 | 关键问题 |
|----------|----------|
| 用户与场景 | 谁在用？在什么场景下用？解决什么痛点？ |
| 核心功能与 MVP | 第一版必须有的功能是什么？哪些功能坚决不做？ |
| 用户路径 | 从进入到完成核心操作，页面怎么走？数据怎么流动？ |
| 业务对象 | 项目里有哪些核心对象（用户、订单、任务、文章……）？ |
| 差异点 | 和同类产品比，为什么用户要用你的？ |
| 技术路线 | 做网页/小程序/App？是否先做 Web MVP？前后端大致怎么考虑？ |
| 里程碑 | 第一版做完的标准是什么？第二版扩展什么？ |
| 验收规则 | 第一版做到什么程度才算完成？（可检查的标准，而非模糊感觉） |

### 第四步：沉淀立项文档
- 让 AI 根据讨论内容，在项目文件夹下生成 **立项文档**（Markdown 格式）。
- 文档必须包含下文所列的“立项文档标准内容”。
- 可依据项目复杂度，拆分为一份或多份文件，但核心信息必须完整、清晰。

### 第五步：确认与锁定
- 通读文档，确认你的意图和 AI 的理解一致。
- 明确告诉 AI：  
  > “后续所有开发、任务拆解、技术选型，都以这份立项文档为依据，不得随意偏离。”
- 文档进入版本管理，后续如有方向变更，必须更新文档，而非仅在对话中口头改动。

---

## 三、立项文档标准内容

任何项目立项文档都必须覆盖以下板块，缺一不可：

1. **项目定义**  
   - 项目名称、一句话描述、面向用户、解决的核心问题、为何值得做。

2. **第一版核心目标**  
   - 第一版要达到的量化或定性目标（例如：用户能完成 XX 流程，核心数据能跑通等）。

3. **功能范围与边界**  
   - **包含功能**（MVP 必须实现）。  
   - **明确排除功能**（第二版或更晚才做）。  
   - **放弃的想法**（讨论过但决定不做的方向，避免后续反复）。

4. **用户路径与页面流程**  
   - 典型用户从进入产品到完成核心任务的步骤、页面跳转、关键交互。

5. **核心业务对象与数据流**  
   - 列出系统中的关键实体及其关系（用户、订单、文章、评论等），初步描述数据如何产生、存储和流转。

6. **技术路线初步判断**  
   - 平台形态（Web MVP / 小程序 / App），前端、后端、数据库的大致技术栈倾向，是否使用第三方服务等。

7. **差异化与优势点**  
   - 相比已有产品的独特价值，哪怕是微小的切入点差异。

8. **里程碑与版本规划**  
   - V1.0 完成标准，V2.0 预想扩展，长期可选路线。

9. **验收标准**  
   - 可执行、可判断的完成条件（如：功能路径全部走通且无报错，核心数据正确入库，边界情况有处理等）。

---

## 四、角色与行为准则
在立项阶段，AI 必须遵守以下行为准则（由宪法和 Skill 体系配合约束）：
- **只讨论、不编码**：除非用户明确要求生成文档本身，否则不得创建代码文件、安装依赖。
- **多追问、少假设**：对模糊信息主动提问，不自行脑补用户需求。
- **保持产品视角**：优先思考“解决什么价值”，而非“技术如何实现”。
- **输出必须结构化**：讨论结论整理为清单、表格、用户路径图（文字描述）等形式，便于形成文档。

---

## 五、检查清单
在正式进入开发前，逐项确认：

- [ ] 项目文件夹已创建，命名规范。
- [ ] AI 已明确理解当前阶段只讨论、不写代码。
- [ ] 用户与核心场景已清晰描述。
- [ ] MVP 功能列表已列出，排除项已明确。
- [ ] 核心业务对象和数据流已初步梳理。
- [ ] 用户操作主路径已推演无断点。
- [ ] 技术路线有初步判断，未陷入过度设计。
- [ ] 验收标准具体可衡量。
- [ ] 完整立项文档已生成并放置在项目目录中。
- [ ] 文档已经你本人确认，并指示 AI 以此为后续开发依据。

---

> 记住：**立项不是追求完美，而是给项目一个足够清晰的起点。**  
> 文档可以迭代，但绝不能没有。没有立项的 AI 项目，就像没有图纸的施工队，做得越快，塌得越彻底。
