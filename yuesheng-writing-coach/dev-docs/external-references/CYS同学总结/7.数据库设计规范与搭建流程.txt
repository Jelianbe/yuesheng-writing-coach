# 数据库设计规范与搭建流程

> 数据库不是凭空建出来的，而是从业务流程里长出来的。以下规范与流程专为 AI 辅助编程场景设计，确保每张表、每个字段都有据可依，后期可维护、可扩展。

---

## 一、核心原则

- **业务先行**：先理清业务对象和关系，再设计表结构，禁止跳过讨论直接建表。
- **关系型优先**：有用户、权限、交易或复杂查询需求的项目，优先选择 MySQL、PostgreSQL 等关系型数据库。
- **范式约束**：默认遵循前三范式，减少冗余和不一致；反范式必须说明理由。
- **字段规范统一**：命名、类型、必备字段、状态枚举等提前约定，杜绝临时决策。
- **设计文件即真相源**：所有结构变更必须从 Schema/Migration 文件发起，文件纳入 Git 管理。
- **分步验证，阶段提交**：基础结构跑通后立即存档，再进入接口与业务开发。

---

## 二、数据库设计搭建流程（8 步）

### 第 1 步：从业务中梳理核心对象
- **目的**：确定系统要管理哪些“实体”。
- **输入**：前端页面原型、立项文档、功能说明。
- **方法**：  
  让 AI 根据页面和用户操作反推数据，如：注册登录 → 用户信息；订单列表 → 订单信息；权限管理 → 角色、权限。
  > 提示词示例：“根据当前的项目页面和功能列表，整理出所有核心业务对象，并说明每个对象对应的业务场景。暂不建表。”
- **产出**：业务对象清单（如：用户、商品、订单、支付记录、收货地址、文章、评论等）。

### 第 2 步：确认对象之间的关系
- **目的**：明确实体间如何关联，避免表关系混乱。
- **关系类型检查**：
  - 一对一：如用户与用户详情（扩展表）。
  - 一对多：如用户 → 订单，文章 → 评论。
  - 多对多：如用户 ↔ 角色（需关联表）。
- **操作**：  
  要求 AI 画出关系简述并解释：
  > “请说明以上业务对象之间是什么关系（一对一/一对多/多对多），关联字段放在哪张表里，为什么这样设计。”
- **产出**：业务对象关系图（文字或简易 ER 说明），明确外键位置。

### 第 3 步：确定数据库服务
- **选型依据**：项目类型、数据复杂度、并发预期。
- **推荐策略**：
  - Web 应用、后台、SaaS、电商 → **MySQL / PostgreSQL**
  - 轻量本地工具 → SQLite
  - 缓存/队列 → Redis（不作为主库，除非明确需求）
- **操作**：  
  让 AI 给出唯一推荐并说明理由：
  > “根据当前项目特点，推荐一个主数据库，说明选型理由、本地与线上部署同步方案，以及是否需要 Redis 等辅助服务。”
- **产出**：确定的数据库服务及部署方案。

### 第 4 步：设计表结构与字段（遵循范式）
- **范式要求**：
  - **第一范式**：字段原子化，一个字段只存一个值，不拼串。
  - **第二范式**：非主属性完全依赖于主键，不存无关数据。但保留历史快照（如订单中的收货地址）需明确说明原因。
  - **第三范式**：消除传递依赖，如已有城市 ID，就不重复存城市名称。
- **约束指令**：
  > “数据库设计必须符合前三范式。任何反范式设计（如冗余字段）必须提前说明原因并记录在文档中。”
- **操作**：  
  让 AI 基于对象和关系生成表结构草稿，逐表校验范式合规性。

### 第 5 步：统一字段与命名规范
- **命名**：表名、字段名统一使用英文小写+下划线（如 `user_id`、`order_status`），避免拼音和保留字。
- **必备字段**：每张业务表至少包含：
  - `id`：主键，通常自增或 UUID。
  - `created_at`：创建时间，自动维护。
  - `updated_at`：更新时间，自动维护。
  - `deleted_at`：软删除标记（订单、财务等不可真删的数据必须添加）。
- **特殊字段处理**：
  - 密码：统一存 `password_hash`，严禁存明文。
  - 金额：用分为单位的整数或 `DECIMAL`，避免浮点数。
  - 状态字段：提前定义枚举（如 `pending / paid / canceled / refunded`），禁止让 AI 随意写字符串。
- **字段类型**：关键字段（手机号是否国际、金额精度、状态扩展性）需人工逐项确认。

### 第 6 步：生成数据库设计文件（Schema / Migration）
- **重要**：不直接连库建表，先用设计文件“签字画押”。
- **文件形式**：
  - SQL 脚本（如 `schema.sql`）
  - 框架 Migration 文件（如 Rails/Django/Laravel 的迁移文件）
  - ORM 模型定义（如 Prisma Schema、TypeORM Entity）
- **操作**：  
  > “请根据已确认的表结构生成完整的 Schema/Migration 文件，先不要执行建表。生成后让我核对。”
- **核对要点**：业务对象是否齐全、关系是否正确、字段规范是否遵循、范式是否符合。
- **确认无误后**，执行建表指令并生成测试数据验证。

### 第 7 步：写入实施计划并归档
- **文档要求**：在项目文档中记录以下内容，形成《数据库设计说明》：
  - 业务对象及关系
  - 数据库选型及理由
  - 表结构总览（字段、类型、约束、备注）
  - 外键关系说明
  - 范式遵循情况（含反范式原因）
  - 软删除策略
  - 验收标准（能连接、建表、插入和查询测试数据）
- **版本管理**：Schema/Migration 文件和设计说明文档一并提交 Git，作为后续变更的基准。

### 第 8 步：搭好基础结构，阶段存档
- **第一步目标**：数据库能正常连接、核心表创建成功、Migration 可执行、测试数据可读写。
- **不要**：在此阶段铺满完整业务字段，仅需覆盖核心对象的基础结构。
- **完成后**：执行 `git commit`，将此时的数据库状态存档。
- **后续变更规则**（写入 Agent 宪法）：
  > “任何数据库结构变更，必须先修改 Schema/Migration 文件并说明原因，再执行数据库操作。禁止绕过设计文件直接修改线上库。”

---

## 三、数据库设计检查清单

设计完成后逐项确认：

- [ ] 所有业务对象已提炼，无遗漏核心实体
- [ ] 对象间关系已明确，外键位置正确
- [ ] 数据库服务已选型，AI 说明了理由和部署方案
- [ ] 每张表都遵循前三范式（或反范式已注明原因）
- [ ] 表名、字段名采用英文下划线规范命名
- [ ] 每张表包含 `id`、`created_at`、`updated_at` 基础字段
- [ ] 需要审计的表已添加 `deleted_at` 软删除字段
- [ ] 密码字段使用哈希存储，金额使用精确类型
- [ ] 状态字段定义了固定枚举值
- [ ] Schema/Migration 文件已生成，内容与设计一致
- [ ] 已执行建表，测试数据插入和查询正常
- [ ] 设计文档和 Migration 已提交 Git

---

## 四、常见避坑提醒

- **禁止 AI 猜测字段**：必须基于页面、流程图或你明确的需求指定，否则会多出无意义字段或漏掉关键字段。
- **金额和时区**：金额精度和货币单位提前确认；时间字段统一使用 UTC 或明确时区策略。
- **索引不是越多越好**：初期仅对主键和外键建索引，后续根据慢查询分析再添加。
- **预留扩展但不过度设计**：状态字段可使用字符串枚举并预留扩展值，但不要在初期就设计复杂继承或多态关联。
- **每一次结构变更都走 Migration**：AI 很可能图省事直接改线上表，必须用宪法规则禁止。

---

> 数据库设计的第一准则：**让它说清楚你的业务，而不是仅能存下数据。**  
> 按此流程，你的数据库会像建筑图纸一样清晰，AI 后续写接口、做统计、加功能时，才有稳固的地基。
