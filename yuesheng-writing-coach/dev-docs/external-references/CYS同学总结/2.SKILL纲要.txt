# Skill 选择纲要

> 本纲要与《Agent 宪法》配合使用：**宪法管原则（什么能做、什么不能做），Skill 管流程（具体怎么做）**。  
> 每次调用 Skill 时，其执行必须遵守宪法中的边界、禁区、决策优先级和完成标准。

---

## 一、选择总则

1. **宪法优先**：任何 Skill 的执行不能突破宪法定义的边界、禁区。如 Skill 流程与宪法冲突，以宪法为准。  
2. **按需加载**：不将所有 Skill 同时加载，仅在语义匹配或用户明确指定时才激活对应 Skill。  
3. **目的导向**：根据当前任务的**核心目的**选择 Skill，避免过程性过度编排。  
4. **可组合**：复杂任务可能需要多个 Skill 顺序或并行协作，此时可用调度类 Skill 协调。  
5. **可干预**：用户可主动指定或强制使用某 Skill，AI 不得绕过用户意图自由发挥。

---

## 二、任务场景与 Skill 映射

| 核心目的 | 典型触发语句 | 推荐 Skill | 对应流程要点 |
|----------|--------------|------------|--------------|
| 需求澄清与设计 | “帮我分析一下这个想法该怎么实现”<br>“先别写代码，讨论方案” | **Brainstorming** | 避免一上来就写代码；先理清需求、约束、设计取舍，形成设计方向。 |
| 制定执行计划 | “把这个需求拆成开发任务”<br>“列一个实现步骤” | **Writing Plans** | 将需求拆解为可执行、可验证的任务序列，明确依赖关系和顺序。 |
| 排查 Bug 或异常 | “这个功能报错了”<br>“帮我找出为什么页面卡顿” | **Systematic Debugging** | 遵循“复现→缩小范围→根因定位→修复验证”系统化流程，禁止猜测。 |
| 确认完成并交付 | “我做好了，检查一下”<br>“这个功能算完成了吗？” | **Verification Before Completion** | 强制自证：提供测试步骤、边界覆盖、无新增问题，未完成项显式声明。 |
| 代码审查 | “帮我看一下这段代码有什么风险”<br>“审查一下最近的提交” | **Requesting Code Review** | 以独立视角检查安全、性能、可维护性、规范遵循，输出风险清单。 |
| 多任务并行推进 | “同时做 A 和 B”<br>“把这几个独立任务一起跑” | **Dispatching Parallel Agents** | 判断任务无依赖后可并行派发，保证各自遵守宪法，最终汇总结果。 |
| 前端/页面验证 | “打开浏览器看看效果”<br>“检查页面在不同尺寸下的表现” | **Browser** | 启动浏览器进行截图、交互验证、控制台检查，不凭口头描述下结论。 |
| 完整工程流协作 | “按工程标准做完这个功能”<br>“从计划到交付全流程” | **Slaver Engineering Workflow** | 架构优先、溯源优先、严格验收，覆盖从设计到交付的完整闭环，防漂移。 |

## 三、Skill 简要清单及说明

### 1. Brainstorming
- **定位**：需求与设计探讨
- **何时用**：用户提出模糊想法、需求不明确、需要多方案对比时。
- **核心约束**：此阶段只产出设计说明和方案建议，**禁止直接修改代码**。

### 2. Writing Plans
- **定位**：任务计划拆解
- **何时用**：需求已明确，需转换为具体开发步骤时。
- **核心约束**：计划需包含每步的验收标准和依赖关系，不确定项应标为“待澄清”。

### 3. Systematic Debugging
- **定位**：系统化排错
- **何时用**：报告异常、错误、性能问题，且根因不明时。
- **核心约束**：禁止直接“试试这样改”，必须先记录现象、划定范围、定位确切根因后再提供修复方案。

### 4. Verification Before Completion
- **定位**：完成前自证
- **何时用**：AI 认为任务已完成，准备交付结论时。
- **核心约束**：必须给出可复现的验证证明，覆盖正常与异常情况；未完成项必须用“⚠️ 待确认”标明。

### 5. Requesting Code Review
- **定位**：代码审查
- **何时用**：提交前质量把关、引入新模块、修改核心逻辑后。
- **核心约束**：以评审者视角输出风险点、改进建议，不修改代码本身，除非明确要求重构。

### 6. Dispatching Parallel Agents
- **定位**：多代理并行调度
- **何时用**：存在多个无依赖关系的独立任务时。
- **核心约束**：每个并行任务必须仍然遵循宪法和各自适用的 Skill，最终汇总结果。

### 7. Browser
- **定位**：浏览器交互验证
- **何时用**：前端页面、UI 组件、交互功能需要实际查看时。
- **核心约束**：一切验证结论以截图或浏览器实际输出为准，不得凭代码推测。

### 8. Slaver Engineering Workflow
- **定位**：完整工程流
- **何时用**：需要端到端按专业标准完成一个特性，从设计、实现到验证时。
- **核心约束**：严格执行“设计→计划→实现→自查→审查→验收”闭环，不跳步，不妥协架构。

---

## 四、使用注意

- **触发方式**：大多数情况下 IDE 会根据语义自动匹配 Skill，无需手动指定。若自动匹配不准，可明确说出 Skill 名称（如“用 Systematic Debugging 排查这个错误”）。
- **宪法约束**：无论使用哪个 Skill，都必须遵守 Agent 宪法中的**边界（不能动的文件/目录）**、**行为禁区**、**决策优先级**和**完成标准**。
- **组合示例**：  
  - 大需求：`Brainstorming` → `Writing Plans` → 逐任务实施（可能嵌入 `Verification Before Completion`） → 最终 `Requesting Code Review`。  
  - 紧急修复：`Systematic Debugging` → 修复 → `Verification Before Completion`。  
  - 前端页面：`Browser` + `Verification Before Completion` 联合使用。
- **自制与适配**：若项目有特殊流程，可让 AI 基于已有 Skill 改造或创建新 Skill，但仍需保持与宪法一致。

---

> 这份纲要不是执行清单的死板顺序，而是帮助你在不同任务场景下**快速命中正确流程**的导航图。  
> 始终牢记：**宪法立规矩，Skill 给方法，两者结合才能让 AI 真正做出可维护的项目。**
