# 后端业务边界界定与规则梳理流程

> 后端的核心不是写接口，而是定义“能做什么、怎么做、数据怎么变”。本流程用于在项目级后端开发前，与 AI 协作界定后端的业务边界、梳理规则，确保后端设计有据可依、开发不漂移。

---

## 一、核心原则

- **业务先行**：先理清业务规则，再讨论技术实现。
- **后端是守门人**：所有关键判断必须放在后端，不能仅依赖前端。
- **API 是入口，不是全部**：接口只是表现形式，背后的校验、流转才是重点。
- **一次收敛**：语言、框架、API 边界必须确定唯一方案，避免多选项导致摇摆。
- **文档即真相**：讨论结论必须写入项目真源文档，后续开发以此为唯一依据。

---

## 二、界定流程（五步走）

### 第 1 步：明确后端场景
- **目的**：确定本次工作是“小脚本”还是“项目级后端”，避免过度设计或设计不足。
- **判断标准**：
  - 小脚本：单次任务、无用户体系、无需登录、逻辑简单（如批量处理文件、生成报表）。
  - 项目级后端：涉及用户、权限、订单、支付、审核、多表关联等。
- **输出**：一句话场景定性，如“本项目为项目级后端，需支撑多用户权限、订单流转和数据统计”。

---

### 第 2 步：梳理业务规则
- **目的**：明确系统必须执行的全部“能不能做”的判断。
- **梳理方法**（逐功能模块询问 AI）：
  - 谁能执行这个操作？（角色：普通用户、管理员、未登录等）
  - 执行前需要满足什么条件？（状态校验、数据完整性、权限等）
  - 什么情况下禁止执行？（限制条件、风险拦截）
- **典型问题清单**：
  - 登录：账号是否被冻结？密码错误几次后锁定？
  - 下单：库存是否充足？是否有未支付订单冲突？是否在黑名单？
  - 退款：订单处于什么状态可退？超过时限是否允许？退款金额如何计算？
  - 内容发布：是否需要审核？敏感词如何处理？发布频次是否有限制？
- **输出**：一份《业务规则清单》，按功能模块列出每条规则的触发条件和判断逻辑。

---

### 第 3 步：梳理数据流转
- **目的**：定义从请求进来到数据落库的完整处理链路。
- **每个核心操作都必须明确**：
  - 前端提交的原始数据是什么？（字段、类型）
  - 后端需要校验哪些内容？（格式、合法性、业务约束）
  - 校验通过后，哪些数据直接入库？哪些需要计算或转换？
  - 涉及多表操作时，先后顺序是什么？是否需要事务？
  - 哪些操作需要记录日志或通知？
- **关键提醒**：涉及历史快照的数据（如订单中的收货地址），必须在此处确认“保留快照”策略，防止后续数据变更影响历史记录。
- **输出**：以核心用户故事为单位，描述数据流转步骤（文字或伪代码均可）。

---

### 第 4 步：定义 API 边界
- **目的**：清晰划分前后端职责，确定每一个接口的规格。
- **对每个 API 必须明确**：
  - 接口功能：一句话说明它完成什么业务。
  - 请求方式与路径：`POST /api/orders`
  - 请求参数（字段、类型、必填/可选、示例）
  - 需要哪些鉴权（登录态、角色、权限点）
  - 成功时返回什么（数据结构、示例）
  - 失败时返回什么（错误码、错误信息规范）
  - 涉及读写哪些数据库表
  - 调用频率限制、幂等性要求（如有）
- **输出**：一份 API 轮廓清单（不要求每个字段都最终确定，但边界必须清晰）。

---

### 第 5 步：选型决策并写入真源文档
- **语言与框架选型**：
  - 基于项目规模、团队情况、部署环境，让 AI 给出**唯一推荐方案**。
  - 要求说明：为什么选它、哪些方案被排除、框架自带能力、需要补充的 SDK 或库。
- **文档化**（生成 `docs/backend-design.md`）：
  - 后端场景说明
  - 业务规则清单
  - 核心操作的数据流转描述
  - API 边界清单
  - 语言、框架选型及理由
  - 目录结构、错误规范、权限模型概述
- **锁定**：与 AI 确认：“后续所有后端开发、接口实现、数据库操作都必须遵守此文档。任何偏离需先更新文档并说明原因。”

---

## 三、与 AI 的沟通要点

在整个界定流程中，使用以下方式与 AI 交互，可避免过早进入代码编写：

- **开局一句话**：
  > “先不要写代码。请根据当前项目的前端流程、数据库设计和业务需求，帮我梳理后端的业务边界、规则和 API 轮廓。”
- **步步确认**：每个步骤产出后，人工核对是否符合业务预期，再进入下一步。
- **抗拒 AI 的“代码冲动”**：如果 AI 开始写具体代码，立即制止：“当前阶段只做设计和文档，不要写代码。”
- **要求解释**：对任何选型或规则，要求 AI 解释“为什么这样做”，确保理解一致。

---

## 四、检查清单

在正式进入后端骨架搭建前，逐项确认：

- [ ] 后端场景已明确（小脚本或项目级后端）
- [ ] 所有核心功能的业务规则已列出，无关键遗漏
- [ ] 关键操作的数据流转已描述，含校验和快照策略
- [ ] API 清单已产出，每个接口的鉴权、入参、出参、异常已定义
- [ ] 后端语言和框架已选定为唯一方案，并文档化
- [ ] 已明确的规则和边界写入真源文档，并指示 AI 以此为后续开发依据
- [ ] 尚未明确的部分已标注为“待定”，不阻塞主干界定

---

> 后端的边界越清晰，AI 写代码时越不会越界。先把规则搬上纸面，再让 AI 在规则内自由发挥，这才是非技术用户驾驭 AI 后端开发的正道。
