## 第一部分：产品与技术调研需求

### RQ-01：国内 AI 写作竞品深度分析

**调研目标**：了解国内头部 AI 写作产品如何处理用户意图分类和路由

**必查产品**：

| 产品 | 重点关注 |
|:-----|:---------|
| **讯飞写作**（科大讯飞） | 意图分类方式、教学路由、中文 NLP 特有的处理 |
| **有道写作**（网易有道） | 批改模式 vs 教学模式的切换、意图识别准确率 |
| **腾讯 AI 写作助手** | 多轮对话中的意图追踪、功能路由设计 |
| **WPS AI**（金山办公） | 文档场景下的意图路由、与 Office 功能的融合 |

**调研维度**（每个产品）：
1. 用户意图是如何被识别的？（关键词？模型？混合？）
2. 不同意图（诊断/教学/改写/生成）如何路由到不同处理模块？
3. 模糊/未明确意图时如何回退？
4. 是否提供显式的"模式选择"UI？还是完全自动路由？
5. 中文写作场景下，意图分类面临哪些特殊挑战？

**产出要求**：
- 每个产品独立分析（500-800 字）
- 对比表格（与 Grammarly/Writer 同维度）
- 对月笙项目的启示（可借鉴的点 + 需要避免的坑）

### RQ-03：中文写作意图分类的技术方案

**调研目标**：中文 NLP 场景下意图分类的可用方案和技术选型

**调研方向**：

1. **中文意图分类模型**
   - 可用开源模型（BERT-wwm、RoBERTa-wwm-ext、ChatGLM、Qwen 系列）
   - 意图分类微调方案（需要多少标注数据？）
   - Zero-shot / Few-shot 方案（LLM 直接在 Prompt 中分类的可靠度）
   - 中文写作场景的意图分类基准（benchmark）

2. **中文关键词匹配的特殊性**
   - 中文分词对关键词匹配的影响（jieba / HanLP / LAC）
   - 中文表达的同义多样性（"帮我看看"vs"帮我瞅瞅"vs"看一下"）
   - 中文俚语/口语化的意图表达

3. **中文 LLM 作为意图分类器的成本**
   - 调用一次分类的成本（token 消耗、延迟）
   - 不同中文 LLM（Qwen / DeepSeek / GLM）的分类准确率对比

**产出要求**：
- 给出 2-3 种可选技术方案（含优缺点对比）
- 估算每种方案的成本（token/次、延迟、标注数据需求）
- 对月笙项目的推荐方案

### RQ-06：业务价值必要性

#### 6.1 场景匹配度验证

**目标**：调研当前教学聊天场景中用户核心诉求的分布，量化 Intent Router 对精准响应的价值。

**调研方向**：

1. **意图分布统计**
   - 分析近 3 个月的聊天日志，统计 5 类意图（diagnose / learn / train / review / general_chat）的请求占比
   - 识别"高频但当前响应不匹配"的意图场景

2. **错误响应量化**
   - 统计无意图路由时"需求响应错误"的高频场景
   - 例如：用户想"训练写作"却触发了"诊断流程"的次数和占比
   - 估算每条错误响应浪费的 token 和增加的延迟

3. **精准响应价值**
   - 计算 Intent Router 落地后，精准路由的意图数量
   - 估算减少的 LLM 无效调用次数

**调研方法**：
- 定量：分析聊天日志，按消息内容人工标注 500-1000 条样本的"真实意图" vs "当前系统实际响应"
- 定性：抽样分析 50 条"响应不匹配"的案例，分类记录用户后续行为（放弃会话/重新表述/点击其他功能）

#### 6.2 业务指标提升预期

**目标**：调研"意图识别精准度提升"与用户核心指标的关联关系。

**调研方向**：

1. **教育行业基准数据**
   - 搜索教育类 AI 产品（Khan Academy AI Tutor、猿辅导 AI 老师等）的公开数据
   - 意图识别精准度提升与用户学习任务完成率、留存率、满意度的关联关系

2. **指标预测模型**
   - 基于行业数据和月笙现有数据，输出预测：
     - 「精准度提升 30% → 任务完成率提升 X%」
     - 「错误响应减少 50% → 用户满意度提升 Y%」
     - 「延迟降低 2 秒 → 留存率提升 Z%」

**产出要求**：
- 给出有数据支撑的指标提升预测范围
- 标注预测的置信度（高/中/低，并说明依据）

#### 6.3 业务扩展性验证

**目标**：验证 Intent Router 架构对未来新增意图的兼容成本。

**调研方向**：

1. **未来意图规划**
   - 访谈 3-5 名业务产品经理，了解未来 6-12 个月是否有新增意图的规划
   - 示例：作业批改、知识点答疑、写作素材推荐、AI 对练

2. **扩展成本对比**
   - 有 Intent Router：新增一个意图需要修改哪些文件？估算工时
   - 无 Intent Router：在当前 `sendMessage()` 中新增一个意图分支需要修改哪些？估算工时
   - 对比长期（12 个月、5 个新意图）的维护成本差异

**产出要求**：
- 新增意图的兼容成本对比表（有/无 Intent Router）
- 12 个月维护成本曲线预测

### RQ-07：技术必要性

#### 7.1 现有架构痛点量化

**目标**：调研当前 `ChatOrchestratorService` 的维护成本，对比 Intent Router 拆分后的提升。

**调研方向**：

1. **当前痛点统计**
   - `sendMessage()` 当前 285 行，每次修改的平均代码冲突率
   - 新增或修改一个意图分支的平均工时（从需求评审到上线）
   - 诊断/教学/训练/闲聊代码耦合导致的 Bug 率（修改一处影响其他逻辑的次数）

2. **拆分后预期**
   - Intent Router 将 5 个 handler 拆分后，每个 handler 的独立行数
   - 修改单个 handler 的平均工时（预期降低比例）
   - 代码耦合度降低带来的 Bug 率下降预期

#### 7.2 混合路由方案对比

**目标**：测试纯关键词、纯 LLM、"关键词优先+LLM 兜底"三种方案的性能指标。

**调研方向**：

1. **测试集构建**
   - 构建覆盖 5 类意图的测试集，每类 40 条，共 200 条
   - 包含：明确意图（80%）、模糊意图（15%）、边界情况（5%）

2. **三种方案测试**

| 方案 | 响应速度 | 准确率 | 成本 |
|:-----|:---------|:-------|:-----|
| 纯关键词 | 毫秒级（<50ms） | 较低（边界模糊场景差） | 0（无 LLM 调用） |
| 纯 LLM | 秒级（1-3s） | 较高（语义理解强） | 高（每次调用都消耗 token） |
| 关键词优先+LLM 兜底 | 关键词：毫秒级 / LLM 兜底：秒级 | 高（规则兜底） | 低（仅 30% 需要 LLM） |

3. **对比输出**
   - 测试集上三种方案的准确率、召回率、F1 分数
   - 单次响应延迟 P50 / P95 / P99
   - 月度 API 费用估算（基于日活 1000 用户、日均 50 条消息）

#### 7.3 集成兼容性

**目标**：调研 `LLMProvider` 接口与现有及未来 LLM 网关的适配度。

**调研方向**：

1. **当前兼容性**
   - `LLMProvider` 接口与已接入 LLM 网关的适配度评分
   - 当前实现的 `chatStream` / `chatStreamWithTools` 是否满足意图分类需求

2. **未来可替换性**
   - 更换 LLM 服务商（如从 A 切换到 B）需要修改哪些文件
   - `IntentRouter.classifyByLLM()` 是否与具体 LLM 解耦

### RQ-08：用户体验必要性

#### 8.1 响应效率感知

**目标**：调研用户对不同路由策略产生的延迟的容忍度。

**调研方向**：

1. **延迟容忍度**
   - 关键词路由（即时响应）vs 纯 LLM 路由（等待 1-3 秒）的用户感知差异
   - 用户在等待 LLM 分类时是否会产生焦虑或中断操作

2. **等待反馈**
   - 用户对"AI 正在思考..."类加载动画的耐心上限（秒）
   - 是否需要实时显示"正在识别意图 -> 正在生成回答"的进度

**调研方法**：
- A/B 测试：对比有/无意图识别反馈的两种聊天交互
- 记录操作完成时间、放弃率、主观满意度

#### 8.2 意图降级体验

**目标**：调研用户对"低置信度降级为 general_chat"的接受度。

**调研方向**：

1. **降级透明度**
   - 用户是否希望知道"系统未识别到具体学习需求"
   - 不同表达方式的用户接受度：
     - 方式 A：直接降级，不告知用户
     - 方式 B：告知"未识别具体学习需求，已切换到闲聊模式"
     - 方式 C：告知 + 引导"是否需要推荐学习内容？"

2. **降级后行为**
   - 用户被降级后是否会重新表述请求
   - 降级是否导致用户流失或满意度下降

## 第三部分：UI 前端调研

### RQ-11：前端组件库选型 ✅ 已完成

> 调研结果详见：[rq-11-component-library-prompt.md](dev-docs/research/rq-11-component-library-prompt.md)

**核心结论**：引入 **Ant Design Mobile (antd-mobile)**，推荐指数 ★★★★★

**三大方案对比**：

| 方案 | 工时 | 小程序兼容 | 推荐 |
|:-----|:----:|:----------:|:----:|
| A：纯手写扩展 | 6-7 人天 | ❌ 不能复用 | ★★ |
| **B：antd-mobile** | **2.5-3 人天** | **✅ 85% 复用** | **★★★★★** |
| C：Radix + 手写 | 4-4.5 人天 | ❌ 完全不能 | ★★★ |

**选择 antd-mobile 的理由**：
1. **组件全覆盖**：Bubble（聊天气泡）/ Skeleton（骨架屏）/ BottomSheet（底部浮层）/ Drawer（抽屉）/ Toast / Collapse / Steps / Card 等 8 个核心组件 100% 覆盖需求
2. **主题定制灵活**：通过 CSS 变量覆盖直接匹配现有 design tokens，与 CSS Modules 混用无冲突（类名前缀 `adm-`，样式隔离好）
3. **包体积极小**：按需引入 8 个组件，gzip 后仅 28-32 KB
4. **小程序路径预留**：官方适配 Taro，H5 → 小程序代码复用率约 85%

**落地建议**：渐进式引入——先换 Bubble/Skeleton/Toast 改造聊天主流程，再逐步接入抽屉/浮层等组件，不影响现有桌面端代码。

### RQ-12：意图差异化交互模式 ✅ 已完成

> 已由移动端设计文档完整覆盖（含 5 类意图气泡样式、布局架构、交互反馈、分阶段落地路径）

**调研目标**：调研教育类 AI 产品中，5 类意图的前端交互模式

| 意图类型 | 参考产品 | 交互亮点 | 落地建议 |
|:---------|:---------|:---------|:---------|
| **diagnose（诊断）** | 讯飞星火 AI（教育版） | 多步骤诊断引导，每步给出轻量提示，支持回退/跳过 | 前端新增 Steps 步骤条，关联 diagnose 意图触发，步骤数据由后端 Intent Router 路由后返回 |
| **learn（学习）** | 有道 AI 助手 | 识别学习意图后，侧边栏展示知识点卡片，聊天气泡关联卡片跳转 | learn 意图触发后，前端加载学习资源卡片组件，卡片数据与聊天消息联动 |
| **train（训练）** | Khan Academy AI Tutor | 训练意图触发互动式任务列表，支持"开始训练/提交答案" | train 意图返回占位响应时，前端展示轻量化训练任务卡片（后续对接完整训练流） |
| **review（复盘）** | 猿辅导 AI 老师 | 复盘意图展示可视化成长曲线（答题正确率、学习时长） | review 意图触发后，前端渲染 ECharts 折线图/柱状图，数据由 teachingContext 提供 |
