# RQ-03：中文意图分类技术方案 — 可直接执行的提示词

> 安排人做调研时，把这份提示词发给对方即可。

---

## 背景（直接发给调研人员）

我们做了一个**意图路由模块（Intent Router）**，需要把中文用户消息分类到 5 种意图：

```
diagnose（诊断）— "帮我看看这段写得怎么样"
learn（学习）    — "怎么才能写好人物对话"
train（训练）    — "我想练习环境描写"
review（复盘）   — "我最近有进步吗"
general_chat（闲聊）— "今天天气真好"
```

目前实现的是**"关键词匹配优先 + LLM 兜底"**混合方案。关键词匹配已经写好了，现在需要验证 **LLM 兜底这一步的技术可行性**——即用 LLM 做中文意图分类，效果如何、成本多少、延迟多高。

我们的技术栈：**LLM 网关已对接多个模型**，当前通过 `LLMProvider` 接口统一调用，支持 `chatStream`（流式）。意图分类只需很短的一次调用（约 50 tokens 输出）。

---

## 调研目标

回答 **3 个核心问题**：

1. **准确性**：主流中文 LLM 做 5 类意图分类，准确率有多少？
2. **成本**：每次分类调用消耗多少 token？大概多少钱？
3. **延迟**：平均响应时间多少？能不能忍受？

最终输出一张对比表，回答"**LLM 兜底这一步在经济和技术上是否可行**"。

---

## 具体需要做的事

### 事项 1：测试集构建（1 小时）

构建一个覆盖 5 类意图的小型测试集，用于后续测试。

**要求**：
- 总 100 条，每类 20 条
- 覆盖 3 种难度：
  - **明确意图**（12 条/类）— "帮我分析一下这段文字" → 明显是 diagnose
  - **模糊意图**（5 条/类）— "我写不下去了怎么办" → 可能是 learn/train/闲聊
  - **边界案例**（3 条/类）— 短文本、口语化、含多意图

**参考模板**（直接往这个方向写）：

| 意图 | 明确意图示例 | 模糊意图示例 | 边界案例 |
|:-----|:------------|:------------|:---------|
| diagnose | "帮我看看这段写得怎么样" | "总觉得哪里不对" | "嗯"（结合对话历史） |
| learn | "怎么塑造人物性格" | "有什么技巧吗" | "然后呢？" |
| train | "我想练习一下对话" | "给我出个题" | "试试？" |
| review | "我进步了吗" | "这几天怎么样" | "看看" |
| general_chat | "今天天气不错" | "唉" | ""（空消息） |

**输出**：`test_set.json`，格式：

```json
[
  {"id": 1, "text": "帮我看看这段写得怎么样", "expected": "diagnose", "difficulty": "明确"},
  {"id": 2, "text": "总觉得哪里不对", "expected": "diagnose", "difficulty": "模糊"}
]
```

---

### 事项 2：LLM 分类测试（2-3 小时）

用测试集调每个模型做意图分类，记录准确率和 token 消耗。

**测试方案**（直接用我们的 LLM 网关调用，不需要额外搭建）：

**Prompt 模板**（固定不变，所有模型通用）：

```
你是一个写作教练的意图分类器。判断用户消息属于哪种意图，仅返回 JSON。

意图定义：
- diagnose: 用户提交文本，要求分析/评价/诊断
- learn: 用户询问技法、写作方法、知识点
- train: 用户要求练习、训练
- review: 用户询问成长、进步、回顾
- general_chat: 闲聊、问候、其他未明确

响应格式（仅返回 JSON）：
{"intent":"diagnose","confidence":0.95}

用户消息：{这里插入测试文本}
```

**需要测试的模型**（挑 2-3 个即可，重点测项目已接入的）：

| 模型 | 为什么测 | 关注点 |
|:-----|:---------|:-------|
| **DeepSeek-V3**（如果已接入） | 性价比高，推理快 | 中文分类准确率、结构化输出稳定性 |
| **Qwen2.5-72B**（如果已接入） | 中文能力公认强 | 模糊意图的区分度 |
| **GLM-4**（如果已接入） | 国产模型中稳定 | 一致性与 DeepSeek/Qwen 的差异 |
| **GPT-4o-mini**（如果已接入） | 国际对照基准 | 中英文理解差异 |

**记录格式**（每个模型一个表格）：

```
模型：DeepSeek-V3
测试总数：100
正确：86
错误：14
准确率：86%

错误分布：
- diagnose ↔ learn 混淆：6 条
- train ↔ general_chat 混淆：4 条
- 其他：4 条

token 消耗：
- 平均输入 token：~120（含 prompt）
- 平均输出 token：~30
- 总消耗/100条：~15,000 tokens
```

**特别注意**：
- 如果某个模型总是输出非 JSON 格式（如 markdown 代码块、多余文字），也需要记录——这会影响解析稳定性
- 测试时关闭流式（`chatStream` 改非流式），因为分类只需要最终结果

---

### 事项 3：三种方案对比计算（1 小时）

基于事项 2 的数据，填这个对比表：

| 维度 | 纯关键词（已实现） | LLM 兜底（待定） | 纯 LLM（对照） |
|:-----|:------------------|:----------------|:---------------|
| 准确率 | 估 60-70%（有边界问题） | 待测（事项 2） | 同上 |
| 单次延迟 | < 50ms | 待测（事项 2） | 同上 |
| 单次成本 | ¥0 | 待测 | 每次×5（所有消息都调） |
| 月度成本（DAU 1000，日均50条） | ¥0 | 待算 | 待算 |
| 整体推荐 | 打底方案 | 待定 | 不推荐 |

**关键计算题**：
- 假设关键词匹配命中率 70%（即 30% 消息需 LLM 兜底）
- 日活 1000 用户，日均 50 条/人
- 每月 LLM 兜底调用量 = 1000 × 50 × 30 × 30% = **450,000 次/月**
- 按模型单价 × 每次 token 消耗 = 月费用 ¥XXX

帮我们算清楚这笔账。

### 事项 4：补充调研（1 小时，可选）

如果时间和精力允许，额外补充：

1. **Few-shot 是否更稳定**：
   - 把 Prompt 里的"意图定义"换成每类给 2 个示例（few-shot）
   - 用同一测试集跑一遍，看准确率是否有提升

2. **中文分词兜底方案**：
   - 如果 LLM 不可用（离线/超时），关键词匹配覆盖不到的场景，jieba 分词能否辅助？
   - 例如：用户说"点评一下"——"点评"不在关键词列表里，但 jieba 可以识别为"动词+教学相关"
