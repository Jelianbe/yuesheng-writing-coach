# R-023: Bug 调试记录

## 原则

**调试时间是最昂贵的工程成本。** 记录不是行政负担——它防止下一次花同样的时间踩同一个坑。

## 四要素模板

### 1. 现象（What）

```
- 触发条件：[什么操作触发的]
- 错误表现：[报错信息 / 异常行为 / 截图]
- 影响范围：[哪些功能受影响]
- 复现率：[必现 / 偶现 / 难复现]
```

### 2. 定位过程（How）

```
- 排查路径：[从哪里开始查 → 查了什么 → 排除了什么]
- 关键线索：[哪个日志/报错/行为暴露了方向]
- 陷入的误区：[如果有的话，记录错误假设，防止下次重蹈覆辙]
```

### 3. 根因（Why）

```
- 直接原因：[代码层面的 bug 是什么]
- 根本原因：[为什么这个 bug 能存在？设计缺陷？遗漏？误解？]
- 引入时机：[大概什么时候引入的，如果能定位的话]
```

### 4. 修复方案（Fix）

```
- 修改内容：[改了什么]
- 涉及文件：[文件列表]
- 验证方式：[怎么确认修好了]
- 防再发措施：[怎么防止同类问题再次发生]
```

## 记录位置

统一写入 `docs/debug-log.md`（调试日志），追加格式：

```markdown
## [YYYY-MM-DD] [简短标题]

**耗时**: XX 分钟
**严重度**: P0(阻塞) / P1(功能受损) / P2(体验问题)

### 现象
（四要素 1）

### 定位
（四要素 2）

### 根因
（四要素 3）

### 修复
（四要素 4）
```

## 时间阈值

| 耗时 | 要求 |
|------|------|
| < 5 分钟 | 不强制记录 |
| 5-15 分钟 | 建议记录（一行摘要即可） |
| **> 15 分钟** | **必须记录完整四要素** |
| > 60 分钟 | 必须记录 + 写入 Lessons Learned |

## 快速记录模板（5-15 分钟用）

对于不需要完整四要素的场景，用一行格式：

```
[YYYY-MM-DD] [标题] (XXmin) — [现象] → [原因] → [修复方式]
```

示例：
> [2026-06-08] saveAnalysis UUID 主键冲突 (8min) — 用 sessionId+messageId 查询返回多条 → 应改用 id 主键 → 调用方先 save() 取 id 再传参

## 与其他规则的协作

| 规则 | 关系 |
|------|------|
| R-006 回退机制 | 修复方案涉及回退时引用 R-006 的备份标准 |
| R-011 记忆强化 | >60min 的调试同时触发 R-011 决策日志记录 |
| R-018 变更溯源 | 修复代码变更需遵循 R-018 溯源链 |

## 检查清单

```
调试结束后检查：
□ 耗时是否超过 15 分钟？（超了就必须记）
□ 四要素是否齐全？（现象/定位/根因/修复）
□ 记录是否写入了 debug-log.md？
□ 是否有防再发措施？
```

## 优先级
中优先级 — 积累调试经验资产，降低重复排障成本
