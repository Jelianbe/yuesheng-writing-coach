# R-007: 双向绑定

## 原则
所有数据变更必须保持一致性，前端显示与后端存储必须保持同步。

## 核心要求
1. **数据驱动** - UI 变化源自数据变化
2. **状态同步** - 前后端状态始终保持一致
3. **变更传播** - 数据变更必须正确传播到所有依赖方

## 实现方式
- **前端状态管理**: 使用 Zustand，确保状态变更的原子性
- **数据持久化**: 数据变更时通过 IPC 同步到 electron-store 或 SQLite
- **UI 同步**: 使用 React 的响应式更新机制

## 检查清单
### AI 可检查项
```
数据变更后检查（AI 可验证）：
□ 状态变更是否使用不可变模式？
□ IPC 调用是否携带 success/error 返回？
□ 相关 store 是否收到通知更新？
□ catch 块是否收集了错误信息？
```

### 人工检查项（需要人在浏览器中验证）
```
数据变更后检查（人工）：
□ 前端UI是否正确更新？
□ 后端存储是否正确保存？
□ 是否存在状态不一致？
```

## 常见问题
| 问题 | 原因 | 解决方案 |
|------|------|----------|
| UI未更新 | 状态变更未正确触发 | 使用 immer 等不可变数据工具 |
| 数据不一致 | 异步操作时序问题 | 使用事务或队列机制 |

## 与其他规则的协作

| 规则 | 关系 | 协作方式 |
|------|------|----------|
| R-028 防御性编码 | 依赖 | 数据变更的边界层（IPC/API）需要 R-028 的防御校验，确保同步数据的可靠性 |
| R-010 最小化范围 | 互补 | 状态变更必须遵循 R-010，每次只修改必要的数据链路，避免过度同步 |

## 优先级
中优先级 - 保障用户体验和数据一致性
