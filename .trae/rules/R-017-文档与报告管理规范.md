# R-017: 文档与报告管理规范

## 规则内容

所有项目文档和报告必须遵循统一的分类体系、版本控制、审核发布和定期维护机制，确保文档的完整性、准确性和可追溯性。

## 触发场景

在以下场景必须执行文档管理检查：
- 创建新文档时
- 更新现有文档时
- 生成报告时
- 归档历史文档时
- 文档定期审查时（每季度）

## 文档分类体系

### 第一层：文档类型

| 类型代码 | 类型名称 | 存储位置 | 示例 |
|---------|---------|---------|------|
| **PRD** | 产品需求文档 | `docs/prd/` | `PRD_月笙写作教练_V1.0.md` |
| **ARCH** | 架构设计文档 | `docs/architecture/` | `diagnosis-system-architecture_V1.0.md` |
| **SPEC** | 技术规范文档 | `docs/specs/` | `api-specification_V1.0.md` |
| **PLAN** | 开发计划文档 | `docs/plans/` | `development-plan_V1.0.md` |
| **RULE** | 开发规则文档 | `.trae/rules/` | `R-001-原子化与状态管理.md` |
| **RPT** | 报告文档 | `docs/reports/` | `verification-report_V1.0.md` |
| **DECISION** | 决策记录文档 | `docs/decisions/` 或 `dev-docs/decisions/` | `ADR-001-app-orchestrator.md` |
| **ADAPTER** | 技术适配器规范 | `dev-docs/adapters/` | `React/IPC/Zustand 层约束` |
| **PROMPT** | Prompt 工程文档 | `resources/prompts/` | `yuesheng-prompt-v3.md` |
| **CASE** | 教学案例文档 | `resources/references/teaching-cases/` | `实战教学案例补充材料.md` |

### 第二层：文档状态

| 状态 | 说明 | 存放位置 |
|------|------|---------|
| **DRAFT** | 草稿阶段 | 原目录，文件名加 `draft-` 前缀 |
| **REVIEW** | 审核中 | 原目录，文件名加 `review-` 前缀 |
| **PUBLISHED** | 已发布 | 原目录，无特殊前缀 |
| **DEPRECATED** | 已废弃 | `docs/archive/deprecated/` |
| **ARCHIVED** | 已归档 | `historical-archive/` |

### 命名规范

```
<类型代码>_<主题名称>_V<主版本>.<次版本>.md
```

**示例**：
- `PRD_月笙写作教练_V1.0.md`
- `ARCH_diagnosis-system_V2.1.md`
- `RPT_verification-report_V1.2.md`

## 报告生成标准

### 报告类型

| 报告类型 | 适用场景 | 核心内容 |
|---------|---------|---------|
| **验证报告** | 功能验证、盲测验证 | 测试目标、测试数据、结果分析、结论 |
| **诊断报告** | 用户诊断、会话诊断 | 病症识别、信号权重、建议动作、训练任务 |
| **进度报告** | 阶段进度、里程碑报告 | 完成项、阻塞项、风险项、下一步计划 |
| **审查报告** | 代码审查、架构审查 | 审查范围、发现问题、建议改进、优先级 |

### 报告结构模板

```markdown
---
type: "报告类型"
title: "报告标题"
version: "V主版本.次版本"
author: "作者"
reviewer: "审核人"
date: "YYYY-MM-DD"
status: "draft/review/published"
---

# 报告标题

## 1. 概述
- 报告目的
- 报告范围
- 相关背景

## 2. 核心内容
### 2.1 关键发现
### 2.2 数据分析
### 2.3 问题识别

## 3. 结论与建议
### 3.1 主要结论
### 3.2 改进建议
### 3.3 优先级排序

## 4. 附录
- 相关文档链接
- 原始数据
- 术语表
```

### 报告质量标准

| 质量维度 | 检查项 | 合格标准 |
|---------|--------|---------|
| **完整性** | 是否包含所有必需章节？ | 所有章节完整 |
| **准确性** | 数据和结论是否准确？ | 无事实错误 |
| **可读性** | 结构是否清晰、语言是否简洁？ | 非技术人员可理解 |
| **可追溯性** | 是否有版本记录和变更记录？ | 每次修改有记录 |
| **时效性** | 是否在有效期内？ | 过期报告需标注 |

## 文档同步要求（吸收自 R-008）

代码变更必须伴随相应的文档更新。每次变更完成后，执行以下检查：

- [ ] 代码注释是否已与实现同步？
- [ ] API 文档是否与实际接口一致？
- [ ] `dev-docs/README.md`（真源索引）是否更新？
- [ ] 相关技术文档是否已反映变更？

**同步责任矩阵**：

| 变更类型 | 必须更新的文档 | 检查时机 |
|---------|---------------|---------|
| API / IPC 变更 | `src/shared/api-contracts/` + ADR | 变更后即时 |
| 架构调整 | `dev-docs/README.md` + 相关 ARCH 文档 | 合并前 |
| 核心类型变更 | `src/shared/types-teaching.ts` + 真源索引 | 变更后即时 |
| 规则变更 | `.trae/rules/` + AGENTS.md | 合并前 |
| Prompt 修改 | `resources/prompts/` + R-025 变更日志 | 提交前 |

## 版本控制机制

### 版本号规则

采用 `主版本.次版本` 格式：

| 变更类型 | 版本号变化 | 示例 |
|---------|-----------|------|
| **重大更新** | 主版本 +1，次版本归 0 | V1.2 → V2.0 |
| **小幅更新** | 次版本 +1 | V1.2 → V1.3 |
| **错别字修正** | 次版本不变，记录变更 | V1.2（记录修正） |

### 变更记录模板

每个文档末尾必须包含变更记录：

```markdown
---

## 变更记录

| 版本 | 日期 | 变更内容 | 变更人 |
|------|------|---------|--------|
| V1.0 | 2026-06-01 | 初始版本 | 张三 |
| V1.1 | 2026-06-15 | 增加诊断报告标准 | 李四 |
| V2.0 | 2026-07-01 | 重构文档结构 | 张三 |
```

### 版本管理流程

```
创建文档 V1.0
  ↓
内容更新 → 创建 V1.1
  ↓
重大重构 → 创建 V2.0（V1.x 归档）
  ↓
定期审查 → 确认继续有效 / 标注过期 / 归档
```

## 审核发布流程

### 审核流程

```
创建/更新文档
  ↓
自检（作者）
  → 检查格式、内容、链接
  ↓
审核（指定审核人）
  → 检查质量、准确性、完整性
  ↓
通过？
  ├─ 是 → 发布（移除 draft/review 前缀）
  └─ 否 → 返回修改（记录审核意见）
```

### 审核检查清单

```
文档审核检查：
□ 文档是否遵循分类体系和命名规范？
□ 是否有明确的版本号和变更记录？
□ 内容是否准确、完整？
□ 链接是否有效？
□ 是否有相关的审批记录？
□ 是否符合对应文档类型的模板要求？
□ 是否有过期内容需要更新？
```

### 发布条件

文档发布必须满足：
1. 通过自检和审核流程
2. 版本号符合规则
3. 变更记录完整
4. 相关依赖文档已同步更新

## 定期维护机制

### 文档审查周期

| 文档类型 | 审查周期 | 负责人 |
|---------|---------|--------|
| PRD | 每季度 | 产品负责人 |
| 架构设计 | 每半年 | 技术负责人 |
| 技术规范 | 每季度 | 技术负责人 |
| 开发计划 | 每月 | 项目经理 |
| 开发规则 | 每季度 | 全体开发者 |
| 报告 | 按需（发布后 30 天内有效） | 报告作者 |
| Prompt | 每次迭代后 | Prompt 工程师 |

### 文档清理规则

| 状态 | 处理方式 |
|------|---------|
| 过期超过 90 天 | 标注 `DEPRECATED`，移入归档 |
| 被新版本替代 | 旧版本移入 `historical-archive/` |
| 不再适用 | 标注 `OBSOLETE`，记录原因 |

### 归档流程

```
确认文档需归档
  ↓
添加归档说明（归档原因、归档日期）
  ↓
移入 historical-archive/对应版本目录
  ↓
更新文档索引
  ↓
记录归档操作到变更记录
```

## 月笙项目特定规范

### 诊断报告管理

| 要求 | 说明 |
|------|------|
| **存储位置** | 数据库（SQLite `diagnosis_reports` 表） |
| **访问权限** | 仅系统内部可见，用户端不可访问 |
| **持久化** | 随用户数据永久保存 |
| **版本控制** | 每次诊断生成新记录，不覆盖旧记录 |

### Prompt 文档管理

| 要求 | 说明 |
|------|------|
| **存储位置** | `resources/prompts/` |
| **版本控制** | 文件名带版本号（如 `yuesheng-prompt-v3.md`） |
| **历史归档** | 旧版本移入 `historical-archive/` |
| **变更审批** | 需经过盲测验证 |

### 教学案例管理

| 要求 | 说明 |
|------|------|
| **存储位置** | `resources/references/teaching-cases/` |
| **格式要求** | 统一使用教学总结模板 |
| **隐私保护** | 学员信息脱敏处理 |
| **定期更新** | 每季度补充新案例 |

## 违规处理

| 等级 | 定义 | 处理 |
|------|------|------|
| P0-严重 | 文档无版本控制、无变更记录 | 立即整改，暂停相关开发 |
| P1-高 | 文档未通过审核流程即发布 | 要求补充审核后重新发布 |
| P2-中 | 文档命名不规范 | 要求重命名后重新提交 |
| P3-低 | 文档过期未更新 | 标注过期，限期更新 |

## 检查清单

```
创建文档时检查：
□ 是否遵循分类体系和命名规范？
□ 是否有版本号和变更记录？
□ 是否使用对应类型的模板？

更新文档时检查：
□ 是否更新了版本号？
□ 是否记录了变更内容？
□ 是否需要重新审核？

定期审查时检查：
□ 文档是否仍然有效？
□ 是否有过期内容需要更新？
□ 是否需要归档旧版本？
```
