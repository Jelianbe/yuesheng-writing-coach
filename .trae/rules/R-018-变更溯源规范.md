# R-018: 变更溯源规范

## 规则内容

每次代码变更必须有文档作为依据。文档是变更的"理由"和"地图"——没有文档依据的变更是盲目的，无法被审核、无法被理解、无法被追溯。

变更必须形成完整的可追溯链条：

```
设计哲学（design-philosophy / research）
    ↓ 引用：说明"为什么这个方向是对的"
技术规格（specs / architecture）
    ↓ 引用：说明"具体怎么做"
任务文档（tasks / plans）
    ↓ 引用：说明"什么时候做、做什么"
代码变更
    ↓ 记录
CHANGELOG / Git提交信息
```

链条上的每一环都必须可向前追溯，不可断裂。

## 触发场景

以下场景必须在变更前检查溯源依据：

| 场景 | 需要的依据文档 | 检查时机 |
|------|---------------|---------|
| 新功能开发 | 设计哲学（方向依据）+ 技术规格（方案依据） | 开发前 |
| 症候/动作/训练新增 | 设计哲学（理论依据）+ 研究文档（教学依据） | 开发前 |
| 状态机阶段扩展 | 设计哲学 + 教学流程设计 | 开发前 |
| 架构重构 | 设计哲学（方向依据）+ 架构设计文档 | 开发前 |
| Bug 修复 | Bug 报告或问题描述文档 | 修复前 |
| Prompt 修改 | Prompt 变更说明文档 | 修改前 |
| 配置项修改 | 配置变更说明 | 修改前 |

## 溯源链条详解

### 第一环：设计哲学（"为什么"）

定义变更的理论基础和方向依据。

```
文档位置：docs/design/ 或 docs/research/
必含内容：
  - 变更对应的核心概念（来自设计哲学中的哪一条）
  - 变更的理论依据（来自哪份研究文档或教学理论）
  - 变更要解决什么问题
  - 这个方向为什么是对的（与项目核心哲学的一致性论证）

示例：
  新增 P008 症候的哲学依据：
  依据：design-philosophy_V1.0.md 第三章「降级规则」
        研究：worldbuilding-character-craft-foundation.md 2.2「冰山理论」
  解决的问题：用户通过大段说明而非角色体验展现世界观
  哲学一致性：符合「教可教的认知能力，而非才华」的核心信念
```

### 第二环：技术规格（"怎么做"）

定义变更的具体实现方案。

```
文档位置：docs/specs/ 或 docs/architecture/
必含内容：
  - 实现方案描述
  - 接口定义（如果是 Repository 或 API 变更）
  - 数据模型变更（如果是数据库变更）
  - 关键决策和权衡（如果有多种方案可选）
  - 回退方案（依据 R-006 回退机制规范）

示例：
  新增诊断表持久化的技术规格：
  1. 新建 005_diagnosis.sqlite 迁移，建 diagnosis_results 表
  2. 新增 DiagnosisService，提供 saveDiagnosis() 方法
  3. 在 chat.handler.ts 的流结束回调中调用
  4. 表结构：{ id, sessionId, messageId, syndromes, confidence, timestamp }
```

### 第三环：任务文档（"做什么"）

定义变更的具体执行计划和验收标准。

```
文档位置：docs/tasks/
必含内容：
  - 任务描述
  - 涉及的代码文件列表
  - DoD（完成标准，至少 3 条可验证）
  - 前置依赖（如果有）

格式参考：TASK-CHAIN.md 中的任务模板
```

### 第四环：代码变更（"做了什么"）

变更的实际执行。所有代码文件本身就是变更的实体记录，但必须伴随：

1. **Git 提交信息**：遵循 R-016 Git 提交规范，在提交信息中引用依据文档
2. **变更说明**：在文档中记录变更摘要

### 第五环：变更记录（"结果是什么"）

变更完成后，在相关文档中记录变更日志。

```
记录位置：
  - 文档末尾的「变更记录」表格（遵循 R-017 规范）
  - CHANGELOG.md（跨版本变更汇总）

必含内容：
  - 变更了哪些文件
  - 变更的核心内容摘要
  - 关联的任务编号（T-xxx）
  - 关联的设计哲学文档和版本
```

## 溯源记录模板

每个重要变更应该在任务文档或规格文档中包含以下溯源信息：

```markdown
## 变更溯源

### 依据链
- **设计哲学**：docs/design/design-philosophy_V1.0.md → [引用具体章节]
- **研究基础**：docs/research/xxx.md → [引用具体章节]  
- **技术规格**：docs/specs/xxx.md → [引用具体章节]

### 变更摘要
- **变更类型**：新增 / 修改 / 修复 / 重构
- **涉及文件**：[文件列表]
- **核心变更**：[变更内容摘要]
- **DoD 达成**：[任务文档中定义的完成标准是否全部满足]

### 验证
- [ ] 变更是否与设计哲学一致
- [ ] 变更是否按技术规格执行
- [ ] 任务 DoD 是否全部达成
- [ ] 变更记录是否已写入文档
```

## 检查清单

```
变更前检查：
□ 是否有文档依据？（设计哲学 / 研究文档 / 技术规格）
□ 是否明确了"为什么要改"？
□ 是否明确了"怎么改"？
□ 是否创建或更新了任务文档？
□ 是否有回退方案？（依据 R-006）

变更后检查：
□ 代码是否与设计哲学一致？
□ 是否记录了变更摘要？
□ 是否更新了相关文档的变更记录？
□ Git 提交信息是否引用了依据文档？
□ 追溯链条是否完整？（每一环都能向前追溯）
```

## 执行机制

| 等级 | 定义 | 处理 |
|------|------|------|
| P0-严重 | 无任何文档依据的代码变更 | 变更被标记为"未经溯源"，不合并，回退后重新提交 |
| P1-高 | 有依据文档但追溯链条不完整（缺某一环） | 要求补充缺失环的文档后重新审核 |
| P2-中 | 依据文档存在但未在提交信息中引用 | 要求补充提交信息 |
| P3-低 | 变更记录未及时更新 | 要求补录变更记录 |

## 与其他规则的关系

| 规则 | 与本规则的关系 | 协作方式 |
|------|--------------|---------|
| R-005 全流程文档化-逻辑解释 | 互补 | R-005 管代码内的注释和逻辑解释；R-018 管代码外的文档依据链 |
| R-006 回退机制规范 | 依赖 | 每次变更前必须有回退方案（R-006），这是 R-018 的检查项之一 |
| R-008 文档同步准则 | 互补 | R-008 要求文档随代码更新；R-018 要求变更前先有文档依据 |
| R-016 Git提交规范 | 依赖 | R-018 要求提交信息引用依据文档，R-016 定义了提交信息的格式 |
| R-017 文档管理规范 | 依赖 | R-018 引用的文档必须遵循 R-017 的分类、版本和命名规范 |

## 优先级

高优先级 —— 保障变更的可追溯性和项目的长期可维护性。
