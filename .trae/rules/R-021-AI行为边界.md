# R-021: AI 行为边界

## 原则

AI 辅助开发的核心风险不是"写不出代码"，而是**写出超出范围的代码**。
本规则为 AI 设定硬性行为栅栏，每条都是审查报告中实际发现问题的直接解法。

## 五条边界

### B1. 先说再干 — 开工声明

动手修改任何代码之前，必须先用一句话说清：
- **目标**：要解决什么问题
- **范围**：涉及哪些文件、不改哪些文件
- **预期产出**：完成后怎么验证

> ❌ 错误：直接开始编辑文件
> ✅ 正确："我要修复 ActiveTrainingView 返回按钮缺失问题，只涉及 ActiveTrainingView.tsx 一个文件，验证方式是点击返回按钮能回到聊天界面"

### B2. 先读再改 — 上下文感知

修改任何文件之前，必须先读取：
1. **目标文件本身** — 了解现有结构
2. **调用方 / 被依赖方** — 理解接口契约
3. **相关类型定义** — 避免引入类型不兼容

> ❌ 错误：看到函数名就猜参数格式，直接写调用代码
> ✅ 正确：先读函数签名和调用处的类型定义，确认参数结构后再改

### B3. 只改必须改的 — 最小化范围

严格限定在任务范围内：
- **禁止**顺手格式化未指定的文件
- **禁止**顺手重构"顺便发现的"其他问题
- **禁止**重命名变量/函数除非任务是做这件事
- **禁止**添加"可能以后有用"的代码或导入

发现额外问题时：记录到任务文档或 issue，不立即处理。

> ❌ 错误：修复 A 文件的 bug 时，顺手把 B 文件的格式也调了
> ✅ 正确：只修 A 文件。B 文件的问题记录下来，等有专门任务再做

### B4. 沿用已有风格 — 风格一致性

新增代码必须与项目现有风格保持一致：
- 命名风格（camelCase / PascalCase / UPPER_SNAKE）与周围代码统一
- 导入顺序与文件中已有 import 一致
- 缩进、空行、括号风格与目标文件一致
- 使用项目中已有的工具函数/类型/常量，不重复造轮子

如果现有风格确实不好，在任务范围内统一修改该文件——而不是只改自己写的那几行造成风格割裂。

> ❌ 错误：在 camelCase 的文件里用 snake_case 写新函数
> ✅ 正确：观察文件前 50 行的命名风格，保持一致

### B5. 验证真实行为 — 不骗自己

完成修改后，验证标准是**真实行为正确**而非**命令能跑通**：
- 运行测试并检查断言语义（不是只看 exit code 0）
- UI 改动需肉眼确认渲染结果（不是只看无报错）
- Skill 注入变更需验证实际注入结果（不是只看编译通过）
- 类型变更需检查所有引用点（不是只看当前文件无红线）

如果无法验证（如缺少测试环境），必须明确声明"以下项未验证：xxx"，不能默认为通过。

> ❌ 错误："flutter analyze 没报错，应该没问题了"
> ✅ 正确："运行 flutter test 全部通过（2035/2035），手动点击返回按钮成功切换到聊天界面，flutter analyze 零 issue"

### B5+. 不确定时必须明说

当 AI 对以下任何一项不确定时，**必须明确声明**，不能沉默通过：

- 测试是否覆盖了所有相关场景
- 改动是否可能影响其他功能
- 某个依赖项是否确实需要引入
- 边界情况是否已处理
- 是否有更简单的实现方式

声明格式：
```
⚠️ 未充分验证：
- [具体未验证项 1] → 建议：[下一步行动]
- [具体未验证项 2] → 风险：[如果出问题会怎样]
```

这与 R-027 质量门禁和 R-022 过程可见形成联动——**不确定性是信息，不是缺陷。隐藏不确定性才是缺陷。**

## 违规示例与对应审查报告问题

| 违反边界 | 审查报告中的实际问题 | 后果 |
|---------|-------------------|------|
| 违反 B3 | RightDrawer.tsx 503 行（应拆分但顺手堆砌） | 可维护性崩塌 |
| 违反 B3 | 内联样式 1260 行零 CSS 类名（顺手写 style={{}}） | 样式债务 |
| 违反 B4 | emoji 与 Lucide 图标混用 | 视觉混乱 |
| 违反 B5 | 多处非空断言 `!` 掩盖潜在 undefined | 运行时崩溃风险 |

## 检查清单

```
AI 修改代码前：
□ 是否说了目标/范围/预期产出？（B1）
□ 是否已读目标文件 + 调用方？（B2）
□ 改动列表是否全部在任务范围内？（B3）
□ 新增代码风格是否与目标文件一致？（B4）

AI 声称完成后：
□ 验证方式是否覆盖真实行为？（B5）
□ 未验证项是否已明确声明？（B5）
```

## 与其他规则的协作

| 规则 | 关系 | 协作方式 |
|------|------|----------|
| R-024 AGENTS.md机制 | 依赖 | R-021 的核心禁止事项被 R-024 的 AGENTS.md 摘要收录，作为 AI 第一眼可见的约束 |
| R-027 AI代码质量门禁 | 被依赖 | R-027 门禁 2（Diff 审查）直接验证 R-021 B3 的最小化范围约束是否被遵守 |
| R-010 最小化范围 | 被依赖 | B3 是 R-010 在 AI 操作层面的具体化 |
| R-019 代码规范标准 | 被依赖 | B4 引用 R-019 定义的规范细节 |
| R-022 过程可见 | 互补 | B1 与 R-022 的四要素模板互补 |
| R-006 回退机制 | 被依赖 | B5 验证失败时触发 R-006 回退流程 |

## 优先级
高优先级 — 解决 AI 协作类规则纳入率仅 11% 的最大缺口
