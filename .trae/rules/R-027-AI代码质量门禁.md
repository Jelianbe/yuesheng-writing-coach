# R-027: AI 代码质量门禁（Flutter）

## 原则

审查报告暴露了 AI 开发产生的**系统性债务**：超长文件、超长函数、内联样式、
静默吞异常。这些如果在门禁层拦截，不会积累到今天。

**门禁不是 bureaucracy——它是防止债务积累的最后一道防线。**

## 四道门禁

### 门禁 1：规格校验（Spec Check）

**问题**：这个改动真的解决了它要解决的问题吗？

检查项：
- [ ] 改动是否符合任务描述 / 需求文档 / Issue 说明？
- [ ] 是否有超范围的改动？（对照 R-010 最小化范围）
- [ ] 是否引入了任务不需要的新依赖或新文件？

**通过标准**：所有改动均可追溯到明确的需求来源。

> ⚠️ 如果任务本身需求模糊，先澄清需求再写代码。不要猜。

### 门禁 2：Diff 审查（Diff Review）

**问题**：是不是只改了该改的东西？

检查项：
- [ ] `git diff` 是否只包含预期内的文件？（对照 R-021 B3）
- [ ] 每个文件的改动量是否合理？（单文件改动 >100 行需特别关注）
- [ ] 是否有"顺手"删除/添加的无关代码？
- [ ] import 变更是否都是必要的？

**通过标准**：diff 清洁，无意外改动。

### 门禁 3：自动化检查（Flutter 四道）

**问题**：改完之后真的能正常工作吗？

```bash
# 1. 格式 —— 只带本次改动的具体文件
dart format --set-exit-if-changed -o none <改动文件>

# 2. 静态分析 —— 全 lib（import 变化可能影响其他文件）
flutter analyze lib --no-pub

# 3. 循环依赖（R-020）
python scripts/check_circular.py

# 4. 全量测试（排除需真实 API Key 的用例）
flutter test --exclude-tags live,external --no-pub
```

检查项：
- [ ] `dart format` 报告 `0 changed`？
- [ ] `flutter analyze lib` 输出 `No issues found`？
- [ ] `check_circular.py` 无循环导入？
- [ ] `flutter test` 全绿（当前基线 **2035 用例**）？
- [ ] 如果有新功能，是否有至少 1 个新测试用例？
- [ ] UI 改动是否经过渲染确认？

**通过标准**：粘贴命令输出，而不仅是说"测试通过了"。

> ⚠️ **format 务必只带具体文件**。曾出现对 `lib test` 整体执行 format，
> 波及 11 个范围外文件的情况——违反 R-010 最小化范围。

### 门禁 4：人工签字（Human Sign-off）

**问题**：高风险变动是否经过了人的判断？

**触发条件**（满足任一即需要人工签字）：
- 诊断引擎 / 症候识别代码变更
- **Skill 注入内容变更**（会改变 AI 行为）
- 数据库 schema 变更（drift tables + migration）
- 涉及 API Key 或安全配置的变更
- **行为锚点快照发生漂移**（需人工复查差异，确认是否预期内）

**签字方式**：任务文档中记录 "✅ 已由 [谁] 在 [时间] 人工审查通过"，附简短审查意见。

## 零行为变更的验证

当改动声称"零行为变更"（逐字迁移、重构、数据/逻辑分离）时，
不能只靠"我觉得没变"——要有证据：

| 手段 | 适用场景 |
|:--|:--|
| 行为锚点快照对比 | Prompt / Skill 内容改动（改动前后逐字节比对） |
| `cmp` 字节级比对 | 迁移类改动，确认原文件与目标分片内容一致 |
| 四道门禁全绿 | 通用 |

若锚点发生漂移，**必须人工复查差异并说明是预期内的**，
不得直接更新快照了事。

## 禁止项（血泪教训）

- ❌ **禁止用 `part` / `extension` 机械拆分服务层大文件凑行数**。
  项目曾将 12 个服务拆成 41 个 part，被定性为**伪拆分**并回退 13 个 commit
  （批次 X-025-ARCH）。实证代价：`ChatService.sendMessage` 迁至 extension 后，
  测试替身 `_FakeChatService` 的 `@override` 契约断裂，触发 9 例
  `pumpAndSettle` 超时。
  **真分解 = 独立类 / 显式接口 / 依赖注入 / 职责级重构**。详见 R-019。
- ❌ 禁止用"更新快照"的方式掩盖未预期的行为漂移。
- ❌ 禁止空 catch 静默吞异常（R-028）：降级可以，但必须留痕。

## 不确定时的处理

当 AI 不确定某个改动是否安全/正确时：

```
❌ 错误：沉默通过，假设没问题
✅ 正确：明确声明不确定项
   "以下项未充分验证：[列表]，建议：[下一步]"
```

这与 R-021 B5（验证真实行为）和 R-022（过程可见）形成联动。

## 分级执行

| 风险等级 | 需要通过的门禁 | 典型场景 |
|:--|:--:|:--|
| 低（单文件 bug 修） | 1 + 2 + 3 | 修 typo、调样式 |
| 中（多文件联动） | 1 + 2 + 3 | 功能增强、重构组件 |
| **高（核心模块变更）** | **1 + 2 + 3 + 4** | 诊断引擎 / Skill / DB schema / 安全 |

## 检查清单

```
AI 声称"已完成"时：
□ 门禁 1：所有改动都有需求来源？
□ 门禁 2：git diff 干净无多余改动？
□ 门禁 3：format / analyze / circular / test 四道全绿且有输出证据？
□ 门禁 4：（如适用）高风险模块已人工审查？
□ 若声称零行为变更：是否有锚点或字节比对证据？
□ 不确定项是否已明确声明？
```

## 与其他规则的协作

| 规则 | 关系 | 协作方式 |
|------|------|----------|
| R-019 代码规范标准 | 依赖 | 门禁 3 的 analyze 验证 R-019 的静态约束 |
| R-013 测试覆盖率要求 | 被依赖 | 门禁 3 的测试标准与基线由 R-013 定义 |
| R-021 AI行为边界 | 互补 | 门禁 2 直接引用 R-021 B3 的最小化范围约束 |
| R-020 循环依赖零容忍 | 并行 | 门禁 3 的 circular 步骤即 R-020 的落地 |
