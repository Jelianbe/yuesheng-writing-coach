# R-027: AI 代码质量门禁

## 原则

审查报告暴露了 AI 开发产生的**系统性债务**：503 行文件、零 CSS 类名、非空断言、内联样式 1260 行。这些如果在门禁层拦截，不会积累到今天。

**门禁不是 bureaucracy——它是防止债务积累的最后一道防线。**

## 四道门禁

### 门禁 1：规格校验（Spec Check）

**问题**：这个改动真的解决了它要解决的问题吗？

检查项：
- [ ] 改动是否符合任务描述 / 需求文档 / Issue 说明？
- [ ] 是否有超范围的改动？（对照 R-010 最小化范围）
- [ ] 是否引入了任务不需要的新依赖或新文件？

**通过标准**：所有改动均可追溯到明确的需求来源。

> ⚠️ 如果任务本身需求模糊，先澄清需求再写代码。不要猜。

### 门禁 2：Diff 审查（Diff Review）

**问题**：是不是只改了该改的东西？

检查项：
- [ ] `git diff` 是否只包含预期内的文件？（对照 R-021 B3）
- [ ] 每个文件的改动量是否合理？（单文件改动 >100 行需特别关注）
- [ ] 是否有"顺手"删除/添加的无关代码？
- [ ] import 变更是否都是必要的？

**通过标准**：diff 清洁，无意外改动。

### 门禁 3：测试证据（Test Evidence）

**问题**：改完之后真的能正常工作吗？

检查项：
- [ ] `npx tsc --noEmit` 通过？（TypeScript 编译零错误）
- [ ] `npx vitest run` 通过？（基线测试全部通过）
- [ ] 如果有新功能，是否有至少 1 个新测试用例？
- [ ] UI 改动是否经过肉眼确认渲染正确？

**通过标准**：粘贴测试运行的输出到任务评论中，而不仅是说"测试通过了"。

### 门禁 4：人工签字（Human Sign-off）

**问题**：高风险变动是否经过了人的判断？

**触发条件**（满足任一即需要人工签字）：
- 诊断引擎代码变更
- 教学 Agent / Prompt 变更
- 数据库 schema 变更
- IPC 通道定义变更
- 涉及安全配置的变更

**签字方式**：任务文档中记录 "✅ 已由 [谁] 在 [时间] 人工审查通过"，附简短审查意见。

## 不确定时的处理

当 AI 不确定某个改动是否安全/正确时：

```
❌ 错误：沉默通过，假设没问题
✅ 正确：明确声明不确定项
   "以下项未充分验证：[列表]，建议：[下一步]"
```

这与 R-021 B5（验证真实行为）和 R-022（过程可见）形成联动。

## 分级执行

| 风险等级 | 需要通过的门禁 | 典型场景 |
|---------|:-------------:|---------|
| 低（单文件 bug 修） | 1 + 2 + 3 | 修 typo、调样式 |
| 中（多文件联动） | 1 + 2 + 3 | 功能增强、重构组件 |
| **高（核心模块变更）** | **1 + 2 + 3 + 4** | 诊断引擎/Agent/DB/IPC |

## 检查清单

```
AI 声称"已完成"时：
□ 门禁 1：所有改动都有需求来源？
□ 门禁 2：git diff 干净无多余改动？
□ 门禁 3：tsc + vitest 通过且有输出证据？
□ 门禁 4：（如适用）高风险模块已人工审查？
□ 不确定项是否已明确声明？
```

## 与其他规则的协作

| 规则 | 关系 | 协作方式 |
|------|------|----------|
| R-019 代码规范标准 | 依赖 | R-027 门禁 3（测试证据）中的 tsc 检查验证 R-019 的类型安全要求 |
| R-021 AI行为边界 | 互补 | R-027 门禁 2（Diff 审查）直接引用 R-021 B3 的最小化范围约束 |
| R-013 测试覆盖率要求 | 被依赖 | R-027 门禁 3 的测试通过标准需要 R-013 的覆盖率要求作为验证依据 |

## 优先级
高优先级 — 拦截系统性代码债务的关键防线
