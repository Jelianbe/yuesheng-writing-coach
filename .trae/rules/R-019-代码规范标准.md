# R-019: 代码规范标准（Flutter）

> 2026-08-29 由 Electron/TS 版重写。原版以 IPC handler、CSS Modules、
> `shared/types.ts` 为样板，不适用当前 Flutter 真源。

## 1. 硬上限：函数 ≤ 50 行

**这是本规则最容易被忽略、也最重要的一条。**

R-019 原文为「函数不超过 50 行，文件不超过 300 行」，但实践中
「300 行」被过度关注，而「50 行」被系统性忽略——**后者才是硬上限**。

- **函数 > 50 行**：必须拆分（提取子方法 / 抽独立类）
- 拆分后若子方法仍超长，说明职责未理清，需重新划分职责，
  而非继续机械切分

> **实测实例**：`chat_service.dart` 中 12 个函数超 50 行，
> 最长 `_sendMessageCore` 293 行（5.9 倍），另有 278 / 271 / 243 / 232 行等。
> 该文件 3004 行的根源在**函数过长**，而非文件行数本身。
> 其中多个 `_inject*` 方法是当年把 1392 行 `sendMessage` 巨方法拆散后的
> 产物——函数变多了，但单个函数照样超长，属同一问题的另一种形态。

## 2. 文件 ≤ 300 行，但**禁止伪拆分**

- 文件超 300 行时，**优先检查是否函数过长**（见上），而非急着切文件
- **服务层禁止用 `part` / `extension` 机械拆分凑行数**
  - 批次 **X-025-ARCH（2026-08-22）** 已将此类做法定性为**伪拆分**
    并全部回退（13 个 commit，12 host / 41 parts 合并回单体）
  - **实证代价**：`ChatService.sendMessage` 迁至 extension 后，测试替身
    `_FakeChatService` 的 `@override` 契约断裂（**Dart 扩展方法非 virtual**），
    调用真实 LLM API 触发 **9 例 `pumpAndSettle` 超时**
  - **真分解** = 独立类 / 显式接口 / 依赖注入 / 职责级重构
- **服务层超限需走 ADR 决策**；登记为已知债务同样是合规路径
- **A 类纯常量知识库可豁免**（`skill_registry` + 各 `skills_*.dart`、
  三大知识库 `syndrome_kb_content` / `technique_kb_content` /
  `training_kb_content`）：part 拆分与内容领域边界严格一致、无逻辑耦合、
  无 override 契约，不触发伪拆分审查

## 3. DRY：相同的数据结构只定义一次

统一集中在 `lib/types/`
（`teaching_types.dart` / `display_types.dart` / `character_types.dart`）。

```
❌ 错误：在多个文件各定义一份相同结构
✅ 正确：在 lib/types/ 定义，其他文件 import
```

### 常量集中管理

跨文件使用的常量必须提取到 `lib/config/`：

| 常量类型 | 位置 |
|:--|:--|
| 通用常量 | `lib/config/shared_constants.dart` |
| 设计令牌（文本 / 颜色） | `lib/config/app_theme.dart` |
| Token 预算表 | `lib/config/token_budget_table.dart` |
| 局部魔法数字 | 使用处附近的具名 `const`（0 / 1 / -1 除外） |

### 禁止的重复模式

| 模式 | 为什么禁止 | 替代方案 |
|:--|:--|:--|
| 同一数据结构在多文件定义 | 改一处漏一处 | 统一到 `lib/types/` |
| 相同工具函数复制粘贴 | bug 修复需改 N 处 | 提取到共享模块 |
| 硬编码路径 / 键名 / 事件名 | 重构时搜不全 | 集中到 `lib/config/` |
| 样式字面量散落 | 改一个字号要动几十个文件 | 设计令牌 |

## 4. 样式：走设计令牌，不写裸字面量

- 文本样式用 `AppTextStyles`，颜色用 `AppColors`
  （均位于 `lib/config/app_theme.dart`）
- 例外：动态计算值

> **现状（2026-08-29 实测）**：`lib/widgets/` 仍有 `fontSize` 485 处、
> `fontWeight` 318 处硬编码。颜色层已 100% 令牌化（残留 0）。
> 字号取值高度集中——14/13/12/15/16 五个值覆盖 84%（407/485），
> 收敛性价比高。
> 按 R-010 最小化范围：**改动涉及某组件时顺手迁移，不单独开批量任务**。

## 5. 防御性（详见 R-028）

- 边界层（Repository / LLM Client / 平台通道 / 表单）必须有 try/catch
- **禁止空 catch**：吞掉错误等于埋雷
- 确需静默降级必须留痕，用 `lib/services/decode_guard.dart`

## 6. 命名与格式

- 变量 / 函数 / 成员：`lowerCamelCase`
- 类 / 枚举 / 扩展名：`UpperCamelCase`
- 常量：`lowerCamelCase`（**Dart 惯例，非 UPPER_SNAKE_CASE**）
- 文件名：`snake_case.dart`
- 格式以 `dart format` 为准（见 R-027 门禁 1）
- 避免 `as` 类型断言与 `!` 空断言，优先用可空类型与模式匹配

## 7. 与其他规则的协作

| 规则 | 关系 | 协作方式 |
|:--|:--|:--|
| R-027 质量门禁 | 验证 | 门禁的 analyze 步骤验证本规则的静态约束 |
| R-013 测试覆盖率 | 验证 | 重构需有测试证明行为不降级 |
| R-028 防御性编码 | 互补 | 本规则要求边界有 try/catch，R-028 定义实现方式 |
| R-020 循环依赖零容忍 | 互补 | import 规范与依赖方向共同维护模块健康度 |
| R-010 最小化范围 | 约束 | 迁移 / 重构只做当前改动涉及的部分 |
