# R-028: 防御性编码

## 原则

**防御性编码有两个极端错误：**

1. **完全不防御** — 用户输入直接传给 API，IPC 参数不校验 → 安全漏洞 + 崩溃
2. **过度防御** — 每个函数都包 try/catch，每个参数都做 null check → 掩盖真实 bug + 噪声满天飞

正确做法：**只在边界防御，内部信任已控制的数据。**

## 边界 vs 内部

### 必须防御的边界（Boundary）

| 边界位置 | 校验要求 | 示例 |
|---------|---------|------|
| **IPC Handler 入参** | 必须校验类型、范围、必填字段 | `ipcMain.handle('chat:send', (event, payload) => { if (!payload.message) { ... } })` |
| **外部 API 调用响应** | 必须检查 HTTP 状态码 + 响应体结构 | `if (!res.ok) throw new Error(...)` |
| **用户输入（UI 表单）** | 提交前校验格式、长度、非法字符 | 表单 validation |
| **环境变量 / 配置读取** | 启动时校验存在性和格式 | `if (!process.env.API_KEY) throw ...` |
| **SQLite 查询结果** | 检查 rows 是否存在 | `const row = db.prepare(...).get(); if (!row) return null;` |

### 不应防御的内部（Internal）

| 内部位置 | 为什么不防御 |
|---------|------------|
| Store 之间的函数调用 | 数据形状由 TypeScript 类型保证 |
| 组件内部的 props 解构 | 已由父组件和类型系统保证 |
| 工具函数之间的调用 | 调用方负责传正确参数 |

## try/catch 使用规则

### ✅ 正确使用（有特定错误要处理）

```typescript
// 1. 已知可能失败的特定操作
try {
  const response = await fetch(apiUrl);
  if (!response.ok) throw new Error(`API ${response.status}`);
} catch (error) {
  // 有具体的错误处理逻辑
  showErrorToast('网络请求失败，请检查连接');
  logError(error);  // 记录但不吞掉
  throw error;      // 向上层传播
}

// 2. 需要做清理操作的 finally
let dbConnection;
try {
  dbConnection = await connectDB();
  // ...
} finally {
  await dbConnection?.close();
}
```

### ❌ 错误使用（禁止）

```typescript
// 1. 空 catch — 吞掉所有错误
try {
  doSomething();
} catch {
  // ← 这里什么都没有！bug 被静默隐藏
}

// 2. 无意义的 fallback
const value = maybeUndefined ?? 'default';  // "不可能发生"的情况
// 如果 really不应该 undefined，让它崩掉，这样你能发现 bug

// 3. 包裹整个函数体
async function handler() {
  try {
    // 100 行代码全包在里面
    // 任何 bug 都被catch吞掉，永远不知道哪里出错了
  } catch (e) {
    console.error(e);  // 日志里一行 error，没有上下文
  }
}
```

### 正确的错误传播策略

```
边界层（IPC handler / API route）
  → 捕获 + 记录 + 转换为用户友好的错误消息 + 向上层抛出

业务层（Store / Service）
  → 不捕获（让自然冒泡）或 仅做 context enrichment 后 rethrow

组件层（React）
  → ErrorBoundary 捕获渲染错误
  → 异步操作用 toast/notification 展示
```

## IPC Handler 模板

```typescript
ipcMain.handle('domain:action', async (event, payload): Promise<ResultType> => {
  // 1. 入参校验（边界防御）
  if (!payload || typeof payload.id !== 'string') {
    return { success: false, error: 'INVALID_PAYLOAD', message: '缺少必要参数' };
  }

  try {
    // 2. 业务逻辑（内部不防御）
    const result = await someService.doSomething(payload.id);

    // 3. 出参校验（防御性返回）
    return { success: true, data: result };

  } catch (error) {
    // 4. 错误处理（分类处理已知错误）
    if (error instanceof NotFoundError) {
      return { success: false, error: 'NOT_FOUND', message: '资源不存在' };
    }
    // 未知错误向上抛，让顶层 handler 统一处理
    throw error;
  }
});
```

## 检查清单

```
code review 时检查：
□ try/catch 是否有具体的错误处理逻辑？（不能是空 catch）
□ catch 块是否至少做了 logError(error)？
□ 参数校验是否只在 IPC/API/用户输入等边界层？
□ 内部函数调用是否无 try/catch 包裹？
□ 是否用了无意义的 fallback 值？
```
