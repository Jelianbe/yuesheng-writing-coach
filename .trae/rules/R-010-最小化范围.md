# R-010: 变更最小化原则

## 原则
每次代码变更应当最小化：只解决一个问题，只修改必要的文件，不引入不必要的复杂度。

## 核心要求
1. **单一责任** - 每次提交只解决一个问题
2. **范围限制** - 只修改必要的代码文件
3. **复杂度管理** - 不引入不必要的复杂度
4. **测试保障** - 变更前后测试通过

## 实施指南
### 功能开发
- 每个功能点单独提交
- 避免在单个提交中包含多个独立逻辑
- 每个功能点有独立的测试

### Bug修复
- 只修复报告的问题本身
- 不在修复过程中进行额外的重构
- 验证修复不影响其他功能

### 重构操作
- 将重构与功能开发分离
- 小步快跑，每次重构少量代码

## 示例
```
# ✅ 好的做法
提交1: 修复API配置连接测试超时
提交2: 提取SVG图标到独立组件
提交3: 添加聊天消息流式显示

# ❌ 不好的做法
提交: 修复超时、重构组件、添加聊天功能、更新文档
```

## 检查清单
```
变更前检查：
□ 这次变更是否只解决一个问题？
□ 是否修改了不相关的代码？
□ 是否引入了额外复杂度？

变更后检查：
□ 所有测试是否仍然通过？
□ 代码复杂度是否增加？
```

## 与其他规则的协作

| 规则 | 关系 | 协作方式 |
|------|------|----------|
| R-019 代码规范标准 | 互补 | R-019 的文件拆分建议（≤300 行）需要 R-010 控制拆分范围，避免过度拆分 |
| R-007 双向绑定 | 约束 | 状态变更必须遵循 R-010 的变更范围最小化，只同步受影响的数据链路 |

## 优先级
高优先级 - 保障代码质量和可维护性
