# R-020: 循环依赖零容忍

## 原则

模块间的依赖关系必须形成**有向无环图（DAG）**。任何形式的循环依赖——无论是显式的顶层 import 还是隐式的延迟导入——都是架构债务，必须消除。

## 为什么循环依赖有害

| 问题 | 影响 |
|------|------|
| **初始化顺序不确定** | 模块加载顺序依赖 import 先后，可能导致 undefined 引用 |
| **难以测试和 Mock** | 循环依赖使得单元测试中无法独立替换任一模块 |
| **重构风险高** | 改动一个文件可能引发连锁崩溃，且错误信息不直观 |
| **打包体积膨胀** | Webpack/Vite 无法正确 tree-shake 循环依赖的代码 |

## 禁止的绕过手段

以下手段**全部禁止**用于规避循环依赖：

| 手段 | 示例 | 为什么禁止 |
|------|------|-----------|
| **延迟导入（函数内 import）** | `function foo() { const bar = require('./bar'); }` | 掩盖了真实的架构问题，运行时才暴露错误 |
| **try-except 包裹导入** | `try { require('./a') } catch {}` | 静默吞掉错误，导致不可预测的行为 |
| **importlib 动态导入** | Python: `importlib.import_module('xxx')` | 同上 |
| **TypeScript `import type` 滥用** | 用 `import type` 绕过值级循环但逻辑上仍耦合 | 仅允许真正的类型导入，不允许用其掩盖设计缺陷 |
| **全局变量/事件总线桥接** | 通过 window/globalEvent 绕过直接 import | 将编译期问题推迟到运行时 |

## 正确的解决方案

当发现循环依赖时，按以下优先级处理：

### 方案 1：提取公共依赖（首选）
```
A ← B （A 和 B 都依赖 C）
 ↓ ↗
 C（提取到共享层）
```
示例：`drawer.store` 和 `panel-session.store` 都需要对方的数据 → 提取 `drawer-constants.ts` 存放映射表。

### 方案 2：依赖反转（DIP）
```
A → IInterface ← B
```
示例：组件不应直接 import Store，而应通过 props/callback 注入依赖。

### 方案 3：合并模块
如果两个模块总是成对使用且互相依赖，说明它们本应是一个模块。

## 项目中的高风险区域

基于当前代码结构，以下区域最容易产生循环依赖：

| 区域 | 风险点 | 建议 |
|------|--------|------|
| **Store 层** (stores/) | drawer ↔ panel-session ↔ session 三方联动 | 保持 drawer-constants 作为单向桥梁，Store 之间禁止互相 import |
| **Layout 组件层** (components/layout/) | RightDrawer ↔ SessionTabBar ↔ ResizeHandle | 子组件只接受 props，不直接 import 父组件 |
| **IPC 通信层** (main/ipc/) | handler ↔ service ↔ store | handler → service → store 单向流动，禁止反向调用 |
| **类型定义层** (shared/types.ts) | types 被 everywhere import | types 必须是叶子节点，禁止 import 任何业务模块 |

## 检测工具配置

```json
// package.json scripts 中添加
{
  "scripts": {
    "check-circular": "madge --circular --extensions ts,tsx src/"
  }
}
```

或在 CI pipeline 中集成：
```bash
npx madge --circular src/ && echo "✅ 无循环依赖" || (echo "❌ 发现循环依赖" && exit 1)
```

## 检查清单

```
新增 import 时检查：
□ 是否形成了 A→B→...→A 的闭环？
□ 是否使用了上述禁止的绕过手段？
□ 依赖方向是否符合架构分层（renderer → shared → main 禁止反向）？

重构/拆分组件时检查：
□ 拆分后的子组件是否不再 import 父组件？
□ 提取的新模块是否位于正确的层级？

CI/CD 门禁：
□ check-circular 脚本是否通过？
□ 是否有新增的循环依赖警告被忽略？
```

## 与其他规则的协作

| 规则 | 关系 | 协作方式 |
|------|------|----------|
| R-019 代码规范标准 | 被依赖 | R-019 的 import 规范与 R-020 的循环依赖检查共同维护模块依赖健康度 |
| R-010 最小化范围 | 互补 | 小改动不易引入新循环依赖 |
| R-005 全流程文档化 | 互补 | 重构消除循环依赖时需要通过 R-005 记录逻辑解释 |

## 优先级
高优先级 — 随着组件拆分和 Store 数量增长，循环依赖风险持续上升
