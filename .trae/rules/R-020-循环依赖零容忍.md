# R-020: 循环依赖零容忍（Flutter）

## 原则

模块间的依赖关系必须形成**有向无环图（DAG）**。任何形式的循环依赖——
无论是显式的顶层 import，还是通过延迟导入、`dynamic` 等手段绕过的隐式
循环——都是架构债务，必须消除。

> ⚠️ **Dart 对 import 循环不会报错**（这点与 ES modules 不同）。
> 循环依赖会静默存在，直到运行时才暴露（如 `late` 变量未初始化、
> 常量求值顺序错误、Provider 初始化死锁）。
> 因此**必须靠工具主动检测**，不能指望编译器报错。

## 为什么循环依赖有害

| 问题 | 影响 |
|:--|:--|
| **初始化顺序不确定** | `late` 字段可能未初始化即被访问 |
| **难以测试和 Mock** | 无法独立替换任一模块 |
| **重构风险高** | 改动一个文件引发连锁崩溃，错误信息不直观 |
| **常量求值异常** | 顶层 `const` 循环引用可能在运行时抛错 |

## 检测工具（项目已配置，提交前必跑）

```bash
python scripts/check_circular.py
# 期望输出：OK: no circular imports in lib (289 modules)
```

该脚本已纳入 **R-027 门禁 3**。当前基线：**289 modules，无循环导入**。

## 禁止的绕过手段

| 手段 | 为什么禁止 |
|:--|:--|
| `deferred as` 延迟导入 | 掩盖真实架构问题，错误推迟到运行时 |
| 用 `dynamic` 调用规避类型依赖 | 丧失类型安全，问题同样推迟到运行时 |
| 全局单例 / 事件总线桥接 | 编译期问题推迟到运行时 |
| 只导类型不导值以"绕过" | 逻辑上仍耦合，未真正解耦 |

## 正确的解决方案

按以下优先级处理：

### 方案 1：提取公共依赖（首选）

```
A ← B   （A 和 B 都依赖 C）
 ↓ ↗
 C      （提取到共享层）
```

项目实例：`lib/types/` 与 `lib/config/` 即为此角色，被各层共享。

### 方案 2：依赖反转（DIP）

```
A → IInterface ← B
```

项目已有实践：四大纯能力（GenUi / Material / Teaching / Diagnosis）
以契约接口注入，`session_providers.dart` 中 watch 后传给 `ChatService`，
实现可在一处替换而不波及消费者。

### 方案 3：合并模块

若两个模块总是成对使用且互相依赖，说明它们本应是一个模块。

## 项目分层（单向依赖，禁止反向）

```
widgets/  →  providers/  →  services/  →  data/repositories/  →  data/database/
                  ↓              ↓                ↓
              config/        types/         contracts/
```

- `types/`、`config/`、`contracts/` 是**叶子节点**，禁止 import 任何业务模块
- **下层禁止 import 上层**（如 repository 不得 import widget / provider）

## 高风险区域

| 区域 | 风险点 | 建议 |
|:--|:--|:--|
| `providers/` | Provider 之间互相 watch | 共同依赖抽到更下层 |
| `services/` | service ↔ service 互调 | 抽公共子服务，或经 provider 注入 |
| `widgets/` 大页面 | 父页面 ↔ part 子组件 | part 只定义扩展，不反向 import 宿主以外 |
| `data/repositories/` | repository 之间互调 | 由 service 层编排，repository 之间保持独立 |

## 检查清单

```
新增 import 时：
□ 是否形成了 A→B→...→A 的闭环？
□ 是否使用了上述禁止的绕过手段？
□ 依赖方向是否符合分层？（下层不得 import 上层）
□ scripts/check_circular.py 是否通过？

重构 / 拆分 Widget 时：
□ 拆分后的子组件是否不再 import 父组件？
□ part 文件是否只定义扩展、不引入新的反向依赖？
```

## 与其他规则的协作

| 规则 | 关系 | 协作方式 |
|:--|:--|:--|
| R-027 质量门禁 | 落地 | circular 检查即门禁 3 的一环 |
| R-019 代码规范标准 | 互补 | import 规范与依赖方向共同维护模块健康度 |
| R-010 最小化范围 | 互补 | 小改动不易引入新循环依赖 |
| R-005 全流程文档化 | 互补 | 重构消除循环依赖时需记录逻辑解释 |

## 优先级

高优先级 — 随着 Widget 拆分与 Provider 数量增长，循环依赖风险持续上升
