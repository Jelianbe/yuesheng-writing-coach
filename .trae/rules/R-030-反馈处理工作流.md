# R-030：反馈处理工作流

## 规则内容

**所有反馈必须经过完整的 10 步处理流程后才能产生代码变更。** 其中 Step -1/0/1/2/3/3.5/4/4.5/5/5.5/6 共 11 个节点，Step 3.5/4.5/5.5 为子步骤，计数器不含 -1。每一步都有明确的入口和出口条件，跳过或简化任何步骤都必须显式声明理由。

## 流程概览

```
Step -1   预分类（A/B/C/D/E 五通道）
    ↓ B 类进入主流程
Step 0     查重 TASK-CHAIN.md
    ↓ 无重复
Step 1     产出溯源报告 + ★ Skill 库遍历与选型
    ↓ 报告完整 + Skill 选型表就绪
Step 2     原子化拆分 + 三大原则排序 + 冲突检测
    ↓ 通过检验
Step 3     用户确认（R-009 用户主权）
    ↓ 批准
Step 3.5   ★ Git 分支备份（R-006 回退机制落地）
    ↓ 备份就绪
Step 4     执行（按 DoD 分型，按 Skill 选型调用对应 AI 代理）
    ↓ 完成
Step 4.5   ★ 代码质量审查（CODE_REVIEW_CHECKLIST 逐项检查）
    ↓ P0=0
Step 5     验收（自动化 + 人工）
    ↓ 全部通过
Step 5.5   ★ 用户确认 → 合并到 main
    ↓ main 已同步
Step 6     TASK-CHAIN 闭环更新 + 备份清理
```

---

## 各步骤详细规则

### Step -1：反馈预分类（入口过滤）

**目的**：不是所有反馈都值得进入完整流程。

| 分类 | 定义 | 处理方式 | 是否进入主流程 |
|------|------|---------|:--------------:|
| **A 类** | Bug / 崩溃 / 数据丢失 / 安全漏洞 | 紧急修复通道（R-018 豁免：≤5 行且不涉及 SQL Schema/IPC 通道/安全/状态管理/DB 迁移时可直接执行） | 视规模 |
| **B 类** | 功能缺失 / 体验问题 / 技术债务 / 代码质量 | **进入完整 10 步流程** | **是** |
| **C 类** | 纯意见 / 方向性讨论 / 探索性问题 | 记录到 `docs/decision-log.md`，不进入任务链 | 否 |
| **D 类** | 超出范围（违反界面改造边界 / 核心链路无关） | 引用对应边界声明拦截 | 否 |
| **E 类** | 纯文档/内容变更（.md / 配置文件等，不含代码逻辑） | 简化通道（Step -1→Step 0→Step 3→直接写入→Step 6，跳过备份/审查/验收/tsc 编译） | 简化流程 |

**强制检查**：
```
□ 分类结果是否明确？（不能模糊归入多个类别）
□ 若 A 类，是否符合 R-018 豁免条件？（≤5 行且不涉及 SQL/IPC/安全/状态管理/迁移）
□ 若 D 类，引用了哪条边界声明？
```

**复杂度标记**（B 类进入主流程时标记，用于判断跳过 Step 2/3.5）：
| 标记 | 条件 | 可跳过步骤 |
|------|------|-----------|
| 微型 🌱 | B 类且 ≤3 行修复，不涉及 SQL/IPC/状态管理 | Step 2 + Step 3.5 |
| 小型 📄 | B 类且 ≤15 行，影响单一文件 | Step 2 |
| 中型 📦 | 默认值，涉及 2-3 个文件 | 无 |
| 大型 🏗️ | 涉及 ≥4 个文件或跨进程变更 | 无（需 < 4d） |

### Step 0：查重 TASK-CHAIN

**强制动作**：在 [TASK-CHAIN.md](../yuesheng-writing-coach/docs/tasks/TASK-CHAIN.md) 中搜索关键词，确认是否已有相同/相似任务。

**命中时的处理选项**（必须向用户展示）：
1. 推进现有任务（尚未完成）
2. 补充为子问题（现有覆盖不完整）
3. 替换现有任务（新反馈更准确）
4. 并行处理（与现有独立）

**未命中** → 生成反馈编号（格式 `FB<日期>-<序号>`，如 FB240611-001），进入 Step 1。

### Step 1：溯源报告（R-018 合规）

**必须产出**以下内容：

1. **问题定义**：标题（≤50 字）+ 分类 + 严重度(P0/P1/P2) + 影响范围
2. **溯源四环**（R-018 变更溯源规范）：
   - 设计哲学依据（为什么做）
   - 技术规格依据（怎么做）
   - 研究基础依据（教学链路相关时）
   - 前序任务衔接（从哪来）
3. **Skill 库遍历与关联**：
   - **遍历 Skill 库**：搜索 `.agents/skills/` 目录 + `trae/rules/skills/` + IDE Skill 工具中可用的 Skill，列出所有与本次反馈相关的 Skill
   - **速查表印证**：对照 [SKILLS-QUICKREF.md](../yuesheng-writing-coach/docs/tasks/SKILLS-QUICKREF.md) 场景映射表交叉验证，补全遗漏
   - **映射决策**：为每个子任务明确选取 1 个 Skill（如 modular-refactoring-architect、bug-detective、test-automation-expert 等），说明选型理由
   - **输出**：在溯源报告中列出 `Skill 选型表（任务 → Skill → 理由）`

> **模板文件**：[FEEDBACK-REPORT-TEMPLATE.md](../yuesheng-writing-coach/docs/tasks/FEEDBACK-REPORT-TEMPLATE.md)

### Step 2：原子化拆分与排序

**拆分要求**（R-010 最小化范围）：

| 约束 | 标准 |
|------|------|
| 单一职责 | 每个子任务只解决一个问题 |
| 规模上限 | ≤ L（4d），XL 禁止必须拆 |
| 可验证 | 每项 ≥3 条 DoD（R-004）|

**三大原则逐项检验**（TASK-CHAIN §〇）：

| 原则 | 检验问题 |
|------|---------|
| 一、收尾确认 | 前序任务是否已完成？DoD 是否达成？ |
| 二、基础提供 | 本任务为后续产出什么？如何验证可用性？ |
| 三、自然衔接 | 从前序哪个具体输出开始？引用文件/函数名？ |

**冲突检测**（5 项）：
- [ ] 与已完成任务矛盾？
- [ ] 与待执行任务重叠？
- [ ] 违反界面改造边界声明？
- [ ] 属于"影子功能"反模式？
- [ ] 前置依赖未就绪？

### Step 3：用户确认（R-009 用户主权）

**必须获得用户对以下 7 项的确认**：
1. 问题理解正确
2. 拆分粒度合理
3. 优先级认可
4. 执行顺序同意
5. Skill 选型接受（含 Skill 库遍历结果）
6. 范围无遗漏
7. 备份策略确认

**出口条件**：
- □ **批准** → Step 3.5 备份
- □ **修改** → 返回 Step 2
- □ **暂不执行** → decision-log.md 记录 + 退出
- □ **取消** → 终止

### Step 3.5：执行前备份（R-006 回退机制）⭐

**这是最高优先级的强制性步骤。无备份不得执行代码变更。**

#### 备份操作标准流程

```bash
# 1. 确认工作区干净（若有未提交改动先处理）
git status

# 2. 创建备份分支（命名规范：backup/pre-FB<编号>）
git checkout -b backup/pre-FB240609-001

# 3. 提交基线快照
git add -u && git commit -m "backup: FB<编号> 执行前基线"

# 3b. 创建轻量 tag（保留至发版后清理，用于事后回归恢复）
git tag backup/FB240609-001

# 4. 切回工作分支
git checkout <当前开发分支>
```

#### 回退能力验证

备份创建后必须确认以下回退方式可用：

| 场景 | 操作 |
|------|------|
| 全部回退 | `git reset --hard backup/pre-FB<编号>` |
| 查看差异 | `git diff backup/pre-FB<编号>..HEAD --stat` |
| 单文件回退 | `git checkout backup/pre-FB<编号> -- <path>` |
| tag 恢复 | `git checkout backup/FB<编号>`（保留至发版后清理） |
| 验收后清理 | `git branch -D backup/pre-FB<编号>`（分支可删，tag 保留至发版） |

### Step 4：执行

**执行者**：AI 代理负责代码变更执行，开发者负责审查和确认。涉及 SQL 迁移、IPC 通道变更等敏感操作时，需开发者确认后再合并。

按 DoD 分型执行（参考 FEEDBACK-REPORT-TEMPLATE.md 附录）：

| 类型 | 验证底线 |
|------|---------|
| 工程 | tsc 0 错误 + 测试覆盖 + 行为不变性 |
| 内容 | 格式校验 + 命名一致 + 可被消费 |
| 研究 | 调研报告 + 关键信息提取 + 做/不做决策 |
| 审查 | 全维度 + 无否决项 + 报告归档 |
| 混合 | 覆盖所涉类型子集 |

### Step 4.5：代码质量审查 ★

**执行完成后、提交流验前，必须使用代码审查清单进行质量检查。**

#### 审查流程

1. 使用 [CODE_REVIEW_CHECKLIST_V1.0.md](../yuesheng-writing-coach/docs/standards/CODE_REVIEW_CHECKLIST_V1.0.md) 列出的 4 层检查项（P0/P1/P2/专项）
2. 逐项回答，不可跳过
3. 发现问题时必须给出具体文件+行号

#### 出口条件

| 条件 | 动作 |
|------|------|
| **P0=0** | ✅ 通过，进入 Step 5 验收 |
| **P0≥1** | ❌ 阻塞，返回 Step 4 修复，修复后重新审查 |
| P1/P2 问题 | 记录到审查报告，可在本步骤修复或标记为已知债务进入 Step 5 |

#### 审查输出要求

```
# 代码审查报告

审查文件: [文件路径]
P0 致命问题数: X
P1 架构问题数: X
P2 质量问题数: X

## P0 致命问题（必须修复）
| # | 问题 | 文件:行号 | 修复建议 |

## P1 架构问题
| # | 问题 | 文件:行号 | 修复建议 |

## P2 质量问题
| # | 问题 | 文件:行号 | 修复建议 |

总评: [P0=0 即通过]
```

#### 与 CODE_REVIEW_CHECKLIST 的关系

| 清单层级 | 对应 R-030 处理方式 |
|----------|-------------------|
| 第一层 P0（致命）| **必须修复**，否则阻塞 Step 5 |
| 第二层 P1（架构）| 建议修复，可在 Step 4.5 处理或标记为已知债务 |
| 第三层 P2（质量）| 可选修复，记录到审查报告 |
| 第四层（专项）| 按上下文选用，覆盖 DB/React/IPC 专项检查 |

### Step 5：验收

**双重验收**缺一不可，支持两种模式：

**交互模式**（人在线时，默认）：
- **自动化验收**（5 项必选）：
  - [ ] `npx tsc --noEmit` → 0 errors
  - [ ] `npx vitest run` → passed
  - [ ] `npm run build` → success（如需要）
  - [ ] `npm run check:size` → 无超限文件（检查单文件 ≤300 行）
  - [ ] `npm run check:circular` → 无循环依赖（使用 madge 檢查 import 图）
- **人工验收**（至少 3 项）：
  - [ ] 功能正确性（实际操作验证）
  - [ ] 无回归（对比基准行为）
  - [ ] UI 表现（如涉及前端改动）
  - [ ] 控制台无报错

**自动模式**（人不在线，如定时任务）：
- **自动化验收**同上 5 项
- **人工验收**降级为生成变更 diff 摘要 + 验收报告，留待人上线后审查确认

### Step 5.5：用户确认 → 合并到 main ⭐

**用户验收通过后，将备份分支合并到 main，确保反馈修复正式落地。**

#### 合并流程

```bash
# 1. 确认验收通过（Step 5 双重验收全部通过）
# 2. 确认当前在开发分支
git branch  # 确认不在 main 上

# 3. 切到 main 并拉取最新
git checkout main
git pull origin main

# 4. 合并开发分支（--no-ff 保留分支历史）
git merge --no-ff <当前开发分支> -m "feat: FB<编号> <简要描述>"

# 5. 推送 main
git push origin main

# 6. 切回开发分支继续
git checkout <当前开发分支>
```

#### 出口条件

| 条件 | 动作 |
|------|------|
| **main 已合并推送** | ✅ 进入 Step 6 闭环更新 |
| **合并冲突** | ❌ 阻塞，向用户报告冲突详情，人工解决后再继续 |

**注意**：合并到 main 前必须确保 Step 5 的自动化验收（tsc + test + build）全部通过。合并使用 `--no-ff` 以保留分支拓扑。

---

### Step 6：闭环更新

**必须在 TASK-CHAIN.md 中完成以下更新**：

| 更新项 | 说明 |
|--------|------|
| 新增条目 | 在对应章节添加任务的完整描述 |
| 当前指针 | 如有调整则更新 |
| 状态一览 | 添加到待执行/已完成分区 |
| 依赖图 | 如有新增依赖关系则更新 |
| 变更记录 | 在 §十一 追加版本号和摘要 |

**同时完成**：
- [ ] 变更溯源记录写入（R-018 四环）
- [ ] 备份分支清理（保留 tag，分支可删；发版后集中清理所有 backup/* tag）
- [ ] 报告归档到 `docs/reports/FB<编号>-报告.md`（确认输出路径与 FEEDBACK-REPORT-TEMPLATE.md 一致）

> **路径完整性提示**：R-030 引用的所有辅助文件（`SKILLS-QUICKREF.md`、`FEEDBACK-REPORT-TEMPLATE.md`、`CODE_REVIEW_CHECKLIST_V1.0.md`）均已创建。

## 快速决策树（执行时参考）

```
收到反馈？
  │
  ├── 是 A 类（崩溃/数据丢失）？
  │     └── ≤5行 且 不涉及 SQL/IPC/安全/状态管理/迁移？ → 直接修（R-018 豁免）
  │         └── 否则 → 进入主流程
  │
  ├── 是 D 类（超范围）？
  │     └── 引用边界声明 → 拦截 → 结束
  │
  ├── 是 C 类（纯讨论）？
  │     └── decision-log.md → 结束
  │
  └── 是 B 类（功能/体验/债务）？
        └── ★ 进入 10 步完整流程 ★
             │
             TASK-CHAIN 查重 → 已有？→ 展示选项给用户
                              → 无有？→ 继续向下
             │
             溯源报告 + ★ Skill 库遍历选型
             │
             原子化拆分 → 三大原则检验 → 冲突检测
             │
             用户确认 7 项？→ 否 → 退出/调整
                          → 是 → ↓
             │
             ★ Git 备份分支 ★
             │
             执行（按 Skill 选型调用代理）
             │
             代码质量审查（P0=0）
             │
             验收（自动化 + 人工）
             │
             ★ 用户确认 → 合并到 main ★
             │
             更新 TASK-CHAIN → 清理备份
             │
             ✅ 闭环完成
```

## 优先级

高优先级 — 保障所有变更的可追溯性和可控性，是项目治理的基础设施。
