# R-012: 假设驱动开发

## 原则

任何可能显著影响系统行为的改动，必须先提出**可证伪**的假设，通过实验验证后采纳或回退。禁止"改了看看效果"的无目标改动。

## 假设模板

### 📋 模板说明
- **浅色字段**（改动描述/影响机制/预期效果/验证方式/回退条件/基线数据）：改动**前**填写
- **深色字段**（实验结果）：改动**后**填写

```
改动描述: （一句话说清改了什么）
影响机制: （为什么这个改动能产生效果）
预期效果: （量化指标：如 tsc 错误数从 X→Y、渲染时间从 Zms→Wms）
验证方式: （如何测量上述指标）
回退条件: （满足什么条件时自动回退）
基线数据: （改动前的当前值，必须有实测数据）
实验结果: （← **改后填写** 接受/拒绝 + 具体数据和原因）
```

## 决策矩阵

| 条件 | 决策 | 行动 |
|------|------|------|
| 目标达成 **且** 基线不降 | ✅ 接受 | 合并变更，记录假设验证结果 |
| 目标部分达成，有副作用 | ⚠️ 有条件接受 | 记录 trade-off，标记需后续优化 |
| 目标未达成 | ❌ 拒绝 | 回退变更，记录教训到 project_memory |
| 无法测量 / 无基线数据 | 🔴 阻止启动 | 必须先建立基线再开始 |

## 四层分类

| 层级 | 场景 | 要求 |
|------|------|------|
| **L1 算法/性能** | 排版引擎、诊断解析器、训练推荐算法 | 必须：基线 benchmark + 对比测试 + 性能 profile |
| **L2 功能行为** | UI 交互逻辑、Provider 联动、Repository 操作 | 必须：用户场景复现步骤 + before/after 截图/日志 |
| **L3 架构决策** | Provider 拆分、Widget 重组、模块边界调整 | 必须：影响范围分析 + 回退脚本就绪 |
| **L4 配置/样式** | CSS 变更、主题调整、布局微调 | 建议：视觉对比截图即可 |

## 检查清单

### 改动前（启动门禁）
```
□ 是否有明确、可量化的目标？（不是"提升体验"而是"首屏渲染从 2.1s→1.5s"）
□ 是否有可证伪的验证方案？（能明确判断成功/失败）
□ 是否设定了量化的回退条件？（不是"效果不好就回退"而是"错误率>5%则回退"）
□ 是否记录了基线数据？（当前 tsc 错误数、当前渲染时间、当前测试通过率）
□ 回退方案是否已准备？（git stash / revert 命令 / 数据库迁移回滚脚本）
```

### 改动后（验收门禁）
```
□ 是否按验证方案实际测量了结果？
□ 测量数据是否与基线进行了对比？
□ 实验结果是否记录到了变更文档或 commit message？
□ 如果拒绝假设，是否回退了代码变更？
□ 教训是否写入了 project_memory.md 的 Lessons Learned？
```

## 与其他规则的协作

| 规则 | 协作方式 |
|------|----------|
| R-006 回退机制 | 假设被拒绝时，R-012 触发 R-006 执行回退 |
| R-010 最小化范围 | 每个假设对应一个原子化改动，便于独立验证 |
| R-018 变更溯源 | 假设模板作为变更溯源的证据链第一环 |
| R-004 准出标准 DoD | DoD 中应包含假设验证的通过标准 |

## 示例

### 正面示例：DB-REFACTOR-P0 诊断表加 UNIQUE 约束
```
改动描述: diagnosis_results 表增加 (session_id, message_id) UNIQUE 约束
影响机制: 唯一约束防止 saveAnalysis 批量覆盖 bug
预期效果: 同一 session+message 组合只能有一条诊断记录
验证方式: 插入重复数据 → 断言抛出 IntegrityError
回退条件: 迁移失败或现有数据存在重复 → 先清理再迁移
基线数据: 当前 diagnosis_results 共 N 条，无重复 (session_id, message_id)
实验结果: ✅ 接受 — 迁移成功，插入重复数据正确报错
```

### 反面示例：随意修改拖拽手柄样式
```
改动描述: 把 ResizeHandle 改成更好看的颜色
影响机制: （无）
预期效果: （无量化指标，仅主观感受"好看"）
验证方式: （无）
回退条件: （无）
→ ❌ 违反 R-012 — 无假设、无基线、无可证伪验证方案
```

## 优先级
高优先级 — 保障改动的有效性和可追溯性
