# R-022: 过程可见

## 原则

**隐式思考是错误的温床。** 当操作复杂到无法一眼看全时，必须先把思路说出来。
说清楚的过程本身就是一次自我审查——很多问题在"说"的时候就暴露了。

## 三要素模板（简化版）

从原始四要素（意图/依赖/方法/预期产出）压缩为三条最关键的：

### 1. 做什么（Intent）

一句话说清目标和不动什么：

```
目标：[解决什么问题]
范围：[改哪些文件] | 不动：[明确列出不改的]
```

示例：
> 目标：修复会话切换后消息不同步问题
> 范围：lib/widgets/chat_page.dart（加初始化逻辑）、lib/providers/session_providers.dart（加 loadMessages）
> 不动：chat.handler.ts、diagnosis 相关

### 2. 怎么做（Approach）

关键决策点，不是逐步操作清单：

```
方案：[选了哪种实现方式，为什么]
风险：[可能影响什么，怎么应对]
```

示例：
> 方案：用 useEffect 监听 currentSessionId 变化触发重新加载，而非在切换函数内手动调用（解耦）
> 风险：可能产生重复请求 → 用 messageId 去重

### 3. 怎么算完成（Verification）

具体的、可操作的验收标准：

```
验证：[执行哪些步骤确认正确]
```

示例：
> 验证：① 切换会话后历史消息正确加载 ② 切回原会话消息不变 ③ 控制台无重复请求

## 触发条件判断

| 操作类型 | 是否需要过程声明 | 说明 |
|---------|:-------------:|------|
| 单文件修 bug | 否 | 简单改动直接做 |
| 单文件新增功能 | 建议 | 如果逻辑复杂建议声明 |
| 2-3 文件联动修改 | **是** | 涉及多文件协调 |
| 3+ 文件或架构变更 | **必须** | 必须写三要素 |
| 数据库 schema 变更 | **必须** | 不可逆操作 |
| Skill 注入内容变更 | **必须** | 会改变 AI 实际行为 |
| drift 表结构 / 迁移变更 | **必须** | 不可逆操作 |

## 与 R-021 的区别

| 维度 | R-021 AI 行为边界 | R-022 过程可见 |
|------|------------------|---------------|
| 关注点 | AI 的行为约束 | 操作前的沟通义务 |
| 适用对象 | 每次 AI 代码操作 | 复杂/多文件操作 |
| 核心动作 | 5 条禁止/要求 | 3 要素声明模板 |
| 典型场景 | "不要顺手格式化其他文件" | "这个重构我打算这样做" |

简单理解：**R-021 是交通规则（不能做什么），R-022 是行车路线（打算怎么走）。**

## 检查清单

```
复杂操作开始前：
□ 是否写了三要素（目标/方案/验证）？
□ "不动"的列表是否明确？
□ 验证方式是否具体可执行？
```

## 与其他规则的协作

| 规则 | 关系 | 协作方式 |
|------|------|----------|
| R-018 变更溯源规范 | 互补 | R-022 的过程声明是 R-018 溯源链中变更过程的显式记录 |
| R-023 Bug调试记录 | 互补 | Bug 排查过程中的复杂操作需要 R-022 的三要素声明，排查结果通过 R-023 记录 |

## 优先级
中优先级 — 提升复杂操作的透明度和可追溯性
