# R-006: 回退机制规范

## 原则
回退不是"恢复 git"，而是"有记录地恢复到改动前的可用状态"。

## 快照备份分级标准

### L0 — 最小备份（所有改动必须执行）

适用于：单文件 bug 修复、小功能新增、样式调整

```bash
git stash
# 或
git commit -m "WIP: 改动前快照 YYYY-MM-DD HH:mm"
```

**恢复命令**：`git stash pop` 或 `git reset --soft HEAD~1`

### L1 — 完整备份（重构/多文件联动时必须）

适用于：涉及 3+ 文件的改动、架构调整、数据库 schema 变更、IPC 通道变更

```bash
# 1. 创建备份分支
git checkout -b backup/YYYYMMDD-HHmm-任务简述

# 2. 确认备份点可编译/可运行
npm run build   # 或 npm run typecheck

# 3. 切回工作分支继续改动
git checkout 原分支名
```

**恢复命令**：`git checkout backup/YYYYMMDD-HHmm-任务简述`

**L1 备份额外记录**（写入改动说明或 task doc）：
1. 备份时间戳
2. 涉及文件完整列表
3. 当前基线状态（build 通过 / 测试通过情况）
4. 预期改动范围

### L2 — 分布式备份（高风险操作）

适用于：数据库迁移、Prompt 大版本变更、依赖大版本升级

在 L1 基础上增加：
- **数据库**：`.dump` 备份文件 + 迁移前 schema 截图
- **Prompt**：当前版本 copy 为 `prompt-vX.Y.Z-backup.md`
- **依赖**：`package-lock.json` git 追踪 + 当前 `node_modules` 可用性确认

## 回退触发条件

| 等级 | 触发条件 | 响应时间 | 操作 |
|:----:|---------|:--------:|------|
| P0 | 核心功能不可用（诊断/聊天/IPC 通信失败） | 15 分钟内 | 恢复备份 → 分析根因 |
| P0 | 模块导入失败 | 立即 | git checkout -- 恢复文件 |
| P1 | 功能降级 20% 以上 | 1 小时内 | 评估是否回退或继续修复 |

## 回退后操作
1. 确认回退后系统可用（运行 `npm run test`）
2. 记录回退原因到任务文档
3. 分析根因，制定新方案

## 检查清单
```
改动前检查：
□ 是否已备份当前状态？（git stash/commit）
□ 是否有明确的回退路径？
□ 回退触发条件是否量化？
□ IPC 通道变更是否记录原定义？（如涉及）
```

## 与其他规则的协作

| 规则 | 关系 | 协作方式 |
|------|------|----------|
| R-018 变更溯源规范 | 依赖 | R-018 要求每次变更必须有回退方案，R-006 是 R-018 溯源链的必要环节 |
| R-023 Bug调试记录 | 互补 | Bug 修复可能涉及回退操作，R-023 的调试记录应包含回退决策信息 |

## 优先级
最高优先级 - 保障生产环境稳定性
