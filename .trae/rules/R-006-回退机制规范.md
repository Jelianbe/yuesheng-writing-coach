# R-006: 回退机制规范

## 原则
回退不是"恢复 git"，而是"有记录地恢复到改动前的可用状态"。

## 快照备份标准

### 标准备份（所有改动必须执行）
```bash
git stash  # 或 git commit -m "WIP: 改动前快照 YYYY-MM-DD HH:mm"
```

### 架构级备份（重构/拆分/合并时必须）
在改动说明中记录：
1. 备份时间戳
2. 涉及文件列表
3. 当前基线测试结果
4. 回退命令

## 回退触发条件

| 等级 | 触发条件 | 响应时间 | 操作 |
|:----:|---------|:--------:|------|
| P0 | 核心功能不可用（诊断/聊天/IPC 通信失败） | 15 分钟内 | 恢复备份 → 分析根因 |
| P0 | 模块导入失败 | 立即 | git checkout -- 恢复文件 |
| P1 | 功能降级 20% 以上 | 1 小时内 | 评估是否回退或继续修复 |

## 回退后操作
1. 确认回退后系统可用（运行 `npm run test`）
2. 记录回退原因到任务文档
3. 分析根因，制定新方案

## 检查清单
```
改动前检查：
□ 是否已备份当前状态？（git stash/commit）
□ 是否有明确的回退路径？
□ 回退触发条件是否量化？
□ IPC 通道变更是否记录原定义？（如涉及）
```

## 优先级
最高优先级 - 保障生产环境稳定性
