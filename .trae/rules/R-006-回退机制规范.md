# R-006: 回退机制规范（Flutter）

## 原则

回退不是"恢复 git"，而是"有记录地恢复到改动前的可用状态"。

## 快照备份分级标准

### L0 — 最小备份（所有改动必须执行）

适用于：单文件 bug 修复、小功能新增、样式调整

```bash
git stash
# 或
git commit -m "WIP: 改动前快照 YYYY-MM-DD HH:mm"
```

**恢复命令**：`git stash pop` 或 `git reset --soft HEAD~1`

### L1 — 完整备份（重构 / 多文件联动时必须）

适用于：涉及 3+ 文件的改动、架构调整、数据库 schema 变更、
Skill 注入内容变更

```bash
# 1 创建备份分支
git checkout -b backup/YYYYMMDD-HHmm-任务简述

# 2 确认备份点基线可用
flutter analyze lib --no-pub
flutter test --exclude-tags live,external --no-pub

# 3 切回工作分支继续改动
git checkout 原分支名
```

**恢复命令**：`git checkout backup/YYYYMMDD-HHmm-任务简述`

**L1 备份额外记录**（写入改动说明或 task doc）：
1. 备份时间戳
2. 涉及文件完整列表
3. 当前基线状态（analyze / test 通过情况）
4. 预期改动范围

### L2 — 分布式备份（高风险操作）

适用于：数据库迁移、Skill / Prompt 大版本变更、依赖大版本升级

在 L1 基础上增加：

- **数据库**：备份 drift 数据库文件 + 迁移前 schema 说明
- **Skill / Prompt**：内容以 Dart 常量形式受 git 追踪
  （`skill_registry.dart` 与各 `skills_*.dart`），用 **git tag 或备份分支**
  固化版本即可
- **依赖**：`pubspec.lock` 受 git 追踪，确认当前依赖树可用

> ⚠️ Skill 内容变更会改变注入 prompt，属高风险（R-027 门禁 4 需人工签字）。
> 若存在行为锚点快照，**改动前先冻结**，改动后比对漂移并人工复查差异，
> 不得直接更新快照了事。

## 回退触发条件

| 等级 | 触发条件 | 响应时间 | 操作 |
|:----:|:--------:|:--------:|:--|
| P0 | 核心功能不可用（诊断 / 聊天 / Skill 注入失败） | 15 分钟内 | 恢复备份 → 分析根因 |
| P0 | 模块导入失败 | 立即 | `git checkout --` 恢复文件 |
| P1 | 功能降级 20% 以上 | 1 小时内 | 评估是否回退或继续修复 |

## 回退后操作

1. 确认回退后系统可用：
   `flutter analyze lib --no-pub` +
   `flutter test --exclude-tags live,external --no-pub`
2. 记录回退原因到任务文档
3. 分析根因，制定新方案

## 检查清单

```
改动前检查：
□ 是否已备份当前状态？（git stash / 备份分支）
□ 是否有明确的回退路径与恢复命令？
□ 回退触发条件是否量化？
□ 基线的 analyze / test 是否已确认通过？
□ 若涉及 Skill 注入：行为锚点快照是否已冻结？
□ 若涉及 DB schema：数据库文件是否已备份？
```

## 与其他规则的协作

| 规则 | 关系 | 协作方式 |
|:--|:--|:--|
| R-018 变更溯源规范 | 依赖 | R-018 要求每次变更必须有回退方案，R-006 是溯源链的必要环节 |
| R-023 Bug调试记录 | 互补 | Bug 修复可能涉及回退，调试记录应包含回退决策信息 |
| R-027 质量门禁 | 验证 | 回退后须重新跑四道门禁确认可用 |

## 优先级

最高优先级 — 保障生产环境稳定性
