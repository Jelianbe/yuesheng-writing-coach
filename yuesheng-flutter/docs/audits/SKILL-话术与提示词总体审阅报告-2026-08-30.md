## B. P0/P1 改写建议（具体替代文本）

> 以下为每个 P0/P1 的具体改写建议，不是方向性描述。改写时应保持原 Skill 的教学意图，只改变约束强度和表达方式。

### B.1 P0-1 / P0-2 / P0-3：训练前桥接固定模板（三处重复）

**问题**：同一模板"我注意到你在[X]方面有一个[Y]模式。我觉得可以试试…原因是…"在三处重复，且"必须输出"+"我注意到…有一个问题模式"是断言式替学员下结论。

**统一改写建议**（只保留一处，建议放在 feedback-cognition，其余两处删除或改为引用）：

```
### 训练前的认知桥接

当学员从诊断进入训练、且学员表现出需要理解"为什么练这个"时，
用自然语言解释训练方向。原则：

- 从学员自己说过的话或写过的文本出发，不凭空总结"问题模式"
- 用试探性语气："你刚才提到 X / 你这段里 Y，我读到的感觉是 Z——要不要试试一个练习？"
- 原因必须引用学员原文中的具体内容，不用通用写作常识
- 如果学员已经明确知道为什么练，跳过桥接直接进入训练
- 不说"我注意到你有一个…问题"——改为"你这段里有一个地方，我想跟你讨论一下"
```

## D. 存疑项（发现但没把握）

### D.1 writer-psychology 的心理障碍识别是否属于产品定位

**存疑原因**：writer-psychology 要求 AI 识别学员的六大心理障碍（完美主义瘫痪、冒名顶替综合征等）并给出"教练应对"。这在任务书的判断标准中属于"诱导推测学员的心理状态"（P0）。但该 Skill 的定位明确写着"教练不是心理咨询师——我们的边界是写作教练。但写作心理是写作能力的天然组成部分"（skills_beginner_p1.dart:15-17）。

**不确定的点**：产品是否有意让 AI 做写作心理层面的支持？如果是，那么"信号识别"和"常见原因"是合理的教学工具，只是表达方式需要从"诊断"改为"关注"。如果产品定位不允许 AI 触及心理层面，则整个 Skill 都需要重新设计。

**建议**：需产品负责人确认 writer-psychology 的定位边界。本报告将其标为 P0（P0-4/P0-5），但改写建议保留了心理支持的功能，只改变了表达方式。

### D.2 coaching-rhythm §5.3 "训练完成后的桥接"是否有意保留

**存疑原因**：第 182-184 行的注释明确说："§5.3 为保持格式完整，亦列出「训练完成后的桥接」示例句式。该示例**仅作文风示范**，训练完成后的实际反馈**以 feedback-cognition 为准**——本处不重复触发，避免两段认知反馈叠加给用户。"

**不确定的点**：既然"仅作文风示范"且"不重复触发"，为什么还要保留在 §5.3 的"输出格式"中？AI 读到"格式："和"示例（完整）"时，很可能认为这是需要执行的格式，而非"仅示范"。注释的澄清是否足够防止 AI 误触发？

**建议**：如果确实不触发，建议将"训练完成后的桥接"和"多轮进度桥接"从 §5.3 移出，或明确标注"以下为参考示例，不在此触发"。

### D.3 "29 个 Skill"与实际 37 个的差异

**存疑原因**：任务书称 29 个，实际 37 个。差异主要在 core 组（3→8）。可能任务书的"core 3"只算 core-iron-triangle、core-product-identity、writing-anchors，而把 teaching-strategy、phase-mapper、scenario-rules、validation-rules、reply-voice 归为其他类别？但代码中这些的 meta.group 都是 'core'。

**建议**：需确认任务书的 29 个计数来源。本报告以实际代码为准。

### D.4 attitude 档位的"反馈结构"是否是硬约束

**存疑原因**：三个档位都写了"反馈结构：肯定→方向→行动"等，但没有写"必须"。doubao 档位写的是"反馈结构："（没有"必须"），yuesheng 同理，sensei 写了"三要素缺一不可"。这些是"偏好"还是"硬约束"？从上下文看，attitude skill 的目的是定义档位差异，结构约束可能是有意的硬约束。

**建议**：如果档位差异需要通过结构来保证，保留结构约束是合理的。但"缺一不可"可能过于刚性。本报告标为 P1，建议改为"倾向"。

### D.5 gap-detector 的推断模式是否有实际价值

**存疑原因**：推断模式要求 AI 从"体裁惯性、首因效应、笔墨密度、内在裂纹"推断学员意图。其中"内在裂纹"（同一角色前后行为矛盾）是有文本证据的，可以推断。但"体裁惯性"和"首因效应"是通用写作常识，不是学员意图的可靠线索。

**不确定的点**：推断模式在实际运行中是否经常被触发？如果大部分时候 confidence=low 不输出，那这个模式的价值有限。如果经常输出，则幻觉风险高。

**建议**：建议限制推断模式只使用"内在裂纹"（有文本证据的）和"笔墨密度"（可量化的），去掉"体裁惯性"和"首因效应"。

### D.6 知识库 manual 内容是否在审阅范围内

**存疑原因**：任务书说"知识库：syndrome_kb_content*（症候）、technique_kb_content*（技法）、training_kb_content*（训练）"，并要求"整理 Skill 与知识库的依赖关系"。但任务书的核心问题（去模板化、提升灵活性、防止幻觉）主要针对 Skill content 的话术部分。知识库的症候定义、技法示范等是教学知识，不是直接面向学员的话术。

**本报告的处理**：审阅了知识库的 L2 索引部分（kSyndromeIndexContent、kTechniqueIndexContent），未深入审阅 L3 manual 的完整内容（manual_1~6 共约 11 万字节）。L3 内容主要是症候定义和技法教程，幻觉风险较低（都是标准化知识），但可能也存在固定模板。

**建议**：如需对 L3 知识库内容做同样深度的审阅，需单独安排任务。

## G. 推荐扩展（系统性完善建议）

> 本节基于审阅过程中发现的**系统性问题**提出，不是对单个 Skill 的修补，
> 而是从工程化、数据闭环、治理流程三个层面完善整套 Prompt 体系。
> 每条建议标注优先级和实施难度，供排期参考。

### G.1 短期可做（1-2 周，低风险，高收益）

#### G.1.1 话术反模式自动化检测（Prompt Lint）

**问题**：本次审阅发现三处逐字重复的"我注意到你在[X]…有一个[Y]模式"模板（P0-1/P0-2/P0-3），以及两处重复的诊断确认话术（P1-3/P1-5）。这些问题靠人工审查才发现，说明没有自动化防线。新写的 Skill 很容易重蹈覆辙。

**建议**：写一个 Dart 脚本（放在 `scripts/` 下），扫描所有 `skills_*.dart` 的 content 字符串，检测以下反模式：

| 检测模式 | 正则/关键词 | 对应问题类型 |
|:---------|:------------|:------------|
| 强制触发 | `必须输出`、`每轮都要`、`每次必须` | 强制触发 |
| 固定格式 | `格式：`、`开头用`、`按照以下格式` | 固定模板 |
| 断言式替学员下结论 | `我注意到你`、`你有一个…问题`、`你的问题是` | 替学员下结论 |
| 报告腔 | `置信度`、`已确认事实`、`推测`、`验证方法` | 报告腔 |
| 跨文件重复 | 同一 ≥20 字的字符串在多个文件中出现 | 内容重复 |

脚本输出命中位置（文件:行号），CI 中可作为门禁。允许白名单（如 validation-rules 中的安全规则是合理的"必须"）。

**预期收益**：防止新写的 Skill 引入固定模板；三处重复的模板如果当时有这个脚本，会在 PR 阶段被拦截。

**实施难度**：低。纯文本扫描，约 100 行 Dart 代码。

---

#### G.1.2 共享话术原则的单一真源（去重复）

**问题**：诊断确认机制在 `teaching-strategy §3.8`（skills_l1_core_p1.dart:243-251）和 `diagnosis-confirmation §2.1`（skills_diagnosis_p1.dart:213-216）两处重复；训练前桥接模板在三处重复。重复意味着改一处忘一处，最终产生矛盾指令。

**建议**：在 `skill_registry.dart` 中定义共享原则常量，各 Skill 通过字符串拼接引用，而不是各自复制：

```dart
const String _sharedDiagnosisConfirmationPrinciple = '''
### 诊断确认原则
诊断后应用自然语言邀请学员回应，确认是否认同。
不使用固定话术，核心是让学员有机会否认或修正。
''';

// 在 teaching-strategy 的 content 中：
content: _teachingStrategyBody1 + _sharedDiagnosisConfirmationPrinciple + _teachingStrategyBody2,
```

`diagnosis-confirmation` 保留完整的状态机和详细指引，`teaching-strategy` 只引用原则常量。

**预期收益**：改一处全局生效；消除"两处说的不一样"的风险；减少 token 重复注入。

**实施难度**：低。重构字符串拼接，不改变注入内容。

#### G.1.3 Skill 元数据增加"话术自由度"标签

**问题**：目前 `SkillMeta`（skill_registry.dart:24-36）有 id/name/group/description/loadWhen/volume，但没有标注每个 Skill 的话术风格。审阅时需要逐个读 content 才能判断哪些是硬约束、哪些是参考示例。

**建议**：`SkillMeta` 增加 `promptStyle` 字段，三档：

| 档位 | 含义 | 典型 Skill |
|:-----|:-----|:-----------|
| `strict` | 含硬约束，AI 必须遵守 | validation-rules（安全规则）、scenario-rules（平台立场） |
| `guided` | 有示例但标注为参考，AI 可灵活组织 | narrative-design（提问库）、coaching-rhythm（五步节奏） |
| `free` | 纯原则描述，AI 完全自主 | coaching-actions-v2（明确"不是话术库"）、teaching-modes |

dispatcher 注入时可根据 `promptStyle` 调整：`strict` 全量注入，`guided` 注入时加前缀"以下为参考示例"，`free` 正常注入。

**预期收益**：治理时一目了然；新写 Skill 时作者必须思考"我这个是硬约束还是参考"；为后续 A/B 测试打基础。

**实施难度**：低。加字段 + 逐个标注（37 个 Skill，每个 1 分钟）。

### G.2 中期建设（1-2 月，中等风险）

#### G.2.1 学员话术反馈闭环

**问题**：目前没有机制知道 AI 说的话学员是否买账。`diagnosis-confirmation` 收集了学员的 confirmed/rejected/modified 回应，但这些数据只用于当前对话的状态流转，没有结构化存储和事后分析。话术迭代全凭"感觉这个说法不好"。

**建议**：

1. **结构化存储诊断确认结果**：在诊断确认后，将学员回应类型（confirmed / rejected / modified）连同触发该回应的 Skill id 和话术摘要存入 DB。
2. **轻量训练反馈**：在每个训练练习结束后，加一个 1-tap 反馈："刚才这个引导方式对你有帮助吗？"（👍 / 👎）。不强制，不打断流程。
3. **定期分析脚本**：每周/每月生成报告：
   - 哪些 Skill 的话术导致高否认率（rejected 比例 > 30%）
   - 哪些话术模式与训练完成率正相关/负相关
   - 按 attitude 档位拆分（豆包/月笙/sensei 哪个档位的反馈更好）

**预期收益**：话术迭代从"凭感觉"变成"数据驱动"；直接服务于"去模板化"目标——如果某个固定模板的否认率高，数据会说话。这是整套系统从"写死话术"走向"持续优化"的关键一步。

**实施难度**：中。需要 DB schema 变更（加反馈表）、UI 入口（1-tap 按钮）、分析脚本。但不改变核心教学逻辑。

#### G.2.2 按情境动态裁剪 Skill（推广 advanced-phases 的做法）

**问题**：目前大部分 Skill 是全量注入。`advanced-phases` 已经做了按 phase 裁剪（skills_advanced_outline_p7.dart 的 `advancedPhasesContentFor`，P3 只注入 P3 段，P4 只注入 P4 段），但只有这一个 Skill 做了。其他高体积 Skill（writer-psychology 约 4000 tokens、coaching-rhythm 约 3500 tokens）在不相关的情境下也全量注入，浪费 token 且可能给 AI 过多约束。

**建议**：推广到以下高体积 Skill：

| Skill | 裁剪维度 | 裁剪逻辑 |
|:------|:---------|:---------|
| writer-psychology | 学员是否表现出心理压力信号 | 无信号时只注入"信号识别清单"（约 500 tokens），不注入六大障碍详情（约 3500 tokens） |
| coaching-rhythm | 当前是否在训练循环中 | 非训练时不注入 §5（训练桥接格式，约 800 tokens） |
| outline-diagnosis | 用户是否发送了大纲 | 无大纲时只注入"激活条件"，不注入五步诊断法详情 |
| diagnosis 组（gap-detector 等） | 是否有学员文本 | 纯聊天时不注入诊断输出格式 |

实现方式与 `advancedPhasesContentFor` 一致：定义 `contentForContext(DiagnosticContext ctx)` 方法，dispatcher 调用时传入 ctx。

**预期收益**：减少 token 消耗（估算可降 20-30%）；减少 AI 被无关约束干扰（间接提升灵活性）；与 R-026 的"最小必要注入"原则一致。

**实施难度**：中。需要 dispatcher 支持 `contentFor` 钩子 + 每个 Skill 写裁剪逻辑。但 advanced-phases 已经验证了模式，可复用。

#### G.2.3 自然语言部分的证据强制校验

**问题**：`[YS_DIAGNOSIS]` JSON 已经要求 `evidence` 字段（原文片段 5-20 字，syndrome_kb_content.dart:66,90），但**面向学员的自然语言部分**没有强制引用原文。AI 可能在 JSON 里填了 evidence，但自然语言里说的是通用常识（"开头不够抓人""节奏有点平"）。这正是任务书列出的"常识替代证据"问题。

**建议**：在 `validation-rules` 或 `chat_context_builder` 的 system prompt 中增加一条硬规则：

> 面向学员的诊断性陈述必须紧跟原文引用。格式参考："你这段里写了「原文片段」，我读到的感觉是…"。不允许只说"开头不够抓人"而不引用具体哪一句。

同时可考虑在输出后处理层做轻量校验：如果自然语言部分包含症候关键词（如"情绪标签""视角漂移"）但没有引号包裹的原文片段，触发警告或二次生成。

**预期收益**：从系统层防止"常识替代证据"；比 Skill 内文字要求更可靠（Skill 内的要求 AI 可能忽略，系统层规则优先级更高）。

**实施难度**：中。system prompt 规则是低难度部分；输出后处理校验需要定义检测规则和二次生成逻辑，中等难度。可分两期做，先加 prompt 规则。

### G.3 长期规划（3-6 月，高价值）

#### G.3.1 话术 A/B 测试框架

**问题**：目前话术改了就全量上线，无法知道新版是否比旧版好。"去模板化"的效果无法量化——你把固定模板改成自由表达后，学员的否认率是升了还是降了？训练完成率呢？不知道。

**建议**：建立 Skill content 的版本化 + A/B 分流：

1. **版本存储**：每个 Skill 支持多个 content 版本（v1, v2, v3…），DB 或文件中存储。
2. **分流逻辑**：按学员 ID 哈希分流（保证同一学员始终看到同一版本，避免体验跳变）。分流比例可配置（如 10% 流量试新版）。
3. **核心指标**：
   - 学员否认率（diagnosis-confirmation 的 rejected 比例）
   - 训练完成率（练习开始 → 完成的比例）
   - 症候达标率（训练通过率）
   - 学员主动反馈（G.2.1 的 👍/👎）
4. **决策规则**：新版运行 ≥2 周、样本量 ≥100 后，如果否认率下降 ≥10% 且训练完成率不下降，则全量推广；否则回滚。

**预期收益**：话术优化有科学依据；"去模板化"从"相信这样更好"变成"数据证明这样更好"。这是整套系统从"手工调 prompt"走向"工程化优化"的标志。

**实施难度**：高。需要版本存储、分流逻辑、指标采集、看板。但 G.2.1 的反馈闭环是前置依赖，建议先做 G.2.1 再做这个。

---

#### G.3.2 AI 输出前自检钩子（系统层防幻觉兜底）

**问题**：目前防幻觉全靠 prompt 内的规则，AI 可能不遵守。即使 validation-rules 写了"不替学员下结论"，AI 仍可能输出"你有完美主义倾向"。没有系统层兜底。

**建议**：在 LLM 输出后、展示给学员前，加一个轻量自检层（不需要第二次 LLM 调用，用规则匹配即可）：

| 检测项 | 规则 | 命中后动作 |
|:-------|:-----|:-----------|
| 心理断言 | 匹配"你有…倾向""你是…型""你的问题在于" | 追加"这是我的猜测，你觉得呢？"或触发二次生成 |
| 无证据诊断 | 包含症候关键词但无引号原文 | 触发二次生成，要求补充原文引用 |
| 禁用模板 | 匹配"我注意到你在…方面有一个…模式" | 触发二次生成，要求换一种说法 |
| 越权决定 | 匹配"我们接下来练…""你应该先…" | 追加"你觉得呢？"转为协商语气 |

自检层是异步的、可降级的——如果检测超时或出错，直接放行原始输出，不影响主流程。

**预期收益**：系统层兜底，不依赖 AI 自觉；即使 prompt 有漏洞，输出层也能拦住最危险的幻觉。这是"防止幻觉"的最后一道防线。

**实施难度**：高。需要定义精确的检测规则（误报率要低）、二次生成逻辑、性能保障。建议从最高风险的"心理断言"单项开始，验证有效后再扩展。

---

#### G.3.3 L3 知识库内容的话术治理

**问题**：本次审阅覆盖了全部 37 个 Skill 的 content 和 L2 索引，但**未深入 L3 manual**（syndrome manual_1~6、technique lib_1~3、training 1~4，约 15 万字节）。L3 内容在训练时直接注入 system prompt，对 AI 行为影响很大。其中症候定义中的"学员会…"、技法示范中的"正确/错误"、训练模板中的话术，可能也存在固定模板和替学员归因的问题。

**建议**：对 L3 知识库做同样深度的审阅，重点关注：

1. **症候定义**："学员通常会…""根源在于…"是否是替学员归因？应改为"常见表现包括…"
2. **技法示范**："错误示范"是否过于绝对？有些"错误"写法在特定语境下是合理的
3. **训练模板**：模板中的教练话术是否固定？应标注为示例
4. **严重度判断**：L1/L2/L3 的判断标准是否依赖通用常识而非学员原文？

审阅方法与本次相同：逐文件阅读、标注文件:行号、按 P0/P1/P2 分类。

**预期收益**：全链路一致性。Skill 层去模板化了，但 L3 注入的内容还有模板，等于白做。L3 治理是"去模板化"的最后一块拼图。

**实施难度**：中。体量大（约 15 万字节）但方法成熟（本次已验证）。建议分症候库、技法库、训练库三批进行。

### G.4 治理流程建议

#### G.4.1 Prompt 变更自检 Checklist（更新 R-026）

**问题**：R-025（Prompt 治理）和 R-026（Prompt 工程规范）有流程要求，但没有针对"话术变更"的具体自检清单。本次发现的问题，如果在 PR 时有人按清单检查，大部分能拦住。

**建议**：在 R-026 中增加"话术变更自检清单"，所有修改 Skill content 的 PR 必须逐项确认：

```
话术变更自检清单（修改 skills_*.dart 的 content 时必填）：

[ ] 1. 是否引入了新的固定句式？（"格式：""必须输出""开头用"等）
      如果是，是否标注了"以下为示例，AI 应灵活组织语言"？
[ ] 2. 是否有"每轮都要""每次必须"等强制触发？
      如果是，是否考虑了"学员不需要时可以跳过"的例外？
[ ] 3. 是否要求 AI 推断学员的心理状态/写作意图/动机？
      如果是，是否有确认机制（"是这样吗？"）和低置信度不输出的保护？
[ ] 4. 诊断性判断是否要求引用学员原文？
      是否避免了"开头不够抓人""节奏有点平"等无证据的通用判断？
[ ] 5. 是否与已有 Skill 内容重复？
      （用 G.1.1 的 lint 脚本检查跨文件重复）
[ ] 6. 是否使用了"置信度""已确认事实""推测"等报告腔词汇？
[ ] 7. 是否替学员做了决定（"我们接下来练 X""你应该先做 Y"）？
      如果是，是否改为协商语气（"要不要试试 X？"）？
```

**预期收益**：从流程上防止问题复发；新人写 Skill 时有明确的检查标准；PR review 时有据可依。

**实施难度**：低。纯文档更新，在 R-026 中追加一节即可。
