## 5. K-7~K-9 重新切分方案

### K-7：注入编排器（MessageInjector）★ 推荐先做

**目标**：迁聚类 A 的 5 个 _method（731 行）

**新建独立类**：`lib/services/message_injector.dart`
- 独立类 + DI（X-025-ARCH 教训复盘，禁 extension）
- 字段依赖：sessionRepo / studentModelRepo / chapterRepo / characterFactRepo / eventFactRepo / subplotFactRepo / referenceRepo / outlineRepo / capabilityDriftDetector
- 5 个公开方法：
  - `Future<void> injectProfileAndIntents(...)`
  - `Future<({ReferenceItem?, String?})> injectReferences(...)` — 内含 preloadReferenceDetails
  - `Future<void> injectOutlineFactsAndFiles(...)`
  - `Future<void> injectChapterObservations(...)`
  - `Future<String?> injectDiagnosisLock(...)`

**chat_service 改造**：
- 删除 `_injectProfileAndIntents` / `_injectReferences` / `_injectOutlineFactsAndFiles` / `_injectChapterObservations` / `_injectDiagnosisLock`（共 731 行）
- `_sendMessageCore` 改为通过 `_messageInjector.method(...)` 委派
- 装配 `messageInjectorProvider` 在 `session_providers.dart`

**风险点**：
1. markStage 闭包签名 `void Function(String) markStage` — 通过参数传入独立类
2. focus-related 3 个 helper（_buildFocusHistory / _parseUserFocusFromMessage / _buildInterventionAdjustmentNote）只在 _injectDiagnosisLock 内使用 → 跟随迁入 MessageInjector
3. K-2~K-4 阶段诊断注入已迁 DiagnosisCommitter；不要回流

### K-8：引用预载（ReferencePreloader）

**目标**：迁聚类 C 中的 _preloadReferenceDetails（85 行）+ 引用解析逻辑

**两个选项**：
- **选项 A（推荐）**：合并到 K-7 的 MessageInjector，因为 `_preloadReferenceDetails` 只被 `_injectReferences` 调用，迁出后 MessageInjector 内部封装即可
- **选项 B**：独立类 ReferencePreloader，但 chat_service 仍需在 _injectReferences 委派

**决策**：选 A，K-8 不做独立批次

### K-9：诊断残余（DiagnosisCommitter 续迁）

**目标**：迁聚类 B 的 4 个 _method（656 行）

**两种切分**：

| 方案 | 描述 | 风险 |
|:--|:--|:--:|
| **B-1（推荐）**：全部迁入 DiagnosisCommitter | 4 个方法作为 DiagnosisCommitter 的公开 API，chat_service 保留薄壳 | 高：diagnoser.commitDiagnosisFromContent + chat_service.commitDiagnosisFromContent 共存易混 |
| **B-2**：拆 `DiagnosisFlowHandler` 独立类 | 4 个方法迁入新独立类，chat_service 仅保留最薄的 commitDiagnosisFromContent 入口 | 中：新增类数量，但职责更聚焦 |

**决策**：B-2，更彻底地独立

**新建独立类**（若选 B-2）：`lib/services/diagnosis_flow_handler.dart`
- 4 个公开方法：`commitDiagnosisFromContent` / `parseAndPersist` / `commitDiagnosisAndSuggestions` / `handleTrainingResult`
- 字段依赖：diagnosisCommitter / diagnosisService / llmClient / sessionRepo / stateRepo / studentModelRepo / teacherSuggestionRepo / referenceRepo
- chat_service 薄壳：
  ```dart
  Future<String> commitDiagnosisFromContent({...}) =>
      _diagnosisFlowHandler.commitDiagnosisFromContent(...);
  ```

**风险点**：
1. 公开 API 名 `commitDiagnosisFromContent` 在 chat_service + diagnosisFlowHandler 双重——文档要清晰标注
2. _parseAndPersist 内部调 LLM client（独立 stream 包装）—— 需要诊断流
3. _handleTrainingResult 涉及阶段总结卡插入——耦合 genui

## 8. _sendMessageCore 311 行残余处理

K-7 + K-9 后 _sendMessageCore 从 311 行缩至 ~100 行——但 R-019 上限 50 行，仍超限。

**两种处理**：

| 方案 | 描述 | 风险 |
|:--|:--|:--:|
| **C-1**：保留在 chat_service 内，登记 known debt | 主流程是 chat_service 的本质职责，拆出失去"主流程"语义 | 低 |
| **C-2**：拆 `SendMessageOrchestrator` 独立类 | 主流程编排也迁出，chat_service 仅保留 sendMessage 薄壳 | 中 |

**决策建议**：C-1（保留 + 登记 known debt）

理由：
- _sendMessageCore 是 chat_service 公开 API `sendMessage` 的实现体
- 拆出后 chat_service.sendMessage 仅一行委派，类本身几乎无意义
- 与"chat_service 是教学循环控制器"语义冲突
- 登记为 R-019 known debt（与文件行数债务一起），未来视情再议
