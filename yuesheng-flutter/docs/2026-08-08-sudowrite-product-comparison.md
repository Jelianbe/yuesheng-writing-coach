## 1. 研究背景与目的

- **对象**：Sudowrite（AI 小说写作工具，2022 年上线，定位"非评判性 AI 写作伙伴"）
- **动机**：为月笙写作教练的产品方向做行业参照——哪些设计成立、哪些是历史包袱、哪些绝不能照搬
- **核心问题**：用户为什么付费？为什么弃坑？复杂设定系统（人设库/世界观/Timeline/Lorebook）为什么普遍失败？

## 2. Sudowrite 产品拆解

### 2.1 产品定位

| 维度 | 内容 |
|------|------|
| 解决的问题 | 写作"摩擦力"：卡壳/描写不生动/节奏失衡/不知道哪里要改——而非"帮你写" |
| 定位口号 | non-judgemental AI writing partner（非评判性写作伙伴） |
| 核心用户 | 类型小说作者（科幻/奇幻/言情/悬疑/恐怖）、有基础但效率低、愿意为"写作体验"付费 |
| 非目标用户 | 完全依赖 AI 代写者、纯文学作者、零基础新手 |

### 2.2 工作流程（场景化功能矩阵）

```
灵感 → Brainstorm（头脑风暴）
     → Story Bible（故事圣经：梗概/大纲/角色/世界观）
章节写作 → Write（续写）→ Describe（描写）→ Rewrite（改写）
修改 → Chat（剧情讨论）→ Developmental Edits（发展性编辑）
     → Line Edits（逐行建议）→ Beta Reads（试读反馈）
```

关键洞察：**从"写作痛点"出发拆功能，而非从"AI 能力"出发**。用户不需要想 prompt，每个功能对应一个明确场景。

### 2.3 数据结构

| 模块 | 内容 | 维护成本 |
|------|------|---------|
| Story Bible | 梗概/大纲/角色/世界观 | 中等 |
| Style Memory | 学习用户写作风格 | 零（自动） |
| Series Continuity | 系列作品跨书一致性 | 中等 |

核心原则：**最小必要原则**——不做精细 Lorebook/时间线，核心设定集中在 Story Bible。

### 2.4 AI 架构（多模型混合）

```
用户输入 → 专有叙事层（前处理）→ 模型路由
   ├─ Claude（通用推理）
   ├─ OpenAI（通用生成）
   ├─ Muse（小说专用）
   └─ Ballad（风格专用）
 → 专有叙事层（后处理）→ 用户输出
```

- 通用模型保底、专用模型垂直优化、专有叙事层做差异化
- 采用**结构化 Story Bible + 上下文窗口**而非纯向量 RAG——叙事需要全局一致性，RAG 适合问答不适合长文

### 2.5 商业模式

- 按量计费（积分制）：不同档位满足不同需求，未使用积分结转
- 研究异议：**积分制与"贵"的差评并存**——按量计费会惩罚长篇写作，是真实痛点而非"设计聪明"

## 3. 用户真实反馈（多源交叉验证）

### 3.1 高频好评

1. **"终于能写下去了"**——克服空白页恐惧/卡壳（付费核心动机）
2. **Describe 描写能力突出**——环境/氛围/动作描写一次到位（感知价值最高）
3. **"像有个写作搭子"**——可讨论剧情、提供陪伴与情绪价值

### 3.2 高频差评

1. **AI 味太重**——文字标准、工整、平庸，缺个性与灵魂
2. **长篇一致性差**——人物 OOC、伏笔丢失、世界观前后矛盾
3. **贵**——积分消耗快，长篇写作成本高，性价比感知弱

### 3.3 最核心的抱怨

> "改 AI 写的东西，比自己写还累。"

### 3.4 最核心的价值

> "降低了开始写的心理门槛。"——价值是**启动**，不是**代写**。

## 4. 失败案例与根因（为什么复杂设定系统普遍失败）

| 功能 | 用户说的需求 | 真实情况 | 失败根因 |
|------|------------|---------|---------|
| 人设库/人物系统 | 防止 OOC | 90% 用户不认真填，填了 AI 不一定用得对 | 人物是活的，会随剧情成长；设定库跟不上 |
| 世界观系统 | 保持设定一致 | 设定在写作中逐步完善，非一开始全想好 | 维护成本高、更新不及时、多数设定用不上 |
| Timeline | 防止时间线乱 | 90% 小说不需要，Excel 可替代 | 手动维护太累，属"专业工具"非大众需求 |
| Lorebook | 让 AI 更懂我的世界 | 用户懒得填、填了用不对 | 边际收益递减；基础设定有用，越细越没用 |
| Agent 自主写作 | "帮我写完" | 不可控、纠错成本高、方向跑偏 | 用户要的是助手不是代笔，失去掌控感 |

### 4.1 深层判断：是需求还是历史包袱？

**大部分是历史包袱**，来源：
1. 产品经理思维惯性（"专业写作工具就该有"）
2. 对标竞品焦虑
3. 高估用户自律性
4. 低估 AI 自动学习能力

**为什么作者宁可自己记设定？** 设定不只是信息，还是创作过程的一部分——整理设定的过程本身在梳理思路，不能被工具替代。

**本质分歧**：这些功能服务"规划型作者"（先想好再写），而 AI 写作工具主流用户是**发现型作者**（边写边想）。

## 5. 抽象规律

### 5.1 行业共识

1. **AI 是辅助，不是替代**——定位"代写"的产品失败
2. **场景化功能 > 通用聊天**——拆场景、免 prompt，使用率更高
3. **降低门槛 > 提升能力**——付费动机是"敢开始写"，情绪价值 > 功能价值

### 5.2 行业误区

1. 功能越多越好 → 学习成本高、80/20 定律
2. 设定越细越专业 → 维护成本高、ROI 低
3. Agent 越智能越好 → 用户要控制权，不要 autonomy

## 6. 与月笙的对照分析（批判性复核）

> 本节对研究报告的结论做了独立复核，不照单全收。

### 6.1 报告扎实、月笙应继续的方向

| 结论 | 对月笙的映射 |
|------|-------------|
| 核心价值是"启动"不是"代写" | 月笙定位是教练（诊断→训练→反馈），不碰续写/生成，方向正确 |
| 场景化功能 > 通用聊天 | 症候体系 = 场景化的进阶：Sudowrite 拆"动作场景"，我们拆"问题场景"（每症候配三段式教学法） |
| 给具体建议，不要抽象评价 | 「自查锚点」设计：不甩术语，给学员能自行对照的具体问题 |
| 降低心理门槛 | 即时反馈（达标率/阶段迁移）比功能堆叠更能建立学员信心 |

### 6.2 报告结论过绝对、需警惕之处

| 报告说法 | 异议 |
|---------|------|
| "人设库/世界观没用" | 真正问题不是"设定没用"而是"手动维护太重"。NovelAI Lorebook 高级用户使用率不低。对月笙：**画像/诊断历史不要做成要学员填写的表单** |
| "隐式记忆替代显式设定"很轻巧 | 难的不是提取而是"何时注入 + 错误记忆纠正"。对月笙：**教学焦点要能跟随证据变化，不被一次诊断焊死** |
| 积分制"设计聪明" | 与"贵"的差评自相矛盾。教学产品按量计费会惩罚练习，违背训练逻辑，**不学** |

### 6.3 月笙差异化机会（报告间接证实）

- **反 AI 味**：Sudowrite 头号差评是"AI 味重"。月笙已有的态度档位（豆包/月笙/sensei）+ 表达密度约束，正是对着这个痛点打，值得强化
- **教学产品 vs 工具产品的目标差异**：工具目标是效率，教学目标是能力。月笙必须如实告知 AI 局限、避免学员过度依赖，培养"会用 AI 的作者"而非"不会思考的打字员"

## 7. 对月笙的具体建议

> 落地状态：本节 3 小类共 9 条建议，2026-08-08 经代码真源对照**全部已落地**（证据见 §9）。

### 7.1 保留/强化

- 症候体系 + 三段式教学法（示范参考/常见错误/自查锚点）— ✅ 已落地
- 态度档位表达个性化（反 AI 味）— ✅ 已落地
- 即时反馈与阶段迁移可视化（让学员感知进步）— ✅ 已落地
- 训练闭环的"启动感"——先让学员敢写，再谈写得好 — ✅ 已落地

### 7.2 不做/删除

- 不做代写/续写/一键生成整本书 — ✅ 已守住（教练定位无生成功能）

### 7.3 设计红线

- 长期记忆走**证据驱动**：画像字段跟随证据变化，防"自动设定固化错误认知" — ✅ 已落地
- 教学焦点（current_teaching_focus_id）不被一次诊断焊死，需可迁移 — ✅ 已落地
- 工具只是手段，写作能力才是目的——不围绕单一工具教学 — ✅ 理念级，持续遵守
