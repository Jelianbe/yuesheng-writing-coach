# 症候增删操作手册（b9 注册表真源化 / b11 退役机制 / token 预算闸门）

> 依据设计稿：`docs/2026-08-11-b9-syndrome-registry-design.md`（批次 27-31 已落地）、`docs/2026-08-11-b11-syndrome-retirement-design.md`（批次 36-39 已落地）
> 适用范围：月笙教学体系症候（P 系）的新增、删除与退役
> 更新日期：2026-08-11

## 一、核心原则

**症候元数据唯一真源** = `lib/services/syndrome_registry.dart` 中的 `kSyndromeRegistry`。

- 所有 **表格行 / 计数 / ID 列表 / 测试断言** 均从注册表派生，增删症候**不需要**手动同步它们。
- 仍需人工编写的只有 **3 处核心内容**：
  1. 注册表一条 `SyndromeRecord`
  2. 症候库手册段 `### P0XX`（症候知识库）
  3. 训练库训练段 `## P0XX`（训练知识库）
- 另有 **4 个内容型保留点** 按需处理（见 §三 步骤 4）。
- **退役 ≠ 删除**（b11）：正式退役 = 注册表记录标记 `retired: true` + 退役原因，定义文本保留、表格/计数/检索全自动剔除，历史记录聚合经 `kSyndromeMergeMap` 归一；「删除」是完全移除（见 §四）。

## 三、新增一个症候（P0XX）

### 步骤 1：注册表追加记录

文件：`lib/services/syndrome_registry.dart` → `kSyndromeRegistry` 末尾。

追加一条 `SyndromeRecord`，字段清单：

| 字段 | 必填 | 说明 / 取值 |
|---|---|---|
| `id` | ✅ | `'P0XX'`，连续递增，**永不复用**（跳过退役 ID） |
| `name` | ✅ | 全名（手册标题/类型速查用），可含合并注释，如 `'信息倾泻症（含原 P001 世界观膨胀子类型）'` |
| `shortName` | ✅ | 精简名（training-templates-index / 技法 L3 表用） |
| `keyword` | ✅ | 索引表「问题类型关键词」列（独立字段，非名称） |
| `oneLine` | ✅ | 一句话（索引表「一句话描述」列） |
| `typeLine` | ✅ | 短句（类型速查「核心问题」列，与 oneLine 不同源） |
| `trainingLine` | ✅ | 核心本质一句话（training-templates-index，与上述均不同源） |
| `type` | ✅ | `SyndromeType`：`motivationDeficit` / `expressiveDeficit` / `structuralDisorder` / `commercialAppeal` |
| `level` | ✅ | `SkillLevel`：l1-l5 |
| `group` | ✅ | `MaxAttemptsGroup`：`expression`(≤3) / `structure`(≤5) / `deep`(≤5) |
| `position` | ✅ | `chapter` / `serial` / `global` / `beginning` / `middle` / `end` / `local` |
| `techniques` | ✅ | 推荐技法 ID 列表，**首选在首位**；与技法映射表、技法库 L2 表共用 |
| `actions` | ✅ | 推荐动作 ID 列表，**首选在首位**；与 v1/v2 动作映射表共用 |
| `v1ActionName` | — | v1 动作映射专用名，与 `name` 不同时设置 |
| `v2ActionName` | — | v2 动作映射专用名，与 `shortName` 不同时设置 |
| `retired` | — | b11：`true` 表示退役（默认 null/false 为活跃） |
| `retiredReason` | — | b11：退役原因 `merged` / `removed`（retired=true 时必须填） |
| `mergedInto` | — | b11：并入目标症候 ID（仅 `merged` 时填，须指向活跃症候） |

### 步骤 2：编写手册段（人工）

文件：`lib/services/syndrome_knowledge_base.dart` → `kSyndromeManualContent`，追加 `### P0XX 名称` 段。

结构（对齐现有症候）：

```
### P0XX 名称

> **position_sensitivity**: <与注册表 position 一致>

**核心问题**：…
**触发信号**：…
**判断原则**（基于上下文，非硬性标准）：
- …
**严重度判断**（结合三维标定表综合评估）：
- L1 / L2 / L3 …
**例外情况**：…
**few-shot 锚点**（✅ 命中 / ❌ 未命中）：
> …
> 判定：…
> 理由：…
**推荐教学动作**：首选 <A0XX 动作名>，备选 <A0YY 动作名>（首选必须与注册表 `actions[0]` 一致）
```

> ⚠️ 四库一致性测试 #2 会校验 `### P0XX ` 存在；`actions[0]` 与手册「推荐教学动作」首选需一致（#12 只校验表格行，首选动作一致性靠人工）。

### 步骤 3：编写训练段（人工）

文件：`lib/services/training_knowledge_base.dart` → `kTrainingFullKnowledge`，追加 `## P0XX 名称` 段。

结构（对齐现有症候）：**核心本质 / 教学要点 / 常见误区 / 严重度判断参考 / 素材库**。

> ⚠️ 四库一致性测试 #3 会校验 `## P0XX ` 存在。

### 步骤 4：4 个内容型保留点（按需处理）

| # | 内容 | 位置 | 什么情况要动 |
|---|---|---|---|
| 1 | 重叠优先级规则 | 症候库手册重叠规则表 | 新症候与现有症候有重叠判定时，登记（如 `P0XX vs P0YY → 谁优先 / 共诊`）。**登记方式分两种**：互斥/根因语义对（validation 层要硬拦截的）除手册外还须进四库 #8 pairs + manual 断言（如 P032/P012、P033/P030、P034/P009）；纯优先级关系（不做硬拦截）只登记手册即可（如 P032/P031、P032/P025、P034/P010）。以设计稿「重叠优先级」表标注的「进 #8 / 仅手册」为准 |
| 2 | 类型分组表 | `skill_registry.dart`「四、症候类型分类」 | 把 P0XX 加入对应 5 组之一（展示力不足 / 结构视角失控 / 动机意图缺失 / 语言表达 / 商业节奏留存），可带批次注释。**这是唯一手写的症候表格**（含自定义分组与教学策略文本）。同一组后续批次再加入症候时，批注累积更新（如「批次15」→「批次15/批次32-33」） |
| 3 | 技法索引表「适用症候」列 | `technique_knowledge_base.dart` 技法索引表 | 若新症候启用了某技法且需在索引表精选展示，补一行。该列是人工精选（≠注册表反查），不会自动派生 |
| 4 | 新技法/新动作名 | `kTechniqueShortNames` / `kActionShortNames` | 仅当 P0XX 用到了库外的新技法/新动作时，各加一条。沿用已有技法/动作则不动 |

## 四、删除一个症候

> 正式退役（保留定义文本、不进诊断/检索/渲染）走 **b11 机制**（设计稿 `docs/2026-08-11-b11-syndrome-retirement-design.md`，批次 36-38 已实现）：注册表 `SyndromeRecord` 标记 `retired: true` + `retiredReason`（merged/removed）+ 可选 `mergedInto`，表格/计数/白名单全部自动派生剔除；历史记录聚合经 `kSyndromeMergeMap` 归一。**本节的「删除」是完全移除场景**（注册表记录连同手册段/训练段一并删，供彻底废弃时使用）。

1. **注册表**：删除对应 `SyndromeRecord`。**ID 永不复用**，建议在删除处留注释记录退役原因（参照 b6 设计稿 `2026-08-11-b6-syndrome-id-lifecycle-design.md`）。
2. **手册段**：删除 `### P0XX` 整段（含 `position_sensitivity`、few-shot 锚点、推荐教学动作）。
3. **训练段**：删除 `## P0XX` 整段。
4. **内容型保留点清理**：
   - 重叠优先级规则中涉及该症候的行
   - 类型分组表中该症候
   - 技法索引表「适用症候」列中仅指向该症候的引用
5. **悬空引用拦截**：内容中任何残留的 `P0XX` 会被四库一致性 #9 测试直接拦截，按报错逐一清理（如提示文本、示例 JSON、历史说明中的引用需评估保留或改写）。
6. **验证 + 文档同步**：同 §三 步骤 5。

## 六、隐藏触点（最容易漏的 4 处）

1. **备选技法显示格式**：`technique_knowledge_base.dart` 的 `_l2AltColumn` 把备选列分三组（斜杠组 / 带名组 / 无名组，硬编码 Set）。新症候若希望备选技法**带技法名**显示，需把 ID 加入 `namedGroup`；否则默认走「无名单值」格式。若渲染行与现有格式预期不符，`#12` 会提示行不一致，照提示调整分组即可。**实战判据（b10 批次 32-34 验证）**：
   - 备选 1 个 → 默认「无名」单值即可（如 P015 备选 `T018`）
   - 备选 ≥2 个 → 建议入 `namedGroup`，渲染为「T0XX 技法名、T0YY 技法名」（P003 备选 2 个、P032 备选 2 个、P033 备选 2 个、P034 备选 3 个均走此格式）
   - 3-4 个备选 → 也可复刻斜杠组格式（P006/P007/P008/P009/P011 历史格式 `T017/T018/T022`，无技法名）
   - 判定不一致时，`#12` 报「渲染行缺失」即提示需要入组；报「行数与注册表不一致」则提示多/少行，照报错调整
2. **`position` 双写一致性**：注册表 `position` 字段与手册段 `> **position_sensitivity**:` 行均为人工填写，需保持一致。
3. **资产清单清单表**：`docs/教学诊断训练资产清单.md` 的症候清单表是手写文档，增删时同步。
4. **退役过滤一律 `retired != true`（b11 批次 37 经验）**：`retired` 是 `bool?`，null 视为活跃。渲染循环/派生/测试统一用 `.where((s) => s.retired != true)`，**不要**写 `== false`（null 会漏判），也不要写 `!s.retired`（lint 强制显式判空）。退役时内容型保留点仍需人工清理（重叠规则表 / 类型分组表 / 技法索引精选 / #8 pairs / namedGroup，见 §四）。

**实战经验要点**：

1. **触发信号/判断原则写作**：与既有症候差异化边界要在「核心问题」里显式写清（如 P032 对照 P012/P031、P033 对照 P030、P034 对照 P009/P010），避免误诊混淆——这正是重叠优先级表的依据。
2. **few-shot 锚点**：设计稿只给方向，落地时按现有格式扩成「✅ 命中 ≥1 + ❌ 未命中 ≥1」完整块（原文/判定/理由三行），锚点示例需与严重度 L2 对应。
3. **重叠对登记方式**：互斥/根因语义对进 #8（同时登记手册），纯优先级只登记手册——见 §三 步骤 4 #1。
4. **`#8` 双向一致性**：进 #8 的 pair 必须在手册重叠规则表有对应行，否则 manual 断言失败；反之手册行不要求进 #8。
5. **类型分组批注累积**：同组分批加入时批注追加，如「批次15」→「批次15/批次32-33」。
6. **验证节奏**：每批独立 `flutter analyze`（0 issues）+ 全量 `flutter test` + 独立 commit（带批次号），再进入下一批，避免多症候错误混叠。
7. **文档同步放最后一批**：三症候全部落地后再统一同步三份文档（资产清单/审查包/待办清单），减少中途重复修改。

4. **静态表是审计上界，动态才是真实状态**：修订后静态合计 ~58,100 > 50,000（所有阶段同时最坏），但动态最坏 ~43,006 < 50,000（L2 只加载一组、L3 只注入 focus）。静态表超限 ≠ 运行超限，它的作用是**提示需要降级机制**。
5. **运行时闸门只裁独立注入消息**：`systemPrompt` 内嵌 L2 组（priority 1 最先裁）物理上不可独立裁剪，闸门不重建 systemPrompt，L2 组在 `planDegradation()` 返回时被「未标记」跳过。可裁阶段按 priority 顺序：L3 结构(2) → 训练知识(4) → 画像(5) → 引用(6) → 附属(7) → 历史(8)。
6. **超 warning 线不裁只提示**：40,000 < 总量 ≤ 50,000 时仅报告 `overWarning`，避免误伤教学信息；超 50,000 才裁剪。报告区分 `overBudget`（超限但可能无可裁阶段）与 `triggered`（实际裁了 ≥1 阶段）——语义缺口由单测抓出。
7. **阶段名常量 `BudgetStageNames` 是真源**：chat_service 打标与闸门匹配都用常量，避免字符串散落漂移（与注册表真源化同思路）。新增注入阶段时：加一个常量 → 预算表加条目 → 注入点打标，三处对齐。
8. **历史消息是最大可裁变量**：运行时历史全量追加无截断（预算 8,000），引用/附属上下文内部已有 15,000 chars 截断。闸门设计历史最后裁（priority 8），先裁引用/附属等大块。
9. **闸门单测覆盖 4 场景**：不超限 no-op / 超警告不裁 / 超上限按序裁剪（验证保底与后序阶段保留）/ 未标记阶段跳过。正常路径（~43k）闸门零影响，仅极端超限防御性降级。

### 前置流程经验：扩容方向如何确定（图谱体检 → 行业研究 → 双向印证）

b12 靠行业研究直接锁方向，b13 首次加入**内部图谱体检**前置，两条路径合并成标准流程：**先体检找内部空缺 → 再行业研究找外部缺口 → 双向印证 → 写设计稿**。图谱体检基于注册表真源数据即可完成，无需额外工具：

1. **三维审计**：类型×层级交叉表（找类型真空/层级空档）+ position 分布表（找位置稀薄）+ 重叠规则覆盖统计（孤岛检测）。本次实例：`motivationDeficit` 类型仅 P009（真空）、beginning/middle/end 合计仅 5/36（稀薄）、P022/P023/P024/P026 零重叠规则（孤岛）、L5 全空（保守偏置所致，记录不补）。
2. **冗余识别（只记录不修）**：重叠枢纽（P006 有 9 条规则，占 1/4）、单技法依赖（P005 仅 T012、P013 仅 T024）、commercialAppeal 7 症候同质化（靠 position 细分已缓解）。识别冗余的价值在于：扩容时避开与既有症候同构的方向。
3. **行业研究映射表**：把外部高频问题（编辑拒稿原因 / 编辑开放日雷区 / 写作专栏经验）逐条映射「现有症候覆盖情况」，标 ✅（已覆盖）/ ⚠️（部分覆盖）/ ❌（空缺）。本次结论：目标模糊 / 被动主角 / 降智反派三项 ❌，与内部 motivationDeficit 真空双向印证。
4. **双向印证判据**：内部空缺 ∩ 外部高频 = 扩容方向。只有单侧证据的方向慎选（如「中段失速」外部证据强但内部与 P006 重叠风险高，本次未选）。
5. **扩容前先体检的收益**：避免凭直觉扩容导致同质化——commercialAppeal 曾在批次 15 一次扩 5 个，靠 position 细分才缓解；b13 有体检兜底，方向明确且差异化边界在注册表阶段就设计好。

### 机制决策经验（关联收尾）：先观测后强制

本次会话同时收尾了阶段 0 决策 D8「评估顺序观测」——评估顺序（学员自评 → 改前改后对比 → AI 评估）是 skill 指令约束而非代码强制，落地为**轻量观测**：chat_service `_observeEvaluationOrder` 在 FEEDBACK 子阶段回复后，用正则检测「自评引导 / 改前改后对比 / 评估三档」三步结构，仅 debug 级留痕不干预 LLM 输出。

经验：机制类待决策项（如评估顺序、介入级别、门控阈值）一律**先观测后强制**——debug 日志留痕成本极低，积累真实 LLM 行为数据后再决定是否升级为代码层状态机，避免拍脑袋强制造成教学误伤。
