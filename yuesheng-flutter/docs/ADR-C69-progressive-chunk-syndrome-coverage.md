# ADR-C69：分块诊断路径的症候覆盖只有一半（P003–P021 vs 注册表 P003–P041）

- **状态**：**已实施**（方案 A：清单 + 范围说明均由注册表派生；护栏 10 用例 + 5 变异全拦截）
- **日期**：2026-09-03
- **涉及模块**：`lib/services/progressive_diagnosis.dart`（分块诊断核心链路）
- **起因**：A.12.36 收官后，台账「超长分块 4000 字」被标为下一开工点。侦察该登记项时
  **发现原登记意图早已失效**，转而发现一个比它严重得多的问题，遂立本 ADR。

---

## 1. 结论先行

1. **原登记项「超长分块 4000 字」= 常量化任务，早已完成**，台账第六次过期（§2）。
2. **4000 这个数字在模型输入里完全不存在**——实证：L3 输出 / systemPrompt /
   L3 注入 / 全部 37 个 skill 原文，均无命中（§3）。
3. **但侦察翻出一条更严重的缺陷**：长文本分块诊断只能识别 **19 / 39** 个症候，
   缺失的 P022–P041 共 20 个**在分块路径下从未可用**（§4）。
4. **因果链清晰且可归因**：症候体系扩容了两次（19→29→39），每次都同步了「四库」
   + `skill_registry` + `skill_layers`，**唯独漏了 `progressive_diagnosis.dart`**；
   而四库一致性测试不覆盖该文件，所以扩容后既没同步、也没护栏兜住（§5）。
5. **修 prompt 即可生效，无需改校验链路**（validator 只拦退役症候）（§6.1）。

## 2. 开工查证：原登记项早已失效（台账第六次过期）

A.12.34 登记表述：「超长分块 4000 字（服务层）— 位于 `chat_service` /
`progressive_diagnosis` 的诊断路由逻辑，超出 UI 层边界，需单独立 ADR」，
意图是**把 4000 这个魔法数字常量化**（与同批 `UILimits` 常量化同类）。

按 A.12.36 沉淀的方法论，不读台账状态列，改用双证据链：

**证据链 ① — git 提交记录枚举**

```

  aeb64890  X-025-ARCH-5 回退 part 伪拆分（439→439 行，零行为变更）
  d7983619  progressive_diagnosis 419 行主题分组拆分（R-019 ≤300 行）
  f79c0e67  batch 96-25: 工程迁入主仓库  ← 常量在此已存在
```

`f79c0e67`（工程迁入）**早于 A.12.34 的登记时间**。

**证据链 ② — 源码验真**

```

lib/services/progressive_diagnosis.dart:336  if (content.length <= kDiagnosisChunkThreshold)  ← 唯一使用点
```

**1 处定义 + 1 处使用，零硬编码绕过**。其余 4000 字面量逐一定性：

| 位置 | 性质 |
|:--|:--|
| `progressive_diagnosis.dart:9` | 注释「THRESHOLD=4000」 |
| `chat_service.dart:1052-1053` | 注释「≤4000 字」「>4000 字」 |
| `chat_teaching.dart:38` | 注释「>4000 字」 |
| `writing_coach_panel_teaching.dart:376` | 注释「THRESHOLD(4000)」 |

widget 层所谓「4000 路由」实际都是调用 `runProgressiveDiagnosis`，注释里的 4000
只是说明文字，不构成第二套真相。

> **判定**：原登记项「超长分块 4000 字常量化」→ **非缺陷 / 已失效**，建议台账中销项。

## 3. 4000 在模型输入中不存在（实证）

`syndrome_kb_content.dart:167` 的「本段仅适用于非渐进式路径（短文本 <4000 字，
不走分片分析）」是唯一进入知识库文本的 4000。按 V4.9 查证它是否真被注入：

`_extractSyndromeSection`（`syndrome_knowledge_base.dart:23-37`）按 `### P0XX`
提取症候段，结束边界取 `min(下一个 \n###, 下一个 \n## )`。

该句位于 `## 诊断执行指引`（`:165`），而此段在 `kSyndromeManualContent` 中排在
**所有 `### P0XX` 症候段之后**（part 拼接点在 `:156`），因此**任何症候段都会在它
之前截断，它永不进入 L3 输出**。

探针实测（临时测试，已删除）：

```
症候总数=39  L3 输出长度=38427      L3 输出含 "4000": false
systemPrompt 长度=73519            systemPrompt 含 "4000": false
L3 注入长度=2065                   L3 注入含 "4000": false
逐个遍历 skillRegistry 全部 37 个 skill 原文 → 无一含 "4000"
```

> **判定**：该句是**死文字**——既不生效，也不构成第二套真相。写在这里只会误导
> 后来人（本批就被它误导过一次，以为它是 prompt 侧的 4000 真相）。

## 4. 真正的缺陷：分块路径只能诊断 19 / 39 个症候

分块路径用**独立的** `kChunkSystemPrompt`（不在 `skill_registry` 内），其症候
列表是硬编码的：

| 处 | 范围 | 数量 | 是否真源 |
|:--|:--|:--:|:--|
| `syndrome_registry.dart` | P003–P041 | **39** | ✅ 真源（无退役） |
| `kChunkSystemPrompt` 症候列表（`:149-153`） | P003–P021 | **19** | ❌ 硬编码 |
| `buildMergePrompt` 格式要求（`:274`） | 「症候编号 P003-P027」 | 25 | ❌ 硬编码 |

**三处彼此不一致（39 / 19 / 25）**，且分块路径缺两道：

- `analyzeChunk` 阶段：模型只看到 19 个症候的参考列表；
- `buildMergePrompt` 阶段：格式要求写「P003-P027」，进一步压制 P028+ 的输出；
- merge prompt 开头的「引用内置 syndrome-diagnosis 技能」只是**文字引用，不注入内容**，
  模型在合并阶段手上没有任何症候定义。

**缺失的 20 个症候**（P022–P041）：

重复用词/基础语病 · 爽点乏力症 · 期待感断裂症 · 黄金三章失效症 · 章节钩子缺失症 ·
追读动力不足症 · 画面感缺失症 · 段落失控症 · 节奏比例失衡症 · 设定矛盾症 ·
金手指失衡症 · 升级节奏失衡症 · 配角工具人症 · 对话注水症 · 流水账叙述症 ·
心理内耗症 · 支线涣散症 · 目标模糊症 · 被动主角症 · 降智反派症

**反直觉之处**：分块路径服务的是 **>4000 字的长文本**——恰恰是最需要完整诊断
的场景，覆盖反而只有 **48.7%**。短文本（≤4000）走主 systemPrompt，索引表从注册表
派生，覆盖全量 39 个。

## 5. 因果链：两次扩容，都漏了这一个文件

不是「移植时遗漏」，是**扩容时没同步**。三个历史节点：

| 时间 | 事件 | 症候数 |
|:--|:--|:--:|
| 2026-08-07 | `t5-work-import` 从 RN 移植，手册「P003-P021 全部定义，逐字保留」 | 19 |
| 2026-08-11 | **b8 基线扩容**（设计文档 §4 同步清单） | 29 |
| 2026-08 后续 | 再次扩容 | 39 |

b8 扩容设计文档 `docs/2026-08-11-b8-syndrome-baseline-expansion-design.md` §4
列了 5 个文件的同步清单：

- `syndrome_knowledge_base.dart`（手册 / 索引 / 映射表）
- `technique_knowledge_base.dart`（技法库）
- `training_knowledge_base.dart`（训练库，头部声明 P003-P027 → P003-P031）
- `skill_registry.dart`（类型分组 / 动作映射 / 索引表 / 提示文本 4 处）
- `syndrome_skill_levels.dart` + `skill_layers.dart`

**`progressive_diagnosis.dart` 不在清单里**。

而 `four_libraries_consistency_test.dart`（四库一致性测试）覆盖的正是那批库，
`progressive_diagnosis.dart` 不在「四库」之内 → **扩容后既没同步，也没护栏兜住**。

两处硬编码的来历也随之清楚：`kChunkSystemPrompt` 停在移植时的 19 个；
`buildMergePrompt` 的「P003-P027」停在 b8 扩容的中间态。

## 6. 修法选项

### 6.1 先确认：校验链路是否放行

**无需改动**。

- `diagnosis_validator.dart:101` 只拦 `kRetiredSyndromeIds`（退役症候），
  **不校验「是否为已知症候」**；注册表当前**无退役症候**。
- `diagnosis_parser.dart:247` 的 `_kSyndromeIdRe` 只校验 `P0xx` 格式，
  且 N5「只观测不拦截」。

→ 只要分块 prompt 给出后段症候，P022–P041 即可识别、落库，链路不改。

### 6.2 三个方案

| 方案 | 做法 | 优点 | 代价 / 风险 |
|:--|:--|:--|:--|
| **A（推荐）** | 症候列表改**从注册表派生**（ID + 名称 + 一句话），`buildMergePrompt` 的范围说明同步派生 | 一劳永逸，杜绝第三次漂移；与 b9「表格行从注册表派生」既有做法同源 | prompt 变长约 600 字/块；长文本多块时 token 成本上升 |
| B | 手工把列表补齐到 P041，例外指引也补齐 | 改动直观 | 下次扩容**还会再漏一次**——这正是本缺陷的成因 |
| C | 只改 `buildMergePrompt` 的「P003-P027」 | 最小改动 | 不解决根本：`analyzeChunk` 仍只给 19 个，模型识别阶段已被限死 |

### 6.3 例外指引的处理（A 的配套决策）

`kChunkSystemPrompt` 现有 16 条例外指引（P003/P004/P005/P006/P008/P009/P011/
P012/P014/P015/P016/P018/P019/P020 例外）同样硬编码，且只覆盖前段症候。

三个选项：**① 不动**（后段症候无例外指引，可能过度诊断）／
**② 从「manual」派生**每症候的例外段（最准，但 token 明显增加）／
**③ 补一句通用兜底**（如「各症候的例外情况以诊断手册为准」，成本最低但依赖模型自觉）。

### 6.4 护栏缺口（A 的必配套件）

`kChunkSystemPrompt` / `buildMergePrompt` **不在 `skill_registry` 内**，
因此 `skill_prompt_anchor_test.dart` **完全覆盖不到**——改它们零锚点漂移。
这是个**测试盲区**，也是本缺陷潜伏至今的直接原因。

建议补两条护栏：
1. **覆盖一致性**：`kChunkSystemPrompt` 派生的列表必须等于注册表全部非退役症候
   （`kSyndromeRegistry`），**逐处断言、用计数不用 contains**（V4.7 / V4.8）；
2. **范围说明一致性**：`buildMergePrompt` 的范围串必须由同一真源派生，不得另写字面量。

## 8. 实施记录（方案 A + 例外兜底 ③）

### 8.1 代码改动（`progressive_diagnosis.dart`，+65 / -11）

| # | 改动 |
|:--|:--|
| ① | 新增 `_activeSyndromeLabels()`：注册表非退役症候 → `P003 情绪标签化` 形态，ID 升序 |
| ② | 新增 `_syndromeIdRange()`：→ `P003-P041`，供 merge prompt 的范围说明用 |
| ③ | 静态内容拆出两个 const：`_kChunkExceptionGuide`（例外指引 16 条 + 兜底）、`_kChunkOutputFormat`（JSON 示例）——让构造函数远离 R-019 的 50 行硬上限 |
| ④ | `_buildChunkSystemPrompt()`：清单块每行 4 个（沿用 RN 紧凑排布，39 条摊 10 行而非 39 行），拼上 ③ 两块 |
| ⑤ | `kChunkSystemPrompt` 由 `const String` 改为 `final String = _buildChunkSystemPrompt()`——**调用处 `:405` 的 `const ChatMessage(...)` 必须同步去掉 const**，否则编译报 `invalid_constant`（实测踩到） |

| ⑦ | 例外指引末条补兜底（6.3 的 ③）——16 条例外只覆盖 P003-P021，后段 20 个不能"零例外" |

派生结果实测（10 行 × 4 个，39 条全在）：

```

- P007 句式节奏单一 / P008 语言堆砌 / P009 角色空心化（含原 P002 角色工具化症状） / P010 OC 平面化
  …（中略 7 行）
- P039 目标模糊症 / P040 被动主角症 / P041 降智反派症
症候编号 P003-P041（由注册表派生，ADR-C69）      ← merge prompt 范围行
```

**顺带的发现**：硬编码版的「P009 角色动机缺失」与注册表真名
「P009 角色空心化（含原 P002 角色工具化症状）」已经对不上——硬编码连名称都过时了，
不只是漏条目。

`kChunkSystemPrompt` 由 1046 → 1385 字符（**+339**，低于 §6.2 预估的 +600）。

### 8.2 护栏（`progressive_chunk_syndrome_coverage_test.dart`，10 用例全绿）

| 组 | 断言 |
|:--|:--|
| ① 覆盖一致性 | 注册表每个非退役 ID 逐个断言出现在 prompt 中；清单块内每个 ID **恰好** 1 次（防重复行） |
| ② 范围派生 | `buildMergePrompt` 含注册表真实范围；不含 P003-P027 / P021 / P031 等过时区间 |
| ③ 无硬编码回退 | 源码「症候编号」后不得跟字面量；不得再现 `- P003 情绪标签化` 清单行 |
| ④ 兜底句 | 例外指引末条覆盖「未列出的症候」 |
| ⑤ 生效性 | `:405` 确实以 `kChunkSystemPrompt` 作为 system message；后段代表项 P022/P028/P034/P041 存在 |

### 8.3 变异验证（`tool/_c69_mutation.py`，5 变异全拦截、无漏网）

| # | 变异 | 命中 |
|:--|:--|:--|
| A | 清单回退为 RN 逐字多行字面量 | ①×2、③、⑤ |
| B | 范围改回硬编码 P003-P027 | ②×2、③ |
| C | 删掉例外指引兜底句 | ④ |
| D | analyzeChunk 换成别的 prompt | ⑤ |
| F | 派生逻辑被截断到 P021 | ①×2、⑤ |

脚本沿用 ADR-C68 的 V4.10 范式（`try/finally` 恢复 + 锚点不存在即显式报
INJECT-FAILED）。本批首轮就靠 INJECT-FAILED 抓到一次注入失败——兜底句后
紧跟 `''';` 无尾换行，加了 `\n` 就匹配不上。

### 8.4 判据自身的两处修正（避免假阳性）

1. **① 的清单位置**：首版把 prompt 里所有 `- ` 开头的行都算作清单行，
   把 16 条例外指引（`- P003例外：…`）也算进来，于是每个 ID 都被判「出现 2 次」。
   改为只取「症候类型参考」与「例外情况指引」之间的块。
2. **③ 的扫描范围**：首版直接扫全文件的 `P003-P027`，把 ADR 注释里记录历史的
   那一句也判为违规——**注释不是代码**。改为锚定生效位置（`症候编号 ` 之后）。

两条都是 V4.7「判据过宽」的同类。

## 9. 登记

- 「超长分块 4000 字」→ ❌ **非缺陷 / 已失效**（常量早在 `f79c0e67` 已存在，1 定义 + 1 使用）
- `syndrome_kb_content.dart:167`「<4000 字」→ ❌ **死文字**（不进模型输入，建议加注或删除）
- **C69（分块路径症候覆盖 19/39）** → ✅ **A.12.37 闭环**（方案 A + 护栏 + 5 变异验证）
- 台账状态过期第六次 → 再次验证 A.12.36 沉淀的开工动作有效：**git 提交记录枚举 + 源码验真**

### 9.1 遗留

- **模型行为需真机复核**：长文本分块诊断现在能识别 20 类此前缺失的症候，
  输出分布会变。这是**预期内的行为变更**，但未经真机验证，与 ADR-C68 §6 同款留档。
- **兜底句是权宜**：例外指引仍只覆盖前段 16 个症候，后段依赖一句通用兜底
  （6.3 的 ③ 而非 ②）。若真机复核发现后段误报偏多，再升级为从手册派生例外段。
