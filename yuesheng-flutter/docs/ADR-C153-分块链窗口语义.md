# ADR-C153 · 分块链窗口语义：把 6 条例外写成一条规则

- **状态**：已裁定（2026-10-21）
- **日期**：2026-10-21
- **影响面**：`lib/services/progressive_diagnosis.dart`（分片 prompt + `ChunkNote` + 解析 + merge 渲染）
- **关联**：ADR-0006（结构画像）、ADR-C69（注册表派生）、ADR-C80（分块空内容降级）、ADR-C152（AER 观测层）
- **不涉及**：短链（≤4000 字，判据全量注入，无窗口问题）

---

## 1. 问题

分块链（>4000 字）把一章切成 ~3000 字的块逐块判。块内看不到前文铺垫、后文解释、片段外人物关系，
但**分片 prompt 从未告知模型这件事**。

原 prompt 只有一句 `文本片段 ${i+1}/${n}`（`_chunkMessages` 的 user 段）—— 报序号不等于说明「你只有这些」。

后果：判据里凡属跨片依赖的，在分片阶段会被**当成已判定的真阳性**写进 notes，merge 阶段无法区分
「块内可指认的真问题」与「看不到前文所以下的断言」。

## 2. 为什么不能在内容层补例外清单

最直接的修法是照手册原文，把 6 条高风险豁免逐条加进 `_kChunkExceptionGuide`
（P019 / P020 / P022 / P035 / P036 / P037）。**本 ADR 明确否决这条路。**

三条理由（均可复算）：

| # | 理由 | 证据 |
|:--|:--|:--|
| 1 | 这 6 条的成立条件**都不需要指认任何位置** —— 类型自证、意图自证、跨片依赖 | 逐条核对原文，见 §3 |
| 2 | 不需要位置 ⇒ **任何文本都能套用**。列进清单等于给每个分片发一张免责模板 | 同上 |
| 3 | 掉的是剧情组真阳性 —— 「章末无钩子、长线无牵引」那批最该报的 | 这正是 P019/P020 的主判场景 |

按例外写还会漏：新增同类判据时没人会想起来补清单。

## 3. 6 条豁免的实际内容（否决清单方案的依据）

| 症候 | 豁免条件 | 归类 |
|:--|:--|:--|
| P019 章节钩子缺失 | ①卷末/收官章 ②高密度信息章 ③长线情感绑定已建立 | ②③ 类型/意图自证；① 需位置但**本章末尾可自证** |
| P020 追读动力不足 | ①单元剧/副本流 ②日常/治愈流 ③短篇完结型 | 全部类型自证 |
| P022 节奏比例失衡 | ①慢热型整体节奏 ②单段落内部 ③高潮段执行差 | ①**全文节奏比例**（跨片）；②③ 位置可指认 |
| P035 撞文同质 | ①类型通用件 ②刻意复古 ③短篇小品 ④流水线世界（须全文自洽）⑤陌生环境首次亮相 | ①②③⑤ 自证；④「全文自洽」**跨片** |
| P036 细节失真 | ①概括交代背景 ②悬疑留白 ③诗化/意识流 ④醉汉/幼儿视角 ⑤已由后文解释的非常规设定 | ①②③④ 自证；⑤**后文解释**（跨片） |
| P037 故事核缺失 | ①多线并行且有交汇点 ②短篇/单章小品 ③单元剧 ④悬念式延迟揭示 ⑤第一人称意识流 | ②③⑤ 自证；①④ **跨片** |

⇒ 6 条中真正需要跨片信息的只有 **P022① / P035④ / P036⑤ / P037①④** 五处，
但它们散在 6 个 ID 下，各自措辞不同。**按规则写一次覆盖，按例外写六次且各有遗漏。**

## 4. 裁定：写规则，不写清单

新增 `_kChunkWindowBoundary`（分片 prompt 的**判读前提**，置于例外清单之前）与
`_kChunkSelfContainedProbe`（块内可自证的对照示例）。

核心是三句：

1. 只依据片段内可指认的证据判定；看不到片段外信息时，**既不得据此否定，也不得据此肯定**；
2. 判据依赖片段外信息时**标 `uncertain: true`**，不勉强给结论，交 merge 裁决；
3. 「本片段看不出问题」≠「本章没问题」≠「本章有问题」。

第三条容易被忽略，但它是 1、2 的必要补充：没有它，模型会把「我没看到」默认读成「不存在」。

**`片段 1/1` 单块例外**：只有一条分片时本章即全文，跨片前提不成立 —— 不写这一条，
「只有一段」的短章会被误当跨片处理。

### 与 merge 侧的分工

| 阶段 | 可见范围 | 职责 |
|:--|:--|:--|
| 分片 | 单块（+200 字 overlap）+ 覆盖区间 | 只做块内可自证判定；判不了的标 `uncertain` |
| merge | **全部分片 + 原文覆盖区间** | 重判 `uncertain` 条目；仍判不了的标 `pending_context` |

merge 侧对应机制**早已存在**（`pending_context`，W-15-B，已有完整消费链：
`diagnosis_parser` → `merge_convergence` → `diagnosis_integration_service.buildPendingContextSources`）。
本 ADR **不重复发明**，只补它缺的前半段 —— 之前 `pending_context` 在分块链上是**空转的**：
分片侧从不产出「我判不了」，merge 侧就没有输入源。

## 5. 契约

| 项 | 裁定 |
|:--|:--|
| `ChunkNote.uncertain` | 新增，缺省 `false` |
| 分片输出 JSON | 新增 `"uncertain": bool`，附字段说明 |
| 解析 | `_parseUncertainFlag` 认 `true` / `"true"` / `"True"` / `1` / `"yes"` |
| merge 渲染 | 笔记 JSON 必须带 `"uncertain"`（缺省也显式落 `false`） |
| merge 指令 | 新增「分片不确定标记的处置」三态：能确认→输出且 `pending_context=false`；确认不成立→丢弃；仍缺信息→输出且 `pending_context=true` |
| 落点 | 只在分片与 merge 两侧，**不改诊断结果结构、不改落库** |

### 为什么解析要容错

模型对 `uncertain` 的返回类型不稳定：`true`(bool) / `"true"`(String) / `1`(num) 都实测见过。
写 `n['uncertain'] == true` 会把后两种静默判成 false ⇒ **窗口边界声明在最常见的两种输出下失效**，
而失效方向恰好是「把判不了的当成判得了」—— 要防的那一侧。

函数内不抛异常：它在 `_parseChunkNotes` 的 try 内，抛异常会连带丢掉**整块**笔记。

## 6. 读数与留口

### ★ 留口（未覆盖，如实标出）

**#W-5 只覆盖序列化层**（`ChunkNote.uncertain` 是否进 merge prompt），**未覆盖分片侧的解析**。

原因：`ProgressiveResult` **没有 `chunkResults` 字段**，分片结果不对外暴露；唯一出口是 merge prompt，
而该出口在测试里取到的内容与单点 `buildMergePrompt` 不一致。已排除的假设：
`extractJson`（实测返回完整 105 字符）、`_parseChunkNotes` 的 severity 白名单（`L1` 合法）、
`planMergeBudget` 降级（实测 `levels: []`）、快照截断（上限 64KB，实测 3353 字节）。

**根因未查明** —— 按纪律「给不出的是印象不是发现」，此处如实留口，不硬凑一个绿。

**解封条件**（任一即可）：
1. 给 `ProgressiveResult` 加一个仅测试可见的 `chunkResults` 出口；
2. 把 `_parseUncertainFlag` 提到公开 API。

在这两条之一落地前，**「uncertain 的五种输入形态都被正确解析」这句话没有被任何测试证明**。

## 7. 失效条件

若将来给 `pending_context` 换了语义（不再表示「合并后仍判不了」），§4 的两端分工即失效。
