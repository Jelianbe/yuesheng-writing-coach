## 一、背景与目标

### 1.1 产品定位

月笙是**写作教练**产品（非通用写作工具），核心原则（R-009 用户主权）：
- **不替用户写句子、不替用户做决定**；
- 教练姿态 = 找根因、引导学员自己写。

因此产品在功能取舍上**区别于**番茄作家助手 / 口袋写作 / 阅文作家助手等通用写作工具（后者以"AI 代写"为核心卖点，月笙明确不做）。

### 1.2 竞品对照组调研结论

2026-09-05 对百灵创作、口袋写作、阅文作家助手、番茄作家助手四家竞品做了功能体系对照。与本方案相关的关键结论：

| 功能域 | 百灵 | 口袋 | 作家助手(阅文) | 番茄 |
|---|---|---|---|---|
| 角色 / 设定管理 | 素材库（人物/场景/对白） | **角色档案库**、人物关系 | **妙笔·角色设定 / 世界观设定**、设定模板中心 | —（偏平台侧） |

**角色/设定管理是行业全标配**（四家中三家做了专门的档案库/设定页），且是阅文妙笔 AI 的核心卖点之一。月笙目前**有数据、无界面**——是写作机侧与行业差距最大的一项。

### 1.3 目标

为写作机补齐**角色管理的人机协作层**：让 AI 自动抽取的人物数据可被用户查看、确认、拒绝、修正、补充，并支撑后续消费（F05 时序矛盾检测、划词评价"综合考量"等）。

**本方案范围**：角色标签页（列表 + 详情 + 编辑 + 确认机制 + 别名 + 相关事件 + 并入主角色）。
**非本方案范围**：划词 AI 评价、设定/事件/世界观标签页、大纲增强、**代码侧别名归一化进入 prompt（语义级，高风险，后置单独立项）**。

## 二、技术背景与现状盘点

### 2.1 三层架构设计（早期 V2.0 前置研究 §3.2）

产品早期设计了一套**三层记忆架构**，其中 L2 即"识别层"——**长期作品知识库（时序知识图谱 TKG）**：

```
L1 短期工作记忆（会话级）：对话历史 + 章节文本缓冲(近3000字) + 意图向量
L2 长期作品知识库（作品级 TKG）：
   节点：人物{首见章节, 核心目标, 性格标签, 成长弧} / 事件{时间章节, 参与人物,
         因果链前驱后继, 剧情影响等级} / 地点 / 伏笔{埋设位置, 回收位置, 状态}
         / 规则（世界观）
   边：人物-人物 / 人物-事件(参与·见证·主导·受害) / 事件-事件(因果→·并行·时间先于)
   实现：从 L1 文本自动抽取 → 增量更新（每章/会话结束落库）→ 防污染（废弃不写）
L3 个人写作风格模型（用户级）：句长/对话占比/高频词指纹/声线漂移监控
```

L2 的流动规则（本方案核心依赖）：
> "打开章节 / **提及某人物** → 从知识库**查询相关节点** → 组装简洁上下文 → 注入"（按相关性增量注入，非全量）

### 2.2 识别层落地现状（已核实）

| 环节 | 状态 | 实现 |
|---|---|---|
| 数据表 | ✅ 已建 | `CharacterFacts` / `EventFacts` / `SubplotFacts` / `OutlineEntities` / `OutlineImpressions`（共 20 表，schema v26） |
| 自动抽取（写入） | ✅ 在跑 | `diagnosis_committer.applyFactExtractionFromContent`，经注入协议 `kFactExtractionProtocol`（`[YS_FACT]` 块，诊断时让 AI 输出人物/事件/支线三类结构化事实） |
| 诊断注入（读取） | ✅ 在跑 | `message_injector.dart` 767-894 行：读 FACT → detector 纯函数 → 注入 F05 时序矛盾 / F07 因果链断裂 / F11 情节闭环补充观察 |

**结论：识别层（自动抽取 + 落库 + 诊断注入）已完整落地，但产出的数据没有任何界面让用户查看与人工校正。**

### 2.3 数据结构（本方案直接依赖）

**CharacterFacts 表**（`lib/data/database/tables.dart:505`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | 主键 |
| manuscriptId | TEXT FK→Manuscripts | 作品级（cascade） |
| name | TEXT | 人物主名，unique(manuscriptId, name) |
| firstSeenChapter | INT? | 首次出现章节序号 |
| firstSeenAt | INT? | 首次出现时间 |
| **assertions** | TEXT(JSON) | `CharacterAssertion[]`，默认 `[]` |
| **aliases**（新增，D-1） | TEXT(JSON `String[]`) | 子命名（别名），参与匹配 |

**CharacterAssertion**（`lib/types/character_types.dart`，JSON 内嵌，带 TKG 时间双维度；v1.1 起增补三字段）：

| 字段 | 类型 | 说明 |
|---|---|---|
| attribute | String | 属性名（如 "性格" "职业" "独生子女状态"） |
| value | String | 属性值（如 "冷静" "捕快" "独生子"） |
| chapter | int? | 断言所在章节（sort_order） |
| timestamp | int | 断言时间（unix 秒） |
| **status**（新增，D-2） | String | `confirmed / rejected`（**无 pending**，见 D-2） |
| **source**（新增，D-4） | String | `ai / user`（来源可溯） |
| **evidence**（新增，D-3） | String? | 原文摘录（`[YS_FACT]` 协议增补，见 D-3） |
| **chapterHash**（新增，D-6） | String? | 抽取时该章节内容的指纹——重诊时同章 hash 变化 → 旧断言标 `stale`（重复诊断语义的唯一判据，见 D-6） |
| **stale**（新增，D-6） | bool | 旧版标记：所属章节内容已改写/删除。灰显、不参与 F05、可在角色页一键清除 |

**EventFacts 表**（事件侧，用于"相关事件"关联）：含 `name` / `chapter` / `eventType`（决定|转折|突发|冲突|日常）/ `causeEventId` / `effectEventId` / `participants`(JSON 人物列表) / `description`。**v1.3 起同批新增 `stale`（bool）+ `chapterHash`（String?）列**（表结构变更，D-8 同批实现）——章节改写后旧事件同样标 stale，F07 因果链不消费，与角色侧语义一致。

**大纲侧栏确认模式**（`lib/widgets/outline_drawer.dart`，批次 87-4，本方案的 UI 模板）：已实现"AI 提取 → 侧栏展示 → 快速确认/拒绝（pending/active）"闭环。**注意：大纲的 pending/active 语义不能直接照搬到角色断言**——角色断言的确认策略见 D-2。

### 2.4 现状缺口（本方案要补的）

1. **角色数据"有数据、无界面"**：CharacterFacts 自动积累，无任何展示/人工校正入口；
2. **CharacterAssertion 无确认状态**：无法区分"有效/已拒绝"，F05 检测与后续消费无法区分可信度；
3. **无别名（子命名）机制**：正文用别名提及时，检测/关联会漏判或误判为两人；且 `unique(manuscriptId, name)` 导致**写侧必然产生重复行**（"阿晴"被抽成独立角色），无合并入口；
4. **无角色↔事件关联展示**：事件侧已存 `participants`，但角色侧看不到"这个角色参与了哪些事件"；
5. **断言无原文摘录（评审硬伤）**：`[YS_FACT]` 协议目前只输出 `attribute/value/chapter`，无 `evidence` 原文——「查看原文」此前无数据来源（已由 D-3 解决）；
6. **断言无来源字段**：修正/补充后无法区分"AI 抽的 vs 用户写的"（已由 D-4 解决）；
7. **重复诊断语义未定义（二轮评审实证）**：现行 `upsertCharacter` 按 `(attribute, value, chapter)` 三元组去重且**保留先出现者**（`character_fact_repository.dart:66-79`）——用户改写章节后，旧版本断言**永不失效**、继续触发 F05 幽灵矛盾；重写引入的新事实则是叠加而非替换。TKG 越诊越脏，角色页上线后这些幽灵断言将全部可见（已由 D-6 解决）。

## 三、需求定义

### 3.1 功能需求（FR）

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-1 | 角色列表 | 按作品展示全部角色：名字、首见章节、断言摘要；支持搜索、排序（首见章节/最近更新） |
| FR-2 | 角色详情 | 按属性分组的断言列表，每条可拒绝/修正/补充，**可查看原文**（依赖 evidence，D-3；缺失时反查兜底，失败明确"未定位到原文"） |
| FR-3 | 别名（子命名） | 角色可维护多个别名，别名参与事件关联与 F05 匹配（主名 ∪ 别名） |
| FR-4 | 相关事件（内容关联） | 详情页展示该角色参与的事件总结（事件名+章节+类型+一句话描述），可跳章节 |
| FR-5 | AI 底稿 + 人工校正 | AI 自动抽取生成底稿（抽取即生效，新手零负担）；用户可拒绝错误抽取（防污染）、修正值、补充漏抽 |
| FR-6 | 入口 | 写作页底部 tab「角色」（与大纲侧栏并列） |
| FR-7 | 新建角色 | 支持手动新建（补充 AI 未识别到的角色） |
| FR-8 | **并入主角色**（评审②，D-5） | 将另一行角色（如 AI 按别名误建的独立行）的断言迁移并入主角色，原行删除或标记。解决写侧重复散落 |
| FR-9 | **旧版断言标记与清理**（D-6） | 章节改写后重诊：旧断言标 `stale` 灰显（不自动删除），F05 不消费；角色页提供一键「清除本章旧版断言」；章节删除/进回收站同语义 |
| FR-10 | **批次沉淀提示 + 最近批次视图**（D-7） | 某轮诊断有新增事实时，由系统在该条消息末尾渲染轻量提示卡「本次沉淀 N 条人物事实 → 查看」（非 AI 协议输出）；点入角色页「最近批次」过滤视图 |

### 3.2 交互设计

**列表视图**（v1.1：去掉待确认角标——D-2 后无 pending 态，角标无意义）：
```
┌──────────────────────────────┐
│ 角色 (4)            [+ 新建] │
├──────────────────────────────┤
│ ◯ 林晚晴    第3章登场         │
│    性格·冷静 / 职业·捕快 /…  │
├──────────────────────────────┤
│ ◯ 顾行之    第1章登场         │
│    身世·孤儿 / 性格·偏执      │
└──────────────────────────────┘
```

**详情视图**（v1.1：断言带来源标记 + 原文摘录；头部加"并入主角色"入口）：
```
┌──────────────────────────────┐
│ ‹ 林晚晴        [改名][并入…] │
│  别名：晚晴/阿晴  [编辑+]     │
│  首次登场：第3章  更新时间：…  │
├──────────────────────────────┤
│ ⚠ 时序矛盾（F05）            │
│  「独生子女状态」第3章独生子   │
│   → 第15章 出现"妹妹"        │
├──────────────────────────────┤
│ 性格                          │  ← 断言按属性分组
│  [AI] 冷静   第3章 · 查看原文 │  ← source=ai 标记
│  [✗] 暴躁   第5章 · 查看原文 │  ← 已拒绝（灰显）
│  [手] 外冷内热 第7章 · 查看原文│  ← source=user 标记
│  [旧] 独生子女·有妹妹 第15章  │  ← stale（章节已改写，灰显）
│       [清除本章旧版断言 (2)]  │  ← FR-9 一键清理
│  [+ 补充] 属性＿ 值＿ 第＿章  │
├──────────────────────────────┤
│ 相关事件 (5)                  │
│  [转折] 第5章 决定离开金陵     │
│  [冲突] 第7章 与顾行之对峙     │
└──────────────────────────────┘
```

**核心流程**：AI 抽取（带原文摘录）→ 角色进入列表（默认生效）→ 用户详情页逐条 拒绝 ✗ / 修正 / 补充 / 查看原文 → 已确认断言参与 F05 与后续消费；已拒绝断言灰显、不参与（防污染）；重复角色经「并入主角色」合并；**章节改写后旧断言标 stale 灰显、可一键清除，F05 不消费**（D-6）。

**确认入口约定（D-7）**：抽取**静默沉淀**，不在诊断回复内做逐条确认卡——诊断消息末尾由**系统渲染**（非 AI 协议输出）轻量提示「本次沉淀 N 条人物事实 → 查看」，点入角色页「最近批次」过滤视图。理由：① 事实确认无需即时反馈（F05 是延迟消费数据），打断心流不值得（PRODUCT.md 心流价值）；② 聊天消息是不可变历史，内嵌确认卡与 DB 状态必然双源分叉——确认状态必须单真源。

### 3.3 已定决策

| # | 决策 | 结论 |
|---|---|---|
| 1 | 确认粒度 | 逐条断言级（F05 是断言级检测，粗粒度无法拒绝单条错误抽取） |
| 2 | 新手负担 | AI 抽取即默认生效（不要求用户逐条点确认），可手动拒绝/修正/补充 |
| 3 | 入口位置 | 写作页底部 tab，与大纲并列 |

### 3.4 待评审决策（v1.3 定稿 D-1~D-8）

| # | 决策 | 建议 | 理由 |
|---|---|---|---|
| D-1 | 别名归一化路径 | **路径 B（代码侧）**：不动抽取 prompt 的语义判断，别名由用户手动补，检测/关联按"主名 ∪ 别名"匹配；prompt 语义级归一化拆后续批次 | 改 prompt 语义判断 = 高风险（R-027 需人工确认），影响全量诊断链路；首波规避 |
| D-2 | 断言状态枚举 | **默认 `confirmed`，枚举仅 `confirmed / rejected`（删除 `pending`）** | 评审③：默认已确认 + pending 无产生路径 → 三态实为两态。当前无"待确认审核"强需求，不硬造伪状态；后续如需批量审核再引入 |
| D-3 | 「查看原文」数据来源 | **`[YS_FACT]` 协议 `characters.assertions` 增补 `evidence` 原文摘录字段** + `findKeywordExcerpt(value)` 兜底 + **反查失败明确显示"未定位到原文"**（不假装能查） | 评审①：此前断言只有 attribute/value/chapter，反查概括词大概率落空。**诚实承认这动了 prompt**——但属低风险纯增字段（AI 只需摘录原文，无语义判断），与 D-1 的语义级改动分属不同风险等级，需独立评审 |
| D-4 | 断言来源字段 | 同一批 JSON 变更中加 `source: ai \| user`（零迁移成本） | 评审④：修正/补充后需区分来源；支撑"事实可信、进步可见"卖点 |
| D-5 | 角色合并 | **本批实现最小「并入主角色」**：目标角色详情页发起，选择来源角色 → 断言迁移（source 保留原值）→ 来源行标记 `rejected`（软删）；**合并后两行断言并存可能产生新的 F05 矛盾——这是功能在正确工作（把矛盾摆出来让用户裁决），详情页需展示并可逐条处理** | 评审②：`unique(manuscriptId, name)` 下别名必然产生独立行，无合并则数据越用越散；别名价值漏掉写侧一半 |
| D-6 | **重复诊断语义** | **标记制，不做覆盖制**：断言新增 `chapterHash`（抽取时章节文本指纹）+ `stale` 标记。重诊时同章 hash 变化 → 旧断言标 stale（灰显、不删、F05 不消费），新断言正常叠加；角色页一键「清除本章旧版断言」；**章节删除/进回收站 → 该章断言同标 stale** | 现状实证：upsert 保留先出现者，旧断言永不失效。不做「重诊即覆盖」的三个理由：① 长文分块诊断同一章跑多次，按调用覆盖会误杀合法增量；② 诊断部分失败时覆盖制丢数据；③ 自动删数据违反 R-009 保守原则（防污染教训：标灰让用户清） |
| D-7 | **确认入口** | **静默沉淀 + 批次视图**，不做诊断内嵌逐条确认卡（理由见核心流程节）；拒绝时提供**可选**理由 chips（抽取错误 / 章节已改写 / 重复 / 其他，不强制、无自由文本）——理由数据是后续改进 `[YS_FACT]` 协议的唯一真实用户信号 | 心流价值 + 状态单真源；拒绝理由成本极低、决策价值高 |
| D-8 | **事件侧同语义** | EventFacts 的 chapter 与角色断言同病（章节改写后旧事件永生、继续进 F07 因果链）。**同批实现**：EventFacts 加 `stale`/`chapterHash` 列（表结构变更），F07 只消费非 stale；章节删除/回收站钩子同时标角色+事件 | 同一数据语义问题，分开修会出现半套行为；EventFacts 是独立表，同批一次迁移到 v28 省二次 bump |

## 四、技术方案

### 4.1 数据层

| 改动 | 内容 | 风险等级 |
|---|---|---|
| `CharacterFacts` 加 `aliases` 列 | TEXT(JSON `String[]`)，schema 变更之一 | 🟡 中（需迁移测试覆盖存量库；`database.g.dart` 由 build_runner 重新生成，勿手改） |
| `EventFacts` 加 `stale`/`chapterHash` 列（D-8 同批） | bool + TEXT(String?)，schema 变更之二；**两表同批一次迁移到 v28**（v26→v28） | 🟡 中（同上；一次迁移避免二次 bump） |
| `CharacterAssertion` 加 `status / source / evidence / chapterHash / stale` 字段 | JSON 内嵌（**无表迁移**）；`tryFromJson` 宽松解析，缺失字段默认 `status=confirmed`、`source=ai`、`evidence=null`、`chapterHash=null`、`stale=false` | 🟢 低 |
| `[YS_FACT]` 协议增 `evidence` 字段 | `diagnosis_committer.dart` 的 `buildFactProtocolContext`：`characters.assertions[]` 格式加 `"evidence":"原文摘录（≤30字）"` | 🟡 中（**动注入 prompt**，D-3；纯增字段低语义风险，需 R-027 评审确认；已核实该函数**未被任何快照测试冻结**、fact_validator 宽松解析，实现风险实际偏低） |

### 4.2 服务层

| 改动 | 内容 |
|---|---|
| 事件关联查询 | `CharacterFactRepository`（或复用 `EventFactRepository.listEvents`）新增：按"主名 ∪ 别名"过滤 `participants` 的查询。作品级事件量小（几十条），全加载内存过滤即可，无需 SQL LIKE |
| 匹配归一化 | F05 检测与事件关联统一走"主名 ∪ 别名"匹配（别名由用户维护，不碰 prompt 语义） |
| F05 接入可信断言 | `conflict_detector`（纯函数）改为只消费 `status == confirmed` **且 `stale == false`** 的断言；断言来源（source）不影响 F05（AI/用户断言同等参与） |
| **角色合并（FR-8/D-5）** | 新增并入逻辑：来源角色断言迁移至目标角色（source 保留）→ 来源角色行标记（软删/rejected）→ **来源角色名自动收进目标 aliases 列表**（不动历史 participants 数据——D-1 的「主名 ∪ 别名」匹配天然兼容全部历史事件，省掉 participants 改写出错面） |
| **重复诊断语义（FR-9/D-6/D-8）** | 事实落库时记录 `chapterHash`；重诊同章 hash 变化 → 该章**旧断言与旧事件同标 `stale`**（保留不删）；F07 与 F05 同规则只消费非 stale；**章节删除/进回收站钩子 → 该章断言+事件同标 stale**（恢复不自动解除 stale，用户手动，如实标注） |
| **批次沉淀提示（FR-10/D-7）** | 事实落库处返回本次新增条数；chat 侧由**系统**在该诊断消息末尾渲染轻量提示卡（非 AI 协议输出、无状态分叉）；点击跳角色页「最近批次」过滤视图（按落库时间过滤即可，无需独立 batch 字段——`updatedAt`/断言 `timestamp` 已够用） |

### 4.3 UI 层

| 改动 | 内容 |
|---|---|
| 角色列表页（新） | 参考 `outline_drawer` 模式；路由 + Riverpod Provider 注入 |
| 角色详情页（新） | 断言分组 / 拒绝（含可选理由 chips）/ 修正 / 补充 / 来源标记（AI/手）/ **查看原文（evidence + 反查兜底）** / 别名标签编辑 / 相关事件 / 时序矛盾提示 / **并入主角色入口** / **stale 断言灰显 + 一键清除本章旧版** |
| 入口 tab | 写作页底部「角色」tab；**「最近批次」过滤视图**（FR-10 提示卡的落点） |

### 4.4 边界与约束（验收红线）

1. **R-009 用户主权**：补充断言为**纯手动输入**，不做"AI 代填建议值"；
2. **R-019 硬上限**：新增函数 ≤50 行（页面按硬上限拆分；文件超 300 行登记债务，同现有 76 个超限文件）；
3. **依赖注入**：新 repository 方法经 Provider 注入，不引入全局状态；边界层（repository/表单）校验 + try/catch（R-028）；
4. **R-029**：不硬编码任何密钥/敏感配置；
5. **「查看原文」诚实降级**：evidence 缺失且反查失败时，**必须明确显示"未定位到原文"**，不得假装定位成功；
6. **stale 不自动删除（R-009 保守原则）**：章节改写只标 stale（**角色断言与事件同规则**），清除动作永远由用户发起；恢复章节不自动解除 stale（如实标注）。

## 五、风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 数据库迁移 v26→v28（两表：aliases + EventFacts stale/chapterHash） | 🟡 中 | 完整迁移测试链；migration 守卫随 schema version 上移；生成文件勿手改；一次迁移避免二次 bump |
| `[YS_FACT]` 协议增 evidence（动 prompt） | 🟡 中（低语义风险） | D-3 独立评审（R-027）；纯增字段不改变 AI 语义判断路径；输出 token 增量可控（每断言 ~30 字） |
| 别名语义级归一化触碰 prompt | 🔴 高 | **首波走路径 B**（代码侧，不碰语义）；prompt 归一化单独立项 |
| 老数据兼容（断言无新字段） | 🟢 低 | `tryFromJson` 缺失字段默认 confirmed/ai/null |
| 角色合并的数据一致性 | 🟡 中 | 迁移为事务性操作；来源行软删可回滚；**来源角色名自动收进目标 aliases**（不动历史 participants） |
| stale 语义引入 F05 行为变化（旧幽灵矛盾消失） | 🟢 低（正向） | detector 只消费 confirmed 且非 stale——**现状是旧断言永生并持续触发幽灵 F05**（缺口 7 实证），本变更消除幽灵；需 detector 测试覆盖 stale 排除分支 |
| 章节删除/回收站钩子遗漏 | 🟡 中 | 验收点显式列出（**角色+事件双侧**）；恢复章节不自动解除 stale（如实标注给用户） |
| R-019 函数 ≤50 行约束增加编写成本 | 🟢 低 | 页面按硬上限拆分；六道门禁兜底 |
| R-009 越界（AI 代填） | 🟢 低 | 写入验收点，实现时守住"纯手动输入" |

### 6.2 验收标准

1. **六道门禁全绿**：格式 / `flutter analyze lib` / 全量测试 / 循环依赖（baseline）/ 密钥扫描 / R-019（baseline）；
2. **新增测试**：migration 测试（**v26→v28 两表**）、repository 关联查询测试、detector 行为（只消费 confirmed 且非 stale）测试、角色合并（事务/软删/别名自动收编）测试、协议解析（evidence 兼容缺失）测试、**重复诊断语义测试（同章改写 → 旧断言+旧事件 stale、新断言叠加、F05/F07 排除）**、**回收站钩子测试（角色+事件双侧）**、两页面 widget 测试；
3. **人工验收**：AI 抽取（含 evidence）→ 拒绝/修正/补充 → 拒绝项灰显且不参与 F05 → 别名参与事件关联与 F05 匹配 → 查看原文可定位（缺失时明确"未定位"）→ 并入主角色后断言迁移、原行软删、**来源名进入目标别名、合并产生的 F05 矛盾可见且可逐条处理** → **改写章节重诊后旧断言与旧事件均 stale 灰显、一键清除可用、F05/F07 幽灵矛盾均消失** → 批次提示卡出现且跳转正确 → 相关事件跳章节可定位。
