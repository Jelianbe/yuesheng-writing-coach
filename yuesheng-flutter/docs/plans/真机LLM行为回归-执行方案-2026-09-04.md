## 一、为什么现在做（目的）

第 1~8 批共修复/裁决 **60+ 条**（C 系 1~69、N 系 1~40、V-05 副本治理、E.3 元规则）。
验证手段分三层：

1. **LLM 行为验证**（盲测 / 独立采样）——只有第 1~6 批做过（审阅文档 §A.6~A.12.20）；
2. **静态护栏 + 变异验证 + 锚点快照**——第 7、8 批的主要手段；
3. **单元 / 集成测试**——代码侧修复的覆盖手段。

关键缺口：**第 7、8 批的全部 prompt 侧修复（C57 / N29 / N28 / N30 / N34 / N38 / E.3 /
N35 / N36 / C69 等）从未经过 LLM 行为验证**。锚点漂移只能证明「文本进了注入路径」
（V4.9），不能证明「模型按新文本行动」。本方案补上这一层，作为 8 批修复的最终验收。

## 五、判分与失败处理

- **单场景判据**：3 次采样中预期行为命中 ≥2 次 → 通过；1/3 → 记「观察项」（复跑 3 次，
  再 1/3 升失败）；0~1/3 且措辞级一致 → 失败。
- **失败处理**：登记新 C 号（不占已用号段）→ 按 R-027 走 ADR → 修复后**只重跑失败场景**
  （不整轮重跑）。禁止顺手修非失败项（R-010）。
- **好行为回归失败 = 最高优先级**：说明后批修复碰坏了前批成果，立即停批上报。
- **全部通过后**：在审阅文档头部与 `待办执行清单.md` 各加一行收口记录（由执行者按其
  台账格式登记，本方案不预写）。

  只写报告）。
