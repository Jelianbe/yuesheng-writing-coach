> 所有行号均为代码真源位置（`lib/` 相对路径），描述与代码一致。

## 〇、审查目标与范围

**四个模块**：
1. **训练执行**：训练循环 skills、介入级别、结果解析与反馈衔接、训练知识库 L3、评估引擎
2. **数据层**：19 张表模型、Repository、外键约束、数据安全、迁移机制
3. **UI 链路**：对话流卡片渲染、路由、写作面板、成长评估 UI、引用管理 UI、动画无障碍
4. **工程安全**：敏感数据存储、签名构建、调试隔离、错误处理、网络、依赖

**三个重点专题**（用户特别强调）：
- **专题 A 引用层**：@W001 语法、上下文注入、管理操作、生成端、会话装配
- **专题 B 解析层**：六个协议块 parser、四个 validator、流式拦截、失败降级
- **专题 C 诊断两层拆分**：大纲层（AI 写剧情/人设/设定梗概）+ 写作层（文字/写法解析）的拆分方案与实现

**设计总原则**（审查基准）：
- 内容做**锚点与边界**，不给 AI 大段照念话术，放开 AI 自主组织
- **代码引擎 vs LLM 分工**：确定性计算在代码侧，教学话术流程在 LLM skill 指令
- **防御性代码不可简化**：静默跳过、NO_OP 合并、双重校验来自真实事故

## 五、重点专题 A：引用层

### 5.1 @ 语法与解析（mention_parser.dart）

- 规则：`@W001`=第1作品、`@W001/C003`=第1作品第3章、`@W001/F002`=第1作品第2素材；正则 `@(W\d+)(?:/([CF]\d+))?`（L18）

- cleanedText：只移除解析成功的 @ 引用；失败的保留原文（L66-70）
- 发送端：chat_page `_handleSend` parseMentions（L362）→ 逐条 addReference（file 类型因 CHECK 约束跳过 L371）→ **无主引用时首条自动设主**（L377）→ cleanedText 替换发送文本（L381）

### 5.2 引用上下文注入（chat_context_builder.dart buildReferencesContext，L460-578）

- 预算：total 15000 / primary 0.75 / secondary 0.25（L466-468）
- 主/次引用拆分（isPrimary==1 → primaryRefs）；file 固定 50KB 预算截断；chapter smartTruncate（保首尾）；manuscript 聚合元信息 + 目录 + 前 2 章预览
- 调用：chat_service L399-454（预加载缓存 _preloadReferenceDetails L2208-2252）

### 5.3 引用管理操作（reference_repository.dart）

- addReference 幂等（ON CONFLICT DO UPDATE excerpt_range；isPrimary=true 事务内 _setPrimaryInTx，L258-287）
- removeReference：删主引用自动另选 createdAt 最早为新主；无引用清空 sessions 缓存（L294-347）
- **setPrimaryReference 对 file 类型直接 throw ArgumentError**（L355-366）——但引用层允许 file 参与（@F 引用），见审查问题
- _setPrimaryInTx 同步冗余缓存（chapter 主引用回填 manuscriptId+chapterId）（L370-421）

### 5.4 生成端（reference_picker.dart）

- 双模式 default/mention（L27-42）；buildMentionPath(列表 index) 生成编号（L283-304/L342-347/L469-474）

### 5.5 会话装配（session_repository.dart）

## 七、重点专题 C：诊断两层拆分方案（大纲层 vs 写作层）

### 7.1 方案设计（用户提出的诊断两层拆分，B72）

**拆分动机**：① **大纲层（事件/人物层）**——AI 自主提取剧情/人设/设定梗概沉淀入库，形成可交互记忆；② **写作层（写法层）**——文字内容/写作手法诊断（现有症候链路）。两层分离后，跨章节检测（F09 角色动态关系）才有可信数据源。

**用户核心关切**：记忆可交互性 + 同人物两次入库导致印象混乱。方案落地"三件套"：**实体对齐（防重复入库）→ 增量合并（防印象覆盖）→ 用户确认（pending 态兜底）**。

### 7.2 实现方法

1. **实体对齐**：注入当前实体索引（名+别名+已确认印象）让 AI 匹配防重复（outline_service.buildEntityIndexContext L91-116）；应用侧匹配优先级：① matched_entity_id（**必须存在于当前实体集合，防 AI 幻觉 id**）→ ② 别名交集规则 → ③ 新建 pending（applyOutlineExtraction L126-215）
2. **增量合并**：命中已有实体 → 追加印象不覆盖（L183）；conflict_with 仅采信同实体已有印象 id（L185-188，防幻觉）
3. **用户确认**：新建实体/印象 pending 态 → 确认卡（outline_confirmation_card）接受→approveImpression（冲突旧印象 superseded + 实体 active）/拒绝→rejectImpression

**防 AI 幻觉双闸**：matched_entity_id 必须存在；conflict_with 必须指向同实体已有印象
**来源可追溯**：每条印象带 source_chapter_id/No + version（印象混乱可回溯纠正）
**零侵入写作层**：大纲块独立，解析失败不影响诊断

### 7.3 表结构与协议

- v18 迁移：outline_entity（entityType character/setting/plot + entityKey + aliases，UNIQUE(manuscript_id,entity_key)）+ outline_impression（impression + sourceChapterId + version + conflictWith + status，UNIQUE(entity_id,impression)）
- 协议块：原 `[YS_OUTLINE]`，批次74 改名为 `[YS_ENTITY]`（旧「大纲诊断」skill 占用 [YS_OUTLINE]，改名隔离）
- 挂接：chat_service 5.1.8 注入实体索引 + 步骤 9.1 解析落库（不装配 outlineRepo 则跳过）

### 7.4 与写作层/其他 AI 角色关系

- **三层 Agent 架构**（agent_skills.dart）：Reviewer 审稿门控（PASS/FAIL 二元判决，L13-81）→ Editor 叙事层观察（9 维度现象描述，非诊断，L85-175）→ Diagnosis 技术层症候诊断（主流程）
- **拆分澄清**：大纲层=记忆沉淀（[YS_ENTITY]）；写作层=症候诊断（[YS_DIAGNOSIS]）；Reviewer/Editor 是独立的条件触发分支（Editor 与 Diagnosis 互斥，Editor 分支提前 return）
- ReviewerGate.enabled = **false 默认关闭**（shared_constants L104-109）；TeacherGate.enabled = true（L113-120）

const Map<TrainingResult, List<String>> _kTrainingResultPatterns = {
  TrainingResult.passed: ['达标', '通过', '很好', '完成', '成功'],
  TrainingResult.partial: ['部分达标', '部分正确', '方向对了', '还需要'],

TrainingResult? parseTrainingResult(String content) {

    }
  }
  return null;

/// 容错 JSON 解析：原生失败 + 含中文引号 → 替换重试；无中文引号 → rethrow
/// 不做：中文逗号/冒号容错、markdown fence 容错（各 parser 自行处理）
Object? parseJsonLenient(String jsonStr) {
  try {
    return jsonDecode(jsonStr);
  } catch (originalError) {
    final fixed = jsonStr.replaceAll('\u201C', '"').replaceAll('\u201D', '"');
    if (fixed == jsonStr) {
      rethrow;  // 没有中文引号可替换，无法容错
    }
    return jsonDecode(fixed);
  }
}

## 十二、设计原则与决策史（防误判须知）

1. **AI 自由度**：内容只给锚点和边界；审"约束是否适度"而非"锚点是否够详"
2. **代码引擎 vs LLM 分工**：确定性计算在代码、话术在 LLM——"规则代码里没实现"可能是刻意分工（如评估顺序、降级阶梯）
3. **症候数量不限制 + 优先级排序**：教学原则，勿建议"截断"
4. **防御性代码不可简化**：静默跳过、NO_OP 合并、双重校验来自真实事故
5. **RN 已废弃**：真源 = yuesheng-flutter；发现两处不一致以 Flutter 为准（含签名策略差异）
6. **两层拆分是刻意设计**：大纲层记忆沉淀与写作层症候诊断分离、零侵入，勿建议合并
7. **保守迭代史**：大量防御来自断点事故，删改需谨慎；外部 AI 凭概述推断常有 1/3 失实，结论需行号级复核
