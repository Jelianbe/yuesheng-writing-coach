判别式（ADR-C64 §3）：当前输出是否符合设计意图？

- 症候库侧「识别到多少报多少」**符合**设计意图（诊断须全量落库）→ 不改数量规则；
- 教学侧「每轮聚焦 1-2 个」**符合**设计意图（避免学员负担过重）→ 不改数量规则；
- **但两侧并置而不说明分工，导致模型行为不确定**——这**不符合**任何一侧的设计意图。

故本批修的是**「未声明的分工」**，而不是任何一侧的规则本身。

### 2.2 冲突的直接证据：一个词

`skills_attitude.dart:79` 用的是「不堆叠多个**诊断**」——与症候库的「**不限制**问题数量」**字面直接冲突**。其余三处封顶表述用的是「建议 / 回复 / 同轮处理」，指向已较明确，属间接歧义。

### 2.3 既有实测（台账 2146-2149，N36）

> 「不限制问题数量」vs「每轮聚焦 1-2 个症候」。gp-13 补充观察：
> L1068「先输出自然语言 + 再输出 JSON」把两者**缝在同一轮**里，字面可自洽
> （前者管 JSON、后者管自然语言），但 prompt 从未明说 → 模型只能猜。

旁证（本批核实）：

- `diagnosis_validator.dart:80` 只对 `syndromes` 校验**非空**，无数量上限 → 代码侧默认全量。
- `shared_constants.dart:81` `maxSyndromeChanges = 5` → UI 侧静默截断超 5 条的展示，说明「报得多」是预期内的常态。

### 2.4 决定性查证：无上限侧 6 处里，只有 1 处真正进入模型输入

清单里「无上限」看着有 6 处，但**模型看不到其中 4 处**。查证链：

**① 症候库手册只按症候 ID 提取单个段落**

`syndrome_knowledge_base.dart:42`：`getSyndromeContent` 通过
`_extractSyndromeSection(kSyndromeManualContent, id)` 逐个症候提取。边界逻辑（:28-36）：

```dart
// 结束边界：下一个三级段（### P0XX）或二级段（## 章节标题），取更早者。
// 修复：最后一个症候段（如 P034）之后若只有 `## ` 二级标题，旧逻辑会落到
// 文件末尾，把手册尾部非症候内容（类型速查/诊断规范/重叠规则）一起吞进 L3 详情。
```

注释明说：**「诊断规范」被刻意排除在 L3 之外**（这是一次已修复的缺陷）。故
`syndrome_kb_content.dart:172`（手册尾部 `## 诊断执行指引` 下的数量原则）
**永远不会被提取**。

**② `syndrome_kb_content_manual_1.dart:79 / 81` 在「重叠规则」章节内**

该两处位于 `### 症候重叠优先级规则`（:27-90）章节，是**三级段但非 `### P0XX` 症候段**
→ 提取正则匹配不到 → **不进 L3**。

**③ 锚点实证：L3 注入零漂移**

首轮锚点 diff 显示 `prompt 39 / skillContent 8 / **L3 0**`——改动 :172 后 L3 用例
**一个都没变**，从数据上证实了 ①②。

**④ `progressive_diagnosis.dart:266` 是单侧存在，无冲突**

该 prompt 是独立构造的（`# SKILL: 症候诊断手册` + 分片笔记 + 统合要求），
**不含任何教学层 skill**，封顶侧表述不在其中 → 只有「不限制数量」一侧，构不成冲突。

**结论**：真正进入模型输入的「无上限」表述只有 `syndrome_kb_content.dart:44`
（及其同语义块的 :86），二者同属 `kSyndromeIndexContent` → 注册为
`syndrome-diagnosis-index` skill。**台账「无上限侧 6 处」应更正为「1 处生效」。**

> 方法论留档：prompt 类缺陷修法前，必须先查证**这段文本是否真的会被注入**。
> 症候库 / 手册类内容常按 ID 切片注入，写在文件里 ≠ 模型看得到。
> 与 ADR-C66 §4.2 同源——**「文件里有」不等于「生效」**。

### 2.5 实测模型的数量取值（台账 2172）

gp-12 的 `syndromes` 数为 **2/3/2**，gp-13 为 **3/3/3**——都超过封顶侧的「1-2 个」，且在 2 与 3 之间摆动。与「模型在两套规则间摇摆」的假设一致（样本受串行污染，仅作旁证，不作结论）。

## 4. 与判别式的边界（值得留档）

改 prompt 文本**必然**改变模型输入。按 ADR-C64 §3 的字面判据，这更像「行为变更」而非「缺陷修复」。

本批的判定：**属于缺陷修复**，理由是——

> 改动的意图与结果都是**消除模型行为的既有不确定性**，而非把行为从 A 改成 B。
> 若模型此前恰好猜对（全量识别 + 讲解聚焦），改动后输出不变；若猜错，改动后
> 才回到设计意图。这与 ADR-C66 §3 记录的「潜伏态缺陷」是同一类边界情形。

但**流程上**仍按「有意的行为变更」处理：重生成锚点基线 + 逐项复查 diff + 提交信息列明。

### 5.3 变异 B 暴露的第二个假判据：「总数 ≥ N」

变异 B 首轮**只有 ② 失败，③ 通过**。原因：③ 初版写作

```dart
final cappedMentions = kCappedScopeNotes.keys
    .map((f) => _count(_readSrc(f), '诊断块'))
    .reduce((a, b) => a + b);
expect(cappedMentions, greaterThanOrEqualTo(kCappedScopeNotes.length));
```

即「三处文件里『诊断块』的**总**出现次数 ≥ 3」。但 `attitude` 文件**别处**也有
「诊断块」字样，删掉说明后仍有 1 次 → 总数恰好仍是 3 → 断言通过。

**修正**：改为**逐处断言**（每个文件各自 `>= 1`）。修正后变异 B 双杀（② + ③ 同时失败）。

> 已写入 **AGENTS.md V4.8**：「总数 ≥ N」与「存在性」同为假判据——**某处缺失可被
> 别处重复掩盖**。凡是「每处都应当满足」的不变量，必须**逐处**断言，不能先求和
> 再与处数比。这是 V4.7 的延伸：V4.7 说不能只判存在，V4.8 说也不能只判总数。
