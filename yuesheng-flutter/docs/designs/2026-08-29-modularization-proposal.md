# 模块化 / 模组化构想 — 记录与核查（2026-08-29）

> **状态**：记录待决，未立项、未执行。
> **来源**：舰长在 Phase 3 执行过程中提出，起因是观察到「改一处要动多处」。
> **本文性质**：如实记录构想、核查结果与**尚未解决的冲突**，不做结论性裁决。

## 1. 原始痛点（舰长澄清版，2026-08-29）

> 「在你做这些事情的时候，你很明显是撞到了这些耦合性的问题……各种各样的内容
> 杂乱在一起的这种情况，事实上导致了我们如今反复优化困难的局面，**改一个地方
> 要同时改多个地方**。我的想法是，可以的话，把大家都给模块化、模组化，相互之间
> 只通过对应的函数进行传递、沟通以及联动。通过这样的方式来降低我们对每一块
> 内容进行改动的难度，以及增加我们后续的可扩展性。」

**目标重述**（两条，按舰长原话的重要性排序）：

1. **降低改动难度** —— 改一块内容只动一个地方（当前痛点）
2. **增加可扩展性** —— 后续新增内容时影响范围可控、可预期

⚠️ 待确认：舰长提到的「面容文化 / 知识文化」疑为语音输入误差，具体所指未确认，
需在下次讨论时澄清（见 §5 待决问题 Q1）。

## 2. 实操证据：改一处到底动了几处

Phase 3 A 组两次裁剪的**实测改动集合**（非估算）：

| 改动 | 涉及文件 | 数量 |
|:--|:--|:--:|
| advanced-phases 阶段裁剪 | `skill_registry` + `skill_dispatcher` + `skills_advanced_outline_p1` + 新增 `p7` + 锚点测试 + 锚点基线 | 6 |
| coaching-rhythm 阶段裁剪 | `skill_registry` + `skills_beginner_p1` + 新增 `p9` + 新增专项测试 + 锚点测试 + 锚点基线 | 6 |

**拆解这 6 个改动文件的成因**：

| 成因 | 文件 | 是否可通过模块化消除 |
|:--|:--|:--|
| 钩子定义与分发（设计使然） | `skill_registry` / `skill_dispatcher` | 否，这是正交装配的固有成本 |
| **正文被 R-019 机械切分到多个 part 文件** | `skills_*_pN.dart` | **是**——这是主要可优化项 |
| 行为锚点护栏（我们主动加的） | 锚点测试 + 快照基线 | 否，这是安全网，不是负担 |

### 2.1 ⚠️ 诊断修正（2026-08-29 晚，本人上一版结论有误，以本节为准）

初版诊断写的是「R-019 的 300 行上限把 skill 正文**机械**切成了 p1~p9」。
**该结论错误**，全量核查后修正：

| 核查项 | 结果 |
|:--|:--|
| 30 个本体中正文内联单文件的 | **26 个** |
| 正文跨 2 个文件的 | 仅 **4 个**：advanced-phases / outline-diagnosis / coaching-rhythm / narrative-design |
| 这 4 个的切分依据 | **按语义章节**，非按行数。如 narrative-design：`p7`(§一~§三 世界观/角色构建) → `p8`(§四~§五 配角/交织) |
| 各分片文件行数 | 155 ~ 196 行，**均远低于 300 行上限**（全部 skill 文件中最大 281 行，无一超限） |

**修正后的结论**：

- 「改内容」实际上**只动 1 个文件**（单文件本体动它自己；跨文件本体按章节定位到其中一个）。
- 「改一处动多处」发生在**机制改动**时（如 Phase 3 加 `contentForPhase` 钩子：
  动了 registry + dispatcher + 注册文件 + 新增切片文件 + 锚点 + 快照，共 6 个）。
  这是**给 30 个本体统一加一项能力的固有成本**，不是内容组织缺陷，模块化也无法消除。
- 因此「R-019 机械切分」这一归因**不成立**，R-019 在此不构成压力。

### 2.3 ⚠️ 落点修正：痛点真身在 UI 层，不在 Skill 层（2026-08-29 深夜）

舰长澄清：痛点来自**过往改动中「一路修改」的执行观察**，并非本次对话的 skill 改动，
也非单次改动的文件数量。据此回溯历史提交的改动规模，结论修正：

| 提交 | 内容 | 文件数 |
|:--|:--|:--:|
| `d99956ca` | 新增 `subBody` 令牌（覆盖 13 处断层） | **25** |
| `b36ac753` | 新增 `microCaption` 令牌（覆盖 11 处） | **19** |
| `a7b6ec5f` | 新增 `noteCaption` 令牌（覆盖 12 处） | **16** |
| `e0dc8341` | 对齐 CI Gate0 格式化 | **65** |

「覆盖 N 处断层」的含义：**同一份样式字面量在代码里被复制了 N 份**。

**UI 层硬编码残留实测（`lib/widgets/`，2026-08-29）**：

| 项 | 残留 | 分布文件 |
|:--|--:|--:|
| `fontSize:` | **485 处** | 82 |
| `fontWeight:` | **318 处** | 76 |
| `Color(0x...)` | **0 处** | 颜色层已 100% 令牌化 ✅ |
| 已用 `AppTextStyles.` | 186 处 | 约 19% 收编率 |

字号取值高度集中，收敛性价比极高：

```
14(125)  13(93)  12(93)  15(63)  16(33)   ← 前 5 个值覆盖 84%（407/485）
11(29)   17(16)  18(10)  20(7)   10(5)
```

**修正后的结论**：

- 「一路修改」的真身是 **UI 样式字面量散落**，不是 skill 层耦合。
- 模块化 / 模组化的正确落点是 **继续 UI 令牌化**，而非 skill 归属重构。
- 该路径已被验证有效：颜色层 `Color(0x...)` 残留为 0，证明令牌化走得通。
- 基础设施就位：`AppTextStyles` 定义于 `lib/config/app_theme.dart:116`。
- 字号/字重层尚余约 81%，且前 5 个值覆盖 84% → 用 5~6 个令牌即可收编主体。

### 2.2 那么痛点还剩什么

剩余的真实痛点只有一条：**内容以 Dart 字符串常量形式存在**，改动需碰 `.dart`
文件（心理门槛、需跑编译/测试）。若目标是「改话术/知识不必碰代码」，唯一路径是
把内容移到非代码载体（如 Flutter assets 的 JSON）。此为真实权衡，需舰长决策：
收益是不必碰 dart 文件；成本是引入资源加载机制与相应的打包/加载处理。

## 3. 提示词诉求的核查（2026-08-28 实测）

舰长的构想经 AI 优化成一份通用清单后，三条核心诉求的核查结果：

| 诉求 | 核查方法 | 结果 |
|:--|:--|:--|
| 禁止隐式索引 / 位置下标 | grep Skill 体系全部文件 | **命中 0**。注册表与分层全是 Map 键控（`skillRegistry['id']`、`l2SkillMap[mode]`），无位置依赖 |
| 禁止全局状态 | 扫描非 const 顶层变量 | 38 处**全部是 Riverpod Provider**——不可变、生命周期托管、可 override、依赖经 `ref.watch` 显式声明。**这是解耦手段，不是耦合源** |
| 校验收敛到模块边界、内部信任输入 | 查规则库 | **R-028 已经是这条规则**。原文："只在边界防御，内部信任已控制的数据"，含边界/内部对照表与检查清单 |

**结论**：三条诉求本身正确，但**均不指向当前项目的实际缺陷**。缺的是「R-028 执行
审计」（检查 64 处防御性兜底是否都在边界），不是「新建模块化体系」。

## 4. ⚠️ 未解决的冲突：与正交模型

提示词要求「skill 与提示词按模块划分归属」。这与 Phase 2 建立的正交模型**直接冲突**：

- 正交模型：知识 × 动作 × 态度，共享本体只存一份，各组挂 `SkillRef` 语境指针
- Phase 2 的**全部工作**就是消灭「10 个本体挂 26 次」的跨组重复挂载

若按模块划分归属，同时遵守「模块间只能通过函数/回调通信、禁止访问内部实现」：

| 选项 | 后果 |
|:--|:--|
| 每个模块持一份本体副本 | **退回 Phase 2 之前**：10 个本体挂 26 次 |
| 跨模块引用共享本体 | 违反「禁止跨模块访问内部实现」 |

**无第三条路，除非放弃正交模型**（而正交模型是舰长亲自签的 ADR）。

## 6. 我的判断（可被推翻）

上一轮我给出「行为不变 + 现状无缺陷 = 零收益」的论证，**该论证有漏洞，已撤回**：
可维护性的收益不体现在行为变化上，而体现在**未来改动成本**上。舰长的诉求成立。

但 §2.1 的全量核查推翻了「症结在物理组织」这一判断：**物理组织已按语义章节对齐**，
26/30 本体单文件、4 个跨文件本体按章节切分且均远低于行数上限。**此处已修正。**

修正后仍坚持的只有一点：

- **全面重构 skill 归属体系成本远大于收益**，且与正交模型冲突（§4）。
  建议不做。

新增一条待验证判断：

- 「改一处动多处」在**内容改动**场景下并不存在（只动 1 个文件）；
  只在**机制改动**场景下出现（给 30 个本体统一加能力），属固有成本。
  若舰长观察到的痛点与我经历的不同，需要具体场景才能对症——见 §5 Q5。
