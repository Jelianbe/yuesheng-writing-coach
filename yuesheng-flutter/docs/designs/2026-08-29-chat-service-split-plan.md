# chat_service.dart 拆分方案 —— ❌ 已否决

> 本文件原为「沿 extension 边界 part 拆 15 文件」的实施方案。
> **该方案已否决**。保留此文件作为否决记录，避免后人重蹈。

---

## 原方案要点

沿现有 12 个 extension 边界，把 `chat_service.dart`（3004 行）拆为 15 个
`part of 'chat_service.dart'` 文件，每个 ≤300 行，宣称零行为变更。

## 否决理由

批次 **X-025-ARCH（2026-08-22）** 已就同类做法做过决策，并**全部回退**：

1. **禁止用 `part` / `extension` 机械搬运凑行数**——明确定性为**伪拆分**：
   将大文件暴力拆成 part 后经代码拼接，**未解决真正耦合问题**。
2. **实证代价**（这是最硬的证据）：`ChatService.sendMessage` 从类内实例方法
   迁至 extension 后，测试替身 `_FakeChatService` 的 `@override` 失效
   （**契约断裂**），调用真实 LLM API 触发 **9 例 `pumpAndSettle` 超时**。
   回退共 13 个 commit（X-025-ARCH-1 ~ 13），12 host / 41 parts 合并回单体。
3. **R-019 的硬上限是「函数 ≤50 行」**，不是「文件 ≤300 行」；
   服务层超限 **需走 ADR 决策**，不是直接动手拆。
4. 本方案（part 拆 15 文件）正是被明文禁止的那一类做法。

## 真正的靶子

不是「文件 3000 行」，而是 **12 个超 50 行的函数**
（最大 `_sendMessageCore` 293 行，5.9 倍）。详见体检报告 §P2-B。

注：这 12 个长函数里，多个 `_inject*` 其实是把当年 1392 行 `sendMessage`
巨方法拆散后的产物——函数确实变多了，但**单个函数仍然超长**，
属于同一类问题的另一种形态。

## 正确方向

- **真分解**：独立类 / 显式接口 / 依赖注入 / 职责级重构
- 或走 **ADR 决策**，将服务层超限登记为已知债务（这是 X-025-ARCH 认可的合规路径）
- A 类纯常量知识库的 part 拆分可保留（已豁免，边界与内容领域边界一致）
