# Flutter LLM Coach Validation

## Purpose

Verify that an LLM-driven coaching/teaching app actually performs its role
(问 → 写 → 诊 → 教 → 练 → 评) correctly, and — critically — that replies are
generated by the model, not pulled from a hardcoded phrase bank. Use this skill
whenever a user asks to "acceptance-test the teacher role", "verify the teaching
loop", "check the LLM behaves like a coach", or "add regression guards for the
prompt / knowledge base".

## When to use

- Acceptance-testing an AI "teacher"/"coach"/"reviewer" role in a Flutter app.
- Building regression protection before changing the system prompt or syndrome
  knowledge base.
- Proving (to a skeptical reviewer) that coaching text is model-generated and
  not templated.
- Validating the full handoff chain: diagnosis → teacher decision → training
  task → evaluation → feedback, with each data object persisted correctly.

## Core principle (non-negotiable)

**Replies are produced by the LLM at runtime. Acceptance must never assert on
natural-language text.** Assert only:

1. **Structured decisions** — detected syndrome IDs, primary syndrome ordering,
   teaching decision (encourage / guide / train / defer), and that any
   `training_task` is locked to the primary syndrome.
2. **Compliance constraints** — the model's `natural_language` contains no
   verdict/blacklist words and leaks no internal syndrome IDs (e.g. `P0\d{2}`).

Any test that compares AI prose against a "golden sentence" is wrong and must be
removed or relaxed to the checks above. Natural-language quality is a human
review concern, not an automated assertion.

To enforce this at the source, assert that the **injected system prompt**
forbids fixed-script templates / standard-answer substitution and requires the
model to organize its own phrasing. See `references/working_example.md` for the
anti-hardcode guard pattern.

## Workflow

### 1. Generate corpus via subagent simulation (not hardcoded fakes)

Do **not** hand-write a `FakeLlmClient` that returns canned strings. Instead,
spawn a subagent that reads the app's *real* system prompts (e.g.
`kTeacherSkillContent`, `kReviewerSkillContent`, `kEditorSkillContent`) and the
syndrome knowledge base, then produces the protocol blocks (`[YS_DIAGNOSIS]` /
`[YS_TEACHER]`) from problem texts. This tests prompt+model reasoning, not
brittle fixtures, and needs no API key.

### 2. Acceptance test against parsed ground truth (structured only)

For each corpus case, feed the protocol blocks through the app's *real* parsers
and validators (e.g. `parseDiagnosis`, `parseTeacherDecision`,
`checkTeacherConsistency`). Assert:
- every expected syndrome is detected (recall 100%);
- no unexpected syndrome is fabricated (false-positive rate 0);
- primary syndrome sorts first;
- consistency passes with zero violations;
- the teaching decision matches and `train`/`guide` carry a task locked to the
  primary syndrome.

Derive the expected set from the same fixture (single source of truth), so the
oracle stays self-consistent.

### 3. Data-flow test with real ChatService + in-memory DB

Drive the *real* `ChatService.sendMessage` against an in-memory drift database
(`AppDatabase.forTesting(NativeDatabase.memory())`) and a `FakeLlmClient`.
Replicate the app's multi-round LLM calls with a `SequenceFakeLlmClient` that
returns the diagnosis response on the first call and the teacher response on the
second (the app re-calls the LLM for the teaching decision). Assert each
handoff persists correctly: diagnosis committed, teacher suggestion locked to
primary, training history written on feedback, subphase reset.

### 4. Dual-mode live comparison harness

Build one test file with two groups sharing identical assertions:
- **Self-check group** — `FakeLlmClient` feeds corpus fixtures, exact match.
  Runs in CI without an API key. Proves the assertion logic itself is correct.
- **Live group** tagged `@Tags(['live'])` — real `LlmClient` against the
  production endpoint, looser match (e.g. tolerate ≤1 extra syndrome). Auto-skip
  with `markTestSkipped` when the API key env var is absent, so it never breaks
  the gate.

Mock `flutter_secure_storage` and `connectivity_plus` so the live client can be
constructed in tests. See `references/working_example.md`.

### 5. Anti-hardcode guard test

Read the *actually injected* system prompt string (the one passed to the LLM,
not a spec file that is never concatenated) and assert it contains directives
such as "不使用固定话术模板", "教原理而非标准答案", "AI 自主组织话术". This
catches the regression where anti-template instructions live only in an unused
spec file. Run it once "red" (before the directive exists) to prove the gap is
real, then "green" after adding it.

### 6. Snapshot regression (structured decisions only)

Freeze the structured decisions of all corpus cases to a JSON baseline. Support
`UPDATE_SNAPSHOTS=true` to regenerate; in default mode, recursively diff and
`fail` on any drift, printing `cases.<id>.<path>: before → after` so a human
decides intentional change vs regression. **Exclude natural-language text from
the snapshot** — only structured fields are frozen.

### 7. Four-gate discipline

Run `flutter analyze lib test` (must report **No issues found!**) and the full
`flutter test` suite (live group auto-skips without a key). Commit test
additions, fixtures, and ledger backfill as independent commits.

## Key non-obvious lessons

- The verdict-word blacklist is often the *full phrase* (e.g. "你可以试着" with
  the second-person 你), not the substring "可以试着". Verify against the real
  constant before "fixing" a fixture.
- A protocol JSON that fails to close its array (missing `]` after the
  `syndromes` list) parses to `null` and silently fails diagnosis. Fix by
  *adding* the bracket — do not delete a nearby one.
- The teacher suggestion table usually stores only structured fields
  (decision / target syndrome / task type / difficulty); the `natural_language`
  is display-only and is **not** a DB column. Do not assert repository-level
  natural-language — it was already validated pre-persistence by
  `checkTeacherConsistency`.
- A live client's key comes from an environment variable (e.g.
  `DEEPSEEK_API_KEY`); never commit it. A 401 from the endpoint proves network
  reachability even when the key is absent.
